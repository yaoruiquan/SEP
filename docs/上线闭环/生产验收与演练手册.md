# SEP 生产验收与演练手册

本文说明如何完成上线闭环中仍需真实环境证据的四类工作：支付宝回调与对账、备份恢复、线上 readiness、生产演练归档。

代码测试通过不等于生产验收完成。只有执行本手册并保存证据，才能在上线规格中标记通过。

## 1. 执行规则

按本顺序执行：

1. 本地或联调环境验证脚本和 SQL。
2. 支付宝沙箱验证完整支付链路。
3. 生产环境执行一次低金额、单订单验证。
4. 备份恢复必须在隔离数据库执行，禁止直接覆盖生产库。

私钥、数据库密码、JWT_SECRET、Cookie 和 Authorization 不写入文档或证据。生产支付使用专用测试账号和最低可接受金额，金额与退款由财务确认。

证据目录建议：

    docs/上线闭环/evidence/YYYY-MM-DD-环境-演练名称/

至少包含 README.md、commands.txt、health-ready.json、application-logs.txt、database-checks.txt、screenshots/ 和 rollback.md。README 记录环境、git SHA、迁移版本、开始/结束时间、执行人、复核人和 PASS/FAIL/BLOCKED 结论。

## 2. 支付回调、幂等与对账

### 2.1 接口

| 用途 | 接口 |
| --- | --- |
| 订阅支付 | POST /api/payment/alipay/create |
| 充值支付 | POST /api/payment/alipay/recharge/create |
| 异步通知 | POST /api/payment/alipay/notify |
| 订阅主动对账 | POST /api/payment/alipay/reconcile |
| 充值主动对账 | POST /api/payment/alipay/recharge/reconcile |

沙箱/生产回调地址必须是公网 HTTPS：

    https://域名/api/payment/alipay/notify

不能使用 localhost、内网 IP 或本机地址。支付宝应用 ID、应用私钥、支付宝公钥和网关必须配置在受控配置中。

### 2.2 正常支付验收

创建一个沙箱订单完成支付，核对：

- 支付宝页面支付成功，回调返回 success；
- 本地订单变为 PAID；
- 订单保存实际金额和购买周期；
- 订阅变为 ACTIVE，起止时间正确；
- 履约只执行一次；
- 钱包/算力、订单、订阅、通知可通过订单号关联；
- Web 订单、订阅和余额页面一致。

保存以下脱敏结果：

    SELECT id, "orderNo", status, "totalAmount",
           "purchaseAmountCNY", "purchasePeriodMonths",
           "payTradeNo", "paidAt"
    FROM orders WHERE "orderNo" = '<ORDER_NO>';

    SELECT id, status, "startDate", "endDate",
           "purchaseAmountCNY", "purchasePeriodMonths"
    FROM subscriptions WHERE "orderNo" = '<ORDER_NO>';

    SELECT "outTradeNo", "tradeNo", processed, "processedAt", "createdAt"
    FROM payment_notifies
    WHERE "outTradeNo" = '<ORDER_NO>'
    ORDER BY "createdAt" DESC;

### 2.3 重复通知幂等

使用同一笔交易的原始通知重放一次，不修改订单号、交易号和签名字段。

通过标准：

- 第二次返回 success，不返回 500；
- 不重复入账、创建订阅、发放权益；
- payment_notifies 不产生重复有效记录；
- 日志记录已处理并跳过。

保存两次回调响应、订单/钱包/订阅前后数量和日志。

### 2.4 履约失败重试

只在沙箱或联调环境通过可控测试故障制造第一次履约失败。通过标准：

1. 支付事实已保存，失败不会伪装成成功；
2. 通知保留 processed=false 或等价失败状态；
3. 日志包含订单号、失败原因和重试信息；
4. 依赖恢复后重放回调或执行补偿，最终只履约一次；
5. 失败期间产生含订单号的告警。

### 2.5 主动对账

使用订单所属用户的登录态调用：

    curl -fsS -X POST "$API_ORIGIN/api/payment/alipay/reconcile" \
      -H "Authorization: Bearer $ACCESS_TOKEN" \
      -H 'Content-Type: application/json' \
      -d '{"orderId":"<ORDER_ID>"}'

充值订单调用：

    curl -fsS -X POST "$API_ORIGIN/api/payment/alipay/recharge/reconcile" \
      -H "Authorization: Bearer $ACCESS_TOKEN" \
      -H 'Content-Type: application/json' \
      -d '{"orderNo":"<RECHARGE_ORDER_NO>"}'

支付宝已支付而本地未支付时，应补齐本地状态；支付宝未支付时不得改为已支付；非所属企业调用应被拒绝且不泄露订单；重复对账不得重复入账。

### 2.6 生产真实支付

发布前确认 readiness、迁移和回滚版本正常。创建专用测试订单，使用测试买家完成支付，观察回调、订单、订阅/充值、钱包和通知，保存支付宝订单页、后台订单页和日志，再按财务流程退款或冲销。财务和产品负责人共同确认后才算通过。

## 3. 备份与恢复

### 3.1 备份目标

PostgreSQL 使用 pg_dump custom 格式，上传目录保存 uploads.tar.gz，并生成 SHA256SUMS。Redis 不作为事实数据备份。当前目标 RPO 为 24 小时，数据库恢复目标 RTO 为 60 分钟。

### 3.2 执行生产备份

    cd /opt/sep/app
    SEP_ENV_FILE=/opt/sep/.env \
    SEP_BACKUP_DIR=/opt/sep/backups \
    SEP_UPLOADS_DIR=/opt/sep/uploads \
    ./deploy/production/backup-sep.sh

检查：

    ls -lh /opt/sep/backups/latest
    shasum -a 256 -c /opt/sep/backups/latest/SHA256SUMS

通过标准：存在 sep.dump、uploads.tar.gz（目录存在时）和 SHA256SUMS，校验通过，备份时间和代码版本已记录。

### 3.3 隔离库恢复

1. 创建隔离数据库和低权限账号。
2. 把 DATABASE_URL 指向隔离库。
3. 执行：

       CONFIRM_RESTORE=YES \
       SEP_ENV_FILE=/opt/sep/.env.restore-drill \
       SEP_BACKUP_DIR=/opt/sep/backups \
       ./deploy/production/restore-sep.sh /opt/sep/backups/TIMESTAMP

4. 单独解压上传文件到恢复目录，不能覆盖生产目录。
5. 启动临时后端，检查迁移和 readiness。
6. 执行登录、订阅、订单、对话、通知和文件读取 smoke。
7. 核对 users、enterprises、subscriptions、orders、payment_notifies、client_task_mirrors 数量和抽样记录。
8. 记录恢复开始/结束时间和 RTO。
9. 删除隔离库和临时容器，保留报告和校验结果。

通过标准：校验和通过、数据库和迁移正常、关键记录可读、文件可读、核心 smoke 通过，RTO 不超过 60 分钟。校验和失败或恢复失败时停止，不得继续覆盖任何生产数据。

## 4. Readiness 与发布后观察

发布前执行：

    API_ORIGIN=https://longdaoSEP.cn
    curl -fsS "$API_ORIGIN/api/health"
    curl -fsS "$API_ORIGIN/api/health/ready"

health 只表示进程存活；health/ready 必须 HTTP 200 且全部为 ok。生产检查项至少包括 postgres、redis、taskQueue、knowledgeQueue、sub2api、embedding。任何 failed 都不能发布或放量。embedding 失败时检查 Ollama 网络、模型加载和向量维度。

发布后至少观察 15 分钟，建议每分钟执行：

    for i in $(seq 1 15); do
      date -u
      curl -sS -o /tmp/sep-ready.json \
        -w ' readiness_http=%{http_code}\n' \
        "$API_ORIGIN/api/health/ready"
      cat /tmp/sep-ready.json
      sleep 60
    done

同时观察 5xx、P95/P99 延迟、Redis/队列、WebSocket、支付回调、上传下载，以及数据库、Embedding、sub2api 和迁移错误日志。

通过标准：15 分钟 readiness 始终 200，没有未解释 5xx，核心 smoke、支付回调、WebSocket、上传和对话均正常。失败则停止放量，按蓝绿回滚手册恢复上一版本。

## 6. 完成条件

以下全部满足才可以宣布上线闭环完成：

1. 正常回调、重复通知、履约失败重试、主动对账均有证据；
2. 备份校验和恢复演练有证据，RTO/RPO 达标；
3. 生产 readiness 连续观察通过；
4. 核心浏览器流程通过；
5. 失败订单、退款、人工补偿和回滚责任人明确；
6. 证据已脱敏归档并由责任人复核。

仅代码和本地测试通过时，应标记为“代码完成，生产验收未完成”，不能标记为可公开上线。
