# SEP 上线闭环规格

## 1. 目标

本规格定义 SEP 从“功能开发完成”到“可公开生产上线”的最低门槛。上线必须同时满足：

- 权限与多租户隔离可证明；
- 计费、订阅、退款和订单状态可追溯；
- 生产依赖、队列、实时连接和文件存储可用；
- 数据可备份、可恢复、可回滚；
- 核心用户流程有浏览器级回归证据。

能力适配器覆盖不完整（RPA / AI_APP / SKILL）不属于本阶段阻断项，按现有产品决策暂不纳入本规格。

## 2. 上线门禁

### P0：阻断上线

1. **平台权限**
   - 公告创建、修改、删除、发布、后台查询仅允许 `ADMIN`。
   - 钱包手动调账仅允许 `ADMIN`，请求必须经过 DTO 校验并记录审计。
   - 成本分析所有接口必须从当前用户服务端解析企业，不接受客户端传入企业作为授权依据。
   - 数字员工内部详情与公开市场详情分离；公开接口不得返回 `systemPrompt`、`modelId`、密钥或内部配置。

2. **订阅与计费**
   - 所有使用入口同时校验 `status=ACTIVE`、`endDate` 未到期和有效授权。
   - 多周期订单的退款金额必须基于实际订单金额/订阅快照，不能固定使用年费。
   - 支付回调、主动对账、重复通知必须幂等；履约失败必须允许重试并产生告警。

3. **生产配置**
   - `JWT_SECRET` 缺失、过短或使用默认值时，生产启动失败。
   - 所有模块从同一配置源读取 JWT 密钥，不得存在默认密钥回退。
   - 生产前端必须显式配置 `NEXT_PUBLIC_WS_URL`，使用 `wss://`。
   - CORS 变量统一为 `CORS_ORIGIN`，生产不得回退 localhost 白名单。
   - 普通和蓝绿生产 Compose 统一使用 `SEP_DB_USER` / `SEP_DB_PASSWORD` 低权限数据库账号。

### P1：上线保障

- `/health` 作为 liveness；readiness 已检查 PostgreSQL、Redis、任务队列、知识队列、生产 sub2api 和 Embedding。
- Redis/队列不可用时生产拒绝接收任务，不得静默降级为进程内执行；代码已返回 503。
- 审计日志已具备 3 次重试、90 天清理任务和失败告警日志。
- 已增加请求 ID、统一异常格式、敏感接口基础限流和 JSON/urlencoded 请求体上限。
- WebSocket 已校验 Origin，访问令牌已改为连接建立后的首条认证消息，不再出现在 URL 查询参数中。
- 完成 PostgreSQL、上传文件、员工包的备份恢复演练，记录 RPO/RTO。
- 完成支付宝沙箱/生产回调验收和异常订单人工处理流程。

### P2：规模化与运营

代码已落地（待提交）：

- WebSocket 员工状态与通知广播：状态轮询周期 1s→3s、状态缓存 TTL 2.5s、in-flight 请求合并、
  并发查询上限 `MAX_CONCURRENT_STATUS_QUERIES=8`，避免按在线用户高频查库。
- 用量 / 成本 / 审计查询：分页 `pageSize`/`limit` 上限、日期范围与 granularity 校验、
  审计导出独立 `AUDIT_EXPORT_MAX_ROWS=5000` 且超限显式失败，代码层杜绝无上限 LIMIT 拼 SQL。
- Docker：`backend/Dockerfile` 与 `web/Dockerfile` 统一固定基础镜像 `node:20.19.0-alpine3.21`，
  以 `node` 非 root 用户运行。
- CI 质量门禁：新增 `.github/workflows/quality.yml`，固定执行 backend typecheck/lint/unit、
  web tsc/unit、全量 build。
- 发布监控与回滚：新增蓝绿切换脚本、readiness/5xx/延迟/队列/Redis/WebSocket 观察窗、
  Caddy 蓝绿 upstream 切换与失败恢复，见 `docs/上线闭环/P2-发布监控与回滚.md`。

仍需线上演练（未取得生产证据前不标记 P2 全通过）：

- 灰度/批次发布验证：当前仍是整体蓝绿切换，非按百分比灰度。
- 压测与慢查询监控基线，确认分页与索引在实际数据量下生效。
- 发布后真实告警 / 自动回滚演练、依赖漏洞扫描结果件归档。

## 3. 本阶段实施顺序

### 阶段一：P0 安全与生产阻断

- 平台角色守卫补齐；
- 成本分析改为服务端企业上下文；
- 数字员工内部响应字段收敛；
- 订阅到期和多周期退款规则修正；
- JWT fail-fast；
- 生产 WebSocket/CORS/数据库变量统一。

### 阶段二：P1 可靠性与验收

- readiness 与依赖检查；（已完成 PostgreSQL、Redis、任务队列、知识队列、生产 sub2api、Embedding 检查）
- 生产队列 fail-fast；（已完成 Redis/队列不可用时生产返回 503）
- 审计可靠写入/清理；（已完成 3 次重试、90 天清理任务和失败告警日志）
- 安全基础设施；（已完成请求 ID、统一异常格式、敏感接口基础限流和请求体上限）
- 备份恢复与支付回调演练；
- Playwright 核心流程。

### 阶段三：P2 性能与运维

- 压测、索引和状态广播优化；
- 监控、告警、灰度和回滚；
- 文档、值班和故障处理手册。

## 4. 验收证据

每个门禁必须至少有一种可复核证据：

- 自动化测试：权限、越权、状态机、计费和幂等；
- 类型检查、构建和静态扫描输出；
- 生产配置检查结果；
- Playwright 流程录屏/报告；
- 备份恢复演练记录；
- 支付回调和队列故障演练记录。

## 5. 发布停止条件

出现以下任一情况，停止发布并回滚到上一版本：

- 任一跨企业读取或写入测试失败；
- 支付成功但订阅/钱包未履约且无法自动重试；
- readiness 不通过或队列不可用；
- 数据库迁移失败；
- WebSocket、HTTPS Cookie 或文件上传在生产域名下不可用；
- 核心 Playwright 流程出现未解释失败。
