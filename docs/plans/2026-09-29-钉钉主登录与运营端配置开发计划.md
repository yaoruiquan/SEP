# 钉钉主登录与运营端配置开发计划

> 文档日期：2026-09-29  
> 适用项目：SEP 硅基人才平台  
> 当前状态：官方接口已复核，P0 后端 Provider 与运营端配置已完成，Web 登录闭环待开发（2026-09-29）  
> 目标：以钉钉作为国内用户的主要第三方登录方式，并同步完善 Web 登录、邀请加入、账号绑定、运营端配置与安全审计能力。

---

## 1. 文档目的

本计划用于指导 SEP 从当前“邮箱密码 + 微信/QQ OAuth 预留实现”升级为“钉钉优先的企业级登录体系”。本次不是只增加一个登录按钮，而是完成以下闭环：

1. 后端接入钉钉 OAuth 登录和账号绑定。
2. Web 登录页、注册页、邀请加入页统一支持钉钉登录。
3. 运营端后台可以可视化配置、启用、检查钉钉登录，不再要求运营人员直接修改 `.env`。
4. 保留邮箱密码、邮箱验证、忘记密码等本地登录能力作为兜底和账号恢复手段。
5. 防止首次钉钉登录误建重复账号，明确账号绑定、冲突和邀请场景。
6. 为后续微信、QQ、支付宝等登录方式复用统一 Provider 架构。
7. 保持桌面客户端当前“邮箱密码/刷新令牌”协议稳定；钉钉优先作为 Web 端登录方式，客户端通过已有客户端认证接口兼容登录结果。

本计划同时作为实施基线。2026-09-29 已重新读取钉钉开放平台当前官方文档并据此修订接口契约；后续实现不得回退到历史 `/sns/getuserinfo_bycode`、旧版 `/sns/gettoken` 等接口。

---

## 2. 当前代码检查结论

### 2.1 已经具备的能力

当前认证中心基础设施已经比较完整，适合在现有抽象上增加钉钉 Provider，而不是重新做一套认证系统：

- 已有统一 OAuth 抽象：
  - `OAuthProviderAdapter`
  - `OAuthStartInput`
  - `OAuthCallbackInput`
  - `OAuthTokenSet`
  - `NormalizedOAuthProfile`
- 已有 OAuth state 事务服务：
  - `AuthOAuthTransaction`
  - state/nonce 只保存摘要
  - state 单次消费
  - 校验 provider、redirectUri、过期时间和重复回调
- 已有 OAuth 业务服务：
  - 启动授权
  - 回调处理
  - 登录
  - 邀请加入
  - 第三方身份绑定
  - 第三方身份解绑
- 已有第三方身份模型：
  - `AuthIdentity`
  - `[provider, providerAccountId]` 唯一
  - `[userId, provider]` 唯一
- 已有安全能力：
  - 登录事件审计
  - OAuth 回调 IP 限流
  - Refresh Token 轮换
  - Web httpOnly Refresh Cookie
  - 桌面端独立认证接口
- 已有前端回调页：
  - `web/src/app/(auth)/oauth/callback/page.tsx`
- 已有运营端系统设置中心：
  - `web/src/app/(platform)/admin/settings/SettingsCenter.tsx`
  - 支持按 category 分组
  - 支持敏感配置不回显
  - 支持数据库覆盖 `.env`
  - 支持测试按钮
- 已有微信、QQ Provider 和对应的 OAuth 流程测试，可作为钉钉实现样板。

### 2.2 当前缺口

1. OAuth Provider 注册表只有微信、QQ，需要增加 `dingtalk`。
2. 配置元数据只有微信、QQ字段，需要增加钉钉字段。
3. `SettingService` 的 OAuth 配置检查只支持微信、QQ，需要抽象为通用 Provider 检查。
4. 运营端设置页面只展示微信和 QQ，需要增加钉钉独立卡片并突出“主登录方式”。
5. 登录页只展示微信、QQ按钮，需要改为钉钉主按钮，并根据后端配置决定是否展示。
6. 邀请加入页当前只支持微信、QQ，需要增加钉钉加入。
7. 绑定第三方账号的前端类型目前只声明微信、QQ，需要扩展为 `dingtalk`。
8. 配置检查目前只检查字段是否存在和回调地址是否为 HTTPS，不能验证钉钉真实凭据是否可用。
9. 账号首次登录策略需要针对钉钉的“可能没有邮箱”场景明确处理。
10. 当前生产环境启动校验只覆盖微信、QQ，需要加入钉钉启用时的必填校验。
11. 客户端当前以邮箱密码登录为主，尚无桌面端浏览器 OAuth 登录协议；不能直接把 Web Cookie 回调复用给桌面客户端。

### 2.3 当前未发现必须新增数据库表的原因

钉钉登录可以直接复用：

- `AuthIdentity` 保存钉钉身份；
- `AuthOAuthTransaction` 保存一次性 state；
- `AuthEvent` 保存登录、绑定、解绑和失败事件；
- `AuthSession`、`AuthToken` 保存统一会话。

因此第一版不新增用户表、第三方账号表或 OAuth 状态表。只有在后续需要保存钉钉企业组织映射、部门同步、unionId/openId 历史快照时，才单独设计企业身份映射表，不能把组织数据混入通用登录身份表。

## 3. 官方接口复核结论（2026-09-29）

本节是 P0 开发的强约束，优先级高于本文此前的占位设计。核对来源为钉钉开放平台当前公开文档：

- 网页登录教程：`https://open.dingtalk.com/document/orgapp/tutorial-obtaining-user-personal-information`
- 获取用户 token：`https://open.dingtalk.com/document/isvapp/obtain-user-token`
- 获取用户通讯录个人信息：`https://open.dingtalk.com/document/isvapp/dingtalk-retrieve-user-information`

### 3.1 应用类型边界

官方当前网页登录教程以“企业内部应用 > 钉钉应用”为例，并明确说明企业内部应用不支持跨组织授权登录，只能由组织内成员登录；第三方企业应用流程类似，但需要按第三方企业应用的授权/开通流程处理。

因此本项目不把“企业内部应用”误写成面向所有互联网钉钉用户的通用登录：

- P0 Provider 实现通用 OAuth 2.0 协议，配置字段使用官方统一语义 `clientId/clientSecret`；
- 如果 SEP 当前只服务一个已认证企业，可使用企业内部应用；
- 如果 SEP 要服务多个企业，必须创建并发布第三方企业应用，并完成被服务企业授权开通；
- 第三方企业应用的 `clientId`/`clientSecret` 在官方 token 文档中对应 `SuiteKey`/`SuiteSecret`，企业内部应用对应 `AppKey`/`AppSecret`；代码不把二者写死成不同流程；
- P0 不承诺“任意个人钉钉账号均可登录”，登录范围由应用类型、发布状态、可见范围和企业授权决定。

### 3.2 当前授权端点和参数

构造链接方式使用：

```text
GET https://login.dingtalk.com/oauth2/auth
```

必填参数：

| 参数 | 值 | 说明 |
|---|---|---|
| `redirect_uri` | URL 编码后的服务端回调地址 | 必须与钉钉后台安全设置一致 |
| `response_type` | `code` | 固定值 |
| `client_id` | 应用的 Client ID | 企业内部应用后台通常显示 AppKey；第三方企业应用对应 SuiteKey |
| `scope` | 默认 `openid`，按已申请权限可配置为 `openid corpid` | 不擅自申请或拼接未审核权限 |
| `state` | 服务端生成的一次性随机值 | 现有 `OAuthStateService` 校验和单次消费 |
| `prompt` | `consent` | 官方网页登录示例使用的固定值 |

官方还提供 `window.DTFrameLogin` 内嵌二维码方式。P0 先使用服务端构造授权链接，不把钉钉前端 SDK 作为后端登录的必要依赖；后续如需要二维码 iframe，再单独接入官方 `DTFrameLogin`。

### 3.3 当前换取用户 token 接口

使用当前 OAuth 2.0 接口，不使用旧版 `/sns/*`：

```text
POST https://api.dingtalk.com/v1.0/oauth2/userAccessToken
Content-Type: application/json
```

请求体：

```json
{
  "clientId": "应用 Client ID",
  "clientSecret": "应用 Client Secret",
  "code": "OAuth 2.0 临时授权码",
  "grantType": "authorization_code"
}
```

返回至少使用 `accessToken`、`refreshToken`、`expireIn`；P0 只在内存中使用用户 token，不落库、不写日志、不返回浏览器。官方文档还说明 access token 有效期为 7200 秒，refresh token 有效期为 30 天；本次登录只需要授权码换 token，refresh token 暂不持久化。

### 3.4 当前用户信息接口和稳定身份键

使用：

```text
GET https://api.dingtalk.com/v1.0/contact/users/me
x-acs-dingtalk-access-token: <accessToken>
```

官方响应示例包含 `nick`、`avatarUrl`、`mobile`、`openId`、`unionId`、`email`、`stateCode`。P0 规范化规则：

- 优先使用 `unionId` 作为 `AuthIdentity.providerAccountId`；
- 若官方响应缺少 `unionId`，才回退使用 `openId`，并在代码注释中说明其应用作用域；
- `unionId/openId` 之外的字段不能作为第三方身份主键；
- `nick` → `name`，`avatarUrl` → `avatar`，`email` → `email`；
- 官方接口未给出邮箱已验证语义，`emailVerified` 使用 `null`；
- 教程说明调用该接口获取当前授权用户时使用路径参数 `me`，不是把临时 code 直接当作用户 ID。

### 3.5 P0 不实现的旧/旁路方案

以下内容不进入 P0：

- 旧版 `/sns/getuserinfo_bycode`、`/sns/gettoken` 等历史接口；
- 浏览器直接调用 `api.dingtalk.com` 换 token；
- 将 `mobile`、姓名、邮箱用于自动合并本地账号；
- 把企业 `corpId` 当作用户身份主键；
- 通过内嵌二维码参数猜测或自动补齐 `org_type/corpId`。只有产品确认需要专属组织二维码时，才在独立阶段增加这些参数。

**阶段一验收：已完成（2026-09-29）。** P0 实现按以上官方端点和字段开发。

## 4. 产品决策

### 4.1 登录方式优先级

| 优先级 | 登录方式 | 定位 | 第一版处理 |
|---|---|---|---|
| P0 | 钉钉登录 | 国内企业用户主登录方式 | 完整开发、启用、审计和运营配置 |
| P0 | 邮箱密码 | 账号恢复、管理员和非钉钉用户兜底 | 保留，不删除 |
| P1 | 邮箱验证/忘记密码 | 账号恢复和安全校验 | 保留并继续作为绑定前置手段 |
| P2 | 微信登录 | 国内个人用户补充方式 | 保留现有实现，暂不作为主入口 |
| P2 | QQ 登录 | 补充方式 | 保留现有实现，暂不作为主入口 |
| P3 | 桌面端钉钉登录 | 客户端快捷登录 | 不与 Web OAuth 混做，另行设计安全协议 |

### 4.2 钉钉登录的默认定位

钉钉登录默认用于：

- 企业用户访问 Web 平台；
- 企业邀请链接加入；
- 已登录用户绑定钉钉账号；
- 已绑定用户再次登录。

钉钉登录不默认替代：

- 平台运营管理员的本地密码登录；
- 桌面客户端的本地登录接口；
- 邮箱密码账号恢复；
- 企业成员的权限判断。

钉钉只证明“第三方身份”，登录成功后仍然由 SEP 自己决定：用户状态、平台角色、企业成员关系、邀请关系和权限。

### 4.3 首次登录账号策略

当前 `AuthIdentity` 与 `User.email` 设计要求用户最终有一个唯一邮箱。钉钉个人身份信息不一定提供可用邮箱，因此采用以下策略：

#### 场景 A：已有 SEP 账号并已绑定钉钉

直接登录已有用户。

#### 场景 B：已有 SEP 账号，但未绑定钉钉

第一版不根据姓名或手机号自动合并账号。应提示用户：

> 该钉钉账号尚未绑定 SEP 账号，请先使用邮箱密码登录，再在安全设置中绑定钉钉。

这样避免因姓名、手机号或第三方资料变化造成账号接管或错误合并。

#### 场景 C：通过企业邀请链接首次使用钉钉加入

允许创建或补全账号，但必须遵守邀请邮箱策略：

- 邀请记录有邮箱时，使用邀请邮箱作为 SEP 登录邮箱；
- 如果钉钉返回可验证邮箱，必须与邀请邮箱一致；
- 如果钉钉没有邮箱，允许使用邀请邮箱落地；
- 邀请只能消费一次，并在同一事务中创建用户、绑定身份和加入企业；
- 已存在本地账号时，不允许通过邀请 OAuth 静默合并，要求先登录后接受邀请。

#### 场景 D：普通入口首次钉钉登录

第一版建议采用“先绑定后登录”的保守策略，不自动生成不可恢复的虚拟邮箱账号。如果产品确认需要开放普通用户一键注册，必须增加：

1. 手机号或邮箱补全页面；
2. 验证码校验；
3. 用户协议和隐私政策确认；
4. 账号创建幂等处理；
5. 补全失败时可安全返回登录页。

## 5. 推荐技术方案

### 5.1 复用现有 OAuth Provider 架构

新增文件：

```text
backend/src/modules/auth/providers/dingtalk.provider.ts
backend/src/modules/auth/providers/dingtalk.provider.spec.ts
```

Provider 实现 `OAuthProviderAdapter`：

```ts
export class DingtalkOAuthProvider implements OAuthProviderAdapter {
  readonly id = 'dingtalk' as const;
  readonly displayName = '钉钉';
  readonly type = 'oauth2' as const;

  isConfigured(): boolean | Promise<boolean>;
  buildAuthorizationUrl(input: OAuthStartInput): Promise<string>;
  exchangeCode(input: OAuthCallbackInput): Promise<OAuthTokenSet>;
  fetchUserProfile(tokens: OAuthTokenSet): Promise<NormalizedOAuthProfile>;
}
```

实现契约已由第 3 节官方复核结论确定：授权使用 `https://login.dingtalk.com/oauth2/auth`，换 token 使用 `POST https://api.dingtalk.com/v1.0/oauth2/userAccessToken`，用户信息使用 `GET https://api.dingtalk.com/v1.0/contact/users/me`。禁止将 Client Secret 放到前端，禁止让浏览器直接调用钉钉换 token 接口。

### 5.2 统一回调地址

建议生产环境使用：

```text
https://longdaoSEP.cn/api/auth/oauth/dingtalk/callback
```

测试环境使用实际测试域名对应路径，例如：

```text
https://sep-dev.longdaoSEP.cn/api/auth/oauth/dingtalk/callback
```

注意：

- 服务端回调地址必须与系统设置中的 `DINGTALK_REDIRECT_URI` 一致；
- 钉钉开放平台配置的 redirect URI 必须与服务端完全一致；
- 不使用前端页面作为第三方平台回调地址；
- 不把 state、code 或 token 写入日志；
- 不使用 HTTP 生产回调地址；
- 如果钉钉平台配置的是回调域而不是完整 URI，按钉钉后台字段要求填写，不能把两种字段混为一谈。

### 5.3 授权流程

```text
Web 登录页
  │
  ├─ GET /api/auth/oauth/dingtalk/start
  │     └─ 服务端检查配置并创建 OAuth state
  │
  ├─ 浏览器跳转钉钉授权页
  │
  ├─ 用户授权/扫码
  │
  ├─ 钉钉回调
  │     GET /api/auth/oauth/dingtalk/callback?code=...&state=...
  │
  ├─ 服务端消费 state，校验 provider、redirectUri、过期和重放
  │
  ├─ 服务端用 AppSecret 换取访问凭证
  │
  ├─ 服务端获取钉钉用户身份并规范化为 NormalizedOAuthProfile
  │
  ├─ resolveIdentity / resolveInvitationIdentity
  │
  ├─ 使用统一 AuthService 签发 Web 会话
  │     └─ Refresh Token 写入 httpOnly cookie
  │
  └─ 重定向 /oauth/callback?provider=dingtalk&status=success
```

### 5.4 身份主键选择

Provider 必须使用钉钉官方稳定、适合长期绑定的用户标识作为 `providerAccountId`。优先级建议：

1. 官方明确稳定且跨应用一致的 union 级身份标识；
2. 如果当前应用只能获得应用内用户标识，则使用应用内稳定 userId/openId，并在代码注释中明确其作用域；
3. 不使用昵称、手机号、邮箱作为第三方身份主键；
4. 不把 access token、refresh token 保存到 `AuthIdentity`。

最终字段映射：

```text
provider           = dingtalk
providerAccountId = 钉钉官方稳定身份标识
providerEmail     = 钉钉返回的邮箱（没有则 null）
name              = 钉钉姓名或昵称
avatar            = 钉钉头像地址（无则 null）
emailVerified     = 只有钉钉明确提供验证语义时才为 true，否则 null
profile           = 脱敏后的原始资料快照
```

### 5.5 Provider 失败处理

钉钉返回错误、网络超时、用户取消或身份字段缺失时：

- 统一跳回 `/oauth/callback`；
- 返回通用错误提示，不把 AppSecret、上游响应正文或 token 放入 URL；
- 记录 `OAUTH_CALLBACK_FAILED`，metadata 只保存错误类别；
- 不创建 User，不创建 AuthIdentity，不签发会话；
- 允许用户重新发起授权。

## 6. 配置中心设计

### 6.1 新增系统配置键

建议在 `backend/src/shared/index.ts` 中增加：

```ts
DINGTALK_OAUTH_ENABLED: 'DINGTALK_OAUTH_ENABLED',
DINGTALK_CLIENT_ID: 'DINGTALK_CLIENT_ID',
DINGTALK_CLIENT_SECRET: 'DINGTALK_CLIENT_SECRET',
DINGTALK_REDIRECT_URI: 'DINGTALK_REDIRECT_URI',
DINGTALK_SCOPE: 'DINGTALK_SCOPE',
```

其中：

| 配置 | 类型 | 敏感 | 默认值 | 说明 |
|---|---|---:|---|---|
| `DINGTALK_OAUTH_ENABLED` | boolean | 否 | `false` | 是否允许用户发起钉钉登录 |
| `DINGTALK_CLIENT_ID` | string | 否 | 空 | 官方 token 接口的 clientId；企业内部应用通常对应 AppKey，第三方企业应用对应 SuiteKey |
| `DINGTALK_CLIENT_SECRET` | string | 是 | 空 | 官方 token 接口的 clientSecret；企业内部应用通常对应 AppSecret，第三方企业应用对应 SuiteSecret |
| `DINGTALK_REDIRECT_URI` | url | 否 | 空 | SEP 后端 OAuth 回调地址，生产必须 HTTPS |
| `DINGTALK_SCOPE` | string | 否 | `openid` | 仅允许配置已申请的 scope；需要企业标识时再使用 `openid corpid` |

如果钉钉当前应用类型还需要企业标识、租户标识或 agentId，必须在确认官方接口要求后再增加字段。不要提前将不确定的字段写入数据库或 UI。

### 6.2 配置存储规则

继续复用现有 `SystemSetting`：

- 数据库配置优先于环境变量；
- 环境变量作为部署兜底；
- `DINGTALK_CLIENT_SECRET` 使用现有密钥加密机制；
- 运营端不回显密钥；
- 敏感字段留空保存时保持原值；
- 明确执行“清除配置”时才删除数据库覆盖；
- 更新配置后立即对新请求生效，不要求重启，除非实现依赖启动时读取；
- 生产 `.env` 示例增加字段，但不写入真实密钥。

### 6.3 运营端页面改造

当前页面：

```text
运营端 → 系统设置 → 配置中心 → 认证与安全
```

改造为：

```text
认证与安全
├─ 邮件服务
├─ 主登录方式
│  └─ 钉钉登录
├─ 其他第三方登录
│  ├─ 微信登录
│  └─ QQ 登录
└─ 登录风控
```

钉钉卡片应显示：

- “主登录方式”标签；
- 当前启用状态；
- 配置来源：数据库覆盖 / 环境变量 / 未配置；
- AppKey；
- AppSecret；
- 回调地址；
- scope（如确实需要运营配置）；
- 配置完整性；
- 最后检查结果；
- “保存配置”；
- “检查配置”；
- “发起真实联调”或“打开登录页”快捷入口（只在安全可控时提供）。

### 6.4 配置检查分级

现有“检查配置”只能做静态检查。钉钉应分为两级：

#### 静态检查

检查：

- 已启用；
- AppKey 非空；
- AppSecret 非空；
- redirect URI 合法；
- 生产环境使用 HTTPS；
- scope 格式合法；
- redirect URI 与当前环境域名一致；
- 回调路径固定为 `/api/auth/oauth/dingtalk/callback`。

#### 真实连接检查

不在后台直接模拟完整用户授权，不要求运营人员提供用户授权码。真实联调通过登录页完成：

1. 运营端保存配置；
2. 静态检查通过；
3. 点击“进入登录联调”；
4. 新窗口打开钉钉授权；
5. 使用测试钉钉账号完成授权；
6. 返回结果页；
7. 后台通过审计事件显示成功或失败。

如果钉钉官方提供服务端应用凭据校验接口，可以增加“凭据连通性检查”；否则不能把“字段不为空”伪装成“真实凭据有效”。

### 6.5 运营端权限和审计

配置接口必须继续使用平台管理员权限：

- 查看配置：平台管理员；
- 修改配置：平台管理员；
- 检查配置：平台管理员；
- 密钥永不回显；
- 审计日志只记录配置键名和操作结果，不记录密钥值；
- 记录启用/禁用、AppKey 变更、回调地址变更、检查结果和操作者。

## 8. API 设计

### 8.1 复用接口

```http
GET /api/auth/oauth/dingtalk/start
```

响应：

```json
{
  "provider": "dingtalk",
  "authorizationUrl": "https://...",
  "expiresAt": "2026-09-29T12:00:00.000Z"
}
```

```http
GET /api/auth/oauth/dingtalk/callback?code=...&state=...
```

服务端处理后重定向：

```text
/oauth/callback?provider=dingtalk&status=success
```

或：

```text
/oauth/callback?provider=dingtalk&status=error&reason=...
```

```http
POST /api/auth/oauth/dingtalk/link/start
Authorization: Bearer <accessToken>
```

```http
GET /api/auth/oauth/identities
Authorization: Bearer <accessToken>
```

```http
DELETE /api/auth/oauth/identities/:id
Authorization: Bearer <accessToken>
```

### 8.2 运营端接口

继续复用：

```http
GET /api/settings
PUT /api/settings
POST /api/settings/oauth/dingtalk/test
```

如果现有 `POST /settings/oauth/:provider/test` 类型限制为微信/QQ，需要扩展为通用 Provider，并统一响应：

```json
{
  "provider": "dingtalk",
  "enabled": false,
  "configured": false,
  "valid": false,
  "checks": {
    "enabled": false,
    "appId": false,
    "secret": false,
    "redirectUri": false
  },
  "message": "尚未启用该登录方式"
}
```

字段名可以保留 `appId` 兼容现有前端，但 UI 标签应显示为“AppKey”或钉钉后台实际名称。若不同钉钉应用类型需要额外字段，应扩展 `checks` 而不是复用错误语义。

### 8.3 是否新增“登录方式状态接口”

建议增加一个不泄露敏感配置的公开接口：

```http
GET /api/auth/providers
```

返回：

```json
{
  "providers": [
    { "id": "password", "enabled": true },
    { "id": "email", "enabled": true },
    { "id": "dingtalk", "enabled": true },
    { "id": "wechat", "enabled": false },
    { "id": "qq", "enabled": false }
  ]
}
```

用途：

- 登录页决定是否展示第三方登录按钮；
- 不让普通用户读取 AppKey、AppSecret、回调地址；
- 避免通过尝试 `/start` 接口判断配置细节；
- 未来扩展支付宝、飞书等登录方式。

如果当前项目不希望新增公开接口，也可以由登录页直接尝试 `/start`，但必须将“未配置”处理为可理解的 UI 状态，不建议长期依赖异常驱动展示。

## 12. 安全要求

1. AppSecret 只存在服务端配置和加密后的数据库值中。
2. 前端只获得授权地址，不获得 AppSecret。
3. state、nonce 必须随机、短时有效、单次消费。
4. redirect URI 必须精确匹配，不接受任意回调地址。
5. OAuth 回调必须使用 HTTPS（本地开发除外）。
6. 不使用昵称、头像、手机号作为身份唯一键。
7. 不根据同名、同手机号或模糊邮箱自动合并账号。
8. 账号冲突时要求用户使用原登录方式完成绑定。
9. 不把第三方 access token、refresh token 写入数据库、日志或 URL。
10. 运营端配置变更必须鉴权并记录审计。
11. 公开状态接口只返回是否启用，不返回密钥、scope 细节或内部来源。
12. 第三方回调错误统一对外，不把钉钉原始错误信息直接展示给普通用户。
13. 禁用钉钉登录只影响新 OAuth 流程，不应误撤销已有本地会话。
14. 解绑前必须确认用户仍有密码或其他可用登录方式。

## 14. 回滚方案

如果钉钉登录出现问题：

1. 运营端关闭 `DINGTALK_OAUTH_ENABLED`；
2. 登录页隐藏钉钉按钮；
3. 保留邮箱密码、邮箱验证和已有其他登录方式；
4. 不删除 `AuthIdentity` 和 OAuth 事务数据；
5. 不撤销现有本地登录会话；
6. 查看 `OAUTH_CALLBACK_FAILED` 和配置审计事件；
7. 修复后重新执行测试环境联调。

代码回滚不应通过删除数据库迁移实现。第一版不新增数据库迁移，因此回滚主要是关闭配置和回退代码版本。

## 15. 完成定义

钉钉登录开发只有同时满足以下条件才算完成：

- 后端 Provider、OAuthService、配置读取和安全校验完成；
- 运营端可以完整配置和检查钉钉登录；
- Web 登录、绑定、解绑、邀请加入全部可用；
- 账号冲突和无邮箱场景有明确处理，不会静默创建不可恢复账号；
- 真实测试账号完成登录闭环；
- 生产配置可以通过，不把密钥提交到 Git；
- 现有邮箱密码、忘记密码、客户端登录协议没有回归；
- 相关单测、类型检查、构建和真实联调记录完成；
- 运营端可以在不 SSH 服务器的情况下关闭钉钉登录并回滚到邮箱登录。

“运营端能填 AppKey/AppSecret”不等于开发完成；“钉钉平台生成了应用”也不等于登录完成。必须经过真实授权回调、身份落库、会话签发、账号冲突、邀请和回滚验收。
