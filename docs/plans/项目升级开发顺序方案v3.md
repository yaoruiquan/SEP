# 项目升级开发顺序方案

> 依据：[硅基员工平台-方向调整设计方案-v3](../architecture/v3/硅基员工平台-方向调整设计方案-v3.md)
> 客户端交接：[SEP客户端-项目交接文档](../对接/SEP客户端-项目交接文档.md)
> 现状基线：16 个 Prisma 模型、9 个后端模块、Next.js 前端（个人视角）
> 排序原则：**按模块优先级**，不按时间；优先级 = 阻塞关系 × 交付价值
> 
> **实际进度**（2026-07-29）：✅ P0-P2 已完成，⚠️ P3 部分完成（ZIP 临时方案），❌ P4 客户端接入层待建

## 0. 一个必须先讲清的前提

> **本节已按 2026-07-29 的五项决策重写。** 早期版本假设「第一个员工 = 一包
> skills 文本，用户丢进自己 agent 目录即可用」，由此得出「模型调用也不经过平台、
> 计量无数据源」的结论。这个前提已被推翻。

已确认客户端形态：**`sep-client`（独立二次开发项目，Electron 主进程 +
进程内 `pi-coding-agent` SDK）**。它向 pi 注册的唯一 provider 是
`sep-gateway`，凭据是平台签发的**短期令牌**（存于 Electron `safeStorage`）。

**执行不在平台，但模型调用经过平台。**

| 设计方案中的能力 | 在本 MVP 中的实际状态 |
|---|---|
| §5.2 客户端模型网关 | ✅ **本期即启用** —— `sep-client` 所有模型调用经 SEP 网关转发 sub2api |
| token 计量 / 算力扣减 | ✅ **有真实数据源** —— 网关逐次调用记账 `ComputeTransaction` |
| 算力余额硬限制 | ✅ 可硬限制 —— 网关在转发前校验企业算力余额，不足即拒 |
| 授权凭据的强制力 | ✅ 有效 —— 令牌失效/实例停用/授权撤销后，客户端拿不到模型能力 |
| 已完成的计费设施 | ✅ **启用**（价格表、保底计费、汇率配置已验证可用，本期即接上）|

**因此本方案的核心结论**：MVP 的价值主线是
**「发现 → 订阅 → 授权 → 安装 → 受控运行」这条链路**。
平台不是分发站，而是**授权中心 + 模型网关 + 计量账本**；
真正的安全边界在网关的逐次校验上（令牌有效 → 实例 ACTIVE → 授权存在 →
算力充足 → 才转发）。

两个随之而来的简化（不是妥协，是决策 2「前期尽量简单且必要」的结果）：

- **平台不经手员工包字节流**：只登记 `packageRef`（`npm:` / `git:`），
  由客户端 `pi install` 直接向 npm registry / git 仓库拉取（决策 5）。
  包完整性交给 npm integrity / git commit hash，平台不做 ZIP + SHA-256。
- **客户端首次使用走账号登录**，不做激活码（决策 3）。

> ⚠️ 反过来的风险也要写明：**客户端必须联网**。网关不可用时员工不可用，
> 没有离线降级路径。这是「模型调用经过平台」的代价，已在设计方案 §11 列为验收点。

## P0 —— 企业组织基座

**为什么最高优先**：现有 `User.role` 只有三个全局角色
（`USER` / `CONTRIBUTOR` / `ADMIN`），无法表达"某企业的管理员"。
企业、部门、成员不存在，则「不同角色不同权限」无从落地，
企业管理台（P2）做不出来，实例归属（P1）也没有主体。

**零依赖，可立即开工。**

### P0.1 新增模型

| 模型 | 要点 |
|---|---|
| `Enterprise` | 数据与权限隔离边界；套餐与算力账户挂此层 |
| `Department` | 树形，`parentId` 自引用 |
| `EnterpriseMember` | `User` × `Enterprise` 关联，承载**企业内角色** + 所属部门 |
| `EmployeeGrant` | 实例授权给哪些部门 / 成员 |

企业内角色枚举：`ENTERPRISE_ADMIN` / `DEPT_MANAGER` / `MEMBER`。

> **关于 `EnterpriseMember`**：已确认 MVP 不做多企业切换，
> 但仍建议用关联表而非把 `enterpriseId` + `role` 塞进 `User`。
> MVP 阶段每人恰好一条记录，前端读第一条即可；将来放开多企业
> 只需删约束，不必做数据迁移与全量权限改写。
> 这是本方案唯一建议"多做一点"之处，成本近零。

### P0.2 主体改造（破坏性变更）

```
Subscription    userId  → enterpriseId    // 订阅主体是企业
ComputeAccount  userId  → enterpriseId    // 套餐含算力额度，挂企业
```

⚠️ 这两处是**现有表的主体变更**，涉及迁移。因当前只有演示数据，
建议直接重置演示数据而非写数据迁移脚本。

### P0.3 自助注册

三步内完成：注册账号时填公司名 → 自动创建企业 → 注册人即首个企业管理员。
不做资质审核、不做邀请码。

### P0.4 多租户隔离（安全基线，必做）

**这是本方案唯一被列为「安全基线」的项** —— 其他功能做错是 bug，
这里做错是**跨企业数据泄露**。现有 `JwtAuthGuard` 只回答"是否登录"，
完全没有企业维度，必须新增。

#### 隔离的两个层次

| 层次 | 作用 | 失效后果 |
|---|---|---|
| **企业范围隔离** | 请求只能触及自己企业的数据 | A 企业读到 B 企业的员工、成员、账单 |
| **企业内角色权限** | 按 `ENTERPRISE_ADMIN` / `DEPT_MANAGER` / `MEMBER` 判定操作 | 普通成员能改组织架构、能花钱订阅 |

两者是**独立**的：角色对了但范围没限，照样越界。必须都做。

#### 实现取向：默认隔离，而非自觉传参

**不要**依赖每个 service 自己记得加 `where: { enterpriseId }` ——
这种"自觉型"约定在几十个查询里迟早漏掉一处，而漏掉的那一处不会报错，
只会静默返回别家企业的数据。

建议做法（按可靠性排序）：

1. **请求上下文强制携带 `enterpriseId`**
   登录态解析出当前用户的 `EnterpriseMember` 记录，把 `enterpriseId`
   注入请求上下文，业务代码从上下文取，**不接受从客户端传入**
   （客户端可篡改，传什么就查什么等于没隔离）。

2. **Prisma 层收口**
   把带企业维度的查询集中到一处（如统一的 repository / 扩展方法），
   由这一层负责注入过滤条件。业务代码调不到"不带企业过滤"的入口。

3. **写操作二次校验归属**
   更新 / 删除某实例前，先确认该实例属于当前企业。
   仅靠"前端只展示本企业数据"是不够的 —— 攻击者会直接构造 ID 调接口
   （越权访问的典型手法：把 URL 里的 ID 改成别人的）。

#### 必须覆盖的对象

所有带 `enterpriseId` 的表，以及**通过关联间接归属企业**的表：

```
直接归属：Enterprise / Department / EnterpriseMember / EmployeeInstance
         / EmployeeGrant / Subscription / ComputeAccount
间接归属：ComputeTransaction（经 ComputeAccount）
         EmployeeInstance 的配置与下载记录
```

> ⚠️ **间接归属的表最容易漏**。`ComputeTransaction` 自身没有
> `enterpriseId` 字段，必须经 `accountId → ComputeAccount.enterpriseId`
> 校验，否则拿到别家的 `accountId` 就能查别家账单。

#### 不受企业隔离约束的部分

- **市场目录与详情**：公开数据，访客可见（决策 9）；
- **运营端（应用 B）**：本就需要跨企业视野，但**必须独立部署 + 独立鉴权**，
  且其接口不可暴露在应用 A 的入口上。

#### 验收（应作为硬性测试项）

1. A 企业用户带自己的合法 token，**直接构造 B 企业资源的 ID** 调接口 → 必须 404/403；
2. 列表接口在无任何显式过滤参数时，**默认只返回本企业数据**；
3. 普通成员调用管理员专属接口（如订阅、改组织架构）→ 必须 403；
4. `ComputeTransaction` 这类间接归属对象同样拒绝跨企业访问；
5. 客户端伪造请求体里的 `enterpriseId` **不生效**（以服务端上下文为准）。

> 建议把第 1、4、5 条写成自动化测试。这类漏洞的特点是
> **功能测试全绿也发现不了** —— 因为正常使用路径永远不会去构造别家的 ID。

### 验收
- 能自助注册企业，注册人为管理员；
- 能建部门树、加成员、设企业内角色；
- **多租户隔离全部通过 P0.4 的 5 条验收项**（含越权构造 ID 的测试）。

## P1 —— 员工模板与企业实例

**依赖 P0。** 现有 `DigitalEmployee` 一张表兼任"市场上卖的东西"和
"企业拿到的东西"，必须拆分（设计方案 §6.4）。

### P1.1 拆分

| 新对象 | 承载 |
|---|---|
| `EmployeeTemplate` | 市场侧：名称、介绍、能力清单、适用行业岗位、履历数据、开发者、审核状态 |
| `EmployeeTemplateVersion` | 版本号、变更说明、发布时间、对应员工包 |
| `EmployeeInstance` | 企业侧：所属企业、来源模板 + **锁定的版本**、企业内名称、部门、配置、状态 |

**关键约束**：
- ❌ 不能用 `@@unique([enterpriseId, templateId])` —— 同企业可多实例（决策 8）；
- ✅ 实例必须存 `templateVersion` —— 否则无法做提示式升级（决策 14）。

实例状态：`PENDING_ACTIVATION` / `ACTIVE` / `SUSPENDED` / `REVOKED`。

### P1.2 现有 Capability 体系的定位

`Capability` + `AgentConfig` / `RPAConfig` / `SkillConfig` / `AIAppConfig`
四张配置表**保留**，语义调整为「模板声明自己由哪些能力构成」，
用于市场详情页展示"我能做什么"。

`SkillConfig` 已有 `template` / `modelId` / `temperature` / `maxTokens`，
与"skills 包"形态天然契合，可作为第一个员工的元数据载体。

### P1.3 提示式升级

模板发新版 → 实例不自动跟进 → 企业管理台显示升级提示 → 企业主动确认。

升级 = 更换实例的 `templateVersion` + 重新下载对应员工包。
配置兼容性 MVP 不做自动迁移，提示里直接写"需重新检查配置"。

### 验收
- 市场模板与企业实例数据分离；
- 同企业能有两个来自同一模板的实例，各自独立配置；
- 模板发新版后，实例仍锁定旧版，管理台出现升级提示。

## P2 —— 应用 A：人才市场 + 企业管理台

**依赖 P1。** 两块功能域合并为一个前端应用（设计方案 §8.2），
因为它们服务同一个人的同一段连续动作。

### P2.1 市场域（公开，无需登录）

```
(market)/
├── page.tsx      员工目录：分类 / 搜索 / 筛选
└── [id]/         员工详情：五段式 + 订阅入口
```

详情页按总体方案 §7.1 五段式组织：
**我是谁 / 我能做什么 / 如何使用 / 做得怎么样 / 如何获得**。

- 访客可浏览目录与详情；
- 订阅需登录，未登录点订阅 → 引导登录；
- 现有 `(user)/marketplace` 可改造复用。

### P2.2 企业域（需登录）

```
(enterprise)/
├── org/          组织架构：部门树 + 成员
├── employees/    已订阅实例：配置 / 下载 / 激活码 / 停用 / 升级提示
├── grants/       授权管理 + 申请审批
└── compute/      算力用量（⚠️ 本期无数据源，见 §0）
```

**三角色可见性**（同一套导航的不同可见项，非不同应用）：

| | 市场 | 实例 | 组织架构 | 授权审批 |
|---|---|---|---|---|
| 企业管理员 | 浏览 + **订阅** | 全部可配置 | 可编辑 | 可审批 |
| 部门负责人 | 浏览 + **申请** | 本部门 | 只读 | 本部门 |
| 普通成员 | 浏览 + **申请** | 仅被授权的 | 不可见 | 不可见 |

> 「订阅」要花企业的钱，只有管理员能做；其他角色只能**申请**。
> 不做这个区分，普通成员点订阅再报 403 是可预见的体验问题。

**`compute/` 页面的处理**：已确认**做一个空架子**，前端能看到即可。

本期无计量数据源（§0），所以：
- 页面结构、卡片、表格布局照常搭好，接口照常接；
- 数据为空时**显式说明原因**，例如「当前员工在本地运行，
  平台暂不计量算力」，而不是干放一个 `0` ——
  区别在于用户能否判断"这是没数据"还是"这是坏了"；
- 将来员工形态演进到经平台调模型（§0），页面无需重做，直接有数。

现有 `(user)/usage` 页面（余额 / 累计消费 / token 汇总 / 交易明细）
可直接改造为企业维度复用，不必新写。

### P2.3 前端实现方案（已确认）

#### 单应用 + 路由分组

**一个 Next.js 应用**，不拆仓库。设计方案 §8.2 提出的"应用 A / 应用 B
独立部署"是出于安全边界考虑，但落地上用**路由分组 + 后端鉴权**即可达到
同等效果；运营端接口的访问控制在后端把住，前端分组负责布局与导航隔离。
真需要物理隔离（明确合规要求）再拆，届时按分组切分成本也低。

```
web/src/app/
├── (market)/          公开，无需登录
│   ├── page.tsx           员工目录：分类 / 搜索 / 筛选
│   └── [id]/page.tsx      员工详情：五段式 + 订阅入口
│
├── (enterprise)/      需登录 + 企业内角色鉴权
│   ├── layout.tsx         侧边栏按角色渲染可见项
│   ├── org/               组织架构（部门树 + 成员）
│   ├── employees/         已订阅实例（配置/下载/升级提示）
│   ├── grants/            授权管理 + 申请审批
│   └── compute/           算力用量（空架子，见 P2.2）
│
├── (platform)/        需登录 + 平台运营角色
│   ├── templates/         员工模板与版本
│   ├── review/            上架审核
│   ├── enterprises/       企业列表与套餐
│   ├── models/            ← 现有 (admin)/admin/models 迁入
│   └── settings/          ← 现有 (admin)/admin/settings 迁入
│
└── (auth)/            登录 / 注册（含企业自助注册）
```

#### 决策 1：同一套页面 + 按角色控制可见性

三种企业内角色**共用同一套页面**，通过角色控制导航可见项、
数据范围与操作按钮，**不为每个角色分别写页面**。

理由：三者看的是同一批数据，差别只在范围和能否修改；
分开写会产生三份高度相似的代码，后续每改一处要改三遍。

> ⚠️ **前端的角色判断只是体验优化，不是安全边界。**
> 隐藏按钮不等于接口调不动 —— 真正的拦截必须在后端（P0.4）。
> 前端这层的价值是"不让用户点到会失败的东西"，不是"防住攻击者"。

#### 决策 2：企业上下文从登录态获取

MVP 不做多企业切换（决策 10），因此：

- 登录接口返回的用户信息中携带 `enterprise`（id、名称）
  与 `roleInEnterprise`；
- 前端存入 Zustand，各页面直接读取；
- **不做企业切换器**，**不在 URL 中携带企业 ID**
  （企业归属由服务端上下文决定，见 P0.4）。

#### 决策 3：市场订阅按钮三态

访客可浏览、不可订阅（决策 9）。按钮**始终显示**，
点击时按状态分流 —— 转化路径最短：

| 状态 | 按钮文案 | 点击行为 |
|---|---|---|
| 未登录 | 订阅 | 弹登录框，登录后回到当前详情页 |
| 已登录 · 企业管理员 | 订阅 | 直接进入订阅流程 |
| 已登录 · 部门负责人 / 普通成员 | **申请** | 提交申请给管理员审批 |

> 第三态很容易被忽略：只有管理员能花企业的钱，
> 其他角色看到心动的员工只能发起申请。若不做这个区分，
> 普通成员点了订阅再报 403 是可预见的体验问题。

## P3 —— 员工包登记 + 客户端网关 + 应用 B（运营端）

> **当前实现状态（2026-07-29）**
>
> | 子项 | 状态 | 说明 |
> |---|---|---|
> | P3.1 员工包登记 | ⚠️ ZIP 临时方案 | `EmployeePackage` 表已建，存储 ZIP 文件 + SHA-256，**缺 `packageRef` 字段** |
> | P3.2 安装与获取 | ❌ 未建 | 下载接口有 ZIP 通道；`packageRef` 方案待 P4.5 补 |
> | P3.3 应用 B 运营端 | ❌ 未建 | 现有 `(platform)` 路由是临时复用，未独立部署 |
> | P3.4 客户端模型网关 | ❌ 未建 | **整个 MVP 的核心缺口**，纳入 P4.3 |
>
> **ZIP 临时方案的取向**：P3 阶段先用 ZIP 打通"运营上传 → 成员下载"这条链路，
> 验证流程可行。后续 P4.5 加 `packageRef` 字段，两种方式并存——
> 第一个员工没有 npm 包时 ZIP 是唯一可行通道，不要急着删。

**依赖 P1。** 这是"可安装、可受控运行"的落地，也是端到端验收的最后一环。

### P3.1 员工包登记（`EmployeePackage`）

平台**不经手包字节流**（决策 5：复用 pi 自己的 package 机制）。
数据库只登记一个引用：

```ts
packageRef: { type: "npm" | "git", spec: "@sep/employee-xxx@1.0.0" }
```

- 所属模板版本、`packageRef`、发布状态；
- 完整性由 **npm integrity / git commit hash** 保证 —— 平台不做
  ZIP 上传、不算 SHA-256、不自建制品仓库；
- 运营端只做"登记 + 改指向 + 发布/下架"，不做文件管理。

> 私有员工包放企业私有 npm registry 或私有 git 仓库；
> 拉取凭据属于客户端与包源之间的事，不经平台。

### P3.2 安装与获取

- 客户端（`sep-client`）用 `pi install <packageRef>` 直接向
  npm registry / git 仓库拉取，**不经平台下载接口**；
- 因此**不需要带时效的下载令牌**（原设计中的防转发机制随之取消）；
- 平台侧只提供 `GET /employees/:instanceId/package`
  返回该实例可安装的 `packageRef` —— 调用需登录 + 企业已订阅 + 授权存在；
- 客户端首次使用走**账号登录**（决策 3），不做激活码。

> **约束力落在网关，不在分发上。** 包本身拿到了也跑不起来：模型调用必须
> 经 SEP 网关，网关逐次校验令牌/实例/授权/算力（见 P3.4）。
> 这是形态从"发一包 skills"改为"客户端 + 网关"后最重要的变化。

### P3.3 应用 B（运营端，独立部署）

```
templates/     员工模板 + 版本 + packageRef 登记
review/        上架审核
enterprises/   企业列表与套餐
compute/       算力账本（网关计量流水，见 P3.4）
models/        模型白名单（现有 (admin)/admin/models 迁入）
settings/      系统设置（现有 (admin)/admin/settings 迁入）
```

**独立部署的理由是安全边界**，不是代码复用：运营端可见全平台数据，
不应与面向客户的代码同包同入口。两应用共享 UI 组件库。

### P3.4 客户端模型网关 + 计量（本期启用，设计方案 §5.2）

`sep-client` 向 pi 注册的唯一 provider 是 `sep-gateway`，
所以**这一层是真正的安全边界与计量入口**，不是可选项。

后端需要的最小实现：

1. **短期令牌签发** —— claims 携带 `enterpriseId` / `instanceId` /
   `memberId`；TTL 读 `SystemSetting`（建议 15 分钟）。
   `enterpriseId` 只能来自服务端请求上下文，**不接受客户端传入**。
2. **逐次校验链** —— 令牌有效 → 实例 `ACTIVE` → `EmployeeGrant` 存在 →
   企业算力余额充足 → 才转发 sub2api；任一环不过直接拒绝。
3. **记账** —— 转发完成后按 P5 已验证的价格表 / 保底计费写
   `ComputeTransaction`，扣减企业算力余额。
4. **客户端侧** —— 令牌存 Electron `safeStorage`（主进程），
   **绝不写入 pi 的明文 auth 文件、绝不进渲染进程**；
   provider 的 `resolve()` 每次调用都重新取，天然支持轮换。

> 已完成的计费设施（价格表 / 保底计费 / 汇率配置）在这里接上，
> 不需要重写 —— 缺的只是网关这个数据源。

激活码作为**可选备用通道**保留：仅在企业 IT 批量部署、不便让每个成员
手动登录时使用（决策 3 定的主路径是账号登录）。

### 验收
- 运营能登记 `packageRef` 并发布版本，改指向后客户端能装到新版本；
- 企业管理员在 `sep-client` 登录后，能对已授权员工执行 `pi install` 成功；
- 未订阅 / 未授权的企业成员拿不到 `packageRef`，即使拿到包也**无法调用模型**
  （网关拒绝，返回可读原因）；
- 撤销授权 / 停用实例后，正在运行的会话下一次模型调用即失败；
- 企业算力余额耗尽时网关拒绝转发，运营端 `compute/` 能看到对应流水；
- 完整端到端：登录 → 看到员工 → 安装 → 对话 → 网关计量出账。

## P4 —— 客户端接入层（SEP 侧）

**依赖 P0-P2（已完成）。** 这一层是 [sep-client](../对接/SEP客户端-项目交接文档.md)
的**硬阻塞依赖** —— 交接文档 §9 列出的 4 个接口，SEP 现在一个都没有，
客户端拿不到它们就只能拿假网关做 PoC。

### 为什么单列一层，而不是塞进 P3

P3.4 原本已经写了客户端网关，但交接文档定稿后暴露出**远不止网关一件事**：
登录方式、令牌形态、实例清单形状都与现有 web 端不同。这些接口彼此耦合
（网关依赖实例令牌，实例令牌依赖客户端登录），拆开做要来回改，故单列。

### P4.0 现状核查：哪些能复用，哪些必须新建

**可直接复用（不动）**：

| SEP 现有资产 | 客户端怎么用 |
|---|---|
| `EmployeeGrant` 两条授权路径查询 | `/client/instances` 的过滤逻辑照搬 `GrantService.myEmployees` |
| `EmployeeInstance` 状态机 + `templateVersion` | 网关校验 `status=ACTIVE`；`lockedVersion` 用于提示式升级 |
| 多租户隔离基线（P0.4 五条验收）| 交接文档 §6.1 直接引用，且强调桌面客户端使其重要性升一档 |
| 计费设施（价格表 / 保底计费 / 汇率配置）| 网关记账直接调 `calculateCost()`，不重写 |
| `SystemSetting` 机制 | 令牌 TTL 用这套配（交接文档 §5.1 明确"不要新建机制"）|
| `PlatformModel` 白名单 | 下发给客户端的 `allowedModels` |

**必须新建（客户端要的和 web 端不是一回事）**：

| 缺口 | 为什么不能复用现有 |
|---|---|
| `POST /client/login` | 现有 `/auth/login` 把 refresh token 塞 httpOnly cookie；Electron 主进程用 `safeStorage` 存，**需要在响应体里拿到 refresh token** |
| 实例级令牌 | 现有 access token claims 是 `{ sub, email, role }`，**没有 `enterpriseId` / `instanceId` / `memberId`** —— 缺了就无法按实例拆分用量 |
| `GET /client/instances` | 现有 `/enterprise/my-employees` 形状不够：缺 `packageRef` / `allowedTools` / `allowedModels` / `config`。**不改现有接口**（web 端在用），另开客户端专用 |
| `Device` 模型 | 完全没有。交接文档 §5.2：激活码砍了但**设备指纹与可吊销记录要保留**，那是吊销能力的基础 |
| `/gateway/v1/chat/completions` | 完全没有。`conversation-stream.service.ts` 是会话级的（维护上下文、工具循环、SSE），网关是**无状态薄代理**，共用不了 |

### P4.1 设备模型 + 客户端登录

```
model Device {
  id           String   @id @default(cuid())
  userId       String
  fingerprint  String   // 客户端生成的设备指纹
  platform     String   // darwin / win32 / linux
  clientVersion String?
  lastSeenAt   DateTime
  revokedAt    DateTime?  // 运营/用户吊销
  @@unique([userId, fingerprint])
}
```

`POST /client/login`：

- 入参 `{ email, password, fingerprint, platform, clientVersion }`；
- **refresh token 放响应体**，不设 cookie —— 这是与 web 登录的关键差异；
- 同时 upsert `Device` 记录（同一用户同一指纹只一条）；
- 已吊销设备（`revokedAt` 非空）拒绝登录并返回可读原因。

> ⚠️ **不要改现有 `/auth/login`**。两套凭据传输方式（cookie vs 响应体）
> 混在一个端点里，将来任何一侧的调整都会波及另一侧。

### P4.2 实例级令牌签发

`POST /client/token`：

- 入参 `{ refreshToken, instanceId }`；
- 校验链：refresh 有效 → 设备未吊销 → 实例属于该用户企业 →
  `EmployeeGrant` 存在且未过期 → 实例 `status=ACTIVE`；
- 签发 claims：

```ts
{
  sub: userId,
  enterpriseId,      // ← 只来自服务端上下文，不接受客户端传入
  instanceId,        // ← 缺它就无法按实例维度拆分用量
  memberId,
  type: 'client-instance',
}
```

- TTL 读 `SystemSetting`，新增 key `CLIENT_TOKEN_TTL_MINUTES`，建议初值 15。

**为什么必须按实例签发**（交接文档 §5.1）：否则只知道这家企业花了多少算力，
不知道是哪个部门的哪个员工花的，v3 §8.1 ③ 要求的用量拆分做不到。

需要新增一个 `ClientInstanceGuard`（或 passport strategy），
与现有 `JwtAuthGuard` 分开 —— 后者认的是 web access token，
两者 claims 结构与校验规则都不同。

### P4.3 模型网关（核心）

`POST /gateway/v1/chat/completions` —— OpenAI 兼容，是**计量的唯一入口**。

**逐次校验链**（任一环不过直接拒绝，返回可读原因）：

```
① 令牌有效且 type=client-instance
② 实例仍 status=ACTIVE          ← 停用后下一次调用即失败
③ EmployeeGrant 仍存在且未过期   ← 撤销授权后下一次调用即失败
④ 模型在 allowedModels 白名单内
⑤ 企业算力余额充足              ← 余额耗尽即拒绝
────────────────────────────────
→ 转发 sub2api → 记 ComputeTransaction（含 instanceId）
```

实现要点：

- **薄代理，不用 Vercel AI SDK**。网关只需转发 OpenAI 格式请求、
  读回 `usage` 记账。上 AI SDK 反而要处理它的流式抽象，是负担。
- 流式（`stream: true`）要透传 SSE，且在流结束时才能拿到完整 usage —— 
  记账发生在流结束后，不是请求开始时。
- 记账复用 `calculateCost(modelId, inputTokens, outputTokens, rate)`，
  并在 `metadata` 里带 `instanceId` / `memberId`，供运营端按实例查账。
- **余额检查的时序问题**：请求前检查余额，但实际消耗要等响应后才知道。
  MVP 取向：前置检查"余额 > 0"即放行，事后扣减可能造成小额透支。
  硬性不透支需要预扣＋结算，本期不做，但要在代码注释里写明这个取舍。

### P4.4 客户端实例清单

`GET /client/instances`（用实例令牌或 refresh token 调，返回该成员全部可用实例）：

```ts
[{
  instanceId, displayName,
  templateId, lockedVersion,     // ← templateVersion，用于提示式升级
  packageRef,                    // ← P4.5 加的字段
  config,                        // 企业侧配置
  allowedTools,                  // 工具白名单（交接文档 §6.2 措施②）
  allowedModels,                 // 模型白名单
  status,
}]
```

**客户端不传任何过滤参数**。服务端从令牌取 `memberId` → 反查企业 →
反查 `EmployeeGrant`（授权给我或我所在部门）→ 过滤 `status=ACTIVE`。
过滤逻辑与 `GrantService.myEmployees` 一致，可提取共用。

`allowedTools` / `allowedModels` 目前**没有数据来源** —— 需要决定放在哪：
挂 `EmployeeInstance.config`，还是挂模板侧、由实例继承。建议前者（企业可调），
但要在 P4.4 开工前定。

### P4.5 `EmployeePackage` 加 `packageRef`

```prisma
/// pi package 引用。与 ZIP 字段并存：
/// - packageRef 非空 → 客户端走 pi install（决策 5 的目标形态）
/// - packageRef 为空 → 回落到 ZIP 下载（第一个员工没有 npm 包时的通道）
packageRef Json?   // { type: "npm" | "git", spec: "@sep/employee-x@1.2.0" }
```

现有 ZIP 字段（`storagePath` / `sha256` / `fileSizeBytes`）**保留不动**。
两种分发方式并存的理由见 P3 状态说明。

运营端发版界面相应加一个"npm/git 引用"输入框，与"上传 ZIP"二选一。

### P4.6 心跳（可后置到 P-B）

`POST /client/heartbeat`：带实例令牌，更新 `Device.lastSeenAt`，
返回吊销/升级指令。客户端连续失败超阈值进入锁定态。

交接文档 §5.4 明确：**不静默降级**，锁定时要显式提示原因。

```

  ↓
P4.1（Device + /client/login）
  ↓
P4.2（实例令牌 + Guard）
  ↓
P4.3（网关）← 核心，依赖 P4.2 的令牌
  ↓

  ↓
P4.6（心跳，P-B）
```

**建议 P4.1 + P4.2 一起做** —— 登录与令牌耦合紧，分开做要来回改。

### 验收

对齐交接文档 §9 的硬阻塞项：

1. 客户端能用账号密码登录，refresh token 从响应体拿到（不依赖 cookie）；
2. 能按实例换取短期令牌，claims 含 `enterpriseId` / `instanceId` / `memberId`；
3. 能拉到"我被授权的实例"清单，含 `packageRef` 与两个白名单；
4. 网关能转发模型调用并记账，`ComputeTransaction.metadata` 可追溯到实例；
5. **停用实例 → 下一次模型调用即失败**（不等令牌过期）；
6. **撤销授权 → 下一次模型调用即失败**；
7. 算力余额耗尽 → 网关拒绝转发，返回可读原因；
8. 跨企业构造 `instanceId` 换令牌 → 404/403（P0.4 第 1 条延伸到客户端接口）；
9. 客户端伪造请求体里的 `enterpriseId` 不生效（P0.4 第 5 条）；
10. 已吊销设备无法登录，也无法用旧 refresh token 换新令牌。

> 第 5、6、8、9、10 条建议写成自动化测试。它们的共同特点是
> **正常使用路径永远不会触发** —— 只有攻击者或异常状态才会走到。
