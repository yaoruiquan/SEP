### 2.0 产品内核（刘凌原话，纪要2 §6 开头）

> 企业的技能沉淀在组织，使用这个技能在个人；但个人用这个技能产生的知识又会回归到组织
> —— 这就形成了一个循环。

这句话决定了三层结构，也决定了**改动只能向上「被采纳」、不能自动上行**：

```
PLATFORM   平台原版      ← 企业怎么改都不影响它
   ↑ 采纳与否由平台自己决定（数据本身都在平台）
ENTERPRISE 企业版        ← 管理员采纳个人改动后生成，只在本企业生效
   ↑ 逐条采纳 / 一键采纳多人改动
PERSONAL   员工个人副本   ← 改完立刻对他本人生效，不提审
```

**现在代码只有上面两层**，而循环恰恰从缺失的 PERSONAL 层开始。

### 2.2 任务清单

**T2.1 DB：`SkillVersionScope` 增 `PERSONAL`，`SkillVersion` 增 `ownerId`**

- `ownerId String?` → `User`，`onDelete: Cascade`；`scope=PERSONAL` 时必填。
  不复用 `createdById`——那是「谁建的」（管理员可能替人建），这个是「属于谁、对谁生效」，
  混用会让「加载某成员的生效版本」不可靠。
- 加索引 `[ownerId, capabilityId]`：`resolveEffectiveVersion` 的热路径。
- `SkillVersionStatus` 增 `PERSONAL_ACTIVE`：个人副本没有草稿/待审之分，改完即生效。

**T2.2 DB：新表 `SkillVersionAdoption`**

一键采纳意味着一个企业版本同时来自多人，`SkillVersion.sourceVersionId`（单值）装不下。
字段：`targetVersionId`（采纳产生的企业版）、`sourceVersionId`（被采纳的个人版）、
`adoptedById`、`adoptedAt`、`batchId`（一次一键采纳的批次号，用于「这次采纳了 5 个人的改动」）。
唯一约束 `[targetVersionId, sourceVersionId]`。

**T2.3 `resolveEffectiveVersion` 加最上面一层**

```
PERSONAL（该成员自己的副本）→ 企业选版 → 员工模板默认版 → 平台最新
```
`CapabilityExecutionContext` 相应增 `userId`（现在只有 `subscriptionId`）。
这是「使用发生在个人」的落点：员工改完副本，下一句对话就该用上。

└──────────────────────────────────────────────────────────┘

▼ 市场调研员 · 3 个技能                                        ← 中文名做分组头
   竞品分析          企业版 1.2 ●生效   5 人在用 · 42 次   2 条待采纳  →

四个设计决策及理由：

#### 一处实现被推翻：一键采纳不能「取最后一条」

第一版 `adoptPersonalVersions` 按 `updatedAt` 取最后一条副本的正文当作采纳结果。实测发现：
采纳 2 条后，新企业版里**只有后改的那个人的内容**，先改的那位被静默丢掉 —— 而变更说明里
写着两个人的名字。界面说做了，实际没做，这比合并出错更糟。

改成 `merge-personal-edits.ts` 的**行级并集合并**（以 diff hunk 为单位）：

- 纯新增：所有人的都保留，同一行内容只留一份
- 只有一人改的区间：按他的改
- 多人改同一区间且改得不一样：**两份都留在正文里**并记入 `conflicts`，变更说明里点明
  「⚠️ N 处内容被多人改成了不同版本，请复核第 X 行附近」

刻意不做智能三方合并 —— 那需要语义理解，猜错会产出一份没人写过的技能正文。

#### 一处 bug 被实测抓到：diff 基线取错了版本

`listPersonalDiffs` 原先用一条 `findFirst` + `orderBy: { scope: 'asc' }` 取基线，想让企业版优先于
平台版。**Postgres 按枚举声明顺序排序**，而 `SkillVersionScope` 的声明是 `PLATFORM` 在前 ——
`asc` 把平台版排在了企业版之前。后果是采纳完之后 diff 仍拿平台原版作基线，把企业已有的定制
显示成成员的改动。改成显式两段查询（`resolveEnterpriseBaseline`）。

#### 已知限制

- **AI 建议是同步调用**，10–30 秒。没引队列：那要多做一套「生成到哪一步了」的状态机，
  而前端等得起。并发生成多份建议时会各自占一个请求。
- **`sampleSize` 目前常为 0**：`ToolExecution` 要走真实工具调用才有记录，而 `OPENCODE_API_BASE_URL`
  仍未配置。建议此时只基于个人副本 diff 生成 —— 实测质量仍可用，但接入 OpenCode 后会更准。
- **合并冲突只报告不阻断**：采纳照常生成版本，管理员需按提示自己复核。做成阻断会让
  「两人改了同一句」变成完全无法采纳。
- ~~提审流的后端仍在~~ **已于 2026-09-02 前后端删净**（见 T2.5）。平台侧审核保留。
- 有 1 行历史数据是 `scope=ENTERPRISE` + `status=PLATFORM_APPROVED`（2026-08-25 的种子数据），
  当前代码不会产生这种组合（`reviewPlatformVersion` 只改 `scope=PLATFORM` 的行）。
  它在时间线上会显示成「平台已通过」，语义不对但不影响功能，清理时机见「后续待议」。

### 3.3 「算力池」是什么 —— 已废弃的旧 Token 池

纪要2 §5 记的「赠送算力用完后，由企业管理端建立『算力池』再分配，目前是手动创建」，
指的是旧的 `ComputeQuota` 表（schema 里 `type: STANDARD|PREMIUM|CUSTOM`，注释「企业池固定为
priority=2」），配套接口 `GET /compute-quota/enterprise-quotas`「[历史] 旧企业 Token 池列表」。

它是 **token 计量的**，8 月 28 日统一人民币账本（`b811cc7`）之后已全部标注「历史模型，
不参与扣减」，前端也只在 `LegacyQuotaNotice` 里作为历史余额提示。**代码里搜不到「算力池」
这三个字** —— 这个概念只存在于旧 Token 配额的三张表里。

所以：**算力池不需要重做，也不需要「改成自动创建」**。它的位置由两样东西接替 ——
赠送算力余额（`SubscriptionCredit`，订阅时自动发放，已经是自动的）+ §5 的算力分配
（按成员的人民币周期上限）。纪要2 §11.2 那条待确认（「算力池由手动创建改为自动创建的触发条件」）
应当在周三当面回答为「该概念已废弃」，而不是去实现它。

### 5.1 四个概念的正确关系

```
① 钱包余额   EnterpriseWallet.balance      企业真金白银的主账本，充值进这里
② 算力余额   SubscriptionCredit（赠送，按员工）+ ① 兜底 = 「还能花多少」
③ 算力分配   【缺】企业给某个碳基员工设的人民币消费上限（可带周期）
             ——是「闸门」不是「钱包」，不影响 ①②，只决定谁被拦
④ 权限       EmployeeGrant：某碳基员工能用哪些硅基员工
             ——与 ③ 完全独立：有权限但额度用尽 = 能看不能用；有额度无权限 = 看不到
```

刘凌的比喻（纪要2 §5）：算力是「管道通到你家的水量」，装哪个水龙头是另一回事。
给员工分配 500 元算力，**不限定他用在哪个硅基员工上**。

数据结构上 ①②④ 已彼此独立，问题是 ③ 完全不存在、且 UI 把四者混在一起。

### 5.2 纪要2 已经定下来的规则（原方案误判为「完全未定」）

- 分配周期支持按 **天 / 周 / 月 / 季 / 年** 设限（「每月最多 500 元」「每天最多 50 元」）
- **两种机制并存**：
  - **周期恢复型**：每天 50 元，当天用完当天停用，次日恢复；**当天未用完的余额次日叠加**
  - **一次性额度型**：本月固定额度，用完即止，需要再充值
- **个人充值**属个人行为，不计入企业分配额度、不走公司账；企业可另行给他分配额度。平台不限制个人充值。
- 前端必须把钱包余额 / 算力余额 / 算力分配 / 使用权限**拆开展示**

### 5.3 定稿建模（2026-09-03 定稿，取代原「建模草案」）

原草案有三处被推翻（见 §5.4 的 Q1–Q3）、两处顺序是反的（见 §5.7 ①②）。下面是要落库的形状。

- **`MemberComputeAllowance`**（已有，本轮扩）：`@@unique([enterpriseId, userId])` 保持不变 ——
  一人一行是「算力分配」这一页不退化成「这人有 3 条额度」的结构保证。
  `limitCNY Decimal?`（null=不限额）· `period` 枚举化为 `DAY|WEEK|MONTH|QUARTER|YEAR` ·
  `carryOver Boolean @default(true)` · `enabled`。
  **没有 `mode` 字段**（一次性额度独立成表，Q1）；**没有 `rollover` 枚举**（结转是布尔，上限固定 1 个周期，Q2）。
  `carryOver` 刻意**不做成 `Int`**：写成「可攒 N 个周期」会让人填 12，而 N>1 就把 O(1) 递推变回链式回溯。

- **`MemberAllowanceWindow`**（新）：每周期一行，懒创建。`allowanceId` · `periodStart/End` · `carriedInCNY`。
  **只存 `carriedInCNY`，不存 `usedCNY`** —— 已用金额继续对账单聚合（走 `[userId, createdAt desc]` 索引），
  避免双写与漂移；窗口行的唯一职责是把结转递推**记忆化**成 O(1)：

  ```
  carriedIn(N) = min(limit, limit + carriedIn(N-1) − used(N-1))
  ```

  上一行不存在时分两种：该周期额度还没创建 → `0`；创建了但没花钱 → `min(limit, limit)` = `limit`（整期结转）。
  两者用 `allowance.createdAt` 与 `periodStart` 比较区分，仍是 O(1)。

- **`MemberAllowanceTopUp`**（新，取代草案的 `mode: ONE_TIME`）：一次性追加额度的流水。
  `enterpriseId + userId` · `amountCNY` · `consumedCNY` · `note` · `grantedById` · `createdAt`。
  不跨周期失效（Q2 的理由同样适用：上限已封顶，再加有效期就是第二套机制）。

- **`MemberAllowanceChange`**（新，草案没有）：额度变更留痕。
  `fromLimitCNY` / `toLimitCNY` / `fromPeriod` / `toPeriod` / `changedById` / `note`。
  成员被拦住时第一个问题是「谁改的」。这行历史很便宜，事后补很贵。

- **`PersonalWallet`** + **`PersonalWalletTransaction`**（新）：`userId @unique` · `balance` ·
  `version`（乐观锁，与企业钱包同一套）· `totalDepositCNY` / `totalConsumeCNY`；
  流水表镜像 `WalletTransaction` 的字段与审计口径（`balanceBefore/After` 快照）。
  没有流水表，「我充的 ¥20 去哪了」无从回答。

- **`ComputeUsageRecord`** 增 `personalPaidCNY` 与 `allowanceWindowId?`，
  恒等式变为 `creditPaid + walletPaid + personalPaid + unpaid == cost`

- **`NotificationType`** 增 `ALLOWANCE_WARNING` / `ALLOWANCE_EXHAUSTED` / `WALLET_LOW_BALANCE`

**扣费顺序（定稿）**：

```
闸门（MemberComputeAllowance）判定「企业资金能不能动」，位置在整条链之前
   ↓
额度未尽：1. SubscriptionCredit（该订阅赠送）
          2. EnterpriseWallet（优先动算力专款）
          3. PersonalWallet（成员自掏）
          4. unpaidCNY 如实记录（余额永不为负，现有硬约束保留）
额度已尽：跳过 1、2 —— 直接 3. PersonalWallet → 4. unpaidCNY
```

两处与草案不同：**闸门守整条链而不只守企业钱包**（草案会让赠送额度成为敞口）；
**个人钱包排最后而不是第 2 位**（草案会让自掏钱的成员静默补贴公司）。理由见 §5.7。

### 5.4 四个问题的定稿答案（2026-09-03）

原定 2026-09-02 当面对齐。四个问题按下述口径**定稿并开工**；每条都记了理由，
当面复核时不必重新推导。三条与「直觉答案」不同，已在各条里标出。

**Q1 两种机制（周期恢复 / 一次性）如何组合？先扣哪个？**

> **答：能并存。但一次性额度不做成第二种 `mode`，而是独立的「追加额度」流水表。
> 扣减顺序：先常规周期额度，后追加额度。**

- 做成 `mode` 会打破 `@@unique([enterpriseId, userId])`：一个人变多行，「算力分配」页
  立刻退化成「这人有 3 条额度」—— 正是会议要拆开四概念的反面。做成追加流水，
  UI 仍是一人一行：`每月 ¥500 · 追加 ¥200`
- 顺序选「先常规」：追加额度的语义是**追加不是替代**（批 ¥200 是因为「他这个月要多干点活」）。
  先花常规，追加就能活到下个周期，管理员不必每期重批
- 这个顺序**必须定**，因为它可观测 —— 追加额度跨周期存活，常规额度不。对比 Q3

**Q2 结转（次日叠加）是否有上限？结转额度是否有有效期？**

> **答：必须有上限，上限 = 1 个周期的额度（即最多攒到 2 倍）。结转额度不单独设有效期。**
> ⚠️ 这一条与纪要2 §5 的字面表述（「未用完的余额次日叠加」，未提上限）不同，理由如下。

- 不封顶会把周期概念彻底废掉：每天 ¥50 攒 30 天，某一天能花 ¥1500 —— 而设 DAY 周期的
  唯一目的就是限制**单日爆炸半径**（跑飞的循环、误操作、滥用）。无上限结转恰好摧毁它要保护的东西
- 「攒到 2 倍」覆盖的是真实诉求：昨天半天没干活，今天想多干点。「攒 30 天一天花光」
  不是任何人的真实需求 —— 那个场景走 Q1 的追加额度
- 一句话能讲清：*未用完的可攒到下一周期，最多攒到 2 倍上限*
- **关键红利**：上限 = 1 周期让结转可以 O(1) 递推（§5.3 的公式），只读上一行窗口。
  上限设成「N 个周期」或不设，就要链式回溯到额度创建那天 —— 而这是每轮对话都要跑的热路径
- 不设单独有效期：有效期要按批次 FIFO 记账（哪块钱是哪期来的），而上限已封住无限累积。
  同一个目的两套机制，多的那套是纯负债

**Q3 结转额度与新周期额度的扣减顺序？**

> **答：不分开记 —— 这个问题在正确建模下不存在。备案答案是「先花结转的」（FIFO），但不实现。**

- `可用 = 上限 + 结转`，消费对总额递减。两者同币种、同归属、同结算时点（都在本周期末结算，
  剩余按上限再结转），**没有任何用户或对账能观察到的差别**
- 实现这个区分要在每个窗口行加第二个计数器、界面加第二个数字、CSV 加第二列，换来零行为差异
- 与 Q1 正好相反：Q1 的顺序可观测所以要定，Q3 的不可观测所以不做

**Q4 中途改额度对当前周期的影响？立即 / 下周期 / 按比例？**

> **答：立即生效，只改「本周期上限」这个数，不动已用金额。不做按比例。**

- 立即生效的理由很实际：**管理员调额度的最常见触发场景就是有人当下被拦住了**。
  下周期生效等于他这次操作当场无效果，他会再点一次、再来问一次，最后问
  「你们这功能是不是坏的」
- 不按比例：闸门不是订阅账单。按比例会产生没人能预测的数字 ——
  *「我把他从 ¥500 调到 ¥1000，为什么他只能再花 ¥250？」* 因为今天 15 号。
  这话在客服对话里没法说
- 语义一行：`可用 = 新上限 + 结转 − 本周期已用`。两个后果必须写进 UI：
  - **调高** → 立刻放行，已用金额照旧
  - **调低到已用金额以下** → 立刻拦下，剩余 0，**不追讨、不影响已发生的账单**。
    保存前弹一句：「该成员本月已用 ¥320，设为 ¥200 将立即停止他的对话」
- 改额度**不动** `carriedInCNY`（它是周期初按旧上限算出来的，窗口行记录的是当时的事实）；
  新上限只约束下一期的结转 cap

**纪要2 §11 另外两项待确认已有答案**，当面只需确认：

- **算力池由手动改自动的触发条件** → §3.3 已认定「算力池」= 已废弃的旧 Token 池
  （`ComputeQuota`），不需要实现自动创建；接替它的赠送额度本来就是订阅时自动发放的
- **平台对企业技能更新何时从人工判断转 AI** → 本轮只做「A 企业更新了此技能」的提示（T2.7），

### 5.7 五条实现前提（四个问题没覆盖，但不定就会写出回归）

四个问题只覆盖了「额度规则怎么算」。下面五条来自读扣费链现有代码，
**其中 ①②③ 与本文档 5.3 原草案（第三轮）写法相反** —— 照原草案实现会引入回归。

**① 闸门位置：拦在整条扣费链之前，不是拦在钱包之前。**

`compute-credit.service.ts:151` 今天就是对的：`memberAllowance.check()` 在赠送额度与钱包检查之前。
原草案把闸门写在「扣钱包前」，那样赠送额度会变成敞口 —— 成员额度用尽后仍能无限花掉
`SubscriptionCredit`，而赠送额度也是真金白银（订阅时从钱包划出去的）。
**分配额度约束的是「这个人能花多少钱」，不是「这个人能花多少钱包里的钱」。**

**② 个人钱包排在最后一位，不是第二位。**

原草案的顺序是「赠送 → 个人 → 企业钱包」。那样只要成员自己充了钱，
公司的钱就永远花不到他头上 —— 成员在静默补贴公司。正确顺序：

```
赠送额度 → 企业钱包 → 个人钱包 → 欠费
              ↑ 闸门说「企业资金已用尽」时，跳过前两步直接到个人钱包
```

个人钱包是**兜底**，只在「企业不给钱了但我还想继续干」时出场。

**③ 已用金额的口径 = `creditPaid + walletPaid + unpaid`，不是 `sum(costCNY)`。**

个人钱包上线后 `costCNY` 里就含了成员自付部分。继续按 `costCNY` 累计，会出现
「他自己掏钱反而更快撞上公司给的额度上限」—— 自付变成了自我惩罚。
现有闸门 `member-allowance.service.ts` 聚合的正是 `_sum: { costCNY }`，**这行必须改**。
同一处口径在 `listAllowances` 的 `groupBy` 里也有一份，一起改。

**④ 闸门是改道器，不是终止器 —— 这决定 `check()` 的返回结构。**

额度用尽后成员**仍可用个人钱包继续对话**，所以 `check()` 不能只返回
`{allowed, reason}`。返回：

```typescript
interface AllowanceCheckResult {
  enterpriseFundsAllowed: boolean;  // 能否动用企业资金（赠送 + 企业钱包）
  allowed: boolean;                 // 本次对话能否发生（企业资金 or 个人余额任一可用）
  reason?: string;                  // 仅在 allowed=false 时给话术
  limitCNY?: string; usedCNY?: string; remainingCNY?: string;  // 前端提示要用
}
```

`chargeUsage` 读 `enterpriseFundsAllowed` 决定跳不跳前两步。少了这个字段，
「额度用尽 + 有个人余额」只能被拦死，Q1/Q2 讨论的一切都成了摆设。

**⑤ 周期边界必须显式指定 Asia/Shanghai，不能吃服务器 TZ。**

现有 `currentPeriod()` 用 `new Date(y, m, 1)` —— 跑在 UTC 容器里就是 UTC 月初。
自然月场景下这个错误只影响每月约 1% 的账单（月初 8 小时），DAY 周期下变成
**每天 33% 的账单归错了窗口**。抽 `allowance-period.ts` 纯函数，五种周期都在这里定，
配单元测试覆盖：1/31 → 2/28 的月末回退、季度边界、跨年、周起始日（周一）、DAY 的 00:00+08:00。

**估算修正**：§0 表格原记「8（高）」是「先消化规则」的估算。规则已定稿，
按上述范围实施为 **4–5 人日**（迁移 0.5 + 周期函数含测试 0.5 + 闸门重写 1.5 +
个人钱包与扣费链 1 + 通知 0.5 + 前端 1）。比原「规则定稿后 5–7 天」低，
因为 Q3 不实现、结转做成 O(1) 递推省掉了批次记账。
