### 1.3 其他已确认的小缺口

- **实时推送没实现**：`web/src/hooks/use-realtime.ts:49` 注释「`/ws/tasks` gateway 尚未实现，传空 URL 禁止连接」，状态刷新全靠 mutation 回写。
- **孤儿任务只能手动回收**：`POST /tasks/:id/reconcile`（`task.service.ts`），需前端主动触发，没有定时任务。
- **额度耗尽无通知类型**：`NotificationType` 只有 INFO/SUCCESS/WARNING/ERROR + 3 个订阅申请类型（`schema.prisma:1779`），无预算/额度类。
- **`ToolExecution` 没有 `skillVersionId`**（`schema.prisma:1027`）：能查「这个能力被调了多少次」，查不出「哪个版本产出了什么」。
- **旧 Token 配额入口还挂在导航上**：`/compute-quota`（`enterprise-shell.tsx:106`），后端已全部标注 `[历史]`（`compute-quota.controller.ts:25-51`）。
- **IA 过度收拢**：`/skills` 直接 `redirect('/contributions')`（`web/src/app/(enterprise)/skills/page.tsx`），能力创作 + 版本迭代 + 审批追踪三件事挤在一个入口——正是会议批评的「过度收拢到一个模块」。
- **OpenCode 契约可能不一致**：`OpenCodeAdapter` 打的是 `/jobs`、`/jobs/:id/run`（`opencode.adapter.ts:83-105`），而 `CLAUDE.md` 记录的服务契约是 `POST /v1/runs`、`GET /v1/runs/{id}`。上线前必须核对。

### 3.2 任务清单

#### DB（一次迁移搞定，避免多次改 schema）

**T1.1** 新增 `TaskRunStep` 表，把步骤从 `TaskRun.steps` 这个 JSON 快照里提出来成为一等实体。

```prisma
model TaskRunStep {
  id           String   @id @default(cuid())
  taskRunId    String
  taskRun      TaskRun  @relation(fields: [taskRunId], references: [id], onDelete: Cascade)
  order        Int
  title        String
  description  String   @db.Text
  employeeId   String
  capabilityId String
  /// 实际生效的技能版本，与阶段二的 resolveEffectiveVersion 对齐
  skillVersionId String?
  dependsOn    String[] @default([])
  status       TASK_STEP_STATUS @default(QUEUED)
  /// 会议要求的「输入」：真正送进模型的 prompt 全文
  inputPrompt  String?  @db.Text
  /// 会议要求的「交接内容」：从哪些上游步骤取了什么产出
  handoff      Json?
  output       String?  @db.Text
  error        String?  @db.Text
  sessionId    String?
  startedAt    DateTime?
  completedAt  DateTime?
  durationMs   Int?
  createdAt    DateTime @default(now())
  updatedAt    DateTime @updatedAt

  @@unique([taskRunId, order])
  @@index([taskRunId])
  @@map("task_run_steps")
}
```

保留 `TaskRun.steps` JSON 一个版本周期作为兼容读，新写只走 `TaskRunStep`；迁移脚本把存量 JSON 展开成行。

**T1.2** `TaskRun` 增字段：`deliverable String? @db.Text`（最终交付物正文）、`deliverableGeneratedAt`、`claimedBy String?` + `heartbeatAt DateTime?`（供 worker 抢占与心跳，替代靠 `updatedAt` 猜孤儿）。

**T1.3** `TASK_EVENT_TYPE` 增 `STEP_HANDOFF`（交接发生）与 `DELIVERABLE_READY`。

#### 后端：把执行引擎搬进服务端（B1）

**T1.4** 新建 `backend/src/modules/task-execution/`，与 `task`（CRUD）分开：

```
task-execution.module.ts
task-execution.service.ts     ← 单步执行：解析交接 → 拼 prompt → 调能力 → 落库
task-runner.service.ts        ← 队列消费：按 dependsOn 拓扑序推进整个 run
task-deliverable.service.ts   ← 全部步骤完成后生成最终交付物
```

- 队列用 **BullMQ + 现有 Redis 7**（`docker-compose.yml` 已有 `sep-redis`，无需引入新中间件）。
- 单步执行**复用现有对话链路**，不要另写一套模型调用：仍走 `ConversationService` 创建 `source=TASK` 的会话 + `ConversationStreamService`，这样计费（`computeCredit.chargeUsage`）、企业模型策略、知识库检索全部自动继承。
- `prompt` 拼装逻辑从 `tasks/page.tsx:393-400` **原样搬到后端**并把结果写入 `TaskRunStep.inputPrompt`。
- `handoff` 写成 `[{ fromStepId, fromEmployeeName, excerpt }]`，同时发 `STEP_HANDOFF` 事件。
- worker 每 10s 更新 `heartbeatAt`；`heartbeatAt` 超过 60s 未动即视为失联，由定时任务标 `STOPPED`（替代 T1.10 之前的手动 reconcile）。

**T1.5** 新增接口（沿用 `TaskController` 前缀，新增到 `task-execution.controller.ts`）：

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/tasks/:id/run` | 确认计划并入队执行（幂等：已 RUNNING 返回 409） |
| POST | `/tasks/:id/stop` | 请求停止，worker 在步骤边界响应 |
| POST | `/tasks/:id/steps/:stepId/retry` | 从该步重跑（下游步骤重置为 QUEUED） |
| POST | `/tasks/:id/steps/:stepId/pause` / `/resume` | 步骤级暂停，替代前端 `pausedRef` |
| GET | `/tasks/:id/stream` | **SSE**，推 `TaskRunEvent` + 步骤增量输出 |
| GET | `/tasks/:id/deliverable` | 最终交付物 |

**T1.6** 最终交付物生成（`task-deliverable.service.ts`）：所有步骤 `COMPLETED` 后，用一次 LLM 调用把 `objective` + 各步 `output` 汇总成一份结构化交付物（标题 / 摘要 / 正文 / 各步来源引用），写入 `TaskRun.deliverable` 并发 `DELIVERABLE_READY`。模型走 `SUB2API_PLANNER_MODEL`，与规划器同一份配置。

> 生成失败不能让整个 run 失败——降级为「按步骤顺序拼接」的机械交付物，并在返回体里标 `degraded: true`。

**T1.7** 定时任务：`@Cron` 每 2 分钟扫 `status=RUNNING AND heartbeatAt < now() - 60s` 的 run，标 `STOPPED` 并把 `running` 步骤标 `FAILED('执行中断')`。现有 `reconcile` 接口保留但改为「手动补救」入口。

### 3.3 现场验收动作（照着做一遍，任一环节断即未完成）

1. 首页点「发起工作安排」→ 顶部大字显示「XX 团队已准备好 · 目前团队成员 N 人」
2. 输入一句业务目标（如「给我们新款保温杯做一份小红书投放方案并配 3 条文案」）→ 生成 3 步计划，能看到每步选了谁、为什么选、依赖谁
3. 点「确认并执行」→ **关掉浏览器标签页，等 1 分钟，重新打开** → 任务仍在推进，进度已前进
4. 展开第 2 步 → 看到「接到的活」（完整 prompt）、「来自 XX 的交接」（第 1 步产出摘要）、「产出」
5. 全部完成 → 点「最终交付」→ 一份带小标题的完整方案，每段可溯源到某一步
6. 「保存为模板」→ 新建任务时从模板载入 → 步骤与依赖完整复现

#### 已知限制

- **步骤串行执行**。依赖图允许并行，但串行让计费与余额闸门行为可预测、演示时接力顺序肉眼可辨。并行是后续优化，不是闭环前提。

#### 已知限制

- **使用统计在应用层聚合**，不是 SQL `GROUP BY`。当前数据量下没问题，但一个能力累积到几万条执行记录时要改成数据库聚合。

- **`skillVersionId` 只对新执行记录有值**。迁移之前的历史记录这一列为 `NULL`，前端如实显示成「未记录版本」而不是假装是平台版。

#### 二次评审改掉的四处（codex review + 本次收尾）

评审补的：
- 统计口径加上「会话员工在本企业有 ACTIVE 订阅」的约束 —— 只按 `user.memberships` 过滤会把成员离职前用别家员工的记录也算进来

本次收尾又发现三个问题：
- **切版用错了订阅**：`setEffective` 传的是 `timeline.subscriptionId`（授权校验命中的第一条），不是下拉里选中的那条。多员工带同一技能时会「选了员工 B，切版切在 A 身上」，而界面上看不出来。

- 顺带补了两处：审核通过 / 驳回后失效 `capability-iteration` 查询（`useReviewEnterpriseSkillVersion` 只失效 `['skill-versions']`，不手动加这一步的话时间线状态不刷新，看起来像没生效）；通过按钮补失败提示。

## 6. 阶段四：钱包 / 算力 / 额度 / 权限四层拆分

### 6.1 四个概念的正确关系（会议要求"前端展示和后台逻辑需要分开"）

```
① 钱包余额        EnterpriseWallet.balance         企业真金白银的主账本，充值进这里
② 算力余额        SubscriptionCredit（赠送，按员工）+ ① 兜底
                  = 「还能花多少」，扣费顺序 赠送 → 钱包
③ 算力分配        【本阶段新建】企业给某个碳基员工设的人民币消费上限（可带周期）
```

### 6.3 任务清单（不受未定规则影响的部分，可立即开工）

#### DB

**T4.1** 新表 `MemberComputeAllowance`——算力分配（概念 ③）：

```prisma
enum ALLOWANCE_PERIOD {
  DAY
  WEEK
  MONTH
  QUARTER
  YEAR
  TOTAL          // 一次性总额，不循环
}

model MemberComputeAllowance {
  id           String @id @default(cuid())
  enterpriseId String
  enterprise   Enterprise @relation(fields: [enterpriseId], references: [id], onDelete: Cascade)
  memberId     String     @unique   // EnterpriseMember，一人一条
  member       EnterpriseMember @relation(fields: [memberId], references: [id], onDelete: Cascade)

  /// 上限金额（元）。null = 不限额
  limitCNY   Decimal? @db.Decimal(14, 6)
  period     ALLOWANCE_PERIOD @default(MONTH)
  /// 周期结束后未用额度如何处理。规则待定稿前默认 RESET
  rollover   String @default("RESET")   // RESET | CARRY_OVER
  enabled    Boolean @default(true)

  createdById String
  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt

  windows MemberAllowanceWindow[]
  @@index([enterpriseId, enabled])
  @@map("member_compute_allowances")
}

/// 每个周期一行，避免每次扣费都对 ComputeUsageRecord 做区间聚合
model MemberAllowanceWindow {
  id          String @id @default(cuid())
  allowanceId String
  allowance   MemberComputeAllowance @relation(fields: [allowanceId], references: [id], onDelete: Cascade)
  periodStart DateTime
  periodEnd   DateTime
  /// 本周期已消耗（元）
  usedCNY     Decimal @default(0) @db.Decimal(14, 6)
  /// 上周期结转进来的额度（rollover=CARRY_OVER 时 > 0）
  carriedCNY  Decimal @default(0) @db.Decimal(14, 6)
  version     Int @default(0)      // 乐观锁，与钱包同一套并发策略

  @@unique([allowanceId, periodStart])
  @@index([periodEnd])
  @@map("member_allowance_windows")
}
```

> **为什么要 window 表**：直接对 `ComputeUsageRecord` 按 `userId + 时间区间` 聚合，每次对话前都要跑一次范围扫描；随着账单增长会变成热点。window 行是 O(1) 读写，且天然记录了「这个周期发生过什么」，对账时可解释。

- `allowanceWindowId String?` —— 命中的额度周期，便于反查「这笔消费算在哪个周期」

恒等式更新为：`creditPaidCNY + walletPaidCNY + personalPaidCNY + unpaidCNY == costCNY`。

**T4.4** `NotificationType` 增 4 个：`ALLOWANCE_WARNING`（达阈值）、`ALLOWANCE_EXHAUSTED`（用尽）、`ENTERPRISE_BUDGET_WARNING`、`WALLET_LOW_BALANCE`。

#### 后端

**T4.5** `MemberAllowanceService`：
- `resolveWindow(memberId, at)`：找到或惰性创建当前周期 window（周期边界按企业时区，统一 `Asia/Shanghai`）
- `assertAvailable(memberId, estimatedCNY)`：对话开始前的前置检查，额度不足抛 `PaymentRequiredException`（402），错误体带 `{ limitCNY, usedCNY, periodEnd, nextResetAt }` 供前端渲染明确提示
- `consume(memberId, amountCNY, usageRecordId)`：扣减 window，乐观锁重试

**T4.6** 扣费链路改造（`compute-credit.service.ts` 的 `chargeUsage`）。**新的扣费顺序**：

```
1. SubscriptionCredit（该订阅的赠送余额）      ← 现有
2. PersonalWallet（成员自己充的钱）            ← 新增，个人充值优先于企业的钱
3. EnterpriseWallet（企业钱包）                ← 现有
   ↑ 第 3 步之前先过 MemberComputeAllowance 闸门；额度用尽则不动企业钱包
4. 都不够 → unpaidCNY 如实记录（余额永不为负，现有硬约束保留）
```

> 顺序里把个人钱包放在企业钱包之前，是对「个人充值费用不计入企业分配额度」的直接落实：个人的钱先花掉，企业额度自然不被消耗。

**T4.7** 接口：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/enterprise/allowances` | 成员额度总览（含本周期用量、剩余、下次重置时间） |
| PUT | `/enterprise/allowances/:memberId` | 设置/修改额度（管理员） |
| DELETE | `/enterprise/allowances/:memberId` | 取消限额 |
| GET | `/me/allowance` | 当前用户自己的额度状态（成员可见） |
| GET | `/me/wallet` | 个人钱包余额与流水 |
| POST | `/me/wallet/recharge` | 个人充值（复用支付宝链路，`payment` 模块） |

**T4.8** 额度告警定时任务：接在现有 `cost-analytics-cron.service.ts` 旁边，每小时扫 window，`usedCNY / limitCNY >= 0.8` 发 `ALLOWANCE_WARNING`，`>= 1.0` 发 `ALLOWANCE_EXHAUSTED`（每周期每档只发一次，靠 window 上的标记位去重）。

#### 前端

**T4.9** 新页面 `/compute-allocation`「算力分配」（导航「费用」组，接替下架的 `/compute-quota`）：成员表格 × 列（成员 / 部门 / 周期 / 上限 / 本周期已用 / 剩余 / 下次重置 / 操作）。批量设置支持「按部门统一设置」。

```
可用算力  ¥1,340.50
├ 赠送额度  ¥340.50   （按员工，仅限对应硅基员工）
```

### 6.4 被规则未定稿阻塞的部分

会议「六、待确认事项 1」原文：*周期性算力额度的具体规则：额度到期后的自动恢复、未用额度是否结转或叠加。*

**处理方式**：schema 里预留 `rollover: RESET | CARRY_OVER`（T4.1），默认 `RESET`。以下三件事**等规则定稿再做**，不要提前猜：

- `CARRY_OVER` 的具体语义（结转是否有上限？结转的额度是否也有有效期？）
- 结转额度与新周期额度的**扣减顺序**（先花结转的还是先花新的）
- 中途修改额度对当前周期的影响（立即生效 / 下周期生效 / 按比例）

**建议在下次现场沟通时用一张表把三个问题一次问定**，不要分次确认——这三个问题彼此耦合，分开回答容易出自相矛盾的规则。

### 6.5 现场验收动作

1. 管理员进「算力分配」→ 给某成员设「每月最多 ¥50」→ 保存
2. 该成员看自己的额度：「本月 ¥0 / ¥50，9月1日重置」
3. 该成员对话消耗到超过 ¥50 → **明确弹窗**说明额度用尽 + 重置时间 + 两个出路
4. 该成员个人充值 ¥20 → 可继续对话；**回管理员端看「本周期已用」仍是 ¥50 不再增长**（个人充值不计入企业额度，这是判据）
5. 管理员把额度改成 ¥200 → 成员立即可继续（或按定稿规则下周期生效）
6. 「雇佣管理」里取消该成员对某员工的授权 → 成员看不到该员工，**但额度数字不变**（权限与额度独立）
7. 四个页面（钱包 / 算力分配 / 用量分析 / 雇佣管理）标题与副标题各说一件事，不重叠
8. 任意余额展示处都能看到「赠送 + 钱包」两条腿与扣减顺序说明

### 6.6 风险

| 风险 | 应对 |
|---|---|
| 扣费链路是刚上线的核心代码（`b811cc7`，8月28日），再改风险高 | 只在 `chargeUsage` 里**插入**个人钱包与闸门两步，不重写既有 credit→wallet 逻辑；`compute-credit.service.spec.ts` / `subscription-credit.service.spec.ts` 已有测试基础，新增用例覆盖四条腿的所有组合 |
| 周期边界与时区容易出错（跨月、跨季度、闰年） | 周期计算抽成纯函数 + 单测覆盖月末（1/31 → 2/28）、季度边界、跨年；统一 `Asia/Shanghai` |
| 并发扣减 window 出现超额 | 与钱包同一套乐观锁 + 重试；额度是「软闸门」，允许极端并发下小幅超出（用 `unpaidCNY` 如实记录），不允许余额为负 |
| 规则未定就实现 CARRY_OVER 会返工 | §6.4 明确划出，schema 预留字段但不实现分支 |

不属于产品决策，但是 9 月演示的硬前置。

### A.1 本地服务重启不恢复（行动项 10）

会议原话：*当前本地重启后前后端服务不会自动恢复，需要补充进程/容器持久化和开机自启配置。*

现状核查：
- `docker-compose.yml`（本地）**没有任何 `restart` 策略**——postgres 与 redis 重启后不会起
- `deploy/production/docker-compose.yml` 有 `restart: unless-stopped`（第 40、128 行）✅ 生产已正确
- 前后端本地靠 `pnpm dev:backend` / `pnpm dev:web` 跑在终端里，没有进程守护

要做：
1. 本地 `docker-compose.yml` 给 postgres / redis 加 `restart: unless-stopped`
2. 本地开发进程用 pm2 托管（仓库已有 `pm2` 相关 skill 可参考），`pm2 save` + `pm2 startup` 实现开机自启
3. 演示机不要用 `pnpm dev`——用 `pnpm build` + 生产模式 + pm2/docker，避免热重载在演示中触发重编译卡顿

### A.2 服务器与访问（行动项 9、11）

- 优先国内服务器（刘凌提供 / 确认）；用海外现有机器需先确认是否依赖代理
- 初期 `IP + 端口` 直连即可；需要正式地址时先用本地 hosts，不急着买域名备案
- 端口开放由服务器负责方确认后申请
- 宝塔等面板按实际部署环境定；`deploy/production/` 已有 Caddy 配置片段与蓝绿部署 compose，可直接复用而不必从零搭
- **注意**：`deploy/production/sep-deploy.sh` 与 `docker-compose.blue-green.yml` 是已有资产，配合林芳部署时先读这两个文件，不要另起一套

### A.3 林芳的两个 Demo（行动项 8）

会议定的做法是「静态页面 + 伪造数据、不强制接数据库、下周一可访问」。本仓库的配合点：
1. 先帮她确认现有页面是客户端还是管理端（会议行动项原文）
2. 智能招聘需区分管理员与普通用户角色——可参考本仓库 `(enterprise)` / `(platform)` 两个路由组的划分方式，以及 `EnterpriseRole` 的角色标签体系

## 附录 C：验收原则

会议原话：*所有功能验收都要回到「是否产生预期结果」，不能只展示开发过程或页面框架。*

据此，本方案每个阶段的「现场验收动作」都写成了**一串可以照着点的操作**，而不是功能清单。落地时的三条硬规则：

1. **能演示 ≠ 能闭环**。B1（浏览器执行）和 B2（版本不生效）都属于「点得动、看着对、实际没通」。验收时必须做那两个破坏性动作：**关掉标签页**（验 B1）、**改完版本回对话里看输出变没变**（验 B2）。
2. **每个阶段完成时更新本文档的对照表**，把 ❌ 改成 ✅ 并附上 commit。下次现场沟通直接拿这份表过。
3. **不新增未在本方案里的需求**（会议行动项 12：新增需求先同步并控制版本边界）。发现漏项先记在本文档末尾的「后续待议」，不直接开工。
