# 技能预览与版本管理实施计划

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** 在企业端员工详情页和运营后台提供受权限控制的 Markdown 技能预览，并建立平台版本、企业定制版本、企业审核、平台审核和员工选版的完整治理闭环。

**Architecture:** 保留 `Capability` 作为技能身份和平台目录元数据，新增独立的 `SkillVersion` 保存每一次 Markdown 正文快照。平台员工绑定只保存平台默认版本；企业对某个订阅的实际选版保存到订阅级选择表，企业私有版本因此不会影响其他企业。版本的审核状态与审核记录独立保存，预览接口只返回正文，不返回模型参数、凭据、压缩包路径或其他内部配置。

**Tech Stack:** NestJS 10、Prisma 6、PostgreSQL 16、Next.js 15 App Router、TanStack Query v5、Zod、Shadcn/ui、`react-markdown`、`remark-gfm`、`gray-matter`。

## 1. 已确认的产品决策

### 1.1 入口与角色

首期只提供两个入口：

1. 企业端员工详情页：查看该企业已授权使用的员工所绑定的技能，并查看当前生效版本和可选版本。
2. 运营后台审核页面：查看平台技能版本和企业提交到平台的版本，完成平台审核。

完整技能正文只开放给：

- 已登录的运营管理员；
- 已属于企业、且该企业拥有该员工有效订阅和当前成员授权的企业成员。

人才市场公开详情、未订阅用户、没有员工授权的成员不得通过任何接口获取完整正文。

### 1.2 文件范围

- 首期支持单个逻辑文件 `SKILL.md` 的 Markdown 正文。
- 当前上传链路仍可接收 zip，但只解析其中的 `SKILL.md` 作为技能正文；目录树、脚本、图片、附件、在线资源暂不进入版本编辑和预览范围。
- 预览只展示正文，不展示 YAML frontmatter、模型参数、温度、maxTokens、内部路径、zipPath、密钥或执行服务配置。
- 服务端保存正文快照，前端提供“渲染视图 / 原始 Markdown”切换。

### 1.3 版本和审核规则

每次创建一份技能内容都产生一个不可变版本快照；修改不能覆盖已经提交审核或已经生效的版本，只能基于某个版本创建新版本。

版本分为两类：

- **平台版本（PLATFORM）**：由平台维护并面向市场提供。平台审核通过后可被企业选用。
- **企业版本（ENTERPRISE）**：企业从平台版本 Fork 后形成，只对所属企业可见。企业审核通过后可在本企业使用；企业可以再提交到平台，平台审核通过后才转为可发布的平台版本。

企业版本提交平台时不直接修改原版本的 `scope` 或 `enterpriseId`。系统创建一条新的平台提交副本，保留来源版本关系；平台审核通过后，该副本成为新的 `PLATFORM` 版本，原企业版本继续属于原企业并可独立迭代。

这里将“生效”拆为两个范围，避免把企业私有迭代强制阻塞在平台审核上：

- 企业私有使用：企业审核通过即可生效，仅限本企业；
- 平台公开使用：平台审核通过才生效，进入平台可选版本。

如果业务最终要求所有企业版本必须经过平台审核后才能在企业内使用，只需把企业版本的 `effectiveStatus` 规则收紧为同时满足两类审核，数据模型无需重做。

员工选版规则：

- 同一个平台员工可以被不同企业选择不同技能版本。
- 同一个企业的不同员工也可以选择同一技能的不同版本。
- 企业管理员选择版本后，选择记录立即指向该版本；只有审核通过的版本可选。
- 已生效版本继续保留，平台发布新版不会自动替换企业当前版本，只提示有可升级版本。

### 1.4 首期不做

- 不做在线执行、沙箱测试、模型结果评估。
- 不做多文件技能包在线浏览。
- 不允许直接编辑公共平台版本。
- 不做自动合并、自动升级和自动回滚；回滚通过重新选择历史已审核版本完成。
- 不在预览接口返回完整 `SkillConfig`，尤其不返回模型配置和其他内部字段。

## 2. 状态机

### 2.1 企业私有版本

```text
DRAFT
  -> PENDING_ENTERPRISE_REVIEW   企业成员提交
  -> ENTERPRISE_APPROVED         企业管理员通过
  -> ENTERPRISE_REJECTED         企业管理员驳回

ENTERPRISE_APPROVED
  -> 创建平台提交副本            企业主动提交到平台；原企业版本保持 ENTERPRISE_APPROVED

平台提交副本：
  PENDING_PLATFORM_REVIEW -> PLATFORM_APPROVED
                           -> PLATFORM_REJECTED

平台审核驳回不影响原企业私有已生效版本。
```

企业管理员驳回后回到 `DRAFT`，平台驳回后也回到可编辑的 `DRAFT` 或 `ENTERPRISE_APPROVED`，具体由服务端按“是否仍为当前企业生效版本”决定，不能删除已产生的审核记录。

### 2.2 平台版本

```text
DRAFT -> PENDING_PLATFORM_REVIEW -> PLATFORM_APPROVED
                                  -> PLATFORM_REJECTED
```

平台版本审核通过后才允许出现在企业的候选版本列表。平台已发布版本不可直接编辑，只能创建新版本。

## 3. 数据模型设计

### 3.1 新增 `SkillVersion`

文件：`backend/prisma/schema.prisma`

建议字段：

```prisma
enum SkillVersionScope {
  PLATFORM
  ENTERPRISE
}

enum SkillVersionStatus {
  DRAFT
  PENDING_ENTERPRISE_REVIEW
  ENTERPRISE_APPROVED
  PENDING_PLATFORM_REVIEW
  PLATFORM_APPROVED
  ENTERPRISE_REJECTED
  PLATFORM_REJECTED
  ARCHIVED
}

model SkillVersion {
  id                  String            @id @default(cuid())
  capabilityId        String
  capability          Capability        @relation(fields: [capabilityId], references: [id], onDelete: Cascade)
  scope               SkillVersionScope
  enterpriseId        String?
  enterprise          Enterprise?       @relation(fields: [enterpriseId], references: [id], onDelete: Cascade)
  parentVersionId     String?
  parentVersion       SkillVersion?     @relation("SkillVersionFork", fields: [parentVersionId], references: [id])
  forkedVersions      SkillVersion[]    @relation("SkillVersionFork")
  sourceVersionId     String?
  sourceVersion       SkillVersion?     @relation("SkillVersionPromotion", fields: [sourceVersionId], references: [id])
  promotedVersions    SkillVersion[]    @relation("SkillVersionPromotion")
  version             String
  content             String            @db.Text
  changeSummary       String?           @db.Text
  status              SkillVersionStatus @default(DRAFT)
  createdById          String
  createdBy            User              @relation("SkillVersionCreator", fields: [createdById], references: [id])
  submittedAt         DateTime?
  enterpriseReviewedById String?
  enterpriseReviewedBy User?            @relation("SkillVersionEnterpriseReviewer", fields: [enterpriseReviewedById], references: [id])
  enterpriseReviewedAt DateTime?
  platformReviewedById  String?
  platformReviewedBy    User?            @relation("SkillVersionPlatformReviewer", fields: [platformReviewedById], references: [id])
  platformReviewedAt    DateTime?
  rejectionReason       String?           @db.Text
  createdAt             DateTime           @default(now())
  updatedAt             DateTime           @updatedAt
  reviews               SkillVersionReview[]
  selections            SubscriptionSkillVersion[]
  defaultBindings       EmployeeCapabilityBinding[] @relation("DefaultSkillVersion")

  @@index([capabilityId, status])
  @@index([enterpriseId, status])
  @@index([parentVersionId])
  @@map("skill_versions")
}
```

字段说明：

- `content` 只保存 Markdown 正文，不保存 frontmatter。
- `parentVersionId` 记录 Fork 来源，支持版本树和后续差异对比。
- `sourceVersionId` 记录企业版本提交平台后生成的审核副本来源；平台副本通过审核后成为新的平台版本，不能回写企业版本的归属。
- `scope = ENTERPRISE` 时必须有 `enterpriseId`；`scope = PLATFORM` 时必须为空，由 service 层校验。
- 版本号由同一技能、同一作用域递增生成，首期可使用 `1.0.0`、`1.1.0` 等字符串；禁止客户端直接覆盖已存在版本号。
- `status` 是当前可查询状态，审核明细写入 `SkillVersionReview`，不能只把审核意见塞进 JSON metadata。

### 3.2 新增审核记录 `SkillVersionReview`

```prisma
enum SkillReviewActorType {
  ENTERPRISE
  PLATFORM
}

enum SkillReviewDecision {
  APPROVE
  REJECT
}

model SkillVersionReview {
  id          String              @id @default(cuid())
  versionId   String
  version     SkillVersion        @relation(fields: [versionId], references: [id], onDelete: Cascade)
  actorType   SkillReviewActorType
  decision    SkillReviewDecision
  reviewerId  String
  reviewer    User                @relation("SkillVersionReviewer", fields: [reviewerId], references: [id])
  comment     String?             @db.Text
  createdAt   DateTime            @default(now())

  @@index([versionId, createdAt])
  @@map("skill_version_reviews")
}
```

`User` 侧必须补齐以下反向关系（名称要与上面的 relation name 完全一致）：

```prisma
createdSkillVersions              SkillVersion[]              @relation("SkillVersionCreator")
enterpriseReviewedSkillVersions   SkillVersion[]              @relation("SkillVersionEnterpriseReviewer")
platformReviewedSkillVersions     SkillVersion[]              @relation("SkillVersionPlatformReviewer")
skillVersionReviews               SkillVersionReview[]        @relation("SkillVersionReviewer")
selectedSubscriptionSkillVersions SubscriptionSkillVersion[]  @relation("SubscriptionSkillVersionSelector")
```

### 3.3 企业订阅级选版 `SubscriptionSkillVersion`

不能把企业版本选择直接放入现有 `EmployeeCapabilityBinding`：该表是平台员工模板的全局绑定，写入企业 A 的版本会影响企业 B。企业选择必须挂在订阅上。

```prisma
model SubscriptionSkillVersion {
  id             String       @id @default(cuid())
  subscriptionId String
  subscription   Subscription @relation(fields: [subscriptionId], references: [id], onDelete: Cascade)
  capabilityId   String
  capability     Capability   @relation(fields: [capabilityId], references: [id], onDelete: Cascade)
  versionId      String
  version        SkillVersion @relation(fields: [versionId], references: [id], onDelete: Restrict)
  selectedById   String
  selectedBy     User         @relation("SubscriptionSkillVersionSelector", fields: [selectedById], references: [id])
  selectedAt     DateTime     @default(now())

  @@unique([subscriptionId, capabilityId])
  @@index([subscriptionId])
  @@index([versionId])
  @@map("subscription_skill_versions")
}
```

约束由 service 层保证：

- `version.capabilityId === capabilityId`；
- 平台版本必须是 `PLATFORM_APPROVED`；
- 企业版本必须属于当前订阅企业且为 `ENTERPRISE_APPROVED` 或企业已批准的平台版本；
- capability 必须确实绑定在订阅对应员工上；
- 选择操作只能由企业管理员执行。

### 3.4 现有模型兼容与迁移

- `Capability` 增加 `skillVersions SkillVersion[]` 关系。
- `User` 增加带显式 relation name 的创建者、企业审核人、平台审核人、审核记录审核人、订阅选版人反向关系；由于 `SkillVersion` 和 `SkillVersionReview` 对 `User` 有多条关系，不能省略 relation name。
- `Enterprise` 增加 `skillVersions SkillVersion[]` 关系。
- `Subscription` 增加 `skillVersionSelections SubscriptionSkillVersion[]` 关系。
- `EmployeeCapabilityBinding` 增加可空的 `defaultSkillVersionId` 外键和 `defaultSkillVersion` 关系，仅用于平台默认版本；非 `SKILL` 能力必须为 NULL。
- `SkillConfig.template` 暂时保留，作为兼容字段和迁移源，不再作为新预览接口的数据源。
- 数据迁移为每个现有 `SKILL` 能力创建初始 `SkillVersion`：从 `SkillConfig.template` 解析 frontmatter，取正文写入 `content`，版本为 `1.0.0`。能力已 `APPROVED` 的初始版本置为 `PLATFORM_APPROVED`，其他版本置为 `DRAFT`。
- 迁移必须保留原始 `SkillConfig.template`，提供回滚和人工核对依据；迁移脚本需要可重复执行且不能重复创建初始版本。

### 4.1 企业端接口

| Method | Path | 权限 | 用途 |
|---|---|---|---|
| GET | `/enterprise/employees/:employeeId/skills` | 已授权成员 | 返回技能列表、当前生效版本、候选版本摘要 |
| GET | `/enterprise/skill-versions/:id/preview` | 已授权成员 | 返回正文、版本号、来源、状态、更新时间 |
| POST | `/enterprise/subscriptions/:subscriptionId/skill-versions` | 企业成员 | 基于已授权版本创建企业草稿/Fork |
| PATCH | `/enterprise/skill-versions/:id` | 版本所属企业成员 | 编辑 `content` 和 `changeSummary`，仅允许 DRAFT |
| POST | `/enterprise/skill-versions/:id/submit-review` | 版本所属企业成员 | DRAFT 提交企业审核 |
| POST | `/enterprise/skill-versions/:id/review` | 企业管理员 | 通过或驳回企业版本，并写审核记录 |
| POST | `/enterprise/subscriptions/:subscriptionId/skills/:capabilityId/select-version` | 企业管理员 | 选择当前员工实际生效版本 |
| POST | `/enterprise/skill-versions/:id/submit-platform-review` | 企业管理员 | 基于企业审核通过版本创建平台审核副本并提交 |

企业员工详情接口应一次返回摘要，不直接内嵌正文；用户点击预览时再请求 preview，避免列表接口泄漏大量提示词。

### 4.2 运营后台接口

| Method | Path | 权限 | 用途 |
|---|---|---|---|
| GET | `/admin/skill-versions` | ADMIN | 按状态、scope、capability、enterprise 分页查询 |
| GET | `/admin/skill-versions/:id` | ADMIN | 详情、正文、Fork 来源、审核记录 |
| POST | `/admin/skill-versions/:id/approve` | ADMIN | 平台审核通过 |
| POST | `/admin/skill-versions/:id/reject` | ADMIN | 平台审核驳回并记录原因 |
| POST | `/admin/skill-versions/:id/create` | ADMIN | 基于平台版本创建新的平台草稿 |

现有 `GET /capabilities/:id` 必须收紧为公开安全字段，不再通过 `FULL_INCLUDE` 无条件返回 `skillConfig.template`。需要新增内部管理查询或显式 preview 接口替代历史调用。

### 4.3 服务层权限校验

`SkillVersionService` 必须集中实现以下校验，controller 不写业务判断：

1. 用户是否属于目标企业。
2. 企业是否对目标员工有 `ACTIVE` 订阅。
3. 当前用户是否有该订阅的有效 `EmployeeGrant`。
4. 企业版本的 `enterpriseId` 是否与上下文企业一致。
5. 当前状态是否允许编辑、提交、审核或选版。
6. 选中的版本是否属于同一个 capability，且不是未审核、驳回或归档版本。
7. 平台审核接口必须校验 `UserRole.ADMIN`，并记录 reviewer。

## 7. 验收标准

### 企业端

- 未订阅或未授权成员请求预览得到 403/404，不泄漏正文存在性。
- 已授权成员能在员工详情页看到技能列表、当前版本和审核状态。
- 预览支持渲染和源码两种视图，内容只包含 Markdown 正文。
- 企业成员能 Fork 并保存草稿；不能修改原始平台版本。
- 企业管理员审核通过后，企业可以将版本选为某个订阅员工的生效版本。
- 员工 A 和员工 B，或企业 A 和企业 B，可以同时选择同一技能的不同已审核版本。
- 平台发布新版不会自动覆盖企业当前选择；企业能看见升级提示并手动切换。

### 平台端

- 运营管理员能按状态查看企业提交版本，查看正文、父版本和审核历史。
- 平台管理员通过后，版本进入平台可选列表；驳回必须有原因。
- 企业私有版本未提交平台或平台驳回时，不出现在其他企业候选列表。
- 公开能力详情不会返回完整技能正文。

### 工程质量

- `pnpm --filter backend test` 通过。
- `pnpm --filter web test` 通过。
- `pnpm build` 通过。
- Prisma migration 可在空库和已有 `SkillConfig` 数据库上执行。
- 预览正文不使用不安全 HTML 注入；敏感字段不存在于响应 JSON。

以下不纳入本期，但模型已预留扩展方向：

## 9. 待实现前最终确认的两项策略

本方案按以下默认策略落地：

1. 企业私有版本企业审核通过即可在本企业生效，提交平台属于可选升级路径；平台审核只决定是否公开进入平台版本池。
2. 平台初始版本沿用现有 `Capability.status` 作为迁移依据，后续版本以 `SkillVersion.status` 为唯一审核状态来源。

如果产品决定改为“企业版本无论私有还是公开都必须平台审核后才能使用”，只需调整 Task 3/4 的状态转移和选版校验，不改变前端入口和数据隔离模型。
