# 认证中心一步到位开发计划

> 日期：2026-09-24
> 状态：分阶段开发中（P5-5 已完成；真实环境联调待执行）
> 适用范围：Web 端、桌面客户端、企业邀请、邮箱密码、忘记密码、邮箱验证、国内第三方登录、会话安全中心
> 目标：在正式上线前整体重构认证系统，不采用“先补一个页面、以后再修底层”的渐进式方案

---

## 一、执行结论

本次认证功能不再基于旧 `AuthService` 做局部补丁，而是以“完整认证中心”作为一个大版本整体实现。

### 1. 技术路线

```text
保留现有 User / Enterprise / EnterpriseMember 业务模型
                    ↓
整体重写 AuthModule
                    ↓
新增 Credential / Identity / Session / Token / Audit 模型
                    ↓
统一 Web 与桌面端会话体系
                    ↓
一次完成密码、邮件、会话、国内第三方登录、安全中心
```

### 2. 不直接引入完整认证框架

本次不直接把 Better Auth、Auth.js 或 Keycloak 嵌入现有系统：

- Better Auth 的 Session、密码重置、OAuth 和 Prisma 建模值得借鉴，但它自带 `User / Session / Account / Verification` 认证模型，与当前 `User / Enterprise / EnterpriseMember / Device` 体系存在重叠。
- Auth.js 更适合 Next.js 应用直接承载认证，不适合作为当前 NestJS 后端、Web 前端、桌面端共用的认证中心。
- Keycloak 适合未来做企业 SSO、OIDC、SAML、LDAP 和多应用身份中心；当前引入会额外增加独立服务、用户映射和运维成本。

最终方案：

```text
自研 AuthModule
+ 借鉴 Better Auth 的会话和身份模型
+ 按 OAuth 2.0 / OIDC 标准接入第三方
+ 按 OWASP 认证安全规范实现
```

### 3. 国内第三方登录优先级

用户主要面向国内，因此不把 Google、GitHub 作为第一批功能。

| 优先级 | Provider | 主要场景 | 计划 |
|---|---|---|---|
| P0 | 微信网页登录 | 普通用户在电脑浏览器扫码登录 | 第一批实现 |
| P1 | QQ 登录 | 普通互联网用户补充登录入口 | 第一批实现或紧随其后 |
| P2 | 支付宝登录 | 有支付宝用户基础、需要补充国内登录方式时 | 预留接口，第二批实现 |
| P2 | 飞书登录 | 企业客户、企业成员、企业 SSO | 企业客户确认需求后实现 |
| P2 | 钉钉登录 | 国内企业客户、组织身份认证 | 企业客户确认需求后实现 |
| P3 | 企业微信 | 企业微信生态或客户明确要求 | 后续扩展 |
| P3 | Google / GitHub / Microsoft | 海外用户或开发者客户 | 不作为国内版本首批目标 |

微信、QQ、支付宝、飞书、钉钉的开放平台产品、审核要求、回调限制和可获取用户字段可能随平台政策调整，实际接入时必须以对应开放平台当前控制台和官方文档为准。

## 二、现有系统审查结论

### 2.1 当前已经具备的能力

当前项目已经具备以下基础：

- `POST /auth/login` 邮箱密码登录；
- `POST /auth/register` 企业自助注册；
- `POST /auth/register-by-invitation` 邀请注册；
- 已登录用户接受企业邀请；
- 企业创建；
- JWT Access Token；
- httpOnly Cookie Refresh Token；
- 前端 Access Token 仅保存在内存/Zustand；
- 登录和注册接口限流；
- CSRF 防护；
- JWT Guard；
- bcrypt 密码 Hash；
- 桌面客户端独立登录和设备记录。

### 2.2 必须整体替换的问题

#### P0：Refresh Token 无数据库会话

当前 Refresh Token 是无状态 JWT，服务器不能主动撤销单个会话，也没有登录设备列表。

必须改为：

```text
随机 Refresh Token
        ↓
数据库保存 tokenHash
        ↓
每次刷新轮换
        ↓
旧 Token 标记 revoked
```

#### P0：Refresh Token 不轮换

当前刷新只生成新的 Access Token，不废弃旧 Refresh Token，也没有 Token Reuse Detection。

必须实现：

- Refresh Token Rotation；
- Session Family；
- Token 重放检测；
- 重放后撤销整个 Session Family；
- 记录安全审计事件。

#### P0：Access / Refresh 使用同一 JWT Secret

必须拆分：

```env
ACCESS_JWT_SECRET=
REFRESH_TOKEN_PEPPER=
```

JWT Strategy 必须明确拒绝 `type !== access` 的 Token。

#### P0：没有密码重置和邮箱验证

必须一次性完成：

- 忘记密码；
- 密码重置；
- 邮箱验证；
- 邮箱变更确认；
- 重置后会话撤销；
- 邮箱不存在时统一响应。

#### P1：User 表直接存 password

新设计将密码移至 `AuthCredential`，支持：

- 密码登录；
- 未来第三方账号无密码登录；
- 未来 Passkey / MFA；
- 账号绑定多种认证方式。

#### P1：Web 与桌面端会话分裂

统一使用 `AuthSession`，但保留不同传输方式：

```text
Web     → httpOnly Cookie 保存 Refresh Token
Desktop → 安全存储 Refresh Token，并通过响应体返回
```

#### P1：企业管理员代设员工密码

当前企业成员创建存在管理员直接提供初始密码的路径。新设计改为：

```text
管理员填写邮箱
    ↓
发送企业邀请
    ↓
被邀请人自行设置密码或使用第三方登录
    ↓
完成入职
```

管理员不再接触员工密码。

## 三、目标架构

```text
User（业务用户身份）
├── AuthCredential       密码等本地认证凭据
├── AuthIdentity         微信、QQ、支付宝、飞书等第三方身份
├── AuthSession          Web/桌面端登录会话
├── AuthDevice           浏览器/桌面设备信息
├── AuthToken            密码重置、邮箱验证等一次性 Token
└── AuthEvent            登录、退出、绑定、重置等审计事件

Enterprise（企业业务）
└── EnterpriseMember     企业成员和企业角色
```

### 3.1 认证与授权边界

认证只回答：

```text
用户是谁？
通过什么方式登录？
当前登录设备是什么？
会话是否仍然有效？
```

授权回答：

```text
用户属于哪个企业？
用户在企业内是什么角色？
用户能不能访问某个员工、能力或资源？
```

认证模块不直接决定企业业务权限，企业权限继续由现有 `EnterpriseMember`、角色和业务 Guard 负责。

### 4.2 AuthCredential


## 五、优先级开发路线

本节是本次实际开发顺序。虽然最终目标是一次性完整上线，但仍需要按照依赖关系推进，否则数据库、前端和第三方回调会互相阻塞。

## P0：认证底座与协议切换

### P0-1. 重写认证领域服务

新增或重构：

```text
backend/src/modules/auth/auth.module.ts
backend/src/modules/auth/auth.controller.ts
backend/src/modules/auth/auth.service.ts
backend/src/modules/auth/password-auth.service.ts
backend/src/modules/auth/session.service.ts
backend/src/modules/auth/auth-token.service.ts
backend/src/modules/auth/auth-audit.service.ts
backend/src/modules/auth/auth-risk.service.ts
```

要求：

- Controller 只负责 HTTP、Swagger、DTO 和 Cookie；
- 业务逻辑全部进入 Service；
- 所有请求使用共享 Zod Schema；
- 所有异常使用 Nest HTTP Exception；
- 所有数据库访问使用 `PrismaService`；
- 不在 Controller 内直接操作 Prisma；
- 所有认证接口补齐 Swagger 描述。

### P0-2. Access Token / Refresh Token 分离

目标配置：

```env
ACCESS_JWT_SECRET=
ACCESS_TOKEN_EXPIRES_IN=15m
REFRESH_TOKEN_EXPIRES_IN=7d
REFRESH_TOKEN_PEPPER=
REFRESH_COOKIE_NAME=__Host-sep_refresh
```

建议策略：

- Access Token：短期 JWT，默认 15 分钟；
- Refresh Token：随机 32 字节以上，数据库只保存 Hash；
- Refresh Token 每次使用后轮换；
- Web Refresh Token 通过 httpOnly、Secure、SameSite=Lax Cookie 传输；
- Desktop Refresh Token 通过响应体返回，并要求客户端存入系统安全存储；
- JWT Strategy 明确拒绝 Refresh Token；
- Access Token 载荷包含 `sub`、`sid`、`type`、`role`，不包含敏感信息。

### P0-3. 统一 Session 服务

必须提供以下服务方法：

```ts
createSession(input)
rotateRefreshToken(input)
revokeSession(sessionId, reason)
revokeSessionFamily(sessionFamilyId, reason)
revokeAllUserSessions(userId, reason)
listUserSessions(userId)
validateRefreshToken(token, clientType)
```

### P0-4. 兼容 Web 与 Desktop

Web：

```text
POST /auth/login
POST /auth/refresh
POST /auth/logout
```

Desktop：

```text
POST /client/auth/login
POST /client/auth/refresh
POST /client/auth/logout
```

两个入口调用同一个 `SessionService`，只允许以下差异：

- Cookie 或响应体传递 Refresh Token；
- `clientType`；
- Desktop 额外要求设备指纹和平台信息。

### P0 验收标准

- 登录后能创建 AuthSession；
- Refresh 后旧 Refresh Token 不能再次使用；
- 重放旧 Token 能触发 Session Family 撤销；
- Web 和 Desktop 都能刷新成功；
- 退出当前设备不会影响其他设备；
- 退出全部设备后所有 Refresh Token 失效；
- JWT Strategy 不接受 Refresh Token；
- Access Token 过期后前端能自动刷新；
- 现有企业登录跳转、角色和企业信息不丢失。

## P1：密码、邮箱和账户恢复

### P1-1. 注册流程重做

保留现有两个业务入口：

```text
企业自助注册
企业邀请注册
```

但内部统一调用：

```text
createUser()
createPasswordCredential()
createInitialSession()
```

企业注册的事务边界仍然保持：

```text
User
+ AuthCredential
+ Enterprise
+ EnterpriseMember
+ ComputeAccount
```

必须同时成功或同时失败。

### P1-2. 密码重置

接口：

```text
POST /auth/password/forgot
POST /auth/password/reset
POST /auth/password/change
```

流程：

```text
输入邮箱
    ↓
统一返回成功提示
    ↓
如果用户存在，创建 PASSWORD_RESET Token
    ↓
发送邮件
    ↓
用户提交 Token + 新密码
    ↓
验证 Hash、用途、过期时间、消费状态
    ↓
更新 Credential
    ↓
撤销全部旧 Session
    ↓
记录审计事件
    ↓
返回登录页，不自动登录
```

安全要求：

- 不暴露邮箱是否存在；
- Token 只保存 Hash；
- Token 只能使用一次；
- 有效期 15～30 分钟；
- 同一账号旧 Token 作废；
- 按邮箱和 IP 限流；
- 重置成功后撤销全部会话；
- 不在日志、错误信息和前端埋点中输出 Token。

### P1-3. 邮箱验证

接口：

```text
POST /auth/email/verification/request
POST /auth/email/verification/confirm
```

策略：

- 旧用户迁移后默认不强制阻断登录；
- 新注册用户显示“待验证”状态；
- 企业邀请用户在完成邀请时要求验证；
- 密码重置和修改邮箱必须要求邮箱验证；
- 未来可以通过配置决定是否强制验证后才能使用平台。

### P1-4. 修改密码

登录后：

```text
POST /auth/password/change
```

默认策略：

- 当前会话保留；
- 其他会话全部撤销；
- 记录 `PASSWORD_CHANGED`；
- 发送密码修改成功通知邮件。

### P1-5. 邮件服务

新增抽象：

```text
MailService
MailTemplateService
MailDeliveryProvider
```

第一版使用 SMTP 配置：

```env
MAIL_ENABLED=false
MAIL_HOST=
MAIL_PORT=587
MAIL_SECURE=false
MAIL_USER=
MAIL_PASSWORD=
MAIL_FROM=
MAIL_FROM_NAME=硅基人才平台
WEB_BASE_URL=
```

邮件模板：

```text
password-reset
email-verification
password-changed
new-device-login
enterprise-invitation
```

开发环境允许使用 Console Mail Provider，只输出脱敏后的测试链接；测试和生产环境必须禁止把真实 Token 写入日志。

### P1 验收标准

- 用户能通过邮箱完成忘记密码；
- 不存在的邮箱和存在的邮箱响应一致；
- 重置链接过期后不可用；
- 重置链接使用一次后不可再次使用；
- 重置密码后全部旧设备失效；
- 邮箱验证后 `emailVerifiedAt` 正确写入；
- 管理员创建员工时不再直接设置员工密码；
- 邀请用户可以在设置密码后加入企业。

## P2：国内第三方登录

### P2-1. Provider 抽象

```ts
interface OAuthProviderAdapter {
  readonly id: string;
  readonly displayName: string;
  readonly type: 'oauth2' | 'oidc' | 'wechat-qr';

  buildAuthorizationUrl(input: OAuthStartInput): Promise<string>;
  exchangeCode(input: OAuthCallbackInput): Promise<OAuthTokenSet>;
  fetchUserProfile(tokens: OAuthTokenSet): Promise<NormalizedOAuthProfile>;
  revoke?(tokens: OAuthTokenSet): Promise<void>;
}
```

统一输出：

```ts
interface NormalizedOAuthProfile {
  provider: string;
  providerAccountId: string;
  email: string | null;
  name: string | null;
  avatar: string | null;
  rawProfile: unknown;
  emailVerified: boolean | null;
}
```

### P2-2. 微信登录

#### 首批目标

先做**网站端微信扫码登录**：

```text
用户点击“微信登录”
        ↓
后端创建 OAuth Transaction
        ↓
生成 state / nonce / 过期时间
        ↓
返回微信授权地址或二维码数据
        ↓
用户扫码确认
        ↓
微信回调后端
        ↓
后端换取用户身份
        ↓
匹配 AuthIdentity(provider=wechat)
        ↓
创建新的 AuthSession
        ↓
回到前端完成登录
```

#### 必须处理

- state 防 CSRF；
- 回调超时；
- 用户取消授权；
- 二维码过期；
- 重复回调；
- 微信身份已绑定其他 User；
- 微信邮箱通常不可作为唯一可靠的账号合并依据；
- 新用户是否直接创建个人账号，或必须通过邀请完成注册；
- 微信昵称和头像只作为初始资料，不作为业务权限依据。

#### 账号策略

普通微信扫码用户：

```text
首次登录 → 创建 User + AuthIdentity
```

企业邀请用户：

```text
先打开邀请链接 → 使用微信登录 → 绑定到邀请邮箱/邀请记录 → 加入企业
```

如果微信身份与已有邮箱账号无法自动确认归属，必须要求用户先登录原账号再绑定，不允许静默合并。

### P2-3. QQ 登录

QQ 登录使用独立 Provider Adapter，不复用微信字段。

核心流程与 OAuth 登录相同：

```text
QQ 授权
  ↓
回调 code
  ↓
换取 access token / open identity
  ↓
获取 QQ 用户资料
  ↓
保存 provider=qq 的 AuthIdentity
  ↓
创建 AuthSession
```

必须以 QQ 互联开放平台当前要求为准，确认：

- Web 网站应用是否具备登录权限；
- 回调地址格式；
- `openid` 或等价唯一身份字段；
- 昵称、头像字段可用范围；
- 应用审核和上线限制；
- 是否需要 HTTPS 公网回调。

### P2-4. 支付宝登录

支付宝登录暂不作为首批阻塞项，但 Provider 抽象必须预留：

```text
provider = alipay
```

项目已有支付宝开放平台接入经验，后续可以复用现有配置管理和密钥保护方式，但登录凭证、授权范围和支付凭证必须分开管理，不能混用支付模块配置。

支付宝开放平台支持网页和移动应用接入，并提供快速登录等能力；具体权限和审核以当前开放平台应用配置为准。

### P2-5. 飞书 / 钉钉

这两个 Provider 更适合企业客户，不与微信/QQ的普通用户登录混为一谈。

后续目标：

```text
企业管理员绑定企业身份源
        ↓
企业成员使用飞书/钉钉登录
        ↓
通过租户、企业 ID 或邀请关系匹配 Enterprise
        ↓
创建用户并加入对应企业
```

需要额外设计：

- 企业租户绑定；
- 企业管理员授权；
- 企业 ID 映射；
- 成员离职后的权限回收；
- 企业级 SSO 登录；
- 同一第三方身份是否允许加入多个 Enterprise。

本次先完成 Provider 抽象和 `AuthIdentity` 模型，不把飞书/钉钉实现作为微信/QQ上线的阻塞项。

### P2 验收标准

- 微信扫码登录完整成功；
- QQ 登录完整成功；
- 首次第三方登录能创建账号；
- 已绑定身份能直接登录；
- 已有邮箱账号不能被第三方邮箱静默接管；
- 第三方账号可以在安全中心绑定和解绑；
- 至少保留一种可用登录方式时才允许解绑；
- OAuth state、nonce、回调过期和重复回调均有测试；
- 第三方登录产生统一的 AuthSession 和 AuthEvent；
- 第三方登录后仍能正确进入企业工作台。

## 六、API 契约

### 6.1 基础认证

```text
POST /auth/register
POST /auth/register-by-invitation
POST /auth/login
POST /auth/refresh
POST /auth/logout
POST /auth/logout-all
GET  /auth/me
```

建议把旧的：

```text
GET /auth/refresh
```

改为：

```text
POST /auth/refresh
```

因为 Refresh 会产生状态变化和 Token 轮换，不应继续使用 GET 表达。

### 6.2 密码和邮箱

```text
POST /auth/password/forgot
POST /auth/password/reset
POST /auth/password/change
POST /auth/email/verification/request
POST /auth/email/verification/confirm
POST /auth/email/change/request
POST /auth/email/change/confirm
```

### 6.3 Session

```text
GET    /auth/sessions
DELETE /auth/sessions/:id
POST   /auth/sessions/revoke-all
```

### 6.4 OAuth

```text
GET  /auth/oauth/:provider/start
GET  /auth/oauth/:provider/callback
GET  /auth/oauth/:provider/status
POST /auth/oauth/:provider/link
DELETE /auth/oauth/:provider/unlink
```

微信扫码如果最终采用二维码轮询，应额外提供：

```text
POST /auth/oauth/wechat/transaction
GET  /auth/oauth/wechat/transaction/:id
```

轮询接口只返回：

```text
PENDING
SCANNED
CONFIRMED
EXPIRED
FAILED
```

不能把第三方 access token 返回给前端。

### 6.5 返回结构

现有 `AuthResponse` 中的企业信息需要保留兼容：

```ts
interface AuthResponse {
  token: string;
  user: UserSummary;
  enterprise: EnterpriseSummary | null;
  roleInEnterprise: string | null;
}
```

可以新增：

```ts
interface AuthSessionSummary {
  id: string;
  clientType: 'WEB' | 'DESKTOP' | 'MOBILE';
  deviceLabel: string | null;
  platform: string | null;
  lastSeenAt: string | null;
  createdAt: string;
  isCurrent: boolean;
}
```

第三方登录成功后也必须返回统一的 `AuthResponse`，不能单独设计一套前端用户结构。

## 十五、风险与决策记录

| 风险 | 影响 | 处理方式 |
|---|---|---|
| 微信/QQ开放平台审核时间 | 第三方登录无法立即上线 | 先完成 Provider 抽象和 Mock Provider，不阻塞认证底座 |
| 国内平台回调限制 | 本地无法完整联调 | 使用公网测试域名或隧道环境，生产必须 HTTPS |
| 用户身份字段不统一 | 账号合并错误 | 以 provider + providerAccountId 为唯一身份，不凭邮箱自动合并 |
| 桌面端协议变化 | 客户端需要同步升级 | 后端统一 Session，保留 Desktop 响应体 Refresh Token 方式 |
| 数据库模型改动大 | 旧代码编译失败 | 认证相关调用全部迁移完成后再删除旧字段 |
| 邮件服务未配置 | 忘记密码无法闭环 | 开发环境 Console Provider，测试/生产环境必须配置真实邮件 Provider |
| 管理员代设密码历史逻辑 | 企业邀请流程受影响 | 统一改为邀请链接和用户自行设置密码 |
| 旧 JWT 仍被接受 | 存在认证旁路 | 切换完成后拒绝旧 Refresh JWT，不保留隐式兼容 |
