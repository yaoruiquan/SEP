# Task Orchestration Center Implementation Plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** 将企业端任务中心从“会话列表”升级为面向目标的任务编排工作区，自动从已订阅硅基员工及其绑定能力中生成执行计划，并在执行时可视化展示员工、技能、步骤状态、进度和中间结果。

**Architecture:** 任务规划由后端真实调用 `SUB2API` 上的模型完成。后端先从当前企业的 ACTIVE 订阅读取员工和绑定能力目录，再通过 OpenAI-compatible `chat/completions` 请求要求模型返回 JSON 计划；服务端提取模型文本、使用 Zod 校验结构，并二次校验所有员工/能力 ID 后返回 `awaiting_confirmation` 计划。用户确认后，前端才按步骤复用现有 Conversation/SSE/Capability 执行链，并将运行状态保存在当前页面状态中。后续再把同一份计划/运行事件抽取为后端 `Task`、`TaskStep`、`TaskRun` 和 `TaskEvent` 持久化模型。

**Tech Stack:** Next.js 15 App Router, React, TanStack Query, existing `api` client, existing Conversation SSE stream, Tailwind/shadcn-style components, Vitest.

---

## Product decisions

- 默认流程为：描述任务 → 调用真实大模型生成计划 → 用户确认 → 执行。
- 不再要求用户先选择单个硅基员工；高级设置允许限制候选范围。
- 计划步骤必须显示：员工、技能、步骤说明、依赖关系、预计状态。
- 普通 `/conversations` 会话不属于任务中心，不在任务中心列表展示。
- 执行页必须显示：当前员工、当前技能、步骤时间线、进度、事件和中间输出。
- 任务中心仅展示由任务编排创建的任务；普通会话历史继续留在 `/conversations`，不在此处兼容展示。
- 本次不修改 Prisma schema；页面刷新后运行中的本地编排状态不保证恢复，文档中记录为后续风险。

## Cockpit UI refinement

- 桌面端采用固定高度的任务驾驶舱：左侧为紧凑执行流程，右侧为硅基员工工作台，页面本身不滚动。
- 任务历史收进抽屉，仅显示由任务编排创建的本地任务；普通会话不会进入任务中心。
- 流程节点展示步骤、前序依赖、员工头像、员工名称、技能以及候场、执行中、完成、失败状态。
- 员工工作台以真实运行状态驱动头像光圈、状态灯、技能调用和实时动作，不使用虚构百分比模拟执行。
- 完成后默认展示交付摘要；完整 Markdown 交付物通过独立 Dialog 阅读，只让报告内容区域滚动。
- 移动端使用“执行流程 / 员工工作台”分区切换，同一时间只显示一个主面板，避免流程与员工台上下堆叠造成页面滚动。
- 移动端空态与计划步骤使用双列紧凑布局；点击步骤会直接切换到对应员工工作台。
- 规划模型返回的 `estimatedSeconds` 在服务端归一化到最多 3600 秒，避免超长预估导致整份合法计划被拒绝。
