# 能力贡献中心（能力投稿中心）——Skill 与 RPA 投稿开发方案

> 日期：2026-09-24
> 状态：首轮内测闭环已完成，进入内测验证与后续迭代
> 本方案仅覆盖能力贡献中心，不扩展为完整的能力生产中心、数字员工编辑器或公共应用市场。

## 1. 结论先行

### 1.1 Skill 是独立能力资产，不是一个数字员工

一个 Skill 应创建为一项 `Capability(type = SKILL)`，由 `SkillVersion` 管理版本；一个 Skill 可以被多个 `DigitalEmployee` 通过 `EmployeeCapabilityBinding` 复用。Skill 投稿不应自动创建数字员工，也不应在投稿时强制选择唯一员工。

推荐关系：

```text
Skill 投稿 → Capability(SKILL) → SkillVersion(v1, v2...)
                                      ↑         ↑
                         数字员工 A ─┘         └─ 数字员工 B
```

数字员工是“岗位角色 + 系统指令 + 模型/权限 + 多项能力组合”的执行主体；Skill 是可被组合的能力模块。投稿后可由企业管理员/能力管理员决定在企业数字员工中采用，平台公开 Skill 则由平台运营或员工模板维护者决定默认绑定。后续可以在能力详情页增加“添加到员工”快捷操作，但不属于本轮投稿闭环的前置步骤。

RPA 同理，是 `Capability(type = RPA)` + `RPAConfig` 的独立能力资产。第一阶段审核通过后提供受控下载，不因上传 ZIP 就创建 RPA 执行员工或在平台云端运行。

### 1.2 审核采用“自动门禁 + 企业审核 + 平台审核”，按发布范围决定人工层级

建议状态流：

```text
草稿
  → 自动校验（失败则退回修改；安全高危项阻断）
  → 企业审核（企业私有投稿需要）
  → 可在企业范围使用
  → 申请公开投稿 + 企业授权
  → 平台审核
  → 公共发布、可检索/安装/下载
```

个人投稿没有企业归属时，可以跳过企业审核，但必须通过自动检查并由平台审核后才能进入公共库。对用户在自己的机器上“发现/导入”文件这件事，不需要平台审核；审核针对上传到平台、被企业/其他用户使用的资产。

**任何待审核或被拒绝版本不应被其他用户安装/下载，也不应被生产数字员工默认绑定。** 投稿人可在草稿或隔离预览中自测，是否允许内部试用应由企业策略控制，不能默认为“审核中即可全员可用”。

### 1.3 本地扫描不能由纯网页静默访问用户磁盘

浏览器无法安全地遍历 `~/.claude`、`~/.codex` 等任意目录。推荐“本地 SEP Client/CLI 扫描 + 用户确认 + 平台上传”；网页目录选择仅作为兼容导入方式，不能取代跨工具全盘发现。扫描器只读取技能目录与必要元数据，默认不执行 Skill 包里的脚本。

## 2. 背景与范围

9 月 23 日会议纪要确认：现状主要是 ZIP 上传，尚无从 Skill 库安装和本地一键导入；目标是把内部验证过的数字员工/技能变成可复用、开箱即用的产品，同时强调能力可迭代、来源和版本可追溯。会议也提出普通用户自行添加能力暂不急于开放。当前产品要求将能力贡献中心作为内测重点使用，因此本方案建议先向内测授权成员开放投稿能力，采用安全隔离和审核门禁，不等于向所有普通用户开放公共市场投稿。

### 本轮包含

- Skill：本地 Agent 工具目录扫描原型、浏览器目录导入、Skill ZIP 投稿；平台上的 Skill 包与版本管理、审核记录。
- RPA：用户上传 ZIP；平台安全校验、元数据登记、审核；审核通过后向授权用户提供下载。
- 投稿人工作台、审核工作台、状态通知、审计记录。
- 本地扫描器的统一清单格式与安全边界，为后续接入 SEP Client/CLI 做准备。

### 本轮已完成与未完成边界

- **已完成**：本地只读扫描器原型、浏览器目录选择兼容导入、Skill ZIP 投稿、RPA ZIP 投稿、自动静态校验、企业/平台审核和按范围下载鉴权。
- **尚未完成**：SEP Client/CLI 的正式“选择后上传”接入、Git 固定 commit 导入、npm/registry 来源安装或导入、公共 Skill 一键安装。
- 本轮不把“能扫描到本地 Skill”误认为“已经上传到平台”；只有用户明确选择并确认后才进入上传和审核流程。

### 本轮明确不做

- 不创建/编辑数字员工，不建设数字员工生产中心。
- 不在服务端执行用户上传 Skill/RPA 中的脚本、npm install、npx 或 RPA 流程。
- 不做 RPA 云端运行，不接管用户电脑执行。
- 不做复杂的能力交易、计费、排行榜或收益分成新规则（复用已有能力/奖励机制时另行核验）。
- 不承诺任意 Agent 工具的私有/非公开目录；首批支持工具以官方公开目录为准，其他目录允许用户手动添加。

## 3. 代码现状与方案复用点

### 已有

- 前端贡献中心：`web/src/features/contribution/`，支持贡献列表、详情、Skill ZIP/正文创建、审核状态看板和版本展示。
- 后端：`backend/src/modules/capability-contribution/`，已有创建、修改、提交企业审核、平台审核授权/审核、Skill 版本、包下载等接口。
- DTO：`backend/src/shared/index.ts`，当前贡献类型只允许 `agent | skill`；已有 Skill 包 sha256 与正文互斥校验。
- Skill 包服务：`backend/src/modules/skill-package/skill-package.service.ts`，校验 ZIP 魔数、20MB 压缩包上限、64MB 解压上限、500 个条目、SKILL.md 必须存在且不超过 500KB；路径校验、内容寻址 SHA-256 存储与服务端重新解析。
- 数据模型：`Capability` 已含 `SKILL/RPA` 类型、贡献者/企业归属、可见性、企业/平台审核状态、校验结果；`SkillVersion` 已支持范围、父子版本、包哈希、审核信息；`RPAConfig` 已有平台、执行模式、包地址/哈希/说明；`EmployeeCapabilityBinding` 已允许一个能力关联多个员工。

### 需要补齐

- 创建 DTO/交互暂未包含 RPA；现有 RPAConfig 不是面向投稿 ZIP 的完整、安全存储设计。
- 当前 Skill 包创建路径以 ZIP 上传或在线正文为主，缺少本地扫描清单、来源类型、原始仓库/包来源、扫描器版本和用户选择确认信息。
- 尚无平台提供给 SEP Client/CLI 的扫描会话、批量导入任务或安全的一次性上传凭证流程。
- 需要明确审查针对“资产首次发布”与“新版本发布”的关系。Skill 已有版本审核模型，建议所有修改形成新版本并重新审核，不覆盖已发布版本。
- 自动校验不是完整的恶意代码沙箱；需要将结构校验与内容风险提示分开，不夸大为“安全认证”。

> 以上结论来自当前代码结构核对；实现前仍需逐项核对权限守卫、服务层状态转换以及现有个人/企业 Skill 版本兼容逻辑，避免破坏存量行为。

## 4. Skill 生态与本地发现设计

### 4.1 目录规范与扫描策略

Agent Skills 生态以目录中包含 `SKILL.md` 为主要发现约定，但不同 Agent 工具还存在自身目录和作用域差异。Vercel `skills` CLI 的价值在于维护大量 Agent 的目录映射并统一安装/发现体验；可借鉴其“Agent catalog + project/global scope + 用户确认”的设计，不建议后端依赖或直接执行其安装命令。

建议本地扫描支持两类根目录：

- **用户级**：用户 home/config 目录下，跨项目可用。
- **项目级**：当前工作目录及其受信任子目录下，仅对该项目生效。

首批适配器目录（扫描规则应做成版本化配置，不散落硬编码）：

| 工具/生态 | 项目级常见目录 | 用户级常见目录/说明 | 备注 |
|---|---|---|---|
| Claude Code | `.claude/skills/<name>/SKILL.md` | `~/.claude/skills/<name>/SKILL.md` | 兼容 Agent Skills 目录型结构 |
| Codex CLI | 当前目录至仓库根目录沿途的 `.agents/skills/<name>/SKILL.md` | `$HOME/.agents/skills/<name>/SKILL.md`；管理员目录 `/etc/codex/skills` | 官方文档还说明支持符号链接；不要把 `~/.codex/skills` 当作跨版本公共规范 |
| Gemini CLI | `.gemini/skills/` 或 `.agents/skills/` | `~/.gemini/skills/` | 官方文档明确支持 `.agents/skills` alias；workspace 目录可能受 trust 状态限制 |
| OpenCode | `.opencode/skills/` 或 `.agents/skills/` | `~/.config/opencode/skills/` / Agent Skills 全局约定（按其当前文档确认） | 建议先支持其公开声明目录，后续兼容 |
| Cursor | `.cursor/rules/` 是官方 Rules 机制 | 暂不把 `.cursor/rules` 当成 Skill 目录 | Cursor 的 Rules 与 Agent Skills 不是同一资产类型；首批只做手动导入/标准 `SKILL.md` |
| Cline | 当前官方公开资料未确认统一的 `SKILL.md` 扫描目录 | 待官方规范或实际版本 fixture 确认 | 首批不自动扫描 `.cline` 全目录；可手动选择标准 Skill 文件夹 |
| 通用生态 | `.agents/skills/`、`skills/` | `~/.agents/skills/` 等 | 对标准目录递归深度有限扫描 |

**跨平台**：规则中使用 home 目录 API，而不是拼接固定盘符。Windows 基于 `%USERPROFILE%`、必要时 `%APPDATA%` / `%LOCALAPPDATA%`；macOS/Linux 基于 `$HOME`。项目相对目录用真实路径归一化，拒绝软链接逃逸出用户明确选择的扫描根目录。Windows 路径大小写不敏感、分隔符统一处理。

**识别规则**：发现候选 `SKILL.md` 后解析 frontmatter、展示名称/描述/目录/来源工具/最近修改时间/哈希/扫描警告；目录中有脚本或附件时只打包，不执行。对相同 sha256 去重，但保留不同安装位置供用户选择。

### 4.2 用户交互

1. 用户在 SEP Client/CLI 中点击“扫描本地 Skills”。
2. 首次展示扫描范围（用户级、当前项目级）并允许取消某些目录；不允许隐式扫描整个磁盘。
3. 显示扫描到的清单、工具来源、摘要、文件数、更新时间和风险提示；默认不勾选高风险项。
4. 用户勾选 Skills，逐项确认上传范围和平台可见性；绝不自动上传所有扫描结果。
5. 客户端只把选中目录打包，调用平台预检/上传；服务端重新解析、计算哈希、检查路径和内容。
6. 返回投稿草稿 ID、自动检查结果和后续审核状态。

浏览器兼容导入：允许用户通过系统目录选择器选取文件/目录，再按同一上传 API 提交；浏览器不声称能扫描工具配置，也不读取用户未选择的路径。

### 4.3 本地组件与跨平台方案

优先复用 SEP Client 的本地文件访问能力；如果当前客户端无法可靠提供文件系统 API，再交付独立 `sep` CLI。不要在本轮同时维护两个扫描器实现：统一提供共享扫描核心库/协议，客户端与 CLI 只做入口层。

建议 CLI 命令形态：

```bash
sep skill scan [--scope user|project|all] [--agent claude,codex]
sep skill list
sep skill inspect <local-id>
sep skill publish <local-id> [--visibility enterprise|public]
```

CLI 扫描/打包在本机；平台服务端不执行外部命令。认证复用 SEP Client 登录会话或短时、单用途上传凭证，禁止把长期 Access Token 写入命令行参数、shell history 或日志。

### 4.4 CLI / 包管理器来源

用户提到的“npm/其他包管理器安装别人上传的 Skills”需要区分：

- **外部来源导入/发布**：投稿人从 Git 仓库、受支持的 Skill registry 或本地 npm 安装目录取得 Skill，然后选择导入平台；
- **从 SEP 平台安装**：其他用户从平台获取已审核版本，客户端按 Agent 目标目录安装；这是消费端能力，可以在贡献中心先定义接口，但不把完整包管理生态作为本轮核心。

建议第一阶段支持：本地扫描、上传 ZIP、导入公开 Git 仓库 Skill（由本地 CLI 下载并确认后上传）。暂不在服务端运行 `npm install` / `npx`。npm 包支持放到后续迭代，前提是明确包名/版本锁定、来源白名单、许可证和依赖供应链扫描。公共平台返回不可变版本 ID + sha256，CLI 安装前验证哈希，并支持安装到指定 Agent/项目/用户作用域。

## 5. RPA 投稿与下载

### 5.1 投稿表单

- 名称、用途说明、适用业务/平台（如实在、影刀、其他）、版本号、入口/启动说明、环境依赖、权限需求、作者、许可证、隐私/数据说明。
- 一个 ZIP 对应一个不可变版本；更改包必须创建新版本。
- 第一阶段执行模式固定为 `DOWNLOAD`，禁止上传后自动执行。现有 `CLOUD/CLIENT` 枚举不代表本轮已支持这些运行方式。
- 上传前需确认用户拥有投稿/再分发权利，不含客户个人数据、账号凭证、Cookie、企业秘密。

### 5.2 上传校验

复用 Skill 包服务可验证的通用 ZIP 防护原则，但 RPA 使用独立配置和策略：文件类型、压缩/解压上限、条目数、压缩炸弹、路径穿越、软链接、重复路径、宏/可执行文件及已知恶意特征检查、秘密扫描、SHA-256。列出入口文件与文件清单供审核人查看。默认禁止包内凭据和个人数据；检测到疑似密钥时隔离并阻断自动发布。

RPA 二进制/脚本静态扫描的覆盖能力有限，报告必须表述“自动检查未发现已知问题”，不能表述“无恶意代码/安全保证”。

### 5.3 下载控制

- 只允许下载审核通过且当前仍发布的版本。
- 私有能力按企业成员和能力权限鉴权；公共能力按平台策略开放。
- 下载由 API 签发短时对象存储 URL 或流式代理，记录下载者、版本、sha256、时间和来源 IP（遵守隐私策略）。
- 详情页提示目标 RPA 客户端版本、依赖、权限、风险等级和免责声明；展示 SHA-256，客户端下载后可校验。
- 撤下/安全事件后立即停止签发新下载链接；已有短时 URL 到期失效。

## 6. 审核机制与权限

### 6.1 适用范围与角色

| 角色 | 能力 |
|---|---|
| 投稿人 | 创建草稿、上传新版本、查看自己的检查/审核记录、按意见修改重提 |
| 企业管理员/能力审核员 | 审核本企业私有能力；授权本企业能力向平台公开投稿 |
| 平台运营审核员 | 审核公共发布、版本升级、下架与复核 |
| 平台安全管理员 | 处理高危扫描结果、恶意文件举报和紧急隔离；与普通运营审核尽量职责分离 |
| 普通使用者 | 仅浏览/下载或安装已获授权且已发布的版本 |

授权依据企业成员角色和现有守卫；不能仅凭前端隐藏按钮实现权限控制。

### 6.2 自动门禁

**阻断项**（不可提交人工审核）：ZIP 无效、超限、路径穿越/越界链接、缺少必要入口、哈希复核不一致、损坏文件、恶意特征命中、明文凭据/私钥命中、许可证/作者必填项缺失、必需元数据不可解析。

**警告项**（进入人工审核，要求 reviewer 明确确认）：shell/PowerShell/JS/Python 执行脚本、sudo/管理员权限、联网下载、外部域名、浏览器 Cookie/账号操作、混淆/二进制、未锁定依赖、缺少许可证、含宏文件。

自动扫描结果须包含规则版本、扫描器版本、扫描时间、错误/警告清单和被扫描包 sha256；同一版本内容一旦改变就必须重新扫描。

### 6.3 企业与平台审核

- 企业私有投稿：自动门禁通过 → 企业审核 → 企业范围可使用/下载。
- 公共投稿：自动门禁通过 → 企业管理员授权（若企业归属）→ 平台审核 → 公共发布。
- 个人投稿：自动门禁通过 → 平台审核 → 公共发布。
- 企业投稿人不能自己批准自己的投稿；平台投稿人不能自己执行平台审核。小团队可配置替补审核人，但保留操作者记录。
- 审核表必须显示清单、源代码/文本预览、哈希、自动扫描结果、权限说明、版本差异和许可证；拒绝需给可操作原因，支持修正重提。
- 每次审核决策记录 reviewer、决策、时间、理由、资产版本/hash、审核范围；不得只覆写状态而丢历史。
- 重新提交或新版本更新：新的审核实例；当前已发布版本继续可用，直到新版本通过后由作者/管理员切换；安全紧急事件可以撤销旧版本下载/绑定。

### 6.4 与现有状态兼容

当前 `Capability` 已有企业审核与平台审核字段，但对投稿来源、扫描批次、完整审核历史和 RPA 版本包还不够明确。实现时先审查现有状态机与 `SkillVersionStatus`，优先复用可复用状态；不建议把所有来源塞入 `metadata` JSON，也不建议仅以单个 Capability 状态表达多个版本的审核。

建议：

- Skill 首次发布/后续版本审核以 `SkillVersion` 为版本事实源；能力级字段仅表示目录条目/当前发布状态。
- RPA 增加版本实体（建议 `RpaVersion`，或在确认现有通用版本模型后统一抽象），保存包 key、sha256、文件清单、版本号、校验报告、审核时间和发布状态。
- 增加结构化来源字段/关联记录：`LOCAL_SCAN | GIT_REPOSITORY | REGISTRY | ZIP_UPLOAD`、来源 URL/提交 SHA、扫描器 Agent/版本、导入时间。不要保存本地绝对路径（除非用户明确选择，仅用于本次客户端 UI）。
- 增加审核事件表，或确认现有 `SkillVersionReview` 是否能覆盖 Capability/RPA 审核；要求完整、不可变审计历史。

数据库设计定稿后再写 Prisma schema/migration；遵守先 migrate 再 generate 的项目流程，不手写历史迁移。

## 7. 建议 API（草案）

沿用 `/contributions` 领域和现有 DTO/Zod 验证风格；最终路由需结合当前 Controller 守卫、文件上传中间件和对象存储能力定稿。

### 客户端发现与导入

平台 API 不负责扫描本机，只接收扫描清单和已选包：

```text
POST /contributions/import-sessions
POST /contributions/import-sessions/:id/items       # 清单元数据/用户选择
POST /contributions/import-sessions/:id/packages   # 上传选中包，服务端重扫
POST /contributions/import-sessions/:id/commit     # 创建投稿草稿
GET  /contributions/import-sessions/:id
```

如果实现一次性预签名上传，则令牌必须单文件/单哈希/短期/单用途，服务端回调后仍需验证实际字节。

### 投稿与审核

```text
POST /contributions                         # 类型支持 SKILL/RPA
POST /contributions/:id/versions            # 创建 Skill/RPA 新版本
POST /contributions/:id/submit              # 触发门禁并进入对应审核
GET  /contributions/:id/reviews             # 查看审核时间线
POST /admin/contributions/:id/reviews       # 审核人提交结构化决策
POST /contributions/:id/platform-authorization # 企业管理员公开投稿授权
```

现有 `/submit-enterprise-review`、`/enterprise-review`、`/platform-review` 等端点若继续保留，应通过兼容层逐步收敛，避免同一审核被多套状态接口表达。

### 公共消费（边界接口）

```text
GET  /capabilities/:id/versions/:versionId/package
GET  /capabilities/:id/versions/:versionId/download-url
POST /client/skills/install-manifest
```

本轮以已存在的投稿包下载能力为基础补 RPA 下载鉴权；从市场检索/一键安装完整闭环可单列后续范围。

所有接口：JWT 守卫、用户从 `req.user` 获取、共享 Zod DTO、Swagger 描述、服务层执行业务规则。不要接收客户端自报的 reviewer/企业身份，不把原始 request body 传给 service。

## 8. 前端交互建议

贡献中心首页提供两个主入口：

1. **投稿 Skill**：`扫描本机`、`导入 Git/Skill 来源`、`上传 ZIP` 三个来源；强调“扫描仅在你的设备执行，选择后才上传”。
2. **投稿 RPA**：上传 ZIP、填写平台/用途/依赖/风险说明，明确审核后可下载，不在云端运行。

“我的投稿”卡片需区分：草稿、自动检查中、需修复、企业待审、平台待审、已发布、被拒绝、已下架。详情页显示版本、sha256、来源、文件清单、检查报告、审核意见和历史事件。

审核工作台按待办队列组织：高危/阻断报告优先；分开呈现 Skill 与 RPA 预览；审核动作提供通过、拒绝并退回、要求补充材料、下架/隔离。所有动作有确认和理由。

内测默认展示操作引导和“不会自动执行上传包内容”的安全提示。不要把“已上传”视觉上做成“已发布”。

## 9. 分阶段实施建议

### Phase 0：状态机和安全设计定稿

- 核验现有企业/平台审核、SkillVersion 审核、访问控制、文件存储与下载实现。
- 决定个人投稿和企业投稿策略、内测权限名单、审核 SLA。
- 明确 RPA 格式、平台和首期包体限制。

### Phase 1：Skill 投稿闭环（贡献中心重点）

- 前端 Skill 投稿入口与来源类型。
- 本地扫描器支持 SEP Client/CLI 的一个统一核心；首批适配 Claude Code、Codex、Gemini CLI、通用 `.agents/skills` 等经官方核验的目录。
- 选中后 ZIP 打包上传、服务端重新校验、创建草稿、审核状态可见。
- Git 来源由本地客户端下载固定 commit 后确认上传；不在服务端执行用户命令。
- 测试 macOS、Windows、Linux 路径和文件名/软链接边界。

### Phase 2：RPA ZIP 投稿和审核后下载

- RPA 创建 DTO、上传/解析/内容寻址存储、版本、校验报告。
- 企业/平台审核队列和下载权限。
- 负向测试覆盖 ZIP 越界、压缩炸弹、凭据、超限、未审核下载拒绝。

### Phase 3：内测质量与安装体验

- 审核通知、投稿修正/重提、版本差异、下载审计。
- SEP Client/CLI 对已发布 Skill 的平台下载、哈希校验、安装到目标 Agent 目录（另立执行任务，不与本轮审核 API 混写）。
- 收集审核耗时、拒绝原因、重复能力、下载成功率及问题反馈。

## 10. 测试计划与验收标准

### 功能验收

- 本地扫描支持用户级/项目级目录，列表清楚显示来源；用户未勾选时不上传任何 Skill。
- 相同 Skill 多 Agent 安装位置可去重展示；编辑源文件后哈希变化，形成新版本而不是覆盖已发布版本。
- Git 导入固定到 commit/hash，并由本机完成获取；服务端没有执行 npm/npx/bash/git 用户命令。
- RPA ZIP 上传后产生不可变版本和 SHA-256；审核通过后授权用户能下载，待审/拒绝/下架版本不能获取包。
- Skill/RPA 都不自动创建 DigitalEmployee；一个能力可被多个员工绑定（但绑定操作不作为投稿必要步骤）。
- 企业审核和平台审核权限正确，投稿人不能自审；所有决策有可追溯历史。

### 安全验收

- ZIP 路径穿越、软链接越界、压缩炸弹、超限/超文件数、伪造扩展名、损坏归档均被拒绝或隔离。
- 对 Skill/RPA 包执行密钥特征扫描；只返回文件路径/类别，不在普通日志或错误信息中泄露密钥原文。
- 包解析/扫描使用资源上限，超时可取消；上传 API 限速、大小限制和鉴权。
- 短期下载地址不可重用/不可访问未发布版本；下载审计不记录敏感文件内容。

### 工程验证

- 共享 DTO/Zod 单元测试、能力贡献 Service 状态转换测试、ZIP 服务安全测试、controller HTTP 测试。
- 前端投稿流程组件测试、审核状态/权限渲染测试。
- 客户端扫描器对三操作系统目录 fixture 的单元测试；真实 macOS/Windows/Linux 手工 smoke。
- 全程不连接真实 DB 的后端单测遵循项目规范；schema 变化再执行项目规定的迁移和生成流程。

## 11. 主要风险与控制

| 风险 | 控制 |
|---|---|
| Skill/RPA 包中存在可执行恶意脚本 | 投稿包只做静态扫描与安全预览；不在平台执行；高危项人工复核；用户安装前警告 |
| 自动扫描本地文件引发隐私担忧 | 明确范围、用户主动触发、逐项勾选、仅上传选中内容、不传绝对本地路径 |
| 各 Agent 路径/规范变动 | Adapter catalog 带版本和测试样本；目录规则更新独立发布；未知目录允许手动选择 |
| npm 供应链风险 | 第一阶段不在服务端运行 npm/npx；客户端导入固定版本/commit；后续再做包签名/锁文件/来源策略 |
| 已发布版本更新破坏用户员工 | 新版本单独审核，保留已发布版本；默认不自动升级绑定版本 |
| “审核通过”被误解为绝对安全 | UI明确审核范围与扫描限制；安全事件支持隔离/撤下和通知 |
| 会议旧决议与内测开放范围不同 | 内测先限授权账号；普通大众投稿开放另行决策，避免扩大权限面 |

## 12. 待产品决策（建议默认值）

| 决策 | 建议默认值 |
|---|---|
| 内测投稿人范围 | 内测企业成员 + 指定平台内部用户；不对所有注册用户开放 |
| 企业私有投稿通过后 | 企业内可见/下载；是否直接可绑定员工须企业策略，建议默认管理员显式启用 |
| 投稿人自测 | 允许在个人隔离预览中检查，不让待审版本成为生产员工默认能力 |
| RPA 首期运行模式 | 仅 `DOWNLOAD`，平台不执行 |
| 公共 Skill 下载/安装 | 先提供版本包下载/API；SEP CLI 安装列 Phase 3 |
| 本地扫描实现 | 优先 SEP Client；缺文件系统能力才独立 CLI，共享扫描核心 |
| 外部来源 | 第一阶段本地目录、ZIP、固定 Git commit；npm registry 后续 |
| Skill 与员工关系 | 一对多复用；投稿时不强制选择员工；能力详情页“添加到员工”后续增加 |
| 能否快速公开 | 否；自动检查通过也需对应范围的人工审核 |

## 9. 2026-09-24 首轮实现记录

已落地的首轮内测闭环：

- 贡献类型首期收敛为 Skill 与 RPA；投稿资产都是独立 `Capability`，不自动创建数字员工。
- RPA 支持 `POST /contributions/rpa-package` 上传 ZIP，50MB 压缩包/256MB 解压后/2000 entries 限制，内容寻址保存 SHA-256；拒绝非 ZIP、非法路径、敏感凭据文件和常见明文密钥。
- RPA 使用 `RpaVersion` 管理审核版本，复用“自动校验 → 企业审核（企业投稿）→ 平台审核”的状态流；首期只允许 `DOWNLOAD`，平台不执行 RPA。
- 增加 RPA 下载鉴权：未审核草稿不能下载；企业审核通过后，企业投稿人及企业成员可下载企业私有包；平台审核通过后，市场用户可下载公开包。
- 前端投稿对话框增加 RPA ZIP、平台（实在/影刀）和使用环境说明；详情页提供审核通过后的 ZIP 下载入口。
- 增加 `scripts/skill-scanner/scanner.mjs` 本地只读扫描原型：扫描 `.agents/skills`、`.claude/skills`、`.codex/skills`、`.gemini/skills`、`.opencode/skills` 等用户级/项目级目录，读取 `SKILL.md` frontmatter、生成确定性 SHA-256 清单并拒绝 symlink 逃逸；扫描器不上传、不执行。

待后续迭代：

1. 将扫描器接入 SEP Client/CLI 的“选择后上传”流程；网页不能静默遍历用户磁盘。
2. 接入对象存储（当前 RPA/Skill 包沿用本地内容寻址目录，适合内测单节点，不适合多实例生产）。
3. 增加平台审核页的 RPA 专属包预览/下载和敏感信息扫描结果展示。
4. 建立正式病毒扫描/沙箱策略；本轮只做静态 ZIP 结构检查，不执行上传内容。
5. `RpaVersion` migration 已生成并纳入本轮代码；正式环境仍需在部署时完成迁移状态核验与应用，不能在生产环境直接执行破坏性重置。
