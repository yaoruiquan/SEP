# 国内电商硅基员工批量上架蓝图（100 人）

**版本**：v1.0
**编制日期**：2026-10-07
**用途**：为 SEP 人才市场批量创建、绑定 Skills、审核并上架 100 个国内电商/通用电商员工模板。

> 范围说明：本方案不包含 Amazon、Shopify、eBay、Walmart 等海外平台专项员工。国内平台场景覆盖淘宝/天猫、京东、拼多多、抖店/抖音电商、快手、小红书、视频号、闲鱼以及不依赖单一平台的通用经营能力。

## 1. 先确认：SEP 当前员工上架流程

当前代码和运营端页面采用“能力（Skill）先审核，员工再组装”的两层流程。员工不是把一段提示词直接发布到市场，而是将已经审核通过的能力绑定到 `DigitalEmployee` 模板后，再走员工审核。

### 1.1 推荐标准流程

```text
准备/创建 Skill 能力（Capability.type=SKILL）
  → 上传或填写 SKILL.md / skillConfig.template
  → 自动校验与安全扫描（包模式必须含 SKILL.md）
  → 提交能力审核 → 能力 APPROVED
  → 创建员工模板（DRAFT）
  → 选择并批量绑定至少 2 个已审核 Skill
  → 设置绑定优先级、启用状态和必要 config
  → 保存草稿，检查员工详情与绑定清单
  → 提交员工审核（PENDING）
  → 平台审核通过（APPROVED + publishedAt）
  → 公开市场 GET /market/employees 可见
  → 上架后做公开详情、订阅、对话和能力执行验收
```

### 1.2 对应页面和接口

| 阶段 | 运营端入口/接口 | 成功条件 |
|---|---|---|
| 创建 Skill | `/admin/capabilities/new`；`POST /admin/capabilities` | `type=SKILL`，有 `skillConfig` 或合规包元数据 |
| Skill 包校验 | `POST /admin/capabilities/upload-skill` | ZIP 合法、含 `SKILL.md`、扫描通过 |
| Skill 审核 | `/admin/capabilities`；`POST /admin/capabilities/:id/submit` → `/approve` | `Capability.status=APPROVED` |
| 创建员工 | `/admin/employees/new`；`POST /digital-employees` | 创建成功，初始 `DRAFT` |
| 绑定 Skills | 新建页批量绑定或 `POST /admin/employees/:id/bindings` | 每个员工至少 2 个绑定，绑定能力已审核 |
| 调整绑定 | `/admin/employees/:id/bindings` | 优先级、启用状态、config 已核对 |
| 提交员工 | `POST /admin/employees/:id/submit` | `DigitalEmployee.status=PENDING` |
| 审核上架 | `POST /admin/employees/:id/approve` | `status=APPROVED`，`publishedAt` 已写入 |
| 公开验收 | `GET /market/employees`、`GET /market/employees/:id` | 仅返回公开字段，市场可检索到员工 |
| 下架/回滚 | `POST /admin/employees/:id/archive` | 员工从公开市场移除，不删除历史数据 |

### 1.3 重要实现约束

1. **员工创建 DTO 必须包含 `capabilityIds`**；目前服务端创建时会验证能力为 `APPROVED`，并为平台已发布 Skill 版本设置默认版本。
2. **员工绑定的是 Capability，不是直接填写 Skill 名称**。本文中的 `skill_id` 是产品设计 ID；实际落库时应映射到已审核 Capability 的数据库 `id`。
3. **公开市场不会返回 `systemPrompt`、`modelId`、`maxSteps`**。员工详情页可以展示名称、描述、行业、岗位和能力摘要，但不要把内部提示词写进公开描述。
4. **每个员工固定绑定 2 个 Skills**，第二个 Skill 负责校验、分析、执行编排或风险控制，避免员工只有“写文案”一项低价值能力。
5. 运营端存在 `POST /admin/employees/:id/publish` 的直接发布快捷接口，但批量上架默认走“提交审核 → 审核通过”路径，方便保留审核记录；仅在已完成人工检查的内部运营场景使用快捷发布。
6. 写操作默认不自动执行：改价、退款、下架、发券、发送消息、批量发布、供应商下单等必须输出待确认动作，并保留审计记录。

## 2. Skill 设计与组装规则

### 2.1 Skill 的统一规格

每个 Skill 建议创建为一个 `Capability`：

- `type`: `SKILL`
- `name`: 使用下表的中文名称；可在内部保留 `skill_id` 作为稳定标识
- `description`: 使用下表的能力边界，不写“保证爆单”等不可验证承诺
- `industry`: 至少包含 `电商`，通用技能可加 `零售`、`市场营销`、`供应链` 等
- `position`: 与适用岗位对应
- `inputSchema`: 输入数据结构，如订单表、商品表、评论、活动目标
- `outputSchema`: 结果结构，如诊断结论、证据、建议、风险、待确认动作
- `skillConfig.template`: SKILL.md 正文或等价提示模板
- `status`: 只有 `APPROVED` 的能力可绑定给员工

### 2.2 每个员工的组装公式

```text
硅基员工 = 角色定位 + 业务边界 + Skill A（主能力） + Skill B（校验/协同能力） + 输出格式 + 风险策略
```

建议所有员工系统提示词包含以下共用规则：

```text
你是 SEP 的国内电商硅基员工。你只能基于用户提供或已授权读取的数据工作；
先说明数据范围和口径，再给结论；区分事实、推断和建议；无法确认时列出缺口；
涉及改价、退款、下架、发券、发送消息、投放预算、下单或对外承诺时，先生成待确认方案，不直接执行；
输出：结论摘要、证据/数据口径、优先级动作、风险与待补信息。
```

### 2.3 Skill 包（ZIP）建议结构

```text
<skill-slug>.zip
└── SKILL.md
```

若使用上传包模式，服务端会校验 ZIP、路径安全、`SKILL.md` 存在和安全扫描结果；若使用在线模板模式，仍应把相同正文保存为能力版本，便于预览、审计和后续迭代。

## 5. 100 人的创建参数建议

### 5.1 公共字段默认值

## 7. 单个员工的实际上架检查单

- [ ] 名称不重复，名称能表达明确场景，不使用“万能”“保证爆单”等夸大表述。
- [ ] 描述不少于 10 个字符，写清输入、输出和边界。
- [ ] `industry=电商`，岗位与员工能力一致，`functionalCategory` 使用 DTO 合法枚举。
- [ ] `systemPrompt` 包含数据口径、事实/推断区分、风险确认和输出格式。
- [ ] 两个 Skills 都是 `Capability.status=APPROVED`，并且类型为 `SKILL`。
- [ ] 绑定优先级已设置：主 Skill 优先级较高，校验/协同 Skill 次之；两个 binding 均 `enabled=true`。
- [ ] 试跑至少 3 类输入：正常任务、缺数据任务、高风险写操作任务。
- [ ] 通过 `/admin/employees/:id/bindings` 检查绑定清单和版本。
- [ ] 先提交 `PENDING`，由管理员检查后 `APPROVED`；不要把“草稿存在”当成“已经上架”。
- [ ] 公开接口未泄露 `systemPrompt`、模型配置、凭据或内部 package 信息。
- [ ] 如有员工包，版本号符合 `x.y.z`，ZIP 不超过 20MB，包内含 `SKILL.md`，并完成扫描。

## 8. 批量验收矩阵

| 验收维度 | 抽样方式 | 通过标准 |
|---|---|---|
| 绑定完整性 | 全量 100 人 | 每人恰好至少 2 个已审核 Skill，200 条预期 binding |
| 公开检索 | 每批抽 5 人 | `/market/employees` 可检索，行业/岗位展示正确 |
| 对话可用性 | 每类抽 2 人 | 能调用绑定 Skill，输出结构稳定 |
| 缺数据 | 每类抽 1 人 | 不编造指标，明确缺口和所需字段 |
| 写操作安全 | 抽查客服、投放、供应链、会员 | 只出方案/待确认动作，不直接执行高风险操作 |
| 合规 | 抽查内容、广告、客服、隐私、财税 | 对不确定法律/税务问题提示专业复核 |
| 版本与审计 | 抽查 10 人 | 能追溯 Skill 版本、审核记录、绑定优先级和员工版本 |

## 9. 不建议在这批员工中直接承诺的能力

- 不承诺“保证爆款、保证涨粉、保证 ROI、保证上首页”。
- 不把平台非公开接口、Cookie、验证码绕过、批量刷量、刷单、虚假评价做成默认 Skill。
- 不让员工自动退款、自动改价、自动下架、自动发券、自动群发消息或自动向供应商下单。
- 不将国外平台字段照搬到国内平台；平台差异应体现在输入 schema、规则 Skill 和数据适配器中。
- 不把“平台连接器尚未接入”写成“已实时读取后台数据”；没有连接器时必须要求用户上传或授权数据。

## 10. 上架完成定义

当以下条件同时满足时，才把本批员工标记为“已上架”：

1. 相关 Skills 已创建、扫描、审核通过；
2. 100 个 `DigitalEmployee` 均已创建并拥有合法的中文名称、描述、行业、岗位和系统提示词；
3. 每个员工至少绑定 2 个已审核 Skill，目标为 200 条 binding；
4. 员工均经过草稿检查并提交审核；
5. 审核通过的员工状态为 `APPROVED` 且有 `publishedAt`；
6. 从公开市场列表和详情接口验证可见性与敏感字段隔离；
7. 抽样对话、缺数据、高风险操作和版本升级检查通过；
8. 保留导入清单、能力 ID 映射、员工 ID 映射、审核记录和验收结果。
