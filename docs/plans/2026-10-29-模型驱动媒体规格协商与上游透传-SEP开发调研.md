# 模型驱动媒体规格协商与上游透传：SEP 开发调研

日期：2026-10-29

状态：SEP V3 源码及本地替身测试已完成，具体交付、适配边界与验证结果见[实施记录](../progress/2026-10-29-媒体规格协商V3实施记录.md)。以下调研基线与上游限制保留用于追溯；不代表功能已经上线、客户端已经启用或上游规格已经验证。

配套：[客户端开发调研](../../../sep-client/docs/plans/2026-10-29-模型驱动媒体规格协商与上游透传-客户端开发调研.md)。

## 1. 已确定的产品方向

- 用户明确指定的规格优先；未指定的规格由执行任务的模型根据用途、素材和需求提出，关键信息不足时与用户交互。
- SEP 和客户端不设置固定业务规格白名单，不为新任务自动补全平台默认规格，也不把能力数组首项当默认值。
- 提示词用于表达创作需求；实际尺寸、时长、比例等由模型提出的结构化参数传递给上游。上游不支持时返回可理解的原因和建议，不静默改参、不自动改为脚本合成。
- 保留身份授权、费用审批、报价一致性、幂等、防重复扣费和文件安全。未知规格不是越权；参数格式、上游不支持、适配器未实现、授权拒绝、价格不可得必须分别处理。
- 规格推断复用客户端现有 agent；SEP 不新增一个替用户决定规格的 LLM 服务。

## 3. 现状与改动地图

### 3.1 为什么仍然只有 4 秒、16:9、720p、24fps、MP4

结论：限制不是单一提示词或企业设置造成的，而是首期真实视频实现的完整固定合同。仅修改 Web 配置、客户端提示词或企业授权，不能解除。

| 层级 | 代码证据 | 当前行为 | 本次要求 |
|---|---|---|---|
| 视频 Profile | [media-video-config.service.ts](../../backend/src/modules/media-config/media-video-config.service.ts) 的 `realCapabilities/realCompatible/assertExecutable` | 返回固定数组；只认可 `minimax-h3` 与固定规格组合 | 用适配器就绪状态决定可执行性；规格信息改为有来源的提示，不能用固定集合拒绝新请求 |
| 模型发现与同步 | 同文件的 discovery/sync；[media-model-sync.service.ts](../../backend/src/modules/media-config/media-model-sync.service.ts) | 发现目录后仍经过已知模型与固定模板筛选 | 将「目录中存在」「授权」「适配器支持此协议」「规格已验证」分开；模型未知不能直接等同于不支持 |
| runtime | `getRuntimeVideoV2` | 从能力数组第一项生成 `defaults`，音频固定为启用 | 新协议不返回业务默认规格；保留旧协议读取兼容 |
| 请求接收 | [media-video.dto.ts](../../backend/src/shared/media-video.dto.ts) | 六个视频规格必填，resolution/outputFormat 为枚举，存在 600 秒与 120fps 上界 | 新版规格字段允许按协议省略、扩展取值；移除无独立安全依据的业务上界 |
| 执行服务 | [media-video-real.service.ts](../../backend/src/modules/media-gateway/media-video-real.service.ts) 的 `requireProfile` | 模型与每一项参数再次固定检查 | 继续校验身份、配置版本、操作、适配器；不再按静态规格集合拦截 |
| 上游提交 | [sub2api-video.adapter.ts](../../backend/src/modules/media-gateway/sub2api-video.adapter.ts) 的 `submit/assertInput/query` | 硬编码 `seconds:4`、`size:1280x720`、`resolution:720p`、带音频及 `metadata.resolution:768P/ratio:16:9`；查询也限定模型 | 改为确定、可审计的字段映射；未知或不可表达的字段明确报适配失败，不能丢弃 |
| 报价与账务 | 执行服务的 quote/usage 校验 | 报价回显和 usage 期望仍固定 4 秒、720p、单视频及模型 | 根据冻结请求与上游合同核对，不再假定唯一规格 |
| 结果验收 | `acceptableH3Output` | 接受 4 或 15 秒、1280×720 或 1344×768、24fps MP4，仍保留冻结 4 秒账务 | 请求、实际输出、上游计费量独立记录；不得把兼容特例宣传为规格支持 |

历史原因：`21ac5149` 引入首期真实视频固定合同；`8b6414bc` 的移除对象是企业层 `maxDuration/allowedAspectRatios/maxResolution/allowedOperations` 策略，并没有移除上述适配器和账务合同。[2026-10-26 企业媒体授权方案](./2026-10-26-企业媒体授权移除规格限制.md) 应按这个边界理解。

本次任务没有发起生成，因而能证实「模型读到固定 runtime」，不能据此断定供应商只支持这些规格，也不能把没有生成归因为付费接口拒绝。

必须分类处理旧的 `max4`、参考图 PNG/5MiB/4096 像素、视频单参考图/10MiB、输出 256MiB、prompt 长度等限制：

- 尺寸、比例、质量、时长、帧率、音轨、输出格式、生成数量的固定产品取值：取消全平台白名单/default。
- 实际适配器暂只支持某种输入格式或单张参考图：如实作为适配器实现边界，不伪装为供应商最大能力。要扩展需同时修改上传、存储、multipart、引用语义与测试。
- 字节数、解析资源、下载体积、并发、超时、路径与地址安全：继续保护系统。若要调整，给出资源依据和独立错误原因，不能用「不限规格」删除保护。
- mock 固定 fixture 是测试约定，继续隔离；不能把 mock 扩展或固定值混入真实 runtime。

## 4. 两端统一契约

### 4.1 职责边界

| 内容 | 客户端/当前任务模型 | SEP | Sub2API/供应商 |
|---|---|---|---|
| 分析用途、提出规格、澄清 | 负责；复用现有 agent | 不新增推理服务 | 无 |
| 用户明确参数 | 保留与展示，禁止推理覆盖 | 冻结后原意传递 | 接受或明确拒绝 |
| 参数校验 | 类型、冲突、文件引用、交互完整性 | 可信边界、字段映射、安全、价格语义 | 模型真实规格能力 |
| 业务默认值 | 不设 host/UI 静默默认 | 不设规格默认值 | 仅可能存在其自身合同默认，需透明处理 |
| Profile 选择 | 用户选择优先，可采用已授权默认路由 | 保留企业 `defaultProfileId` 路由 | 不擅自切模型 |
| 授权与费用 | 展示报价、取得既有授权 | 身份、策略、余额、冻结、结算与幂等 | 提供可信报价/usage |
| 输出与交付 | 保存、展示、验收、交付 | 安全读取、实测和回执 | 返回实际产物 |

「无 SEP 规格限制」指不再由 SEP 制造业务规格；不意味着没有身份校验、可报价要求、字段适配、安全验证，也不保证所有供应商接受任意参数。

### 4.2 版本设计

以下为待实施协议建议，字段及新版本不是现有 API：

1. runtime 新增 `protocolVersion:3`，媒体请求、报价和回执具有对应版本标识。现有 V1/V2 按原 Schema 读取，不能直接把必填 `defaults` 变成可选而不升级。
2. 新版 Profile 保留 `profileId/configVersion/operations/executionMode`、适配器标识/版本、真实授权状态。新增 `capabilityHints`，带 `source/observedAt/confidence`；未知可以为空，不能编造能力数组。
3. `capabilityHints` 是建议和证据，不是允许值白名单；不在提示列表里的值仍可报价/提交。显式负面证据应说明来源，不能转成 SEP 固定规则。
4. 分开表示 operation 已适配、参考素材支持、查询/取消能力、配置健康状态。找不到适配器是 `ADAPTER_UNAVAILABLE`，不能写成「上游拒绝此规格」。
5. 端点优先复用现有 quote/submit/query，通过现有版本协商机制选择合同；若必须新增版本路由，再成对增加 Controller/SDK 文档。无需为了本方案新增通用微服务或独立“规格推理接口”。

### 4.3 请求、冻结规格与实际规格

共同语义：

| 字段 | 含义与不变式 |
|---|---|
| `requestedSpec` | 用户要求与模型补全建议合并后的规格。用户明确字段具有优先权，未知可省略；不是 SEP 自动补齐的结果 |
| `parameterSources` | 按字段记录 `user/model/upstream` 来源及可追溯的决策引用；由客户端记录过程，不能当作权限或用户同意的可信凭证 |
| `specRevision` | 当前需求版本；澄清或改参递增，旧报价失效。可复用已有请求 revision，不强制新增数据库列 |
| `effectiveSpec` | quote 返回、submit 冻结执行的规范化规格；只允许等价格式转换，不允许补业务默认或改变含义 |
| `actualSpec` | 文件实测与可信供应商返回的规格；保留未知值与来源，不以请求值覆盖 |
| `billingDimensions` | 上游报价/usage 认定的计费维度与计费模型，独立于实测文件尺寸/时长，不能互相推定 |
| `semanticHashVersion` | 选择新版规范化/哈希算法；历史任务仍使用旧版本 |

示例是模型针对「竖屏商品短片」提出的一套请求，不是产品默认值，也不证明该通道支持这些参数：

```json
{
  "protocolVersion": 3,
  "profileId": "authorized-video-profile",
  "configVersion": "cfg-current",
  "operation": "text-to-video",
  "referenceIds": [],
  "creativeBrief": "展示商品细节与使用场景，节奏明快",
  "specRevision": 1,
  "requestedSpec": {
    "durationSeconds": 8,
    "aspectRatio": "9:16",
    "resolution": "1080p"
  },
  "parameterSources": {
    "durationSeconds": "model",
    "aspectRatio": "user",
    "resolution": "model"
  }
}
```

字段建议：图片保留 size/width/height、aspectRatio、count、quality 等语义；视频保留 durationSeconds、aspectRatio、resolution/width/height、frameRate、audio、outputFormat。值采用可扩展且有长度/数值安全校验的类型，不再把 480p/720p/1080p/4k 或 MP4/WebM 当全平台业务枚举。具体字段以两端合同测试锁定，不同时保留两套含义重叠的无序参数。

执行细则：

- `undefined` 表示未提供；`false` 是明确关闭音频；`0`、空串、非法数值应按字段语义报错。禁止 `value || default` 或 Zod `.default()` 改写这些区别。
- 同时提供 `size/aspectRatio` 或 `resolution/width/height` 且不一致：返回字段冲突，不能静默选一项。比例化简、别名转换只有可证明等价且合同明确时才能做，并在 effectiveSpec 中透明回显。
- 计价或上游提交的必需规格缺失：quote 返回 `MISSING_SPEC`，列出需要的字段和原因；客户端让现有模型提出或向用户询问。不得发一次收费生成来“试出默认值”。
- 上游允许省略且不影响费用/已明确费用边界的可选字段可以省略；记录“未指定，由上游决定”，不伪造 24fps、medium、count=1 等 SEP 值。若该省略会改变费用却无法得到可靠报价，返回 `PRICE_UNAVAILABLE/MISSING_SPEC`。
- 生成数量也由模型方案或用户明确选择。用户没说时模型可建议 1 张，SEP 不能自动注入 1；数量变化同步影响输出数组、usage 与验收。
- 不允许模型注入任意 `model/baseUrl/header/apiKey` 或不受控 provider JSON。Profile 的模型与连接由可信配置决定；提供受控字段映射扩展点，不以“透传”为名允许任意网络请求。

### 4.4 参数映射与报价必须一致

视频适配器需要把 `durationSeconds` 映射到上游 `seconds/duration`，把图片尺寸映射到 `size`、把 count 映射到 `n`；映射由适配器合同确定。当前 `resolution:720p + metadata.resolution:768P` 的历史特例不得复制为新通道通用逻辑。

对于比例、帧率、音频、格式等字段：

1. 上游有明确字段：按合同传递，JSON 与 multipart 一致。
2. 上游仅接受等价尺寸表达：可做不改变含义的换算；缺失像素信息不能凭比例猜尺寸。
3. 接口无法表达某个用户明确要求：返回 `ADAPTER_FIELD_UNMAPPED` 并说明未提交，不能忽略字段后宣称已生成指定规格。
4. 若要在本地转码/静音/剪裁后交付，必须作为模型提出、用户授权范围内的独立后处理方案；保存生成原件与转换记录，不混入 native generation 的 effectiveSpec。

报价应返回 `effectiveSpec`、规范化说明、版本化语义哈希和全部计价维度。哈希至少覆盖主体作用域、Profile/版本/适配器、操作、prompt 摘要、引用 ID 与内容哈希、请求规格、明确省略状态和 `specRevision`；身份可通过既有作用域唯一键绑定，不必复制敏感身份到响应。价格版本、币种/汇率和连接指纹继续冻结。

submit 必须核对同一套规格、引用、价格版本、配置版本和报价有效期。任何有费用/执行影响的参数变化都重新报价；相同幂等键搭配不同参数返回冲突。模型自报 `parameterSources:user` 不能豁免真实费用审批。

### 4.5 可操作、可脱敏的错误

以下为新增或统一错误语义建议，需与现有错误码兼容映射：

| 情形 | 分类 | 返回与交互 |
|---|---|---|
| 字段类型错误/参数自相矛盾 | `INVALID_PARAMETER / SPEC_CONFLICT` | 字段路径、原因；要求修订，不称为无权限 |
| 必需规格未定 | `MISSING_SPEC` | 字段与必需原因，尚未提交，由模型继续协商 |
| 无企业/Profile/主体授权 | `MEDIA_FORBIDDEN` | 授权问题；不自动换员工或提升只读任务权限 |
| 协议/字段适配尚未实现 | `ADAPTER_UNAVAILABLE / ADAPTER_FIELD_UNMAPPED` | 来源是 SEP 适配层，指出升级/适配方向 |
| 没有可靠价格 | `PRICE_UNAVAILABLE` | 来源是报价合同，不能表述成模型不支持，也不能零价继续 |
| 上游明确拒绝规格 | `UPSTREAM_SPEC_UNSUPPORTED` | 安全字段、请求值、供应商可公开原因；替代方案仅来自真实证据 |
| 请求发出但状态无法确认 | `SUBMISSION_UNKNOWN` | 保留原请求查询，不能自动新建付费请求 |
| 文件与约定不一致 | `OUTPUT_SPEC_MISMATCH` | 保留真实文件、actualSpec、计费状态；等待交付决策，不自动再生 |
| 旧协议无法表达 | `UPGRADE_REQUIRED` | 指明兼容边界，绝不静默降级规格 |

安全错误信封建议包含 `field/requestedValue/reason/source/stage/retryable/submissionState/billingState/alternatives`。`retryable` 只表示可恢复，不等于允许自动再次付费。对于未知提交状态不得标记“未扣费”；价格和实际扣费以可信账务状态为准。

上游响应必须先验证和脱敏，不能直接回传原始 body、供应商内部 URL、Authorization、API key、堆栈或可能回显的敏感 prompt。结构化原因经 allowlist 提取，补充人工可理解说明；没有证据就不要生成虚构的支持值列表。

## 5. SEP 具体工作包

## 7. 状态、数据与安全不变式

### 7.1 一次生成的顺序

```text
客户端分析/询问 → 结构化规格与需求版本
→ SEP 验证主体/配置/文件与适配字段
→ 参数完整且可定价 → quote 冻结 effectiveSpec 与费用
→ 既有费用授权 → 同义 submit（唯一 clientRequestId）
→ 查询原任务 → 安全下载与实测 actualSpec
→ 原请求 usage 对账 → 客户端保存与交付验收
```

缺字段、价格不可得、适配器缺失时停在提交前；询问用户不是生成失败。配置撤销/连接变化需按既有安全规则阻止新执行，旧任务恢复不得切到新连接或新模型。

### 7.2 三个状态维度

- 供应商生成状态：是否已提交、生成完成、可查询/取消。
- 交付验收状态：是否可下载保存、是否符合需求；支持 `matched/mismatched/unknown` 的测量解释。
- 账务状态：是否冻结、结算、释放或对账中。文件不符不自动意味着上游未收费。

新版依据冻结规格验收，不继续使用「4/15 秒都算 4 秒请求成功」的通用规则。容差必须针对容器时间基准等测量误差说明，不能变成业务降级。检查 mime、文件签名、哈希、宽高、帧率、音轨等仍保留；无法安全打开的产物隔离，不能作为交付。

### 7.3 必须保留的保护

- 企业/员工/成员/账号作用域隔离、参考素材归属与过期检查、Profile 授权、真实模式开关。
- 余额、费用授权、价格版本/汇率冻结、真实 usage、幂等唯一键、未知提交恢复。
- HTTPS/可信连接、响应结构与大小、下载流量上限、文件解析安全、SSRF/路径保护与密钥脱敏。
- 启用某项 operation 是协议/授权行为，不是任意提示词授权。请求指定不了取消工具，也不能让只读任务发起生成。

## 8. Sub2API 依赖：两仓库修改的实际边界

只读核查了相邻 `sub2api` 仓库，未作改动：

| 上游文件 | 查到的事实 | 对本方案的影响 |
|---|---|---|
| `backend/internal/service/openai_videos.go` | 解析 `seconds/duration`、`resolution/size`，兼容 JSON/multipart | SEP 可以解除自身固定提交，但仍需验证最终转发字段和供应商合同 |
| `backend/internal/service/gateway_video_billing.go` | 报价只接受 480p/720p/1080p，时长正整数且≤600，要求可核验价格 | 4k/其他分辨率不能因 SEP 去掉枚举就宣称已支持；先返回价格/合同原因，需上游单独协调 |
| `backend/internal/service/video_billing_resolution.go` | 未识别分辨率会规范化为 480p；Grok 计费用时长有 1–15 秒及默认 8 秒；其他模型缺时长也可能用 8 秒 | 新链路不能依赖兜底值掩盖缺失计价维度；报价与实际 usage 必须匹配，超出时要改上游合同 |

因此「上游不支持就返回原因」必须指明到底是 SEP 适配器、Sub2API 价格接口，还是最终供应商拒绝。Sub2API 的默认/规范化也要纳入联调，不能只看供应商原始 API 的能力。

上游协作交付项：可扩展报价规格与计价维度、无歧义的请求回显、与实际计费一致的 usage、可脱敏规格错误、必要的字段转发。图片也要核对尺寸/质量/数量价格合同。未经实现及验证，文档不承诺任意视频规格端到端可用；也不发起付费探测来发现能力。

## 9. 兼容与发布顺序

1. **合同先行**：两仓库确认 B01/C01 fixture；显式选择新协议。现有 endpoint 的真实路径和鉴权不在本文臆造。
2. **SEP 先支持**：B02–B06、报价与 usage、JSON/multipart、输出和恢复测试完成后发布后端；有必要的 Sub2API 合同同步先行。
3. **客户端启用**：仅对协商成功的新协议停止 host 默认补齐；旧服务器不能被客户端伪装成 V3。
4. **旧客户端兼容**：旧 V1/V2 只能投影其实际可表达、可执行的旧合同；不能把提示当任意能力。如果原固定适配器已无法真实履约，应明确不可用/要求升级，不制造假默认。
5. **存量任务恢复**：沿用原请求、原哈希版本、原连接指纹、原报价与 usage 合同；不能用新模型推荐重新解释历史任务，也不能重写历史 JSON 默认值。
6. **灰度/回退**：用版本化新请求路径逐步启用。回退时停止新协议新提交，已提交任务继续由相应版本查询/对账；不能删除新任务记录或改用旧默认重放。

本方案更新了 [2026-10-24 Web 配置方案](./2026-10-24-Web端媒体能力与授权配置优化开发文档.md) 中固定规格、能力列表和默认值相关方向；历史文档保留追溯，其余授权和安全要求继续有效。与 [2026-10-22 视频账务方案](./2026-10-22-SEP视频定价预算与错误链路收敛开发方案.md) 合并实施时，保留真实报价/账务的范围，不把本方案写成新增预算策略。

## 11. 完成定义与本次交付范围

- 新请求全链路没有 SEP 注入的 4 秒/720p/24fps/MP4 或图片 size/quality/count 业务默认。
- 用户参数不被模型建议、静态能力列表、价格归一化或旧 DTO 静默修改；未知能力不被等同为禁止。
- 一套非原固定规格通过 fake 上游的报价、提交、查询、下载、实测、usage、客户端交付合同；真实通道支持范围单独验收。

- 老客户端与历史任务有版本策略，授权、账务、幂等、文件安全没有回退。
