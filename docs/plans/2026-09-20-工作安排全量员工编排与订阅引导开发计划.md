# 工作安排全量员工编排与订阅引导开发计划

- 日期：2026-09-20
- 状态：开发计划，尚未实施
- 目标：工作安排不再仅从当前用户已订阅、已授权的员工中生成计划，而是从所有可公开发现的已上架员工中选人；需要订阅或授权时明确提示，权限补齐后执行原计划。
- 核心原则：**规划可以推荐，执行必须有权；生成计划不等于购买或执行。**
- 本文以当前代码为基线；早期任务中心文档中“浏览器执行”“尚未持久化”等描述已不适用于当前实现。

## 1. 当前实现与改造动机

### 1.1 当前链路

```text
用户填写目标
  → POST /task-plans/preview
  → 企业 ACTIVE 订阅 ∩ 当前成员/部门有效授权 ∩ APPROVED 员工
  → 保留绑定能力的员工，应用可选 employeeIds 范围
  → 通过 sub2api 调用规划模型，返回步骤与依赖
  → 创建并保存 TaskRun，等待确认
  → 用户编辑计划、确认执行
  → 后端队列和 TaskRunner 按依赖逐步执行员工会话
```

关键代码：

| 位置 | 当前职责 |
|---|---|
| `backend/src/modules/task-planning/task-planning.service.ts` | 加载候选、调用规划模型、校验员工与能力 ID |
| `backend/src/modules/task-planning/task-planning.types.ts` | 规划请求与模型输出 Schema |
| `backend/src/modules/digital-employee/digital-employee.service.ts` | 公开市场员工筛选与字段白名单 |
| `backend/src/modules/task/task.service.ts` | 任务、计划编辑与模板持久化 |
| `backend/src/modules/task-execution/task-execution.service.ts` | 启动、重试、暂停、恢复与入队 |
| `backend/src/modules/task-execution/task-step-executor.service.ts` | 单步执行及会话调用 |
| `backend/src/modules/subscription/subscription.service.ts` | 企业订阅、订阅有效性检查 |
| `backend/src/modules/subscription-request/subscription-request.service.ts` | 订阅/使用授权申请 |
| `web/src/app/(enterprise)/tasks/page.tsx` | 工作安排页面及计划编辑，目前使用 `useMyEmployees()` |

### 1.2 本次需要解决的问题

1. 没有已订阅员工时无法生成计划，用户无法先了解完成任务需要什么员工。
2. 已订阅员工能力不匹配时，规划器看不到更合适的市场员工。
3. 仅扩大候选范围会让缺权限的计划先启动、后失败，必须同时增加执行前预检。
4. 企业已订阅不等于当前成员有授权，不能把所有不可用情况都提示为“需要购买”。
5. 规划时的权限状态会过时，不能作为执行时的授权凭据。

## 2. 产品范围与默认决策

### 2.1 MVP 包含

- 默认使用全部可发现员工作为候选来源，包括当前未订阅的员工。
- 候选员工展示当前订阅、授权、申请状态及可用操作。
- 计划中的未订阅员工允许保留、保存、编辑和用于模板。
- 计划页按员工去重汇总待处理事项，并关联受影响步骤。
- 复用现有订阅、续订、授权管理、使用申请链路，不新建支付系统。
- 所有执行入口进行服务端权限预检；缺少必要权限时不启动本轮执行。
- 订阅/授权完成后刷新状态，用户再次确认执行原计划，无需重新调用规划模型。
- 覆盖手动换人、模板、历史计划、重试、恢复与运行期间权限变化。

### 2.2 不包含

- 自动购买、自动扣款、自动批准申请、审批完成后自动执行。
- 在缺订阅时先运行部分步骤、运行到付费节点再暂停的模式。
- 新的任务并行执行引擎、审批工作流引擎、支付/定价改造。
- 强制步骤只能调用所选 `capabilityId` 的运行时改造；当前员工会话仍按既有工具选择机制执行。
- 向量检索、独立推荐服务或新增基础设施依赖。
- 全站订阅和权限体系重构。

### 2.3 选人策略

全量参与候选不意味着为了订阅转化而强行推荐付费员工：

1. 先满足目标与能力要求，不让不合适的已订阅员工勉强承担任务。
2. 能合理完成同一任务时，优先当前可用员工，减少新增订阅与审批成本。
3. 需要未订阅或未授权员工时，在选人理由中说明其适配能力，不能只写“更专业”。
4. 不虚构替代员工或能力；更换员工只能从服务端允许的目录中选择。
5. 保留 `employeeIds` 显式限制：指定后不越界推荐；未指定表示全量来源，空数组应明确报错而不是悄悄放宽范围。

“仅使用当前可用员工”开关可作为后续增强，不作为 MVP 必需项。

## 3. 员工目录与访问状态

### 3.1 “所有员工”的边界

候选来源是**所有市场可发现、已上架且有可用于规划能力的员工**，不是数据库全部记录。

- 当前 `EmployeeStatus.APPROVED` 表示已审核、已上架；市场查询也是这一条件。
- 排除 `DRAFT`、`PENDING`、`REJECTED`、`ARCHIVED` 员工。
- 不新增 `publishedAt IS NOT NULL` 硬条件：该字段目前是发布时间，不是独立发布状态，直接加条件可能误排存量员工。
- 不复用包含完整员工配置的管理接口。使用 `select` 白名单，仅输出名称、公开简介、岗位、行业、头像、价格及可展示能力元数据。
- 不向前端或规划模型暴露 `systemPrompt`、密钥、工具实现配置、其他企业订阅或授权信息。
- 核对能力的可见性、审核状态与实际绑定规则；仅暴露允许公开展示的能力元数据，不因员工上架而直接展开私有能力内容。目录校验与执行可用性应一致。
- “全量”是检索来源，不要求无限量塞入模型上下文。MVP 先测量目录规模，设置可配置的目录/文本预算；超出时采用明确的候选收敛或提示用户缩小范围，不静默只取前若干名并宣称覆盖全量。

### 3.2 统一状态模型（拟新增契约）

由服务端查询企业上下文、订阅和成员/部门授权后计算，不能由 LLM 或客户端决定。

| `status` | 判断 | 用户提示 |
|---|---|---|
| `AVAILABLE` | 员工可执行、订阅有效且有有效成员/部门授权 | 当前可用 |
| `SUBSCRIPTION_REQUIRED` | 企业没有对应订阅 | 需要企业订阅 |
| `SUBSCRIPTION_INACTIVE` | 订阅非 ACTIVE，或 `endDate <= now` | 订阅已失效，需处理 |
| `GRANT_REQUIRED` | 企业订阅有效，但当前成员及部门均无有效授权 | 需要使用授权 |
| `UNAVAILABLE` | 历史计划员工已下架/删除，或所选能力已解绑等 | 不可使用，请更换员工或能力 |

判定优先级：员工/能力不可用 → 订阅缺失/失效 → 授权缺失 → 可用。管理员身份不自动视为使用授权；沿用现有成员/部门授权规则。

申请状态独立放在 `pendingRequest` 中，避免“等待审批”掩盖究竟缺订阅还是缺授权。查询范围必须是**当前企业、当前申请人、对应员工**；已获得权限时优先显示可用，不被遗留待审批申请阻断。

示意结构，最终通过 shared Zod Schema 固化：

```ts
interface TaskEmployeeAccess {
  employeeId: string;
  status: 'AVAILABLE' | 'SUBSCRIPTION_REQUIRED' | 'SUBSCRIPTION_INACTIVE'
    | 'GRANT_REQUIRED' | 'UNAVAILABLE';
  subscriptionId: string | null;
  annualPriceCNY: string | null; // Decimal 转十进制字符串；null 不等于免费
  checkedAt: string;
  pendingRequest: { id: string; kind: 'SUBSCRIBE' | 'GRANT' } | null;
  allowedActions: Array<'SUBSCRIBE' | 'REQUEST_SUBSCRIPTION' | 'REQUEST_GRANT'
    | 'MANAGE_GRANT' | 'VIEW_REQUEST' | 'REPLACE_EMPLOYEE'>;
  reason?: string;
}
```

- 管理员未订阅：展示“订阅员工”；打开既有价格/扣款确认流程，不自动执行。
- 普通成员未订阅：展示“申请企业订阅”。
- 企业已订阅但本人无权：成员“申请使用权限”，管理员按现有权限展示授权管理入口，不重复购买。
- 已有待审批申请：展示申请状态，避免重复提交。
- 价格缺失或不可购买：如实显示不可直接订阅，不展示零元，也不让用户进入必然失败的购买流程；仍可更换员工。
- 待订阅员工及参考费用按 `employeeId` 去重；授权申请不计订阅费用，实际扣款以既有购买流程最终校验为准。

## 4. 服务端设计

### 4.1 统一目录与权限查询

拟新增轻量 `task-access` 模块，通过 `PrismaService` 批量加载并计算访问状态，供规划与执行共用，避免两套判定漂移。

职责：

1. `listPlanningCandidates(userId, employeeIds?)`：返回可发现候选及访问状态。
2. `checkEmployees(userId, employeeIds)`：按当前企业上下文批量查询订阅、有效期、直接/部门授权和本人待审批申请。
3. `checkTaskExecution(...)`：对任务权威步骤和本轮拟执行范围做员工、能力绑定、订阅、授权校验，返回阻塞项。

注册到相关 NestJS 模块，禁止跨企业查询或接受客户端传入企业 ID 作为权限依据。尽量复用既有权限判断，不顺带重写普通聊天链路。

### 4.2 规划接口

保留 `POST /task-plans/preview`：

- 去掉必须存在已订阅员工的前置门槛，改用统一规划目录。
- 向模型提供公开员工/能力资料及简化可用状态，不发送授权详情或申请人信息。
- Prompt 明确全量选人策略、不可自动订阅、仅生成计划。
- 模型仍只返回步骤、员工 ID、能力 ID、理由和依赖；访问状态由后端组装。
- 对模型返回的所有员工/能力 ID 及依赖图做严格验证；发现越界或无效步骤应拒绝整份结果，不能静默删步破坏依赖。
- 步骤返回可选 `access` 展示字段，计划仍为 `awaiting_confirmation`，不是 `RUNNING`。
- 无任何合法候选时提示“暂无可用于编排的员工”；与“企业尚未订阅”区别处理。

拟新增：

| 接口 | 用途 |
|---|---|
| `GET /task-plans/employees` | 登录用户获取可编辑计划用的公开员工目录及本人访问状态；支持搜索与分页 |
| `GET /tasks/:id/access-check` | 检查已保存任务本轮执行准备情况，返回按员工去重的阻塞项及受影响步骤 |

接口均加 JWT、任务归属/可操作权限检查、共享 DTO 与 Swagger。前端使用 `/task-plans/...`、`/tasks/...` 相对 API 路径；部署时沿用现有 `/api` 前缀。

### 4.3 权威数据与历史兼容

- 当前执行权威是 `TaskRunStep`，不能只给兼容字段 `TaskRun.steps` 增加状态后就认为执行已支持。
- MVP 访问状态按请求实时计算，不新增订阅状态快照表、不修改 Prisma schema。
- `TaskPlanStep.access` 仅用于展示；旧任务/模板没有该字段时标记“待检查”，重新查询，不能默认可执行。
- 创建、编辑和模板保存沿用已有持久化链路；客户端上传的 `access` 应丢弃或忽略，不能作为权限证明。
- 任务重新打开、编辑员工/能力、应用模板、订阅成功、申请审批状态变化后，刷新访问状态。
- 历史步骤名称、头像和已有输出继续保留，不因员工下架而破坏历史展示。

### 4.4 执行前预检与失败契约

在 `TaskExecutionService.run()` 中，**重置步骤、清空输出、设置 RUNNING、发送启动事件、入队之前**完成预检。现有 `materialize()` 若有兼容落库行为，应区分“读取/兼容初始化”和“重置执行状态”，不得在检查失败时丢失已有产出。

建议统一返回 HTTP 403 和结构化错误；已有“任务正在运行”的 409 冲突语义不改变：

```json
{
  "statusCode": 403,
  "code": "TASK_ACCESS_REQUIRED",
  "message": "当前计划有员工需要订阅或授权，请处理后再执行",
  "blockers": [
    {
      "employeeId": "employee-example",
      "employeeName": "报告撰稿员",
      "stepKeys": ["step-2", "step-4"],
      "status": "SUBSCRIPTION_REQUIRED",
      "annualPriceCNY": "3000.00",
      "allowedActions": ["REQUEST_SUBSCRIPTION", "REPLACE_EMPLOYEE"]
    }
  ]
}
```

覆盖范围：

- 首次执行：校验全部待执行步骤，任一阻塞则整单不启动。
- 普通继续执行：校验本轮剩余/将恢复的步骤，已完成且不重跑的员工失权不阻止后续合法步骤。
- 从某步重试：按现有 `resetFrom`/下游依赖规则计算真实重跑集合，再预检；校验失败不清空已有输出。
- `retryStep()`、`resumeStep()` 及其他重新入队入口都必须覆盖，不能只保护首次 `run()`。
- 队列等待、孤儿任务恢复及步骤间权限变化无法由首次预检完全覆盖；实际每一步开始前再次校验当前用户的订阅、授权和员工/能力状态，失败时不得创建新会话或调用能力，沿用现有失败收口与可重试机制。
- 保留已有会话层订阅校验。当前 `assertActiveSubscription()` 检查订阅状态和 `endDate`，不能假设它已经检查成员授权。
- 校验任务所属企业与执行用户当前上下文，跨企业或已失去任务操作权限时拒绝。

预检是新增防线，不替代既有鉴权或并发保护；实现时核对“编辑计划与启动同时发生”的竞态，确保校验的步骤版本就是入队执行的版本。

## 5. 前端流程

```text
输入目标（即使零订阅也允许）
  → 全量目录生成计划
  → 步骤显示当前可用/需要订阅/需要授权/不可用
  → 顶部汇总“共 N 位员工，M 位待处理”，按员工去重
  → 用户可：保留计划、订阅/申请、更换员工、删除并修复依赖
  → 完成处理后刷新原计划的访问状态
  → 用户确认执行
  → 后端重新预检，通过后入队
```

交互要求：

1. 计划编辑器不再仅用 `useMyEmployees()` 作为换人/新增步骤目录，改接规划目录；不扩大其他员工页面的授权范围。
2. 每个受影响步骤展示状态；集中处理面板提供对应动作，不重复弹出同一个员工的订阅提示。
3. 待处理时禁用“确认并执行”，提供“处理订阅与授权”；状态查询失败/尚未加载时不误显示“已就绪”。后端依旧必须独立阻断绕过 UI 的请求。
4. 价格用“参考年费”，审批中显示具体状态；不能承诺订阅后自动获得所有人员的授权。
5. 购买和申请需要用户明确操作；申请理由可预填任务用途，但不擅自向申请/通知附加完整敏感任务内容。
6. 跳转购买/申请前保存任务，保留 `taskRunId`；通过现有导航方式返回并刷新，不重建任务、不重新生成计划、不丢失布局与编辑。
7. 对结构化 403 显示缺失清单及动作，不能仅显示通用“执行失败”。检查 API 客户端是否保留错误响应体，必要时以兼容方式扩展。
8. 使用 TanStack Query 管理目录与访问状态；缓存键隔离任务、当前企业/用户，订阅/授权变化后精确失效，切换账号/企业不能复用旧权限。
9. 在桌面与移动端验证提示、长员工名、多个阻塞项和操作按钮，避免遮挡原计划。

## 7. 测试与验收标准

### 7.1 后端

- [ ] 企业零订阅但市场存在合法员工时，预览能成功并返回“需要订阅”，不创建订阅、不执行员工。
- [ ] 草稿、待审核、拒绝、下架及不满足能力可见性规则的候选不会泄漏；`APPROVED + publishedAt=null` 存量记录按当前市场规则处理。
- [ ] 企业 ACTIVE 但 `endDate` 已过期时不可用；授权 `expiresAt <= now` 不可用；有效直接授权或部门授权任一满足即可。
- [ ] 企业已订阅但成员无权提示申请授权，不提示重复购买；其他企业订阅和申请不影响本企业结果。
- [ ] 同一员工用于多个步骤时只返回一个待处理项，关联全部受影响步骤。
- [ ] 待审批申请不重复提交，拒绝/撤回后可以重走原申请流程。
- [ ] 模型编造员工/能力、返回解绑能力或非法依赖时拒绝；客户端伪造 `access=AVAILABLE` 不能绕过。
- [ ] 执行预检失败时队列无新增、任务不启动、原输出和重试计数不被预先修改。
- [ ] 重试和恢复不能绕过预检；仅校验实际将执行的步骤，不误阻断已完成历史步骤。
- [ ] 入队后、步骤开始前撤销授权时，实际执行被阻断，无新会话/能力调用。
- [ ] 旧任务、模板无 `access` 字段可读取并重新检查；下架员工历史输出仍可查看。
- [ ] 非任务所有者/无操作权限用户、企业上下文变化、并发编辑与启动有明确安全结果。

### 7.2 前端与端到端

- [ ] 零订阅空态允许输入目标，不再强制先去订阅。
- [ ] 可用、待订阅、待授权、审批中、失效、不可用状态及角色动作正确。
- [ ] 含多个未订阅员工的计划可保存和重开，提醒按员工去重。

## 8. 风险与控制

| 风险 | 控制措施 |
|---|---|
| 模型频繁推荐未订阅员工，制造不必要购买 | 能力适配优先、相同适配度优先当前可用、明确选人理由 |
| 扩大目录泄漏配置或私有能力 | 白名单查询，沿用市场可见规则，对字段泄漏加测试 |
| 规划状态过时 | 详情刷新、启动前检查、步骤执行前检查三层处理 |
| 预检与运行的权限判定不一致 | 复用统一服务，覆盖 endDate 与成员/部门授权，保留底层校验 |
| 订阅成功但当前成员仍未授权 | 根据真实授权刷新，不把付款成功直接当作 AVAILABLE |
| 自动购买或重复扣费 | 仅显式复用既有支付确认链路，不在规划/预检内发起购买 |
| 上下文超限、规划质量下降 | 目录规模评估、文本预算、明确候选收敛行为，不引入新检索基础设施 |
| 历史 JSON 与 TaskRunStep 权威数据混用 | 动态访问状态与执行状态分离，以权威步骤预检，覆盖旧任务转换 |
| 回跳丢失计划 | 操作前保存，基于任务 ID 恢复，禁止订阅后自动重新生成 |

## 9. 完成定义

用户可以在没有订阅任何员工时生成一个包含合适市场员工的工作安排，清楚看到谁需要订阅或授权；经显式购买/审批/更换员工补齐条件后，可以继续执行同一份计划。任何入口都不能让缺少订阅或授权的员工被实际执行。

本次仅交付开发计划文档；不代表接口、权限校验、UI 或上述测试已经实现或通过。
