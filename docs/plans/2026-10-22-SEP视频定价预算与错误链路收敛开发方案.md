# SEP 视频定价、预算与错误链路收敛开发方案

- 日期：2026-10-22。
- 状态：本地实现与自动化验收已完成；未提交、未部署，生产配置未调整。
- 范围：SEP 后端及企业设置页为主，Electron 客户端配套修复；Sub2 沿用现有定价接口。
- 本次“收敛”指视频定价来源、独立预算、提交错误及账务展示，不是重新设计整个媒体编排系统。
- 实施原则：复用现有接口、账务服务和本地任务字段，不新增服务、依赖或付费验证请求。

## 1. 目标与职责

推荐取消 SEP 单独的视频月预算限制及其设置入口。视频能否付费执行，由已有授权、统一资金来源和用户审批决定。报价必须继续展示，不能因为移除预算而隐去费用。

| 系统 | 负责 | 收敛要求 |
| --- | --- | --- |
| Sub2 | 模型映射、美元定价、倍率、上游调用及用量账单 | 视频价格只在这里配置，不在 SEP 维护第二张美元价目表 |
| SEP | 模型授权、人民币换算、报价冻结、资金预占、提交及对账 | 取消视频专用月预算；复用统一账务；明确返回提交前拒绝原因 |
| Electron | 接收创作需求、本地持久化、费用审批、查询和保存成果 | 用户不重复填模型与参数；不把确定拒绝包装成提交不明；不把未知账务说成未扣费 |

这意味着需要改 SEP 和客户端。当前没有证据表明必须修改 Sub2 的报价算法或限流规则。若业务仍要求企业视频专项预算，应保留其业务设计并改成清晰的可选限制；那是另一项产品选择，不能用隐藏输入框代替取消执行限制。

## 2. 已确认事实与未确认事项

### 2.1 价格来源

现有失败任务持久化的报价包含：

```json
{
  "amountUsd": "4.0000000000",
  "usdToCnyRate": 7.2,
  "amountCny": "28.800000",
  "status": "quoted"
}
```

这笔人民币报价来自 `4.00 × 7.2 = 28.80`。当前代码在这一换算步骤没有再加价；这不代表 Sub2 的美元报价等于供应商成本。

- SEP 的 `Sub2apiVideoAdapter.pricing()` 请求 Sub2 的 `POST /v1/sub2api/videos/pricing`。
- Sub2 返回 `pricing_authority: sub2api_customer_billing`，即对客户的计费报价。
- Sub2 优先使用有效的分组视频价格，否则使用可报价的渠道价格，并计算适用倍率。按秒模式和按次模式的计算不同。
- SEP 消费最终 `amount_usd`，不得再次乘时长或倍率。
- 尚未确认生产中这笔 `$4.00` 对应的具体分组单价、渠道单价和倍率，不能把它写成“已查到每条视频固定 4 美元”。本方案不调整价格数值。

### 2.2 最近一次本地失败

此前针对本地任务 `video_a862ff0c-…` 的关联排查已确认：

- 视频月预算为 ¥100，已有三笔各 ¥28.80 的结算，累计 ¥86.40。
- 新请求报价 ¥28.80，超过剩余 ¥13.60；SEP 提交接口返回 HTTP 402。
- 对应报价未被消费，服务端没有创建该次媒体请求；未进入上游生成或资金预占。
- 客户端把它保存成 `MAYBE_SENT / INTERRUPTED / SUBMISSION_UNKNOWN`，随后不断查询不存在的回执。

本次重新读代码确认：`MediaVideoRealStore.claim()` 在创建请求、消费报价之前执行视频预算检查；客户端丢弃非成功响应体，且没有单独处理 HTTP 402。

上述“未扣费”结论来自该请求的服务端记录和调用顺序，不能仅由 `outputs: []`、列表为空、404 或客户端显示 `NOT_RESERVED` 推导。其他机器的任务也不能直接套用此结论。

## 3. 目标链路

```text
AI 提交创作需求
  -> 客户端选择已授权的 profile 和支持的默认参数
  -> SEP 获取 Sub2 美元报价，冻结汇率、金额、规格与请求摘要
  -> 客户端保存 NOT_SENT 任务，按现有审批策略确认费用
  -> 客户端写 MAYBE_SENT，再提交原 clientRequestId
  -> SEP 校验授权与冻结报价，原子认领请求及并发名额
  -> SEP 统一账务预占
  -> SEP 记录 dispatch 标记，向 Sub2 提交一次
  -> 查询原回执、核验实际账单、结算或释放预占
  -> 客户端保存成片并展示真实任务和账务状态
```

审批、报价和预占分别解决“用户是否同意”“本次按什么价”“资金能否支付”，继续保留。移除的是额外的视频自然月预算闸门及其全量历史金额扫描。

## 4. SEP 后端修改

以下路径均相对于 `/Users/yao/LLM/SEP`。

### 4.1 下线视频专用预算执行逻辑

修改 `backend/src/modules/media-gateway/media-video-real.store.ts` 的 `enforcePolicy()`：

1. 删除 `periodBudget <= 0` 的拒绝分支。
2. 删除为计算视频月度预算而读取历史账务、遍历历史请求、累计已结算和未决报价的逻辑。
3. 删除 `used + quote > periodBudget` 的拒绝分支。
4. 保留企业 profile、操作类型、规格授权和 `maxConcurrentJobs` 检查。
5. 并发检查只查询或统计当前活动请求，不再为预算加载全部历史请求；按现有数据库字段和索引实现，不新增计数服务。
6. 保留 `claim()` 的串行化事务、唯一键和事务冲突重试，确保并发认领不会超限。

执行关闭通过已有真实执行开关或撤销 profile 授权完成，不能再依靠 `periodBudget: 0`。这是行为变化，发布前必须识别此前用零预算禁用付费视频的企业；需要继续禁用的企业迁移到现有授权开关。

### 4.2 字段兼容，而不是立刻删除

涉及：

- `backend/src/shared/media-video-config.dto.ts`
- `backend/src/modules/media-config/media-video-config.service.ts`
- `backend/src/modules/media-config/media-video-config.controller.ts`

首版保留 `periodBudget` 的读取、写入和返回兼容，但标注 deprecated，真实执行不再读取它。保留当前数值校验，不允许传入 `Infinity` 等特殊值。旧后台发来该字段时仍可保存，不能让旧表单突然返回 400。

不把全部企业预算改为极大值，不把 0 重新解释为无限额，不删除历史策略 JSON。关闭专项预算的效果由代码实现，而非伪造数据。字段物理删除留待兼容窗口结束后单独处理，本次不需要 Prisma schema 迁移。

Mock 接口维持不收费语义，并核对共享 schema、fixture 与说明一致。不得因删除真实预算检查而顺带重写 Mock 执行协议。

### 4.3 继续复用统一账务

保留 `backend/src/modules/media-gateway/media-real-billing.service.ts`：

- 报价阶段 `quoteFunding()` 返回当前资金分摊预览，不承诺审批后资金仍充足。
- 提交阶段 `reserve()` 在事务内重新确认并预占资金；这是必要的资金并发校验。
- 结算基于可关联的 Sub2 实际用量证据，不把报价当作实际扣费。
- 明确未派发的失败按原流程释放预占；提交结果不明时继续核对，不盲目释放。
- 实际金额高于已预占时沿用 `RECONCILING`，不能静默追加未经批准的费用。

不得删除预占幂等、CAS、dispatch 标记或用量关联检查。这些约束防止重复收费，不能当作冗余校验清理。

### 4.4 定价只保留一个来源

继续使用：

- `backend/src/modules/media-gateway/sub2api-video.adapter.ts`
- `backend/src/modules/media-gateway/media-video-real.service.ts`

要求：

1. `amountCny = Decimal(amountUsd) × 冻结汇率`，沿用现有六位精度及舍入规则。
2. 报价沿用 `quoteId / pricingVersion / semanticSha256 / expiresAt`，提交消费原报价，不重新报价。
3. 价格不可用、过期或版本不匹配时明确报错，不使用写死的 `$4`、公开价或 fallback 价继续执行。
4. 调整单价去 Sub2，调整换算汇率用 SEP 现有汇率设置；不新增视频专用汇率或价格倍率。
5. 不改变已冻结报价、历史账单或历史结算金额。

首版无需扩大客户端报价协议。现有 `amountUsd / amountCny / usdToCnyRate / pricingVersion` 已足以显示费用及关联核对。若后续要展示分组和倍率来源，再单独扩展审计字段。

### 4.5 复用现有错误响应

现有 `backend/src/common/filters/http-exception.filter.ts` 已能保留网关的 `error.code` 和 `error.requestId`。无需新建错误包装层。

统一约定并测试以下语义：

| 情况 | 响应 | 客户端行为 |
| --- | --- | --- |
| 提交前统一资金不足 | 402 + `INSUFFICIENT_FUNDS`，平台来源 | 明确拒绝，不自动重提 |
| 兼容期旧 SEP 视频预算拒绝 | 402 + `VIDEO_BUDGET_EXCEEDED`，平台来源 | 显示专项预算不足，不伪装成生成失败 |
| 提交前授权撤销 | 403 + `MEDIA_FORBIDDEN`，平台来源 | 展示授权原因，不猜测内容违规 |
| 报价过期 | 409 + `QUOTE_EXPIRED`，平台来源 | 停止该次提交，不自动刷新报价并重提 |
| 企业并发已满 | 409 + `VIDEO_CONCURRENCY_LIMIT`，平台来源 | 提示稍后由用户重新发起 |
| 请求已接收但派发或账务不明 | 原请求回执中的未知状态 | 继续按原身份核对 |
| 网络中断、无法解析或未识别错误 | 无可信的确定拒绝证据 | 保留 `MAYBE_SENT`，只查原请求 |

为本地业务错误补充 `source: 'platform'` 和静态安全文案，并验证经现有 filter 后字段仍在。不要直接透传 Sub2 任意 message 或完整异常对象。

仅“HTTP 状态 + 白名单业务码 + 平台来源 + 已测试的提交前语义”共同匹配，才认定本次明确未派发；不能把全部 4xx 或 5xx 判定成未提交。重复身份、既有回执与跨作用域冲突不属于这个简化规则。

资金不足目前可能已经创建失败回执，但预算拒绝可能完全没有回执。两者都不能伪造 receipt；已有失败回执继续保留在服务端，以供关联审计。

## 6. Electron 配套修改

以下路径相对于当前 `sep-client` 仓库。

### 6.1 读取安全的业务错误

修改 `electron/data/sep-video-media-gateway.ts`：

- 对错误响应按现有有界 JSON 读取方式解析，校验 MIME、体积、字段类型。
- 只提取已知业务码、可信的平台来源、HTTP 状态、请求阶段和受限格式的 request ID。
- 用本地静态文案展示原因，不打印原始响应体、URL 查询参数、提示词或凭据。
- 未知、非 JSON、超大或字段非法的错误响应，保留为无法确认的错误；不据此解除提交不确定性。
- 不增加 POST 自动重试。

### 6.2 复用现有状态，区分明确拒绝与未知

修改 `electron/service/video-service.ts`，并按需调整 `electron/domain/video-media.ts` 的校验与测试。

首版不增加第二套提交状态机，也不将 `MAYBE_SENT` 回退成 `NOT_SENT`：

| 本次证据 | 本地持久化 | 展示与恢复 |
| --- | --- | --- |
| 请求尚未发送 | `NOT_SENT` | 沿用现有未提交语义 |
| 原 POST 收到可信的提交前拒绝 | `MAYBE_SENT` + `STOPPED` + 白名单错误码 | 展示“提交被拒绝”，停止自动查回执，不自动再提交 |
| 原 POST 响应丢失或无法确认 | `MAYBE_SENT` + `INTERRUPTED` + 未知错误 | 展示“提交结果待确认”，只能查原 clientRequestId |
| 获取原回执 | `RECEIPTED` + 原 receipt | 按服务端任务、账务及下载状态处理 |

`MAYBE_SENT` 继续表示“客户端已进入可能发送 POST 的阶段”，明确拒绝由受控错误码和停止状态共同表达。所有视图和恢复入口复用同一个确定拒绝判定，避免仅停止定时器却在重启后继续查询。

允许写入“确定拒绝码”的入口必须是上节的可信错误分类结果；查询失败、下载失败和非受控异常不得伪装成提交前拒绝。冻结的请求、报价及 clientRequestId 不变。

### 6.3 纠正工具和面板反馈

涉及：

- `electron/service/mock-video-host-service.ts`：`jobView()` 及恢复筛选。
- `electron/pi/sdk/pi-coding-agent-adapter.ts`：视频工具输出 schema。
- `src/components/workspace/VideoArtifactsPanel.tsx`：任务状态和账务文案。

要求：

1. 明确拒绝且没有上游派发、预占的证据时，可展示 `NOT_RESERVED`；原回执存在时优先使用回执账务事实。
2. 对真实模式的 `MAYBE_SENT`、无回执、且非确定拒绝任务，用现有 `RECONCILING` 展示“账务待确认”。不再默认 `NOT_RESERVED`。
3. 工具保留白名单错误码与安全文案，删除把所有错误转换成 `Video job reported an error.` 的行为。
4. “报价 ¥28.80”“费用已预占”“实付 ¥…/已结算”分开表达，只有有效结算证据才能说已经扣费。
5. 不把 `SUBMISSION_UNKNOWN` 翻译成“视频生成失败”，也不建议修改提示词、品牌词或改走图生视频来解决资金错误。
6. 用户重新发起是新的付费动作，走完整报价与审批；既有恢复、重新下载按钮绝不能创建新生成请求。

这些修改沿用现有字段和账务枚举，减少持久化升级成本；仍需验证旧任务读取和客户端降级兼容。

## 7. 校验收敛边界

| 校验 | 处理 |
| --- | --- |
| 视频专用月预算及历史金额累计 | 删除真实执行依赖 |
| Skill 下载作为每次视频调用的授权前置条件 | 不再引入；维持已有授权与 Skill 准备解耦 |
| 同一不可变对象在同一信任域内反复 parse | 有覆盖后合并，优先复用已有解析结果 |
| controller 输入与 Sub2 外部响应校验 | 保留，属于不同信任边界 |
| profile 所属、引用图所属与数据作用域 | 保留 |
| 报价冻结、审批后授权撤销检查 | 保留，异步等待期间配置可能变化 |
| 报价阶段资金预览与提交时原子预占 | 保留，前者不能替代后者 |
| 并发、幂等、CAS、提交前 dispatch 标记 | 保留 |
| 输出大小、类型、哈希和账单关联 | 保留 |

本次优先删除预算闸门和错误包装，不顺带大改各层授权结构。额外合并重复校验必须先指出具体重复读取及覆盖证据，不能泛化为“只校验一次”。

## 8. 开发顺序与验收

### 阶段一：客户端先识别明确错误

兼容仍执行预算的旧 SEP，修复 402、无回执账务和工具错误码展示。使用合成错误响应和本地 fixture 验证，不请求生产报价或生成。

### 阶段二：SEP 下线专项预算并同步后台 UI

删除真实预算执行逻辑和历史扫描，保留字段兼容、授权与原子并发。检查现有零预算企业的禁用意图，迁移到已有执行开关后再启用新行为。部署本身不属于编写本文的操作范围。

### 阶段三：只读核对已有任务

历史 `SUBMISSION_UNKNOWN` 不批量改成失败或未扣费。先按原 clientRequestId 核对 SEP 请求、报价消费、资金预占和上游关联证据；404 本身不构成未派发证明。不为修复显示问题重新报价或生成。

### 必须覆盖的测试

| 场景 | 通过标准 |
| --- | --- |
| Sub2 报价 4 美元、汇率 7.2 | 冻结 28.800000 CNY，不重复乘倍率或时长 |
| 旧预算为 0 或累计超旧预算，授权及资金有效 | 新 SEP 不再返回 `VIDEO_BUDGET_EXCEEDED` |
| 授权关闭、profile 撤销或并发已满 | 继续阻止派发，无新增上游 POST |
| 两个并发 claim、重复 clientRequestId、报价重复消费 | 并发上限和原有幂等保证仍成立 |
| 402 + 可信平台资金不足码 | 客户端展示真实原因，重启后也不自动轮询或重提 |
| 402 无业务码、HTML、伪造来源或错误体不合法 | 保持提交未知，不宣称未收费 |
| POST 超时后查到已成功的原回执 | 只查询和保存原结果，submit 调用计数仍为 1 |
| 原请求查询 404 | 保留未知，不回退为未发送 |
| 无回执且提交未知 | 工具和 UI 显示账务待确认 |
| 旧策略和旧本地任务 | 仍能读取；不改写历史金额或请求身份 |
