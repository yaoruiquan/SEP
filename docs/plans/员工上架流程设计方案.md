# 员工上架流程设计方案

**版本**: v2.0（混合模式）  
**日期**: 2026-07-30  
**状态**: 阶段 1 实施中

---

## 背景

硅基员工平台需要一个员工模板的创建、审核、上架流程。考虑到早期 MVP 和后期生态开放的需求，采用**混合模式**分阶段实施。

---

## 核心概念

### 1. 员工模板（DigitalEmployee）
- 平台商品目录中的"原型"
- 包含：名称、描述、能力类型、行业、岗位
- **状态流转**：DRAFT（草稿）→ PENDING（待审核）→ APPROVED（已发布）/ REJECTED（已拒绝）

### 2. 员工包（EmployeePackage）
- 员工模板的版本化发布
- packageRef：npm / git / zip 三种模式

### 3. 员工实例（EmployeeInstance）
- 企业订阅模板后创建的实例
- 企业可自定义配置
- 这才是"实际使用的硅基员工"

---

## 方案 C：混合模式（分阶段）

### 阶段 1：运营主导（当前实施）

**适用场景**: 早期 MVP，员工模板由平台运营创建

**角色**:
- ✅ 平台运营（admin）- 创建、管理、发布员工
- ❌ 外部开发者 - 暂不开放

**流程**:
```
运营创建员工 → DRAFT（草稿）
       ↓
填写完整信息 + 上传包
       ↓
点击「发布」→ APPROVED（直接上架，无需审核）
```

**管理后台菜单**:
```
├── 员工管理
│   ├── [+ 新建员工] ← 运营专用入口
│   ├── Tab: 已发布 ← 默认 Tab
│   ├── Tab: 草稿
│   └── Tab: 待审核 ← 暂时为空，后期启用
```

**特点**:
- 运营创建的员工**直接 APPROVED**（跳过审核）
- 保留审核代码和 Tab，但当前无数据
- 快速上架，无审核延迟

---

### 阶段 2：生态开放（后期扩展）

**适用场景**: 开放平台，鼓励外部开发者贡献

**新增角色**:
- ✅ 外部开发者（contributor）- 创建、提交员工模板

**新增流程**:
```
开发者创建 → DRAFT
       ↓
开发者提交审核 → PENDING
       ↓
运营审核 → APPROVED（上架）/ REJECTED（需改进）
       ↓
（如果被拒绝）开发者修改 → 重新提交 → PENDING
```

**新增入口**:
```
开发者中心（/creator/*）：
├── 我的员工
│   ├── [+ 创建新员工]
│   ├── 草稿列表
│   └── 已提交（审核中/已通过/已拒绝）
```

**管理后台调整**:
```
├── 员工管理
│   ├── [+ 新建员工] ← 仅运营可见
│   ├── Tab: 待审核 ← 显示开发者提交的（不为空了）
│   ├── Tab: 已发布
│   └── Tab: 全部
```

**特点**:
- 开发者提交的走完整审核流程
- 运营创建的仍然直接 APPROVED
- 审核机制保证质量

## 当前实现（阶段 1）

### 运营端功能

**1. 新建员工** (`/admin/employees/new`)

表单字段:
- 基本信息
  - 员工名称（必填）
  - 描述（必填）
  - 行业（下拉选择）
  - 岗位（下拉选择）
- 能力类型（单选）
  - Agent（智能体）
  - Skill（技能包）
  - RPA（流程自动化）
  - AI_APP（AI 应用）
- 员工包（可选）
  - packageRef 类型：npm / git / zip
  - 包地址/文件

操作:
- [保存为草稿] → status: DRAFT
- [发布] → status: APPROVED，设置 publishedAt

**2. 编辑员工** (`/admin/employees/:id/edit`)

- 草稿状态可以随意编辑
- 已发布状态可以编辑信息，但修改需谨慎（可能影响已订阅企业）

**3. 员工列表** (`/admin/employees`)

Tab 切换:
- 已发布（默认）
- 草稿
- 待审核（当前为空，后期启用）

操作:
- 查看详情
- 编辑
- 删除（仅草稿可删除）
- 下架（已发布 → ARCHIVED）

                ┌─────────┴─────────┐
                │                   │

                │                   │
                ↓                   ↓
         ┌────────────┐      ┌───────────┐
         │  APPROVED  │      │  PENDING  │ ← 开发者提交待审核

               │                   │

               │                   │

               │          │                 │
               │          ↓                 ↓
               │    ┌──────────┐     ┌──────────┐
               │    │ APPROVED │     │ REJECTED │
               │    │（已发布） │     │（已拒绝） │
               │    └────┬─────┘     └────┬─────┘
               │         │                 │
               │         │          [开发者修改]
               │         │                 │
               │         │                 ↓
               │         │           ┌──────────┐
               │         │           │  DRAFT   │
               │         │           │ （草稿）  │
               │         │           └────┬─────┘
               │         │                 │
               │         │          [重新提交]
               │         │                 │
               │         │                 ↓
               │         │           ┌──────────┐
               │         │           │ PENDING  │
               │         │           └──────────┘

         [运营下架]      │

               ↓         ↓
         ┌────────────────────┐
         │     ARCHIVED       │ ← 已下架（不可见）
         │    （已归档）       │
         └────────────────────┘

## 数据库 Schema

```prisma
model DigitalEmployee {
  id          String         @id @default(cuid())
  name        String
  description String?
  industry    String?
  position    String?
  status      EmployeeStatus @default(DRAFT)
  publishedAt DateTime?      // 首次发布时间
  
  metadata    Json?          // 审核信息等
  // metadata 结构：
  // {
  //   reviewedBy: string,      // 审核人 ID
  //   reviewedAt: string,      // 审核时间
  //   reviewNote: string,      // 通过备注
  //   rejectReason: string,    // 拒绝原因
  //   createdBy: string,       // 创建者 ID（阶段2）
  //   creatorType: 'admin' | 'contributor'  // 创建者类型（阶段2）
  // }
  
  packages    EmployeePackage[]
  instances   EmployeeInstance[]
  // ...
}

enum EmployeeStatus {
  DRAFT      // 草稿
  PENDING    // 待审核（阶段2开发者提交）
  APPROVED   // 已发布（市场可见）
  REJECTED   // 已拒绝（阶段2）
  ARCHIVED   // 已归档（已下架）
}
```

## API 端点

### 运营端（阶段 1）

```
POST   /admin/employees              - 创建员工（运营）
GET    /admin/employees              - 员工列表（支持 ?status= 筛选）
GET    /admin/employees/:id          - 员工详情
PUT    /admin/employees/:id          - 更新员工
DELETE /admin/employees/:id          - 删除员工（仅草稿）
POST   /admin/employees/:id/publish  - 发布员工（DRAFT → APPROVED）
POST   /admin/employees/:id/archive  - 下架员工（APPROVED → ARCHIVED）
```

### 审核端（阶段 2）

```
POST /admin/employees/:id/approve  - 审核通过（PENDING → APPROVED）
POST /admin/employees/:id/reject   - 审核拒绝（PENDING → REJECTED）
```

### 开发者端（阶段 2 待实现）

```
POST   /creator/employees             - 创建员工（开发者）
GET    /creator/employees             - 我的员工列表
POST   /creator/employees/:id/submit - 提交审核（DRAFT → PENDING）
```

## 业务规则

1. **只有 APPROVED 状态的员工才能被企业订阅**
2. **运营创建的员工直接 APPROVED**（阶段 1）
3. **开发者创建的员工初始 DRAFT，提交后 PENDING**（阶段 2）
4. **只有 PENDING 状态才能被审核**
5. **草稿可以随意修改和删除**
6. **已发布的员工可以下架（ARCHIVED），但不建议删除**（已有企业订阅）

## 附录

### 为什么不是纯审核模式？

**纯审核模式**（运营创建也要审核）的问题:
- ❌ 早期只有运营创建，审核自己没意义
- ❌ 增加操作步骤，降低效率
- ❌ 阶段 1 的"待审核" Tab 永远为空

**混合模式**的优势:
- ✅ 阶段 1 快速上架，无审核延迟
- ✅ 阶段 2 平滑过渡到开放生态
- ✅ 代码复用，审核功能已就绪
