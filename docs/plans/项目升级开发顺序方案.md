# 项目升级开发顺序方案

> 依据：[硅基员工平台-方向调整设计方案-v3](../architecture/硅基员工平台-方向调整设计方案-v3.md)
> 现状基线：16 个 Prisma 模型、9 个后端模块、Next.js 前端（个人视角）
> 排序原则：**按模块优先级**，不按时间；优先级 = 阻塞关系 × 交付价值

---

## 0. 一个必须先讲清的前提

已确认「第一个员工 = 可下载的 skills 包 + 一份说明，用户把它放进自己 agent
的 skills 目录即可使用」。这个决策改变了平台的技术边界：

**执行不仅不在平台，模型调用也不经过平台。**

| 设计方案中的能力 | 在本 MVP 中的实际状态 |
|---|---|
| §5.2 客户端模型网关 | ❌ **无作用对象** —— 用户用自己的模型渠道 |
| token 计量 / 算力扣减 | ❌ **无数据来源** |
| 算力余额硬限制 | ❌ 无从限制 |
| 激活凭据的强制力 | ⚠️ 大幅削弱 —— skills 是纯文本，拷走即可用 |
| 已完成的计费设施 | ⏸️ **闲置**（价格表、保底计费、汇率配置均已验证可用，但本期无用武之地）|

**因此本方案的核心结论**：MVP 的价值主线是
**「发现 → 订阅 → 授权 → 下载」这条分发链路**，而不是运行与计量。
平台在本期是一个**带企业组织与权限的软件分发站**。

计量与网关不删除、不推进，等员工形态演进到"需要平台代调模型"时再启用。
这不是妥协，而是与当前员工形态匹配的合理范围。

> ⚠️ 若这一判断与业务预期不符（例如商业模式依赖算力计费），
> 需要回头讨论员工形态 —— 因为**只要执行与模型调用都在用户侧，
> 平台就无法计量**，这是形态决定的，不是实现问题。

## 1. 模块优先级总览

```
P0  企业组织基座 ──────────► 一切权限与归属的前提，零依赖
     │
     ├─► P1  员工模板与实例  ──► 市场卖什么、企业拿到什么
     │        │
     │        ├─► P2  人才市场（应用 A · 公开域）
     │        ├─► P2  企业管理台（应用 A · 登录域）
     │        └─► P3  员工包与分发（含运营端 · 应用 B）
     │
     └─► P4  基础清理与收尾
              P5  暂不推进（保留代码）
```

| 优先级 | 模块 | 阻塞谁 | 现有基础 |
|---|---|---|---|
| **P0** | 企业组织基座 | 所有其他模块 | ❌ 完全缺失 |
| **P1** | 员工模板 / 企业实例 | 市场、管理台、分发 | ⚠️ `DigitalEmployee` 需拆分 |
| **P2** | 人才市场（公开） | — | ⚠️ `(user)/marketplace` 可改 |
| **P2** | 企业管理台 | — | ❌ 完全缺失 |
| **P3** | 员工包与分发 + 运营端 | 端到端验收 | ⚠️ `(admin)` 可迁 |
| **P4** | 清理与收尾 | — | — |
| **P5** | 暂不推进 | — | ✅ 保留不删 |

## P0 —— 企业组织基座

**为什么最高优先**：现有 `User.role` 只有三个全局角色
（`USER` / `CONTRIBUTOR` / `ADMIN`），无法表达"某企业的管理员"。
企业、部门、成员不存在，则「不同角色不同权限」无从落地，
企业管理台（P2）做不出来，实例归属（P1）也没有主体。

**零依赖，可立即开工。**

### P0.1 新增模型

| 模型 | 要点 |
|---|---|
| `Enterprise` | 数据与权限隔离边界；套餐与算力账户挂此层 |
| `Department` | 树形，`parentId` 自引用 |
| `EnterpriseMember` | `User` × `Enterprise` 关联，承载**企业内角色** + 所属部门 |
| `EmployeeGrant` | 实例授权给哪些部门 / 成员 |

企业内角色枚举：`ENTERPRISE_ADMIN` / `DEPT_MANAGER` / `MEMBER`。

> **关于 `EnterpriseMember`**：已确认 MVP 不做多企业切换，
> 但仍建议用关联表而非把 `enterpriseId` + `role` 塞进 `User`。
> MVP 阶段每人恰好一条记录，前端读第一条即可；将来放开多企业
> 只需删约束，不必做数据迁移与全量权限改写。
> 这是本方案唯一建议"多做一点"之处，成本近零。

### P0.2 主体改造（破坏性变更）

```
Subscription    userId  → enterpriseId    // 订阅主体是企业
ComputeAccount  userId  → enterpriseId    // 套餐含算力额度，挂企业
```

⚠️ 这两处是**现有表的主体变更**，涉及迁移。因当前只有演示数据，
建议直接重置演示数据而非写数据迁移脚本。

### P0.3 自助注册

三步内完成：注册账号时填公司名 → 自动创建企业 → 注册人即首个企业管理员。
不做资质审核、不做邀请码。

### P0.4 权限守卫

- 企业范围守卫：请求只能访问自己企业的数据（**这是多租户的核心防线**）；
- 角色守卫：按企业内角色判断操作权限。

> 现有 `JwtAuthGuard` 只解决"是否登录"，企业隔离必须新增。
> 建议在守卫层强制注入 `enterpriseId` 过滤条件，
> 而非依赖每个 service 自觉传参 —— 后者迟早会漏。

### 验收
- 能自助注册企业，注册人为管理员；
- 能建部门树、加成员、设企业内角色；
- **A 企业用户无法读取 B 企业任何数据**（多租户隔离）。

## P1 —— 员工模板与企业实例

**依赖 P0。** 现有 `DigitalEmployee` 一张表兼任"市场上卖的东西"和
"企业拿到的东西"，必须拆分（设计方案 §6.4）。

### P1.1 拆分

| 新对象 | 承载 |
|---|---|
| `EmployeeTemplate` | 市场侧：名称、介绍、能力清单、适用行业岗位、履历数据、开发者、审核状态 |
| `EmployeeTemplateVersion` | 版本号、变更说明、发布时间、对应员工包 |
| `EmployeeInstance` | 企业侧：所属企业、来源模板 + **锁定的版本**、企业内名称、部门、配置、状态 |

**关键约束**：
- ❌ 不能用 `@@unique([enterpriseId, templateId])` —— 同企业可多实例（决策 8）；
- ✅ 实例必须存 `templateVersion` —— 否则无法做提示式升级（决策 14）。

实例状态：`PENDING_ACTIVATION` / `ACTIVE` / `SUSPENDED` / `REVOKED`。

### P1.2 现有 Capability 体系的定位

`Capability` + `AgentConfig` / `RPAConfig` / `SkillConfig` / `AIAppConfig`
四张配置表**保留**，语义调整为「模板声明自己由哪些能力构成」，
用于市场详情页展示"我能做什么"。

`SkillConfig` 已有 `template` / `modelId` / `temperature` / `maxTokens`，
与"skills 包"形态天然契合，可作为第一个员工的元数据载体。

### P1.3 提示式升级

模板发新版 → 实例不自动跟进 → 企业管理台显示升级提示 → 企业主动确认。

升级 = 更换实例的 `templateVersion` + 重新下载对应员工包。
配置兼容性 MVP 不做自动迁移，提示里直接写"需重新检查配置"。

### 验收
- 市场模板与企业实例数据分离；
- 同企业能有两个来自同一模板的实例，各自独立配置；
- 模板发新版后，实例仍锁定旧版，管理台出现升级提示。

## P2 —— 应用 A：人才市场 + 企业管理台

**依赖 P1。** 两块功能域合并为一个前端应用（设计方案 §8.2），
因为它们服务同一个人的同一段连续动作。

### P2.1 市场域（公开，无需登录）

```
(market)/
├── page.tsx      员工目录：分类 / 搜索 / 筛选
└── [id]/         员工详情：五段式 + 订阅入口
```

详情页按总体方案 §7.1 五段式组织：
**我是谁 / 我能做什么 / 如何使用 / 做得怎么样 / 如何获得**。

- 访客可浏览目录与详情；
- 订阅需登录，未登录点订阅 → 引导登录；
- 现有 `(user)/marketplace` 可改造复用。

### P2.2 企业域（需登录）

```
(enterprise)/
├── org/          组织架构：部门树 + 成员
├── employees/    已订阅实例：配置 / 下载 / 激活码 / 停用 / 升级提示
├── grants/       授权管理 + 申请审批
└── compute/      算力用量（⚠️ 本期无数据源，见 §0）
```

**三角色可见性**（同一套导航的不同可见项，非不同应用）：

| | 市场 | 实例 | 组织架构 | 授权审批 |
|---|---|---|---|---|
| 企业管理员 | 浏览 + **订阅** | 全部可配置 | 可编辑 | 可审批 |
| 部门负责人 | 浏览 + **申请** | 本部门 | 只读 | 本部门 |
| 普通成员 | 浏览 + **申请** | 仅被授权的 | 不可见 | 不可见 |

> 「订阅」要花企业的钱，只有管理员能做；其他角色只能**申请**。
> 不做这个区分，普通成员点订阅再报 403 是可预见的体验问题。

**`compute/` 页面的处理**：本期无计量数据（§0），
建议**先不做这个页面**，或只放一句"当前员工形态在本地运行，
平台不计量算力"。**不要做一个永远显示 0 的页面** —— 那会让人以为是 bug。

### P2.3 可直接复用的前端资产

`components/ui/*`、`features/auth`、`features/model`、
TanStack Query + Zustand 数据层约定。

### 验收
- 未登录能浏览市场目录与详情；
- 管理员能订阅并生成企业实例；
- 三种角色登录后看到的导航项与数据范围符合上表；
- 成员能对未授权员工发起申请，管理员能审批。

## P3 —— 员工包与分发 + 应用 B（运营端）

**依赖 P1。** 这是"可下载"的落地，也是端到端验收的最后一环。

### P3.1 员工包（`EmployeePackage`）

- 所属模板版本、形态（MVP 只做 `ZIP`）、文件地址、大小；
- **SHA-256 校验和**（必需 —— 用户要能验证包未被篡改，也是审核留痕）；
- 上传、版本管理、发布状态。

### P3.2 下载

- 带时效的下载令牌（防止链接被随意转发）；
- 下载权限校验：请求者所属企业是否已订阅该模板；
- 附带**使用说明**：如何解压、把 skills 放到 agent 的哪个目录、如何配置。

> 已确认第一个员工的交付物 = **skills 包 + 说明书**（决策 12），
> 不做客户端壳。说明书是交付物的一部分，不是附属文档。

### P3.3 应用 B（运营端，独立部署）

```
templates/     员工模板 + 版本 + 员工包上传
review/        上架审核
enterprises/   企业列表与套餐
models/        模型白名单（现有 (admin)/admin/models 迁入）
settings/      系统设置（现有 (admin)/admin/settings 迁入）
```

**独立部署的理由是安全边界**，不是代码复用：运营端可见全平台数据，
不应与面向客户的代码同包同入口。两应用共享 UI 组件库。

### P3.4 激活凭据（可选，视投入决定）

设计方案 §4.2 的激活码 + 短期令牌机制，在 skills 形态下**约束力有限**
（纯文本拷走即可用）。

建议：**MVP 先做"下载需登录 + 需已订阅"这一层校验即可**，
激活凭据等到有真正的客户端壳时再做。否则是为一个绕得过去的锁
投入不小的复杂度。

### 验收
- 运营能上传员工包并发布版本；
- 企业管理员能下载 ZIP，校验 SHA-256 一致；
- 未订阅企业无法下载；
- 用户按说明把 skills 放进自己 agent 目录后可正常使用（端到端打通）。

## P4 —— 清理与收尾

与方向无关，可随时插入：

- 演示数据重置：现有 `demo-emp-*`、`coze-verify-*`、`e2e-notools`
  等按新模型重建；
- `web/tsconfig.tsbuildinfo` 是构建产物却被 git 追踪，移出并加 `.gitignore`；
- 现有 `(admin)` 路由迁往应用 B；
- `UserRole` 枚举与 `EnterpriseMember` 角色的关系梳理
  （全局角色只保留"平台运营人员"语义）。

## P5 —— 暂不推进（代码保留，不删除）

| 模块 | 状态 | 保留理由 |
|---|---|---|
| 对话/会话（SSE 流式）| ⏸️ | 已验证可用；若员工形态演进到需要对话补充，逻辑可复用 |
| 工具调用循环 | ⏸️ | 4 个 bug 已修并有测试；下沉到客户端时可移植 |
| 能力适配器（Coze 已端到端验证）| ⏸️ | 证明"平台调外部低代码智能体"可行；员工客户端内部需要时可移植 |
| 计费设施（价格表 / 保底计费 / 汇率）| ⏸️ | 已验证；等员工形态需要平台代调模型时启用（§0）|
| `Task` 对象与任务上报 | ⏸️ | 决策 15：任务本地发起、结果不上报 |
| Agent 编排（多员工协同）| ⏸️ | 设计方案 §8.3 亦列为后续 |
| OpenCode 适配器 | ⏸️ | 有 4 处状态值 bug 待修；服务未部署 |

**明确不删除任何已验证代码。** 其中沉淀的经验
（AI SDK v7 字段结构、Coze SSE 解析、工具名归一化、保底计费取向）
在形态演进时可直接复用。

## 建议起点

**P0.1 + P0.2 + P0.4**（企业组织模型 + 主体改造 + 企业范围守卫）。

理由：
1. 零依赖，不被任何待确认事项阻塞；
2. 是其余所有模块的前提；
3. **多租户隔离属于安全基线**，越早建立越好 ——
   等业务代码铺开后再补企业过滤，漏掉一处就是跨企业数据泄露。
