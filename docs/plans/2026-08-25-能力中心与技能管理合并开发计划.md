# 能力中心与技能管理合并 Implementation Plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** 将企业端“能力贡献中心”和“技能管理”统一为一个能力中心入口，保留发布治理、Skill 版本迭代、员工运行配置之间清晰的业务边界，并分四阶段完成迁移。

**Architecture:** 前端统一入口为 `/contributions`，能力详情工作区承载能力资产、发布流程、Skill 版本迭代和贡献奖励；`Capability` 与 `SkillVersion` 数据模型继续独立。能力中心只管理能力生命周期和版本治理，硅基员工详情继续负责员工实际使用哪个 Skill 版本。旧 `/skills` 路由保留兼容跳转，平台运营端在第四阶段统一为能力审核入口。

**Tech Stack:** Next.js 15 App Router、React、TanStack Query、NestJS、Prisma、PostgreSQL、Zod、Tailwind/Shadcn UI。

---

## 业务边界

| 用户动作 | 归属模块 | 目标入口 |
| --- | --- | --- |
| 创建 Skill/Agent/RPA/AI App | 能力资产 | 能力中心 |
| 编辑 Skill 正文 | Skill 版本治理 | 能力中心 → 版本迭代 |
| 企业审核能力或企业 Skill 版本 | 企业发布治理 | 能力中心 → 审核与发布 |
| 授权公开投稿、平台审核 | 平台发布治理 | 能力中心 → 审核与发布 |
| 查看奖励、积分、采用情况 | 贡献激励 | 能力中心 → 贡献奖励 |
| 选择某个硅基员工实际使用的版本 | 运行配置 | 硅基员工详情/能力绑定 |
| 平台运营审核投稿与平台版本 | 运营审核 | 平台端 → 能力审核 |

不做数据模型合并：`Capability` 是能力资产，`SkillVersion` 是 Skill 内容版本，`SubscriptionSkillVersion` 是企业对员工的运行时选择记录。

## 四阶段交付概览

### 阶段一：统一前端入口

目标：用户只看到一个“能力中心”一级导航，旧 `/skills` 链接可兼容访问。

交付：导航、面包屑、旧路由重定向、能力中心二级导航骨架、入口级回归测试。

### 阶段二：迁移 Skill 版本迭代

目标：将当前 `/skills` 的版本列表、预览、编辑、企业审核、提交平台审核迁移到能力详情的“版本迭代”视图。

交付：版本迭代 tab、版本时间线、版本编辑页入口、版本 API hooks 复用、版本状态映射、Skill 空状态和错误状态。

### 阶段三：增加使用情况与运行配置链接

目标：在能力详情中明确“哪些硅基员工正在使用哪个版本”，但不把员工运行配置逻辑塞进贡献服务。

交付：能力使用情况 tab、后端只读查询、员工与版本映射、跳转员工详情/能力绑定、权限和空状态。

### 阶段四：统一平台运营审核

目标：平台端将“能力投稿”和“技能版本”统一为“能力审核”工作台，按类型和审核阶段筛选。

交付：运营端统一路由与导航、能力/SkillVersion 双队列聚合接口、筛选器、审核详情、旧 `/admin/contributions` 与 `/admin/skills` 兼容跳转。
