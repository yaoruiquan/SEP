## P0 — 术语体系统一（最高优先级）

会议明确这是优先级最高的事项。理由不只是文案好看：术语是产品调性的载体，"硅基 / 碳基"这组对比是对外宣讲的核心叙事，越晚统一，后续要改的代码面越大。

详细规范见独立文档：[`2026-08-10-术语规范与拟人化方案.md`](./2026-08-10-术语规范与拟人化方案.md)

### P0-1 建立前端文案单一来源

**问题**: 当前文案散落在各组件里，改一次要全仓库搜。

**方案**: 新建 `web/src/locales/zh-CN.ts` 作为唯一文案源，组件只引用 key，不写死中文。

```typescript
// web/src/locales/zh-CN.ts
export const zhCN = {
  employee: {
    entity: '硅基员工',
    market: '硅基人才市场',
    mine: '我的硅基员工',
    hire: '立即招聘',
    dismiss: '解聘',
    status: {
      WORKING: '工作中',
      PAUSED: '已暂停',
      ACTIVE: '已上岗',
      PENDING_ACTIVATION: '待上岗',
      DISMISSED: '已解聘',
    },
  },
  member: { entity: '碳基员工', list: '团队成员' },
  capability: { entity: '技能', grant: '赋予技能', revoke: '撤销技能' },
} as const;
```

**为什么不直接用 i18n 库**: 当前只有中文，引入 next-intl 属于过度设计。一个常量文件 + `as const` 已经拿到类型安全和集中管理，将来真要多语言再迁移，成本不变。

**验收**: 全仓库 `grep -r "数字员工" web/src` 返回空。

### P0-2 核心术语替换

按替换风险从低到高执行：

1. **纯展示文案**（零风险）— 导航、标题、按钮、空状态
   - 数字员工 → 硅基员工
   - 员工市场 → 硅基人才市场
   - 成员管理 → 团队成员（碳基员工）
2. **状态标签**（低风险）— 只改 label 映射，不动枚举值
   - 运行中 → 工作中 / 停用 → 已暂停 / 启用 → 已上岗
3. **操作动词**（低风险，需同步确认弹窗文案）
   - 订阅 → 立即招聘 / 删除 → 解聘 / 激活 → 上岗
4. **"下载所有技能" → "下载企业客户端"**（会议明确纠正的语义错误）

**关键约束**: **不改数据库枚举值、不改 API 字段名**。`InstanceStatus.PENDING_ACTIVATION` 保持原样，只在展示层映射为"待上岗"。改枚举需要迁移 + 前后端同步发布，收益为零、风险不小。

### P0-3 "员工实例"展示层命名（已完成）

会议指出"我的员工"和"员工实例"两个概念对用户重复。

代码层 `EmployeeInstance` 不动，仅改展示层。术语映射统一维护在 `web/src/locales/zh-CN.ts`。

## P0-5 用户与企业绑定机制（新增）

会议演示时出现"新注册企业看到已有员工"，事后确认是**用了此前注册过的邮箱**，不是数据隔离缺陷。但它暴露了一个真实的设计空白：**已注册用户如何与企业建立/解除归属关系，目前没有完整设计**。

会议上老板已经把场景和结论都讲清楚了：个人邮箱在上家公司注册过，上家公司也是平台客户，人跳到新公司后还要负责同一块业务。结论是「**必须保证用户唯一**，从原公司注销或解绑，否则系统会越来越复杂」。

### 现状核对（代码事实）

| 位置 | 现状 |
|------|------|
| `auth.service.ts:69` `register()` | 注册 = 开公司。一次事务建 User + Enterprise + EnterpriseMember，注册人直接为 `ENTERPRISE_ADMIN` |
| `POST /enterprise/members` | 第二个人进企业的**唯一途径**，由管理员代建账号并设初始密码 |
| `member.service.ts:70-77` | **缺口所在**：已注册用户直接抛 `ConflictException("已注册并归属其他企业，当前版本不支持跨企业加入")`，无任何出路 |
| 邀请机制 | 不存在（全仓库 `grep invite` 零结果） |
| 解绑 / 离职接口 | **不存在** —— 老板说的"从原公司解绑"没有对应实现 |
| `EnterpriseMember` | `@@unique([userId, enterpriseId])` 结构上支持多企业，但业务层按单企业处理 |

即：新公司管理员想加这个人，系统只会告诉他"加不了"，然后流程终止。原公司也没有任何界面能把人放出来。

### 设计方案

**基本原则**：沿用会议结论 —— MVP 阶段**一个用户同时只归属一个企业**。不做多企业切换，但保留 `EnterpriseMember` 关联表结构，将来放开无需数据迁移（这与 schema 现有注释一致）。

#### 1. 注册入口分流

当前注册强制建企业，需要拆成两条路：

```
注册页
├── 「我要为公司开通」  → 建 User + Enterprise + Member(ENTERPRISE_ADMIN)   ← 现有逻辑
└── 「我受邀加入公司」  → 走邀请码/邀请链接，建 User + Member(MEMBER)      ← 新增
```

后者解决"我只想有个账号、等公司拉我进去"这条路径不存在的问题。

#### 2. 邀请机制（替代管理员代设密码）

现在管理员要替成员想一个初始密码，用户拿到的是别人知道的密码 —— 既不安全，也不像正规产品。

```prisma
/// 企业邀请。用一次性 token 换取加入资格，
/// 密码由被邀请人自己设置，管理员不接触。
model EnterpriseInvitation {
  id           String @id @default(cuid())
  enterpriseId String
  /// 被邀请邮箱。邀请与邮箱绑定，防止链接被转发给他人使用。
  email        String
  /// 一次性令牌（存哈希，不存明文）
  tokenHash    String
  role         EnterpriseRole @default(MEMBER)
  departmentId String?
  position     String?

  status    InvitationStatus @default(PENDING)
  expiresAt DateTime
  /// 谁发的邀请，用于审计
  invitedBy String

  createdAt  DateTime  @default(now())
  acceptedAt DateTime?

  enterprise Enterprise @relation(fields: [enterpriseId], references: [id], onDelete: Cascade)

  @@unique([enterpriseId, email, status])
  @@index([enterpriseId])
  @@map("enterprise_invitations")
}

enum InvitationStatus {
  PENDING   // 待接受
  ACCEPTED  // 已接受
  EXPIRED   // 已过期
  REVOKED   // 管理员撤回
}
```

**为什么存 `tokenHash` 而不是明文 token**：邀请链接等同于一次性登录凭证，明文入库意味着数据库泄露即可冒充任意被邀请人。与 `EnterpriseApiKey.keyHash` 的处理保持一致。

**为什么邀请绑定邮箱**：否则链接被转发，任何人都能用它加入企业。

**MVP 阶段不发邮件**：生成邀请链接由管理员自行转达（微信/钉钉），链接形如 `/join?token=xxx`。邮件服务是独立的基础设施工作，不阻塞本轮。

#### 3. 已注册用户的三种情况

改写 `member.service.ts` 的分支，把死路变成明确出路：

| 情况 | 当前行为 | 新行为 |
|------|---------|--------|
| 已是本企业成员 | 抛 409 | 保持，提示"该成员已在贵司" |
| 已注册但**无企业归属** | 抛 409（不合理） | **允许直接邀请加入** |
| 已注册且归属**其他企业** | 抛 409，无出路 | 返回明确指引：需先由原企业解除归属，或用户自行申请离职 |

第二种情况是当前实现的明显缺陷 —— 一个没有任何企业归属的账号，本该是可以被邀请的。

#### 4. 解绑 / 离职流程（补齐缺失环节）

老板说的"从原公司注销或解绑"需要两个入口：

**入口 A：原企业管理员移除成员**
```
DELETE /enterprise/members/:id   ← 接口已存在，需补充语义
```
需要明确移除后的处置：
- `EnterpriseMember` 记录删除或标记为 `LEFT`
- User 账号**保留**（用户仍可登录，只是无企业归属，处于"待加入"状态）
- 该成员被授权的硅基岗位（`EmployeeGrant`）一并回收
- **企业侧的技能覆写、知识库、工作记录全部保留** —— 这正是会议强调的"员工走了，东西全部沉淀在我这里"

**入口 B：用户自行申请离职**
```
POST /auth/leave-enterprise   ← 新增
```
用户主动解除归属，供"原公司已经不管这事了"的情况兜底。是否需要原企业管理员审批，见下方待确认问题。

#### 5. 用户状态机

补上"无企业归属"这个当前被忽略的中间态：

```
注册(开公司) ─────────────> [企业管理员]
                                │ 移除自己? (不允许，需先转让)
                                ▼
注册(受邀) ──接受邀请──> [企业成员] ──被移除/主动离职──> [无归属]
                                                          │
                                                          ├─ 接受新邀请 ─> [企业成员]
                                                          └─ 开新公司   ─> [企业管理员]
```

**"无归属"状态下的产品行为**：可以登录，但企业端功能全部不可用，落地页提示"您当前未归属任何企业，请等待邀请或创建企业"。当前系统没有这个态，用户会进到一个数据全空的企业端界面。

### 为什么放 P0

三个理由：

1. **演示会撞上**。老板已经用自己的老邮箱撞过一次了。宣讲现场任何人用曾注册过的邮箱走一遍注册，就会走进死路。
2. **它是"招聘"叙事的一环**。碳基员工怎么进公司、怎么离职，和硅基员工的招聘/解聘是同一套语言。术语统一时如果这块逻辑还是残缺的，叙事会断在这里。
3. **改动面会随时间放大**。成员归属是权限、授权、知识库授权的共同上游，越晚补，牵连的模块越多。

## P1 — 技能个性化与沉淀（核心竞争力，本轮做地基）

会议花了最长篇幅讲这个机制，也明确表示"平台级自动蒸馏"是未来的事。本轮只做**能撑起演示叙事的地基**。

### P1-1 企业侧技能覆写（Skill Override）

**需求**: 平台下发默认技能，企业可改提示词 / MD 内容，形成"平台技能 + 企业私有化"的叠加。

**数据模型**（新增，不动 `Capability`）:

```prisma
/// 企业对平台技能的私有化覆写。平台技能保持只读，
/// 企业改动落在这张表，读取时叠加，从而支持「随时回退到平台版本」。
model EnterpriseSkillOverride {
  id           String @id @default(cuid())
  enterpriseId String
  capabilityId String
  /// 覆写内容：提示词、MD 正文、参数默认值。
  /// 用 Json 而非拆列，因为四类能力（agent/rpa/skill/ai-app）可覆写字段不同。
  overrides    Json
  /// 覆写基于的平台技能版本，用于提示「平台已更新」
  basedOnVersion String
  status       SkillOverrideStatus @default(DRAFT)

  enterprise Enterprise @relation(fields: [enterpriseId], references: [id], onDelete: Cascade)
  capability Capability @relation(fields: [capabilityId], references: [id], onDelete: Cascade)

  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  @@unique([enterpriseId, capabilityId])
  @@map("enterprise_skill_overrides")
}

enum SkillOverrideStatus {
  DRAFT      // 草稿，未生效
  ACTIVE     // 已生效
  ARCHIVED   // 已归档（回退到平台版本后保留历史）
}
```

**为什么用覆写表而不是复制一份 Capability**: 复制会立刻产生"平台技能升级后企业副本永久落后"的问题，且无法回答"我改了什么"。覆写表天然保留 diff，回退只需 `status = ARCHIVED`。

**运行时解析顺序**: 平台技能 → 企业覆写 → （未来）岗位级覆写。

### P1-2 技能版本提示式升级

复用 `EmployeeInstance.templateVersion` 已有的设计思路：平台技能发新版**不自动生效**，在企业端显示"平台已更新此技能，查看变更"，由企业主动确认。

会议原话的诉求是"我可以选择接受或不接受"，提示式升级正好对应。

### P1-3 技能沉淀可见性（演示级）

**做**: 企业端展示某技能的覆写历史、被哪些员工实例使用、调用次数。
**不做**: 跨企业蒸馏、Agent 自动学习、每日自动优化 —— 会议已定性为"未来方向，概念阶段"。

演示时的叙事：「这个技能贵司已经调优过 3 次，员工离职这些调优仍然在」。这句话靠上面的数据就能讲，不需要真的做蒸馏。

## P2 — 演示闭环补齐

目标是"开箱即用"的完整链路可走通，支付用模拟。

### P2-1 招聘购物车

会议原话：「不可能订阅一个付一个，很烦」。

**方案**: 前端 Zustand 维护选购清单 → 一次性提交批量订阅接口 → 生成一张合并订单。

**为什么放 P2 而不是 P0**: 单个订阅链路已经能走通，购物车是体验优化。但它在演示中很显眼（企业主一次招 5 个岗），所以排在演示补齐的第一位。

### P2-2 模拟支付流程

会议已确认真实支付（支付宝/微信）延后。本轮实现：

- 企业账户余额（充值走后台手动加值，或"模拟充值"按钮）
- 订阅扣费从平台余额扣，**与 sub2api 的 Token 计费完全分账**
- 订单记录 + 扣费流水，界面可查

**架构上必须现在就分开的原因**: 会议明确"支付必须分离"，如果本轮把订阅扣费也挂到 sub2api 余额上，等真实支付接进来时要拆两套账，返工成本远高于现在就分。所以 —— **支付实现可以推迟，账务模型不能推迟**。

```
SEP 平台余额  ──扣──> 硅基员工订阅费 / 技能购买费
sub2api 余额  ──扣──> Token 消耗（模型调用）
     ↑ 两套余额、两套流水，SEP 通过 API 读取 sub2api 用量，不共享支付通道
```

### P2-3 ~~数据隔离 Bug 修复~~（已排除，非缺陷）

会议现场演示时"新注册企业看到已有硅基员工"，事后确认原因是**演示时用的是此前已注册过的邮箱**，账号本就带有既有企业归属，数据隔离逻辑本身没有问题。此项撤销。

但该现象暴露了一个真实的设计缺口 —— 已注册用户如何与企业建立归属关系，见 [P0-5 用户与企业绑定](#p0-5-用户与企业绑定机制新增)。

## P3 — 知识库调整（我的分析）

你让我自己看知识库要怎么调。核对代码后的结论：**底座不用改，改的是定位和入口**。

### 现状

`backend/src/modules/knowledge/` 已经相当完整：文档解析、分块、向量化、检索、用量日志、按实例/部门授权都有。`KnowledgeGrant` 的 `instanceId` / `departmentId` 双授权维度，恰好匹配会议说的"技能给这个人还是给这个部门"。

### 需要调整的三点

**1. 明确"仅云端"，删掉本地化的中间态**

会议结论是先做云端，本地知识库方案不采纳（理由：向量化数据本质等价于原始数据，用户感知不到安全提升，还增加部署复杂度）。

所以：文档里凡是"本地知识库 / 一键下载安装包 / 本地向量库"的描述都应标注为**已否决**，避免后续开发者按旧文档做。这件事只改文档，零代码成本，但能省掉一次误开发。

**2. 知识库的入口应该挂在硅基员工上，而不是并列的独立菜单**

现在知识库是个独立功能模块。但会议的语境始终是「**某个硅基员工需要知识库，把知识授予这个员工**」—— 知识库是员工能力的一部分，不是平行功能。

建议调整信息架构：

```
我的硅基员工 → 某员工 → 技能配置
                        ├── 已赋予技能
                        └── 已授权知识库   ← 主入口在这里
企业知识管理（独立菜单保留，做批量维护用）
```

这样用户的心智是"给员工配知识"，而不是"管理一个知识库系统"。代码层只需加入口和跳转，`KnowledgeGrant` 不动。

**3. 术语统一（已完成 2026-08-10）**

- "知识库授权给员工" → "授权给员工实例"
- "员工访问知识库" → "硅基员工调用知识库"

所有展示层文案已统一使用"硅基员工"/"员工实例"，不再使用"硅基岗位"。

### 不做的事

- 本地知识库 / 客户端打包（已否决）
- 外部数据源同步、Webhook 拉取（PRD 里的 Phase 2，与本轮演示无关）
- 多向量库选型切换（当前实现够用）

### 风险登记（不阻塞本轮，但要写进文档）

会议后半段老板反复强调的稳定性风险，应该正式记录：企业核心知识全部托管在平台，一旦宕机或丢数据，影响客户正常运营，责任极大。

本轮不为此做架构改造（并发量还没到），但至少要有：知识库文档的定期备份、向量库与原文档的一致性校验。这是低成本的保险。

## 已确认决策（2026-08-10）

四项待定问题均已确认，以下为最终执行口径。

### 决策 1：「员工实例」展示层定名 **硅基员工**（已更新）

**⚠️ 原定名"硅基岗位"已弃用**，最终决策使用"硅基员工"/"员工实例"。

```
我的硅基员工
└── 员工授权配置
    ├── 电商运营总监（销售部）
    ├── 电商运营总监（市场部）   ← 同一模板，两个实例
    └── 数据分析师（战略部）
```

配套文案：「为该部门新增员工实例」「该实例已上岗，工作中」「一次招聘可设置多个员工实例」

代码层 `EmployeeInstance` **不改名**，仅展示层映射。理由见 P0-2 的硬约束：不动数据库枚举与 API 字段。

术语统一见 `web/src/locales/zh-CN.ts`：
- `employee.unit: '硅基员工'` — 实例的展示名
- `employee.grantConfig: '员工授权'` — 管理面板入口名
- `member.entity: '碳基员工'` — 真人成员

### 决策 2：知识库主入口挂到硅基员工下

```
企业端侧边栏
├── 硅基人才市场
├── 我的硅基员工
│   └── 电商运营总监
│       ├── 技能配置
│       └── 知识库授权        ← 主入口
├── 团队成员
└── 企业知识管理             ← 保留，批量维护文档用
```

用户心智是「给员工配知识」，不是「管理一个知识库系统」。后端 `KnowledgeGrant` 不动，只加入口与跳转。

### 决策 3：主动离职 **不审批但通知**

```
用户点击「解除企业归属」
      ↓ 二次确认弹窗

      ↓
原企业管理员收到通知：「张三 已解除与贵司的归属关系」
```

复用已实现的 `notifications` 模块。不锁死用户（避免原公司停用平台后用户永久无法转出），原企业侧留有记录。
