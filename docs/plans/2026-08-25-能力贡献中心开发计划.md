# 能力贡献中心开发计划

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** 为所有注册用户提供统一的能力贡献中心：用户可以创建和迭代 Skill/Agent 等能力，企业拥有企业成员创建的能力，企业管理员审核并授权公开投稿，平台运营审核后才进入硅基人才市场。

**Architecture:** 保留现有 `Capability` 作为能力长期对象，新增企业归属、可见范围和两级审核字段；把 `SkillVersion` 继续作为 Skill 的版本与正文载体，并补齐贡献者创建版本、企业审核、平台投稿授权的接口。前端新增 `(enterprise)/contributions` 能力贡献中心，统一展示能力、版本、审核状态和奖励事件；企业管理员与平台管理员继续使用服务端权限校验，不在前端依赖角色隐藏实现权限。

**Tech Stack:** NestJS, Prisma/PostgreSQL, Zod shared DTOs, Next.js 15 App Router, TanStack Query, shadcn-style components, Vitest/Jest.

## 产品规则

### 身份与归属

- 所有注册用户都可以创建能力，不需要额外申请 `CONTRIBUTOR` 角色。
- `createdById`/现有 `contributorId` 表示实际创作者；如果创作者属于企业，能力 `enterpriseId` 绑定其当前企业。
- 企业成员可以创建、编辑、提交企业审核；企业管理员审核企业能力。
- 没有企业归属的用户可以创建个人能力，第一阶段只允许直接提交平台审核，不自动进入市场。
- 企业成员离职不改变能力的企业归属；管理员需要处理维护人和公开授权。

### 两级审核与可见范围

```text
DRAFT
  -> PENDING_ENTERPRISE_REVIEW
  -> ENTERPRISE_APPROVED  (企业内部可用，默认 ENTERPRISE_PRIVATE)
  -> PENDING_PLATFORM_REVIEW  (仅企业管理员确认后可进入)
  -> PLATFORM_APPROVED  (MARKET_PUBLIC，可进入硅基人才市场)
```

- 企业审核通过后，能力可以在企业内部绑定和使用，但不会自动公开。
- 创作者可以发起“申请提交平台”，但不能代表企业完成公开投稿。
- 企业管理员是平台投稿授权人；如果创作者本人就是企业管理员，则可在同一操作中完成授权。
- 平台运营审核的是平台投稿快照/版本，不直接把企业私有草稿改成公开对象。
- 驳回必须保留原因；修订后重新提交，审核历史不可覆盖。

### 奖励边界

- 第一阶段不接提现，不直接修改企业钱包余额。
- 记录可审计 `ContributionRewardEvent`：审核通过、企业采用、市场采用、有效调用等事件。
- 奖励事件初始状态为 `PENDING`，由后续结算任务转为 `AVAILABLE`/`SETTLED`。
- 测试调用、创建者自用、失败调用和重复刷调用不产生有效使用奖励。
- 贡献奖励归创建人记录；企业采用奖励和公共市场收益归属规则暂以配置字段保存，暂不自动分账。

## 页面信息架构

### `/contributions` 能力贡献中心

- 顶部指标：我的能力、待处理审核、企业内采用、平台采用、待确认奖励。
- 能力列表：名称、类型、归属企业、当前版本、企业审核、平台投稿、可见范围、采用/调用统计。
- 详情工作区：能力概览、版本路线、审核时间线、采用情况、奖励事件。
- 操作：创建能力、编辑草稿、提交企业审核、申请平台投稿、企业管理员确认投稿、创建新版本。
- 只显示当前用户创建或当前企业有权限查看的能力，不复用普通会话列表。

### 创建与版本编辑

- 第一阶段支持 `SKILL` 和 `AGENT`，保留未来扩展 RPA/AI App 的类型入口。
- Skill 编辑器支持 Markdown/SKILL.md 正文、变更说明、输入输出示例和预览。
- Agent 编辑器支持角色说明、平台配置、工具权限说明、输入输出协议；密钥不能回显。
- 创建成功默认 `DRAFT + ENTERPRISE_PRIVATE`（无企业时为个人草稿）。
- 新版本必须填写变更说明；版本内容通过自动校验后才能提交审核。

## 权限矩阵

| 操作 | 创建人 | 企业普通成员 | 企业管理员 | 平台运营 |
|---|---:|---:|---:|---:|
| 创建能力 | 是 | 是 | 是 | 是 |
| 编辑本人草稿/被驳回版本 | 是 | 否 | 可管理本企业 | 是 |
| 提交企业审核 | 是 | 否 | 是 | 是 |
| 审核企业能力 | 否 | 否 | 是 | 是（平台兼容处理） |
| 发起平台投稿申请 | 是（企业审核通过后） | 否 | 是 | 是 |
| 确认平台投稿授权 | 否 | 否 | 是 | 是 |
| 平台审核 | 否 | 否 | 否 | 是 |
| 查看企业私有内容 | 所属企业内按权限 | 所属企业内 | 所属企业内 | 仅审核快照 |

服务端必须基于 `EnterpriseMember.role` 校验企业管理员，不能只看 `User.role`。

## 数据模型变更

### Capability

- 添加 `enterpriseId String?` 和 `Enterprise.capabilities` 关系。
- 添加 `visibility CapabilityVisibility`：`ENTERPRISE_PRIVATE`、`MARKET_PUBLIC`。
- 保留 `contributorId` 作为创作者兼容字段，新增 `createdById` 时评估是否直接复用并在代码中统一命名。
- 添加企业审核字段：`enterpriseReviewStatus`、`enterpriseReviewedById`、`enterpriseReviewedAt`、`enterpriseRejectionReason`。
- 添加平台投稿字段：`platformSubmittedById`、`platformSubmittedAt`、`platformRejectionReason`。
- `Capability.status` 暂保留作为平台公共状态兼容字段；新贡献中心以明确的企业/平台状态为准，迁移时将历史 `APPROVED` 映射为可见范围和平台通过状态。

### SkillVersion

- 允许 `scope=PLATFORM` 的版本由普通注册用户创建，不再要求平台管理员创建。
- 版本提交记录必须保存创建人、企业投稿授权人和平台审核人。
- 新增必要的审核事件字段或复用 `SkillVersionReview`，确保企业审核和平台审核均可追溯。
- 企业版本不得通过修改 `enterpriseId` 直接变成公开版本；平台投稿创建独立快照，保留 `sourceVersionId`。

### ContributionRewardEvent

新增奖励事件表，字段至少包括：

- `id`, `recipientId`, `enterpriseId?`, `capabilityId?`, `versionId?`
- `eventType`: `ENTERPRISE_APPROVED`, `PLATFORM_APPROVED`, `ENTERPRISE_ADOPTED`, `MARKET_ADOPTED`, `VALID_USAGE`
- `points`, `amount?`, `status`, `dedupeKey`, `metadata`, `createdAt`, `settledAt?`

`dedupeKey` 必须唯一，保证重复审核回调、重复调用事件不会重复发奖。

## API 设计

新增/调整 `/api/contributions` 领域接口：

- `GET /contributions/overview`：当前用户贡献指标。
- `GET /contributions/mine`：我的能力列表和状态摘要。
- `GET /contributions/:id`：能力详情、版本、审核历史、奖励摘要。
- `POST /contributions`：创建企业私有能力/个人草稿。
- `PATCH /contributions/:id`：编辑本人可编辑草稿。
- `POST /contributions/:id/submit-enterprise-review`：提交企业审核。
- `POST /contributions/:id/enterprise-review`：企业管理员通过/驳回。
- `POST /contributions/:id/request-platform-review`：创建平台投稿申请，不改变企业私有版本。
- `POST /contributions/:id/authorize-platform-submission`：企业管理员确认并提交平台审核。
- `POST /contributions/:id/platform-review`：平台运营通过/驳回。
- `POST /contributions/:id/versions`：从已审核版本创建新版本草稿。
- `GET /contributions/rewards`：奖励事件和结算状态。

所有 DTO 使用 shared Zod schema；控制器只负责 HTTP 和权限入口，状态迁移放在 service 的事务中。

## 风险与决策记录

- 现有 `Capability.status` 是平台级单状态，迁移期间必须保留兼容逻辑，不能让历史已审核能力全部消失。
- `SkillVersion` 已具备部分双审核字段，优先复用并通过独立平台快照保护企业私有内容。
- Agent/RPA/AI App 暂无统一版本表，第一阶段先用能力投稿元数据和审核事件覆盖，后续抽象 `CapabilityVersion`。
- 奖励先记录事件，避免在审核流程中直接修改钱包余额造成重复发放和财务不可追溯。

## 交付标准

- 任何注册用户都能开始创建能力。
- 企业归属、创建人、企业审核人、平台投稿人四种身份可追溯。
