# 客户端监控与员工使用记录缺失：生产排查报告

日期：2026-10-09（Asia/Shanghai）。本轮范围：只读核查部署、生产数据、客户端本地任务元数据、待同步队列及实际运行包；不修改业务代码、不部署、不迁移、不主动上传历史、不提交 Git。

## 1. 结论

两个页面共用客户端镜像底层数据，但查询口径不同。本次存在三个叠加问题：

1. **上传链路缺少来源头，生产全局 CSRF Guard 在进入任务业务逻辑前返回 403。**运行旧包、现有 beta 新包和当前客户端源码的监控请求均只有 `Authorization`、`Content-Type`，没有 `Origin/Referer`。这解释了待上传队列长期没有成功创建云端镜像；单独升级到现有 beta 包仍无法解决。
2. **实际运行的是旧客户端包。**包内没有历史枚举恢复、定时恢复和 v2 员工参与上报；客户端仓库中的新实现和另一个 beta 包并不等于当前运行包。Web/后端部署新代码不会替换正在运行的 Electron 包。
3. **员工详情只接受有 v2 员工参与证明的记录，历史恢复仍按 v1 上传。**因此即使修好上传并补传历史，旧记录也只会增加客户端监控数量，不会自动进入员工详情的精确使用列表。当前方案缺少可阅读的旧记录降级展示。

企业管理员看本企业全部用户、普通成员仅看本人的查询规则已经实现。本次缺数不是管理员角色判断错误、列表最多三条或数据库迁移漏执行。

### 3.2 403 的确定阻断点

客户端当前源码 `electron/common/platform/client-monitor-api.ts:89`：

```ts
const response = await this.fetcher(this.baseUrl + path, {
  method,
  headers: { Authorization: 'Bearer ' + token, 'Content-Type': 'application/json' },
  body: JSON.stringify(body),
  signal,
})
```

客户端使用主进程的 `globalThis.fetch`，构造时没有注入补来源头的 fetch。两份 asar 包内请求片段相同：

- 运行旧包 `out/main/index.js:4348`。
- beta 新包 `out/main/index.js:4620`。

后端 `backend/src/modules/security/security.module.ts` 将 `CsrfGuard` 注册为全局 guard。`guards/csrf.guard.ts:80`：生产写请求若没有 Origin/Referer，抛出 `ForbiddenException('Missing Origin or Referer header')`。客户端认证端点、模型网关有精确例外，任务监控端点没有例外。

所以出现以下现象是符合代码的：登录、模型调用和通知读取成功；任务 create/status/events/heartbeat 被生产 CSRF 检查拒绝。监控 API 丢弃错误响应正文，只保留 HTTP 状态；旧服务也不记录具体失败原因，使 403 被误认为员工授权问题。

生产后端在 2026-10-09 15:15、15:16 有多次 `POST /api/client/tasks 403`。日志没有记录拒绝原因及 taskId，无法给每一行日志逐条绑定本地任务；根因通过运行包请求代码、生产编译代码、有效授权查询及本地 guard 复现交叉确认。

本地使用生产模式、`CORS_ORIGIN=https://longdaosep.cn` 复现，未发送真实网络请求：

| 操作 | 无 Origin/Referer | 加允许的 Origin |
| --- | --- | --- |
| POST `/api/client/tasks` | Missing Origin or Referer header | CSRF Guard 通过 |
| PATCH `/api/client/tasks/sample/status` | 同上 | CSRF Guard 通过 |
| POST `/api/client/tasks/sample/events` | 同上 | CSRF Guard 通过 |
| POST `/api/client/tasks/sample/heartbeat` | 同上 | CSRF Guard 通过 |

这里“通过”仅指 CSRF Guard，后续 JWT、企业、订阅授权及 DTO 校验仍需独立通过。

## 4. 员工详情为什么仍为零

### 4.1 相同底层数据，不同查询入口

- 客户端监控按企业/发起用户查询 `client_task_mirrors`，兼容 v1 镜像。
- 员工详情按企业 + subscription + employee 查询 `client_task_participations`，联接 run/mirror；要求 run.protocolVersion >= 2。
- 员工详情模型消费来自 `compute_usage_records`，与任务输入输出上传是两条链路。

代码：`backend/src/modules/subscription/subscription-usage.service.ts:138` 客户端列表、`:193` 旧协议覆盖提示、`:377` 客户端详情。

文档生成专家的生产订阅下有两条旧镜像，但 run、participation 都是零。所以员工详情的客户端使用记录必然为零，旧记录计数则恰好为二，与截图提示一致。近七天内也没有可严格归属的 Web 会话记录。

### 4.2 账单有 93 次，不等于有 93 条任务明细

对文档生成专家按 2026-10-02 00:00 至 2026-10-10 00:00（UTC+8）查询账单，得到：

- 模型调用：93。
- inputTokens + outputTokens：2,052,024。
- costCNY：2.088507，页面四位小数约为 ¥2.0885。

与用户截图一致。这 93 条账单的 sessionId 均没有匹配到当前 `conversation_sessions` 云端会话，所以不能按 Web 使用记录读取正文。账单没有替代任务输入输出的能力。

另有十一条满足严格归属的 Web CHAT 会话，其业务活动时间均在 2026-08-04 至 2026-09-02，不在截图的近期范围。不能将“近期列表零条”表述为“该员工全部时间没有任何 Web 记录”。

### 4.3 修好补传后，旧历史仍不会自动成为 v2

当前客户端 `ClientMonitorService.restoreHistory()` 恢复历史时创建的请求没有 protocolVersion=2，也没有精确 participation；相关测试明确保证历史不伪造新版证明。

v2 是新任务实时采集的员工参与信息。后端也拒绝将已存在的旧 run 追认为 v2（`Legacy run cannot be retroactively proven; create a new run`）。这是防止编排任务归属被猜测的设计边界，但当前 UI 只有旧记录数量提示，缺少可查阅入口，不能完整满足用户查看历史输入输出的需求。

## 5. 建议修复顺序与验收要求（尚未实施）

### P0：修复客户端监控统一请求的来源头

复用现有客户端其他写 API 的可信平台来源头处理，为 create/status/events/heartbeat 统一设置与部署允许来源一致的 Origin/Referer。使用已配置的 Web origin，不能假定 Web/API 必然同域，也不能把任意客户端输入直接作为可信来源。

保持 JWT、企业隔离、有效订阅授权不变。新增请求头契约验证及生产模式 CSRF 边界验证，覆盖四个监控写接口。无需默认放宽整个 `/api/client/*` 或生产 CSRF。

### P1：重新构建并核实真正运行的客户端

修复源码后重新构建，确认实际可执行文件、包内构建标识、来源头、历史恢复和 v2 都已进入发行包。不要只看 0.1.2。应使构建版本可区分，并核实历史数据目录，避免从 `longsilicon` 切到另一个 userData 后记录看似消失。

在独立账号、企业、订阅授权验证通过后恢复待同步队列，按 clientTaskId 对账；云端幂等键为用户 + clientTaskId。授权恢复的是当前账号 scope，不跨账号代传。补传应保留真实历史时间，不以同步时间冒充使用时间。

本轮未执行真实补传；补传后的数据库条数、输入输出完整性尚未验证。

### P2：补齐员工详情的历史记录展示

保留 v2 精确员工参与查询。为旧记录增加可阅读的降级入口，并明确标记归属/内容覆盖范围：

- 有足够单员工证据的旧会话，可以作为“旧客户端记录，参与归属未核实”展示任务、使用人、时间及可用正文；需定义服务端准入证据，不能只信任当前 root subscription。
- 无法拆分的旧编排不猜员工节点归属，继续在客户端监控展示完整任务；员工详情提供对应受权限保护的历史入口或解释。
- 从员工详情读取旧任务正文时仍执行企业/用户范围检查及正文审计。
- 不能把 v1 数据直接改为 v2，不能伪造 participation。新 v2 记录继续按任务聚合，详情展开 run/节点和输入输出。

这部分补充涉及已确认方案中的历史兼容边界，应在实施前明确降级入口及准入规则。当前报告仅提出建议，没有改变既有规格或实现。

### P3：同步失败可见、验证跨端一致

客户端提供待同步/已同步/失败的可读状态，记录允许范围内的固定错误分类，避免只留下 HTTP 403 且用户看不见失败。不得落盘 token 或任意错误正文。

验收至少覆盖：

1. 当前账号这十条 clientTaskId 在云端对账，输入输出和真实时间可读。
2. 管理员看到本企业全员，普通成员只能看到本人；不能通过查询参数越权。
3. 新 v2 文档生成任务同时出现在监控与员工详情；两处打开相同底层任务且详情员工参与范围正确。
4. 旧单员工历史有明确标识和受权限保护的可阅读入口；旧编排不猜归属。
5. 重启、断网恢复、账号切换、幂等重放和终态不回退。
6. 模型消费与任务数量继续分别展示，不混成“使用次数”。
