# 技能库技能审核统一优化方案 v1

- 日期：2026-10-09
- 状态：业务规则已确认，已按本文完成工作区后端与 Web 实现及本地回归验证；不代表生产已部署或客户端仓库已接入。
- 范围：SEP 技能库、企业技能版本后端、Web 与客户端接口契约。客户端仓库实现需由客户端开发同步完成。
- 依据：用户确认的个人版本、企业审核、企业默认与自主选版规则，以及当前源码调研。
- 替代关系：本文替代《客户端与Web个人Skill企业审核闭环开发方案-v1》中“独立技能审核板块”“通过后仅本人可用”“不更新企业默认”的设计。旧文档保留作为历史实施记录，其旧测试结果不代表本文方案已实现。

## 1. 目标与已确认规则

技能库是个人修改、企业审核、企业版本发布和版本选择的统一入口。客户端与 Web 只是不同操作入口，不建立两套审核业务。

1. 员工和企业管理员都可以修改有权编辑的技能，保存为自己的个人版本。
2. 管理员保存的版本同样先属于个人，不因为管理员身份自动成为企业版本。
3. 企业管理员拥有审核权限，普通员工没有审核权限。
4. 审核通过后，生成新的企业版本，整个企业的员工可以看到；实际执行仍须具有对应技能的使用授权。
5. 新企业版本成为该企业该技能的默认版本，原企业版本保留，管理员可以随时切回。
6. 每位成员可以使用自己的个人版本、主动选择历史企业版本，或者跟随企业默认。
7. 企业默认更新不得覆盖成员已经明确选择的版本；只有“跟随企业”的成员随默认变化。
8. 客户端原“审核”和 Web 原“采纳”是同一机制，对用户统一叫“审核”。
9. 不再以独立“技能审核”板块承载客户端流程，审核功能融入对应技能的技能库详情。

个人保存、自用和企业发布是三个不同概念：个人修改不需要先获企业审核才能自用；企业审核决定是否将这份内容发布为企业共享版本。

## 2. 改造前问题与根因

本节记录改造前的实现差异；现有实现及验证结果见第 11 节，不应将下面的旧行为作为当前接口契约。

| 环节 | 当前 Web 技能库 | 当前客户端链路 | 需要统一的结果 |
| --- | --- | --- | --- |
| 保存个人修改 | `PERSONAL / PERSONAL_ACTIVE` 工作副本 | 提交为 `PERSONAL / PENDING_ENTERPRISE_REVIEW` | 两种来源均进入同一技能的个人改动视图 |
| 管理员处理 | “采纳”个人副本 | 独立页面“审核”送审版本 | 技能库内统一审核 |
| 通过后的发布 | 新建企业版本、更新相关订阅默认 | 只更新个人版本的审核状态 | 均生成企业版本并更新企业默认 |
| 技能库统计 | 只统计 `PERSONAL_ACTIVE` | 送审版被过滤 | 统计可审核改动、待审快照与审核结果 |
| 本人选版 | 工作副本及已通过个人版可用 | 待审、驳回个人版不能显式选择 | 本人合法个人保存内容可自用，审核状态不等同使用许可 |
| 刷新 | 审核 mutation 已失效技能库缓存 | 独立队列有轮询 | 技能库自身支持跨端刷新，查询内容也必须正确 |

源码定位：

- `backend/src/modules/skill-version/personal-skill-submission.service.ts`：客户端提交、队列与审核；现有通过动作未创建企业版本。
- `backend/src/modules/skill-version/skill-version.service.ts`：个人副本、个人改动查询、采纳、企业默认与执行选版；多个查询仅接受 `PERSONAL_ACTIVE`。
- `web/src/features/capability-iteration/`：技能库列表、版本时间线与“大家的改动”。
- `web/src/features/skill-version/use-skill-version.ts`：独立审核 hooks，审核成功已有缓存失效。
- `web/src/components/shell/enterprise-shell.tsx`：独立“技能审核”导航。

结论：不能只搬审核按钮或增加一次刷新，必须统一发布语义、数据查询、权限和版本选择。

## 3. 统一业务流程

```text
员工 / 管理员在 Web 或客户端修改技能
  → 保存自己的个人内容，可本人选用
  → 对应技能的“个人改动 / 大家的改动”中可见
  → 企业管理员预览正文与差异，执行审核
      ├─ 通过
      │   → 固定本次审核的内容快照
      │   → 写入审核记录
      │   → 创建新的 ENTERPRISE / ENTERPRISE_APPROVED 版本
      │   → 建立个人来源与企业版本的关联
      │   → 更新企业默认
      │   → 企业成员可查看并选择该企业版本
      └─ 驳回
          → 写入审核记录与原因
          → 不创建企业版本，不修改企业默认
          → 本人保留个人内容，可继续修改并再次进入审核

成员执行技能
  → 有明确个人选版：使用所选本人个人版 / 已发布企业版 / 合法平台版
  → 明确跟随企业：使用企业当前默认
```

### 3.1 保存与审核入口

- 保留 Web 现有“保存个人副本后管理员可见”的效率，不额外要求员工必须点击一次“提交审核”。原可采纳改动在技能库中统一显示为“待审核”。
- 客户端保留现有显式提交接口，上传成功后，同样出现在该技能的待审核集合。
- 不以 `submittedAt != null` 排除 Web 改动；Web 工作副本和客户端送审快照都可以进入统一审核服务。
- 两个入口使用同一权限校验、审核记录、企业发布与默认更新逻辑。底层工作副本和送审快照的存储差异不应成为两套业务。
- 管理员也可以保存自己的个人改动并执行审核。当前需求未要求双人审批，本方案不额外引入“禁止审核本人版本”；必须记录提交人与审核人。

### 3.2 个人内容与审核快照

- 可编辑工作副本可以继续使用现有 `PERSONAL_ACTIVE`；客户端送审快照继续使用现有待审、通过、驳回状态。
- 客户端已提交快照保持不可变；修改后创建新提交，使用新的幂等键。
- Web 审核工作副本时，必须固定所见内容。管理员预览后成员又保存了新内容时，应返回冲突并要求重新预览，不能审核管理员未看过的正文。
- Web 工作副本的审核历史必须关联不可变快照，后续编辑不能改变已通过或已驳回记录的正文。
- 个人内容的“本人可用”与“企业审核结果”分开计算。待审核、被驳回只是尚未发布为企业版，不应使本人已合法保存的内容失去自用资格。
- 已固定的历史个人快照和企业发布版本不得删除或覆盖；编辑历史快照时创建新的个人工作版本，可编辑工作副本仍允许保存更新。

## 4. 版本归属、默认与权限

### 4.1 不直接把个人记录改成企业记录

审核通过应新建企业版本，保留原个人版本及回执 ID：

| 记录 | 归属 | 作用 |
| --- | --- | --- |
| 个人工作副本 | `PERSONAL`，保留 `ownerId` | 本人继续修改、自用 |
| 个人审核快照 | `PERSONAL`，保留提交人与原 ID | 客户端查询状态、审核追溯 |
| 审核生成的企业版本 | `ENTERPRISE`，本企业归属 | 企业共享、默认选择与历史回退 |
| 来源关联 | 个人快照 → 企业版本 | 说明企业版本来自谁的哪次改动 |

优先复用 `SkillVersion`、`SkillVersionReview`、`SkillVersionAdoption`。`SkillVersion.sourceVersionId` 已用于企业向平台投稿，不挪用它承载本流程的来源关系。

数据库中的 `Adoption` 命名可暂时保留以降低迁移风险，但新增业务方法、页面文案和对接文档统一使用“审核”。

### 4.2 企业默认

- 默认的业务范围是“企业 + 技能”，不是全平台，也不是某个审核人的个人选择。
- 本次审核生成企业版后，应在同一事务内更新该企业所有有效、绑定此技能的订阅默认记录，不遗漏无审核人个人授权但属于本企业的订阅。
- 当前优先复用 `SubscriptionSkillVersion`，不直接修改跨企业共享的员工模板默认绑定。
- 需要保证后续新增相关订阅能继承企业当前默认，不能只更新审核当时已有的订阅。
- 如当前逐订阅默认模型不能可靠表达新增订阅继承，开发时补齐最小的企业级默认记录或等价持久化机制；不能用“最新创建版本”推断默认，因为管理员可能已切回旧版。
- 多订阅历史默认不一致时，不在上线阶段静默合并；管理员首次审核发布或明确切换默认后，建立统一默认。
- 默认回退只修改默认指针，不删除新版、不修改审核历史，也不重写成员明确选版。

### 4.3 个人选择与执行一致

| 成员设置 | 新企业版发布后的效果 |
| --- | --- |
| 跟随企业 | 自动使用新的企业默认 |
| 使用本人个人版本 | 保持原选择，个人内容仍在 |
| 固定历史企业版本 | 保持原选择，旧企业版仍可用 |
| 后续切换为跟随企业 | 使用切换时的企业默认 |

- 管理员的个人选择和企业默认设置是两个独立操作，页面必须区分“我使用此版本”和“设为企业默认”。
- `MemberSkillVersionSelection.versionId = null` 已表示显式跟随企业，保留此契约。
- 没有显式选择的新成员默认跟随企业。存量用户已有个人副本优先的兼容行为需保留或转为明确个人偏好，不能因上线静默换版。
- 个人选版接口和 `resolveEffectiveVersion` 使用同一选择资格规则，避免页面可选但执行回退。
- 本人个人版本只能由本人选择；管理员审核权限不等于可以把其他人的私有版本直接设为自己的个人版本。共享使用应选择审核生成的企业版本。

### 4.4 查看与使用权限

- 本企业成员可以查看本企业已发布的技能企业版本及其历史，不因缺少个人执行授权而看不到企业版本目录。
- 技能执行与编辑仍校验有效订阅、技能绑定和成员授权。可查看企业版本不等于可执行技能。
- 普通成员只查看自己的个人改动；企业管理员可查看本企业待处理及历史审核记录，不依赖管理员本人是否分配了该技能的使用授权。
- 不允许跨企业查询、审核、选版或修改默认；平台管理员身份不能替代企业管理员身份。

## 5. 技能库页面调整

### 5.1 列表页

- 技能列表展示企业默认版本、本人使用模式及待审核数量。
- 管理员看到本企业该技能待审核总数；普通成员只看到本人记录的状态，不泄露他人私有内容。
- 点击待审核数量进入对应技能详情的“大家的改动”，不跳转独立审核中心。
- 同一工作副本及其对应送审快照不能重复计数；已有来源快照无新改动时，不重复列为待审核。
- 企业版本目录可见性和待审核技能可见性不能仅依赖当前用户的执行授权列表。

### 5.2 技能详情

保留现有详情布局，融入审核能力，不重新建立一套技能管理页面：

- “版本”：展示企业默认、历史企业版和本人个人版；提供本人选版、跟随企业、管理员设置企业默认。
- 成员“我的副本”：编辑与保存个人内容，查看自己的审核进度、原因和对应企业版本。
- 管理员“大家的改动”：同时显示 Web 改动和客户端送审记录，支持待审核、已通过、已驳回筛选。
- 记录展示提交人、提交或更新时间、变更说明、状态、审核人、原因、生成的企业版本；支持正文预览和差异对比。
- 行操作统一为“审核通过”“驳回”；移除个人改动区域的“采纳”“待采纳”“一键采纳”文案。
- 已审核记录只读，允许查看其生成的企业版；后续修改以新记录或新的工作副本改动展示。

“迭代建议”如有独立的建议采纳流程，不因本次个人技能审核统一而机械改名或重构。

### 5.3 独立页面退场

- 移除企业导航中的“技能审核”。
- 原 `/skill-reviews` 保留兼容跳转到技能库；带技能 ID 时进入对应详情的改动页，无技能 ID 时进入待审核技能列表。
- 原审核组件中可复用的预览、原因填写和状态展示融入技能详情，不保留第二个业务入口。
- 保留审核 API 作为 Web 和客户端共用服务接口；取消独立页面不等于取消接口。

## 6. 后端与接口优化

### 6.1 统一审核服务

将现有客户端 `review` 与 Web `adoptPersonalVersions` 的发布逻辑收敛为同一业务实现，controller 仅负责 HTTP、身份和共享 DTO 校验。

一次通过操作需原子完成：

1. 校验本企业管理员身份、技能归属与待审核内容版本。
2. 锁定 / 校验审核快照，防止预览后正文被改动。
3. 原子转换审核状态，写入审核人、时间与审核记录。
4. 创建内容固定的 `ENTERPRISE / ENTERPRISE_APPROVED` 版本，保留合法完整技能正文及包元信息。
5. 写入来源关联，并更新企业级默认及相关有效订阅默认。
6. 返回个人审核记录 ID、审核状态与生成的企业版本 ID。

审核失败应整体回滚，不能出现“客户端显示通过但企业版不存在”或“企业版创建成功但默认未更新”。事务提交后再发通知，通知失败不得撤销或伪报已完成的审核。

同一待审快照只发布一次。并发审核、重复点击与重试不能生成多个企业版；保持现有重复审核 `409` 契约，响应或后续查询应能定位已生成的企业版。不同快照并发发布时，版本编号与默认更新需要同一企业技能范围的并发保护，不能只锁单条个人记录。

### 6.2 API 兼容策略

以下契约已接入工作区实现；客户端开发应使用 [客户端对接文档 v2](../对接/SEP客户端技能提交与企业审核接口对接文档-v2.md) 核对字段、身份及错误处理。目标环境仍须先部署兼容后端和新增迁移。

| 现有接口 | 优化方向 |
| --- | --- |
| `POST /api/enterprise/skill-versions` | 保留客户端提交及幂等契约；提交记录进入技能库审核集合 |
| `POST /api/enterprise/capabilities/:id/personal-version` | 保留 Web 个人保存行为，管理员同样适用 |
| `PATCH /api/enterprise/personal-versions/:id` | 只更新允许编辑的工作副本，不能改审核快照和企业历史版 |
| `GET /api/enterprise/capabilities` | 提供企业默认、本人使用模式及统一待审核统计 |
| `GET /api/enterprise/capabilities/:id/personal-diffs` | 纳入两端记录及审核状态、来源关联；分页避免一次加载全部正文 |
| `GET /api/enterprise/skill-version-reviews` | 保留兼容，消费统一审核记录，不另建业务队列 |
| `POST /api/enterprise/skill-versions/:id/review` | 两端共用；通过后生成企业版并更新默认 |
| `POST /api/enterprise/capabilities/:id/adopt` | 作为旧 Web 接口兼容入口，内部调用统一审核服务，不保留独立发布规则 |
| 技能版本列表 / 时间线 / 预览 | 对齐角色可见性、本人版本使用资格与企业历史版 |
| 个人选版 / 企业默认选版接口 | 独立权限、独立写入，执行解析与页面一致 |
| `POST /api/enterprise/capabilities/:id/default-version` | 管理员按企业技能设置全局默认，无需本人订阅或执行授权；支持回退合法历史版本 |

审核与状态查询响应在原字段外增加可选 `publishedVersionId`，表示本次审核生成的企业版本；可由现有来源关联解析，不必须新增数据库字段。需要时返回企业版本摘要与默认信息，避免客户端把个人回执 ID 误当作企业版 ID。

Web 工作副本的并发审核请求增加内容修订依据，例如 `expectedUpdatedAt`；已有客户端提交快照不可变，不强制客户端升级后才能审核旧记录。新增字段通过共享 Zod DTO 校验，不接受客户端指定审核人、企业或个人归属。

保持客户端 Bearer Token、Origin / Referer 与幂等规则。不得为打通审核关闭来源校验、企业权限或执行授权；客户端提交重试返回原记录当前状态和发布关联，不重置审核状态。

### 6.3 批量审核

- 首先保证单条审核完整闭环，再保留或接入同机制的批量审核。
- 多人改动合并必须让管理员确认最终正文，审核通过针对确认的内容快照。
- 旧批量兼容接口通过 `expectedVersions` 校验各 Web 工作副本修订；多来源必须传入 `expectedMergedContent`，缺失或与事务内重新合并的正文不一致返回 `409`。当前技能库 UI 采用逐条审核，不提供未经确认的批量发布。
- 现有合并函数可能返回冲突并继续发布，统一后禁止把未解决冲突内容直接设为企业默认。
- 批次记录每个来源与最终企业版，避免“通过多条但实际只采用最后一条”。

## 7. 跨端状态同步与缓存

- 当前 mutation 的缓存失效保留并扩展，覆盖技能列表、详情、时间线、个人改动、企业默认、本人使用模式和审核列表。
- 技能库审核相关查询不再无条件继承全局“五分钟缓存、禁用 mount / focus 刷新”的配置。
- 技能库打开或重新聚焦时刷新；前台审核相关视图采用约 30 秒轮询，后台停止。优先使用现有 Query 能力，不为了本次闭环新增实时通信依赖。
- 客户端收到 `201` 只代表已持久化，后续按原个人版本 ID 查询审核结果，并通过 `publishedVersionId` 获取企业版。
- 企业默认改变后，客户端“跟随企业”成员刷新默认指针；明确选版成员不改偏好。执行端以服务端解析为准，不能仅凭本地展示标签决定版本。
- 发布或回退企业默认后，可复用现有通知能力提示相关成员；通知不是唯一的数据同步依据。

## 8. 历史记录兼容与上线边界

| 历史数据 | 处理规则 |
| --- | --- |
| 未审核的客户端提交 | 直接进入对应技能待审核集合，无需重新上传 |
| Web 未处理工作副本 | 继续显示为待审核，审核时建立不可变快照 |
| 已经采纳的 Web 改动 | 显示为已通过及原企业版关联，不重复发布 |
| 旧客户端已通过但没有企业版的个人记录 | 显示“历史已通过、未发布企业版”，不伪装成已完成新闭环 |
| 已驳回客户端记录 | 保留原因和快照，本人内容可自用；修改后重新进入审核 |
| 成员已有明确选版 | 原样保留 |
| 历史企业版与默认回退 | 保留全部版本和操作记录 |

旧客户端“已通过、未发布”记录不能上线时自动批量生成默认企业版，否则会把过去仅批准本人使用的决定扩大为企业发布。提供管理员显式“发布为企业版”兼容操作，复用统一发布事务并补充操作审计；已经有关联的记录不得再次发布。

已由 Prisma 工具生成新迁移 `20261009104548_add_enterprise_skill_defaults`，新增企业技能默认表及 Web 审核快照的工作副本、精确修订关联和索引。未修改历史迁移，不把生产数据库操作作为本地开发或测试的一部分。

建议部署顺序：兼容后端 → 技能库整合 Web → 客户端消费新增关联和默认刷新。发布期间保留旧接口，但避免旧版“通过不发布”的实现与新版共存处理同一队列。回滚必须保留新产生的企业版本、来源与个人选择，不删除业务数据。

## 10. 验收标准

1. 员工和管理员均能在 Web 保存本人个人版本；管理员个人保存不自动发布为企业版。
2. 客户端上传返回 `201` 后，Web 对应技能详情可看到同一版本 ID，待审核统计正确，不需要进入独立页面。
3. Web 个人改动与客户端提交可以在同一技能详情审核，文案均为审核，普通成员无法调用审核 API。
4. 审核通过后，原个人回执保留并更新状态，同时生成新的企业版与来源关联，更新企业默认。
5. 本企业其他员工可查看新企业版和历史版；跨企业用户不能查看。无执行授权者不能借可见性越权执行或编辑。
6. 跟随企业者切到新默认；选定本人个人版或历史企业版者保持原选择，真实执行版本与页面一致。
7. 成员可以从个人版切为跟随企业，或选回旧企业版；管理员可把企业默认切回旧版，新旧版本均保留。
8. 待审或被驳回不禁止提交者本人合法个人内容自用；驳回不创建企业版、不修改默认。
9. 预览后 Web 工作副本发生修改，旧内容审核返回冲突；客户端送审快照不能被后续保存覆盖。
10. 并发、重复审核和提交重试不重复创建企业版；企业版创建或默认写入失败时整个事务回滚。
11. 管理员没有个人技能执行授权时，仍可审核本企业对应改动；审核权限不会赋予其执行权限。
12. 多来源合并冲突未解决时不能审核发布；已审核正文、包信息与客户端原始内容一致，无静默 frontmatter 丢失。
13. 不同窗口、不同管理员和客户端的操作可在前台约 30 秒或聚焦刷新后反映到技能库，列表、详情与客户端状态一致。
14. 历史已通过但未发布的记录被明确标识，管理员显式处理后完成发布，不在上线时自动改变企业默认。
15. 新增相关订阅继承企业当前默认，包括企业默认已经回退旧版的场景。

### 11.1 工作区实现

- `enterprise-skill-review.service.ts` 统一客户端审核及旧 Web 审核入口。事务中按企业技能加 advisory lock、锁定来源记录、校验预览修订、固定审核快照、写审核及来源关联、发布企业版并更新全局默认；并发重复审核返回 `409`。
- `enterprise-skill-default.service.ts` 维护企业技能默认和有效订阅默认；执行解析优先尊重个人 PIN / FOLLOW，新订阅也能继承已回退的全局默认，不覆盖个人选择。
- `skill-version.service.ts` 统一技能库可见性、待审统计、分页改动查询、时间线与真实执行选版。企业版本可见性与编辑、选版和执行授权分别校验；无订阅的留存企业技能仍可展示。普通成员只枚举有授权的员工关系，未获该员工授权的成员仍可从企业共享技能分组查看已发布企业版。
- 企业草稿编辑、个人工作副本保存与弃用同样使用企业技能事务锁，锁内重新校验状态；已发布企业版不能被并发草稿保存改写，已归档个人副本不能继续写入，审核与弃用并发不会删除已产生审核快照的来源。个人弃用也校验有效使用授权。
- Web 将两端记录融入技能详情的个人改动面板，提供正文 / 差异预览、修订校验、通过 / 驳回、状态筛选和审核人展示；移除独立导航并保留旧路由跳转。列表与时间线支持前台 30 秒轮询和聚焦刷新。
- 完整技能正文、frontmatter 和单来源包信息保留。旧客户端已通过但未发布记录只允许管理员显式补发布，不自动批量设置默认。
- 新客户端对接文档 v2 说明原个人回执 ID、`publishedVersionId`、Bearer 与来源校验、幂等重试、PIN / FOLLOW、全局默认和冲突处理；旧文档已标注为历史规则。
