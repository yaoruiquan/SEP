# 模型网关 429 修复开发方案

日期：2026-10-10。状态：已按方案实施并完成本地验证。本轮修复与审查均不部署生产。

## 1. 问题与范围

事故任务 `65151dec-56d7-41b1-8b39-76f1def6fc13`，模型 `deepseek-v4.1-flash`。证据见 [排查报告](../progress/2026-10-10-模型网关429排查.md)。模型执行端点没有跳过全局命名限流规则，实际也执行 `auth=10/60s`，第 11 次请求在平台被拒绝。旧桶按 handler、规则、IP 计数；代理链路下不同成员可能共享代理 IP。标准 `Retry-After` 又被兜底成 60，掩盖了剩余阻断时间。

本次修复仅针对 `POST /api/gateway/v1/chat/completions`、雇佣令牌身份校验、相关 429 响应与关联日志。非目标：`/enterprise/skill-versions`、客户端 `task:retry`、全局代理信任策略、登录限流重构、计费/SSE 协议、生产发布。

## 2. 限流规则

| 项目 | 约定 |
| --- | --- |
| 规则名 | `gateway-model` |
| 维度 | 已验证 JWT 中的 `enterpriseId + memberId + subscriptionId`，结构化序列化后 SHA256 |
| 请求单位 | 每次模型 HTTP 请求计 1 次；工具续轮、客户端重试均是请求，不按任务计数 |
| 默认阈值 | 60 次 / 60000ms；`GATEWAY_MODEL_RATE_LIMIT`、`GATEWAY_MODEL_RATE_WINDOW_MS` 配置 1 至 2147483647 的整数，非法值启动失败 |
| 窗口 | 首次获准请求开启固定窗口；超限请求不续期、不额外启动 60 秒阻断 |
| 共享范围 | 同一企业/成员/订阅下跨模型、任务、会话、客户端共享；不同三元组独立 |
| 存储 | 现有 Redis，单 key Lua 原子检查/计数/过期，Redis TIME 给出恢复时间；跨后端实例共享 |
| 异常 | Redis 故障拒绝执行，503 + `PLATFORM_RATE_LIMIT_UNAVAILABLE`，不降级无限放行 |

这是请求频率限制，不是并发限制、token 限制、企业总额或余额判断。没有并发占用计数，因此不存在断连/取消后释放计数问题。已验证身份但参数非法、业务授权失败或上游失败的请求也占 1 次；无效/缺少/过期令牌不得进入业务桶。后续如需增加企业总量或并发规则，应单独定义，不能混入本规则。

## 3. 接线与安全

1. 仅在模型执行方法跳过现有 `default/auth/chat` 三个全局 Throttler 桶；其他路由不变。
2. 仅此 POST 端点（含等效尾斜线路径）跳过 basic IP 桶，其他 gateway 路由继续受旧规则保护。
3. 方法 guard 顺序：`ClientEmploymentGuard` -> `GatewayRateLimitGuard`。前者验签、有效期、令牌类型和四个必需身份字段；后者只读已验证 claims，不从 header/body/未验证 JWT 解码取计数身份。
4. 不启用全局 `trust proxy=true`，不依赖可伪造的 `X-Forwarded-For`。
5. Redis key 不含明文身份；限流日志只包含 key hash、Request ID、规则、维度、阈值、计数、窗口与恢复时间，不记录令牌/请求正文/API key。

## 4. 响应契约与诊断

- 平台超限：429，OpenAI 兼容 `error.type=rate_limit_error`、`error.code=PLATFORM_RATE_LIMIT_EXCEEDED`、`error.source=platform`。
- `error.rateLimit` 仅包含 `rule/dimension/limit/windowMs/count/retryAfterSeconds/resetAt`；拒绝时 count 表示该窗口已获准请求数。
- 标准 `Retry-After` 为窗口剩余毫秒向上取整的秒数；平台同时提供 `X-RateLimit-Limit/Remaining/Reset`（Reset 为 Unix 秒）。重试不得延长窗口。
- 上游 429：`error.source=upstream`，保留上游安全的 message/type/code/param，未给 code 时使用 `UPSTREAM_RATE_LIMIT_EXCEEDED`。只代表 sub2api 返回 429，不擅自推断具体供应商/额度/并发规则。
- 上游 `Retry-After` 支持秒数及 HTTP-date，规范化后用于客户端标准等待头；没有等待信息时保留现有 60 秒兼容兜底，但它不是已确认恢复时间，不返回虚构规则/计数。
- 通用 filter 优先已有标准等待头，其次异常携带的等待秒数，其次有效命名 `Retry-After-*` 的最大值，最后才兜底 60；普通业务错误 envelope 不变。
- 平台 Request ID 随模型请求发送给 sub2api；上游 429 日志记录平台关联 ID、状态、可安全读取的上游关联 ID、等待时间，不透传任意上游元数据。

## 5. 实施顺序与文件

1. 新增 gateway 专用 Redis limiter/service/guard 和单元测试；加强雇佣令牌 claims 校验。
2. 接入 controller/module；精确排除模型执行端点的 basic IP 规则。
3. 修复 filter 等待头优先级、安全 metadata；修复上游 429 等待信息与关联日志。
4. 为 backend 和 production 示例环境及三种 Compose 透传新配置，不修改真实环境文件。
5. HTTP 回归使用真实 JWT guard、全局 Throttler、basic middleware、专用 guard；mock 授权/上游/Redis，补 Redis Lua 实际执行验证（环境允许时）。

## 6. 验收矩阵

- 同身份 12+ 次工具续轮不再命中 `auth=10`；超过专用阈值才返回平台 429。
- 同代理 IP 的不同成员/企业/订阅独立，同身份换模型/任务/会话不能绕过共享桶；累计超过 basic 的 120 次不跨成员误拦。
- 缺失、伪造、过期、错误类型、缺失身份 claims 的令牌返回 401，不消耗业务桶、不调用上游。
- 超限返回真实剩余时间、阈值、计数、resetAt；拒绝重试不续期，到期恢复。
- 原子计数能处理并发请求，Redis 故障返回 503，不调用上游。
- 上游 429 秒数/HTTP-date 等待头、来源区分、安全白名单字段；非 429 行为和 SSE/工具 payload 不变。
- 登录/普通 REST 路由继续应用旧规则；普通 envelope、客户端相关回归通过。
- 执行针对性 Jest、后端 typecheck/build、diff 检查；记录未执行项。

## 7. 发布与回滚

本轮不操作生产。经用户授权发布后先观察同一任务多轮调用、平台/上游 429 分类日志、Redis 连通性及真实等待时间。蓝绿实例应使用相同 Redis、相同阈值配置；跨环境应隔离 Redis。配置可先采用默认 60/60s，根据合法多轮峰值再调优。恢复旧版本即可回滚代码，但会恢复旧的 10 次/分钟误限流；Redis key 会自动过期，无需删库。

### 验证证据

最终命令：

```bash
env GATEWAY_REDIS_TEST_URL=redis://127.0.0.1:6379/15 \
  pnpm --dir backend exec jest --runInBand \
  gateway client-employment client-task-mirror csrf.guard sensitive-data.filter \
  http-exception.filter basic-rate-limit.middleware auth-rate-limit.service
pnpm --dir backend typecheck
pnpm --dir backend build
git diff --check
```

- Jest：13 组、291 项全部通过；除模型模块外覆盖客户端任务镜像、认证限流、CSRF、错误脱敏及相关 WebSocket 回归。预期异常测试产生的错误日志不是测试失败。
- 完整 HTTP guard 链：连续 15 次工具续轮成功；同代理 IP 下四个身份桶各成功 60 次、分别在下一次返回平台 429，总计 240 次成功请求，不命中旧 basic/auth 桶。
- 固定窗口：拒绝后推进 2300ms，等待时间从 60 降到 58 秒且 resetAt 不变；窗口到期下一次恢复，剩余额度为 59。
- 身份安全：伪造/过期/错误类型/空身份/无过期时间/缺令牌在计数之前被拒绝；已鉴权但参数非法或业务授权失败的请求按约定计数。
- 本机真实 Redis：两个连接同时发出 30 次请求，在阈值 3 下恰好获准 3 次；拒绝不递增、不延长窗口；250ms 窗口到期恢复。只操作随机命名测试 key，无 `FLUSHDB`，测试结束清理对应 key。
- 后端 typecheck、build 均通过，build 同时核对 92 个员工头像资产。
- 改动的 15 个 TypeScript 实现/测试文件执行 ESLint（不加 `--fix`），通过。
- 三份 Compose 通过 `docker compose --env-file /dev/null -f <file> config --quiet`，使用显式校验占位环境变量，没有读取真实部署密钥，没有启动/重启容器。
- 开发过程中修正了新增测试的参数化数组类型、非法参数夹具，以及高频 HTTP 测试反复自动监听临时端口的问题；最终测试应用使用单一临时监听端口，并在结束时关闭。

### 未验证项与风险

- Git 提交状态以仓库记录为准；未部署/重启生产，也没有调用真实计费上游，不能把本地验证表述为事故任务已在线恢复。
- 默认 60 次/60s 是本次明确选定的模型请求保护阈值，并非从历史流量推算出的容量保证；发布后仍需观察正常多轮峰值及 sub2api 限额。
- Redis 是模型执行的前置可用性依赖，故障时拒绝执行；沿用现有共享 Redis 客户端的重连策略，故障响应时延取决于其重试设置。本轮未修改共享客户端配置或真实 Redis 故障演练。
- 本轮未对其他 REST 接口的命名规则选用方式或代理 IP 聚合做全局重构；它们保留旧规则，只修复通用等待头。
- 无法确认上游未提供等待信息时的实际恢复时间；兼容兜底 60 秒不代表上游恢复承诺。
- 生产历史证据不足以重建共享桶中所有其他用户的请求，诊断结论保留原报告中的证据边界。
