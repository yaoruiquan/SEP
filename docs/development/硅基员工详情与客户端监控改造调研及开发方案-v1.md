日期：2026-10-09。
状态：调研完成，五项产品决策已于 2026-10-09 确认，待实施；尚未开始业务代码开发。
范围：SEP 企业端硅基员工详情、客户端监控、后端归属持久化与只读查询，以及相邻 `sep-client` 的 run/编排节点采集和协议扩展。

## 1. 需求与本轮边界

本轮按用户最新要求，将已接受的建议更新为开发依据，仅修改本文档。未修改业务代码、数据库或客户端协议，未提交、推送、部署，也未主动上传真实历史记录。下文“首版/本次实施范围”指后续开发范围，不表示本轮已经实现。

用户明确的方向：

- 删除员工详情的“配置”选项。
- 重新评估“运行情况”里仅显示模型次数、费用及空执行区块的设计。
- 增加每位成员使用这位硅基员工的具体记录，包括输入、输出、时间等。
- 员工详情与客户端监控各有职责，不重复建设两个相同的监控页面。
- 改善客户端监控的排序、分类和可查阅性。

本文将“使用纪律”理解为“使用记录”。“硅基员工”指当前企业的雇佣关系；“使用人/成员”指发起使用的真实用户。

第 10 节记录用户已接受的五项决策。后续开发按本文范围执行，不再以仅按镜像当前员工过滤的简化方案替代精确参与记录；任务级精确计费、无遗漏的全量 Web 历史归属及远程任务操作不在本次实施范围。

## 2. 已核实的现状

### 2.1 详情页不是按员工模板直接查询

页面 `/my-employees/[id]` 的 `id` 实际为 `subscriptionId`，不是 `DigitalEmployee.id`。页面使用：

- `GET /subscriptions/:id`：雇佣关系和员工基础信息。
- `GET /subscriptions/:id/employee-detail`：能力信息。
- `GET /subscriptions/:id/stats?days=7|30`：当前运行数据。
- 管理员另查该雇佣关系的授权范围。

证据：`web/src/app/(enterprise)/my-employees/[id]/page.tsx:108`、`web/src/features/employee/use-employee-stats.ts:42`。

新记录必须以 `enterpriseId + subscriptionId` 为主边界，不能只按模板 `employeeId` 查询。否则同名员工、其他企业或其他雇佣关系可能混入。

### 2.2 “配置”有真实作用，但页面入口可以移除

当前配置页包含企业内称呼、运行配置 JSON、模板版本和最近更新时间；顶部“编辑配置”也跳到该页。保存调用 `PATCH /subscriptions/:id`，同时提交 `name` 和 `config`，并不是静态占位。

更重要的是，`subscription.config.modelId` 在企业允许切换模型且使用 `FOLLOW_TEMPLATE` 策略时，可覆盖员工模板模型。员工运行包也仍返回订阅配置。因此移除 UI 入口不应删除 `Subscription.config`、清空已有 JSON 或删除后端兼容接口。

证据：

- `web/src/app/(enterprise)/my-employees/[id]/page.tsx:165`、`:195`、`:308`、`:655`。
- `backend/src/modules/subscription/subscription.service.ts:285`。
- `backend/src/modules/enterprise-model-config/enterprise-model-config.service.ts:249`。
- `backend/src/modules/client/client.service.ts:785`。

已确定删除配置 Tab 和“编辑配置”按钮；保留已有配置的运行行为。模板版本/更新时间移至概览；保留管理员企业内改名，入口移到员工标题旁，仅更新 `name`，不顺带提交或清空 `config`。

### 2.3 截图的两个区块已经对接后端，问题是口径不匹配

### 2.4 客户端监控并非完全没有排序

当前已有：

- 列表服务端按 `updatedAt DESC, id DESC` 排序。
- 分页及总数，Web 每页 50 条、列表每 15 秒刷新。
- 详情事件按 `sequence ASC, id ASC` 排序。
- 管理员默认查本企业，`MEMBER` 和 `DEPT_MANAGER` 查本人。
- 输入输出脱敏、长文本分片组装、缺片提示、不同 run 内容隔离。

缺少的是：

- 可见的排序选项，以及按成员、硅基员工、状态、时间和任务类型筛选。
- 列表里的硅基员工名称与明确分类。
- 按运行批次组织的可读详情，以及每条正文的发生时间。
- 任务概况和正文/技术事件的分层。目前所有输入、所有输出分别堆放，下面又列一遍原始事件。
- 深链接：任务页当前 Tab 由本地 state 控制，尚不能靠 URL 定位指定员工/任务。

注意：`updatedAt` 会受心跳和历史事件补传影响，是镜像更新时间，不等于用户使用时间。详情里判断心跳延迟的 `now` 也只在行组件挂载时取一次，后续刷新未必重新计算。

证据：`backend/src/modules/client/client.service.ts:897`、`:928`、`:948`；`web/src/features/task/components/client-task-monitor.tsx:30`、`:51`、`:91`；`web/src/app/(enterprise)/tasks/page.tsx:101`。

### 2.5 不能直接拼接已有接口做完整“成员输入输出记录”

| 接口/数据源 | 可复用部分 | 不宜直接作为新页面完整数据源的原因 |
| --- | --- | --- |
| `/client/tasks`、`/client/tasks/:id` | 任务状态、用户、订阅、run、事件和正文 | 尚无订阅/成员/时间筛选、员工摘要；主表只保存当前 run 状态和起止时间 |
| `/subscriptions/:id/stats` | 可靠归属订阅的模型消费和已有权限处理 | 返回聚合与最多 10 条工具执行，不返回使用正文 |
| `/compute-credit/usage-records` | 模型消费和用户范围校验 | 无订阅筛选，费用不能等同某任务费用；不是正文接口 |
| `/conversations`、`/conversations/:id` | 云端会话、消息正文及消息时间 | 仅本人可读；管理员不能直接读同事会话 |
| `/enterprise/employees/:employeeId/usage` | 企业按人使用汇总 | 依赖当前成员关系；范围及时间口径不等同新页面，还把所有消息行数称为轮数 |
| 能力执行查询 | 工具输入输出、版本和耗时 | 能力维度，不是订阅维度；不能替代员工使用记录 |

云端会话与工具执行没有不可变的企业/订阅归属字段。不能根据“这个用户现在在本企业”就让管理员读他全部历史会话。新云端查询需要严格归属校验，且不得放宽原个人聊天接口。

证据：`backend/prisma/schema.prisma:1263`、`:1352`、`:1830`、`:3233`；`backend/src/modules/conversation/conversation.service.ts:114`、`:145`；`backend/src/modules/skill-version/skill-version.service.ts:1833`。

### 2.6 多员工编排和换员工重跑存在归属缺口

客户端 `arrangement` 任务创建镜像时采用第一个节点的 `subscriptionId`；最终输出拼接多个节点结果，但没有在同步正文中保留每个节点的员工标识。其他参与员工可能完全查不到这条任务，第一位员工名下的正文又包含其他员工结果。

同一任务新 run 可以更新镜像的 `subscriptionId/modelId`，但旧事件只有 runId，没有历史订阅快照。因此，直接按镜像当前 subscription 过滤，只能得到“当前主归属员工的相关任务”，不是每位员工每次实际参与的完整履历。

证据：`/Users/yao/LLM/sep-client/electron/runtime/task-runtime.ts:196`、`:696`；`backend/src/modules/client/client.service.ts:844`；`backend/prisma/schema.prisma:3267`。

用户已接受精确参与归属方案，本次实施必须补 run/节点的员工归属和内容上报。此项涉及客户端协议与后端持久化，不能包装成纯前端筛选改造已经能完成。

## 3. 功能边界：两个入口，一套明细

| 入口 | 回答的问题 | 主视图 | 不做什么 |
| --- | --- | --- | --- |
| 硅基员工详情 | 谁使用了这位员工？什么时候？输入和输出是什么？ | 固定当前订阅的历史使用明细，按成员/来源/时间查阅 | 不提供全企业运行调度、不堆原始技术事件、不做完整监控仪表盘 |
| 客户端监控 | 哪些客户端任务正在执行、等待处理或失败？运行在哪里卡住？ | 跨员工任务列表、状态、进度、心跳和错误，默认关注在途任务 | 不重复展示员工能力配置、成员费用排行或单员工经营分析 |
| 算力/账单页面 | 谁消费了多少？支付来源是什么？ | 模型调用、Token、费用及支付拆分 | 不充当使用正文或客户端运行日志页面 |

共用后端权限、客户端内容组装、运行分组及详情组件，不创建第二份任务数据或独立同步队列。员工详情提供“查看客户端任务”链接，打开监控的指定任务；监控提供返回该员工详情的链接。

两个入口出现同一条正文属于复用同一事实，不是重建两套功能。差异主要体现在列表范围、默认筛选、字段和排查能力。

## 4. 员工详情开发设计

### 4.1 页面结构

保留员工身份、简介、雇佣状态、开始对话入口、能力及版本管理。Tab 为“概览 / 能力 / 使用记录”，移除“配置”，把“运行情况”更名为“使用记录”。员工标题旁保留管理员改名入口，提交只包含 `name`。

概览保留能力/授权信息和最近使用摘要；移除只覆盖云端工具的成功率、平均耗时及重复旧执行表。保留少量模型消费摘要和账单入口，明确称为“模型调用 / Token / 模型消费”，不写“执行次数 / 企业实际支出”。成员消费信息保持紧凑，不重新建设消费趋势仪表盘。

使用记录不新增大图表。以可扫描的表格为主，正文按需打开侧面详情。

### 4.2 列表和筛选

- 成员：管理员默认全企业，点击某成员可过滤；普通用户固定本人，不能选择他人。
- 来源：客户端任务、Web 对话、Web 任务会话；来源必须明确，不能伪装成同一种执行。
- 时间：近 7 天、近 30 天、自定义日期；按发生/使用时间，明确 UTC+8。
- 状态：只对具有任务运行状态的数据使用；不能把云端会话 `ACTIVE` 解释成任务执行中。
- 排序：默认最近使用优先，可切换时间升序；同时间使用稳定 ID 次序。
- 分页：服务端过滤后计数和分页；不能把监控某一页 50 条拿来前端筛选并当作完整结果。

列表字段：使用人、标题/输入摘要、来源、适用的状态、首次使用时间、最近使用时间。客户端按当前订阅实际参与的 run/节点计算使用时间；可显示已知的起止时间和耗时，任务当前状态另作任务状态标注，不能冒充该员工参与状态。云端会话显示消息时间，不编造整个会话的“执行耗时”。

成员摘要显示真实记录数和最近使用时间；记录数分别列“客户端任务 / Web 会话”，不把一次模型调用、一条消息、一个任务混成一个“使用次数”。摘要按完整筛选结果聚合，不按当前页聚合。

### 4.3 详情

详情头部：使用人、硅基员工、来源、标题、状态、时间；仅显示已知字段。

客户端内容按 `clientRunId` 分组，默认最近一次可可靠归属当前员工的运行；编排再按实际参与节点展示，每组内部按事件 sequence 展示“用户输入 / 模型输出”的交错时间线。只展示当前订阅的参与正文，跳转监控后仍需重新授权才能读取任务其他内容。云端内容按消息时间和稳定 ID 排序，显示 USER/ASSISTANT，工具详情按需折叠。

旧客户端/旧 run 只有能确定当前订阅实际参与的记录才进入员工使用明细；无法拆分的编排汇总不作为任意员工的独立输入输出，不计入精确参与统计。此类内容保留在有权限的任务监控中，并明确“任务汇总/员工归属未核实”。旧 run 不继承镜像当前员工归属，覆盖限制必须如实返回和展示；这是历史兼容规则，不是首版采集的简化选项。

复用分片组装，但扩展视图模型保留正文的事件发生时间。分片正文用最早片段的发生时间作为正文时间；片段时间明显不一致或缺失时标记为近似/未知。没有 `occurredAt` 时可以显示服务端接收时间，但必须与发生时间区别。

当前协议没有可靠的问答轮次关联 ID，不强行把第 N 个输入与第 N 个输出配对。缺片、无正文、时间未知等状态必须如实显示，不能把缺片结果称为完整全文。

首版只展示已有脱敏文本和安全的附件摘要，不新增本地文件扫描/上传，不显示 token、凭据或任意附件下载链接。管理员可跨成员读取严格归属本企业当前订阅的云端业务正文，归属不明的历史不开放。

## 5. 客户端监控开发设计

### 5.1 从平铺记录改成任务工作列表

顶部采用任务状态分段：在途任务、异常/待处理、全部历史。默认在途任务，同时清晰显示其他分段的数量；筛选为空不代表企业没有历史记录。

状态分组：

| 分组 | 包含状态 |
| --- | --- |
| 在途 | QUEUED、RUNNING、WAITING_APPROVAL、PAUSED |
| 异常/待处理 | FAILED、WAITING_APPROVAL、PAUSED；心跳延迟另作健康筛选 |
| 历史 | 所有状态，可按 COMPLETED、FAILED、CANCELLED 细分 |

分组可以交叉，不把各组数量相加当作总数。心跳延迟是健康标记，不改变业务终态，也不能单凭超过 60 秒就断言设备离线。

### 5.2 分类、筛选与排序

- 分类优先使用硅基员工、成员、任务状态，而不是新增主观的员工行业分类。
- 筛选：员工雇佣关系、使用人、状态、任务类型、时间、标题关键词；管理员可切换“企业 / 本人”。
- 标题关键词首版只查标题，不检索模型正文，避免扩大敏感内容搜索范围。
- 任务类型只使用已有 `taskType` 的真实值并提供标签，未知值保留兼容展示。
- 列表显示员工、成员、标题、状态、进度、当前活动、开始时间及最近同步时间。
- 首版提供最近同步、开始时间、创建时间排序，明确标签。默认监控排序可继续 `updatedAt DESC, id DESC`，不把它称为“最近使用”。
- 如果后续增加纯业务活动时间排序，要新增可信的活动时间来源，不能直接把心跳时间重命名。

筛选、排序、总数及状态计数都在后端处理；修改筛选重置分页，刷新不关闭已选详情。深链接参数至少支持 `tab=monitoring`、`subscriptionId`、`taskId`，仍需后端重新授权。

首版不做“按当前页分组”的伪全量员工统计。可用员工/成员筛选完成分类；若增加分组视图，组计数需来自完整授权范围，组内独立分页。

### 5.3 详情降噪

默认展示当前 run 概况和按顺序排列的正文；旧 run 通过选择器查看。任务事件折叠为诊断区，对正文分片只显示逻辑正文摘要，不逐片重复占据主视图。错误和心跳信息归入诊断区。

长详情按需加载，避免每个展开任务都长期拉取全量历史事件。如增加事件分页，必须提供完整的逻辑正文或片段续载机制，不能因当前页未取齐就误报上传缺片。

保持只读，不顺带加入远程取消、重试、审批或执行功能。心跳时间差由持续更新的时钟重新计算，并区分首次加载失败与刷新失败时的旧数据显示。客户端现有 30 秒循环是上传补偿，不是周期心跳；更可靠的在线状态需要单独设计心跳，不能只改时间计算就宣称已经实现。

## 6. 数据口径与不可补造的信息

### 6.1 三类事实不能强行合并

现有客户端任务事实在 `ClientTaskMirror`；正文在 `ClientTaskMirrorEvent`。本次新增的 run/节点归属持久化补齐员工参与事实，不替代任务镜像。云端会话事实在 `ConversationSession/Message`。费用事实在 `ComputeUsageRecord`。

云端费用表虽有 `sessionId/messageId`，但客户端镜像没有结构化账单关联。不能按同一成员、相近时间或金额比例给每个任务分摊费用。任务级消费首版默认未知；订阅级真实账单汇总可以保留。模型消费与企业钱包实际支出不是同一口径。

值传递链也证实此限制：客户端请求钩子目前只设置 Authorization，未传 task/run 计费键；网关缺少指定头时使用 `gateway:<userId>:<subscriptionId>` 作为 sessionId，以 HTTP requestId 作为 messageId，同用户同订阅不同任务共用该 sessionId。监控正文分片的 messageId 是另一随机 ID，不能当成账单 messageId。

证据：`/Users/yao/LLM/sep-client/electron/pi/sdk/pi-coding-agent-adapter.ts:388`；`/Users/yao/LLM/sep-client/electron/service/client-monitor-service.ts:178`；`backend/src/modules/gateway/gateway.controller.ts:59`。

### 6.2 首版记录粒度

列表以一个客户端任务或一个云端会话为一条记录，不以正文片段计数。客户端重跑仍是一条任务，详情按 run/节点查阅；本次保存可可靠采集的 run/节点状态、起止时间与员工快照，当前镜像主表的状态/时间不能贴到所有旧 run 上。

同一任务可以出现在多位实际参与员工的详情页，各页只展示该订阅的参与内容和使用时间。任务/会话记录数与员工参与次数分别计数，同一 run 同一节点不因重传或分片重复计数。

列表粒度和 run 数据完整性是独立事项：首版不做“每次运行独立一行”，但 run/节点归属与可采集元数据已纳入本次实施。历史无法恢复的字段仍显示未知。任务/run 精确费用需要另建稳定调用关联，不随参与记录建设自动实现，也不纳入本次范围。

### 6.3 历史与时间边界

- 镜像 `createdAt` 是云端创建时间，历史补传时不能当本地任务创建时间。
- `updatedAt` 是镜像更新时间；心跳和旧事件补传都会影响它。
- 使用记录中的业务时间优先来自当前订阅实际参与的 run/节点起止时间和内容事件 `occurredAt`；缺失时显示接收时间并标记，不用其他员工节点或最新 run 的时间覆盖历史。
- 时间范围采用显式 UTC+8，接口传 ISO 时间；日期选择转换为左闭右开 `[from,to)`，不随部署服务器 TZ 漂移。
- 消费仍按账单入账时间；不宣称与本地输入输出时间完全一致。
- 客户端历史正文已截断且本地没有可恢复源时，无法补造。
- 云端正文被硬删除后，即使账单保留也无法恢复。

### 6.4 云端历史的保守接入方案

首版纳入 Web 使用，先展示能够严格证明归属的会话：有该企业/订阅账单锚点、会话员工匹配、会话所有者与归属匹配，并排除混合/不明归属会话。先校验归属，再读取正文；管理员授权不以用户当前企业成员关系代替历史归属证明。

不明归属、无账单锚点、混合员工协作等历史不得凭当前成员关系开放全文，必须标记覆盖限制。安全地读取部分数据不等于“全部历史已对齐”。

无遗漏的未来云端历史还需额外设计创建时的企业/订阅快照及实际处理员工归属，并处理云端多员工协作，不在本次首版范围。首版明确“可严格归属的 Web 记录”覆盖限制，不承诺全量对齐；后续扩围需另立需求，不能借本次客户端参与协议扩展自动扩大云端读取范围。

### 6.5 本次必须建设的精确员工参与记录

客户端需要上报 run 的订阅/员工快照，以及编排节点的 `nodeId/stepKey`、订阅/员工、起止时间、状态、输入输出。事件与正文必须关联到正确 run/节点，不能把编排目标冒充每个节点的实际输入。单员工任务也需要 run 级归属，换员工重跑不能覆盖旧 run 快照。

后端持久化 run/节点归属，复用任务镜像作为监控主记录；员工详情按已验证的参与节点或单员工 run 查询，不只看镜像最新 subscription。监控仍按任务聚合，详情查看各 run/节点；同一次参与只计一次，不按分片数计数。

实施前先完成 shared DTO、字段/实体、兼容和迁移设计，遵守以下最小约束：

- 归属键至少能够区分任务、`clientRunId` 与节点/步骤；相同节点的重复执行须有可区分的执行标识，不仅靠节点名去重。具体实体名称和 schema 在代码设计时确定，不在本文假称已存在。
- 最小元数据包含使用人、已验证的企业/订阅/员工快照、参与标识、状态及可采集的起止时间；正文保留发生时间及所属 run/参与标识，继续使用现有脱敏和分片能力。
- 服务端校验上传者与任务 owner/企业一致，并验证参与订阅归属；不得信任客户端自报的其他企业、用户或员工 ID。已确认快照不随镜像当前订阅或用户当前企业关系迁移。
- 重传必须幂等；run/节点状态和正文归属不能串联。针对当前任务全局 sequence 水位可能丢弃迟到事件的风险，设计兼容的补传/去重规则并补回归测试，不能仅新增字段后宣称已解决。
- 旧客户端继续可用；缺少新字段时标注未知/覆盖限制，不制造参与记录。迁移由工具生成，历史只回填本地仍保有且能确定归属的内容，真实历史上传另行授权。

无法拆分的旧编排汇总保持“任务汇总/归属不明”，不得反推成各员工独立正文。列表、聚合和详情共用同一归属规则，避免有正文却漏计或无权限却计入总数。

此扩展解决员工参与归属，不自动解决任务费用。若同时要求精确计费，还需每次模型调用的稳定归因键与幂等策略，不能整个 run 共用一个账单 messageId。

## 7. 后端接口草案

以下均是拟议接口/参数，不代表已经实现。保留现有接口和旧客户端响应兼容，不引入新依赖。

### 7.1 扩展客户端监控只读查询

`GET /client/tasks` 新增可选 `subscriptionId`、`userId`、`statuses`、`taskType`、`from`、`to`、`q`、`sort`，保留 `scope/page/limit`。列表补最小员工摘要 `subscription:{id,name,employee:{id,name}}`。筛选选项和状态计数来自同一授权范围的服务端查询，不从当前页推导。

所有参数经 shared Zod DTO 校验。`userId` 明确为 User.id，不与企业 memberId 混用。非管理员不得借参数查询他人；跨企业资源保持 404，显式请求企业 scope 保持 403。

详情保持旧契约，新读取能力通过兼容参数或独立只读接口补充；不能破坏正文分片、run 隔离和 sequence 幂等。

### 7.2 增加订阅维度使用查询

建议在现有 subscription 模块内新增 service 方法，不另建采集平台：

- `GET /subscriptions/:id/usage-records`：按成员/来源/时间查询记录，返回 `items,total,page,limit,hasNextPage,coverage`。
- `GET /subscriptions/:id/usage-records/:source/:recordId`：限定当前订阅的只读详情；`source` 为固定枚举。

客户端来源复用监控读取服务和权限；详情还要证明 `recordId` 确实属于路径中的 subscription。云端来源建立严格授权后的读取，原 `/conversations` 所有者权限不变。

跨来源查询必须服务端统一排序和分页。禁止分别拉“一页客户端、一页云端”再混排并当作准确第一页；也不能为了得到一页记录每次加载所有正文。采用有界的元数据查询或统一数据库查询，排序键包含业务时间、来源、稳定 ID。详情才加载正文。

分页刷新可采用固定查询截至时间减少新增记录挤动；页码方案仍需说明活动记录更新后的移动行为，不承诺固定快照。超大数据集再评估游标，不为首版引入不必要基础设施。

费用摘要必须支持与页面一致的成员/自定义时间范围，扩展订阅 stats 的共享筛选能力或在同一查询 service 里聚合账单，不能拿未过滤的 stats 伪装成过滤后结果。账单入口应携带可支持的订阅/成员/时间条件；若现有账单接口缺少订阅筛选，需同步补齐授权查询，不能跳到全企业账单冒充当前订阅明细。正文来源筛选不自动变成账单来源筛选，摘要明确独立账单口径，不制造不存在的来源关联。

## 11. 邻近问题和剩余风险

调研发现，员工列表卡片、旧员工级 stats、旧 enterprise usage 与详情存在企业/本人、自然月/滚动天数、消息行数/轮数等差异。一些旧接口不具备新页面所需的成员隔离。新页面不能直接复用这些查询来扩大数据范围。

这些问题记录为后续统一口径/权限审查项，不在本轮擅自修复所有旧接口。尤其不能因某个旧接口返回企业汇总，就认为普通成员可以读同事正文。

此前同步文档有一处把“create 校验订阅/grant”泛化成创建/状态/事件都检查有效期；实际状态/事件侧校验的是 owner/enterprise。本次以实现为准，新只读查询不要照搬这处过宽描述。

所有结论基于本地代码和用户截图。实际环境是否部署最新同步实现、历史任务是否回填、某条费用对应何种调用，仍需上线前只读验证；不把本地有代码等同于线上已生效。

现有事件去重按任务全局 sequence 水位工作，低于水位的迟到历史事件未必能补入；正常 outbox 串行发送并不等于支持任意乱序恢复。此项保留为同步可靠性风险，不能靠 UI 缺片提示宣称所有历史已修复。
