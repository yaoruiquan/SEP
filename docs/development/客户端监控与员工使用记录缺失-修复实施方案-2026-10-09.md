# 客户端监控与硅基员工使用记录缺失：修复实施方案

日期：2026-10-09。适用仓库：SEP、sep-client。

## 1. 问题与已有证据

详见《客户端监控与员工使用记录缺失-生产排查报告-2026-10-09.md》。生产客户端监控数据库确实只有 3 条任务镜像，均为 v1；没有 v2 run/participation，并非前端限制只显示 3 条。刘凌本机当前任务快照中的 10 条任务均有未完成的上传队列，mirrorId 为空，且与生产这 3 条不是同一批任务。

客户端主进程监控 API 未携带 Origin/Referer，生产全局 CsrfGuard 会在业务处理前拒绝创建、状态、事件、心跳请求。已观察到监控 POST 403；用户有效员工授权已核实，不应通过扩大授权解决。正在运行的旧客户端构建还缺少历史恢复逻辑；仅部署 Web/backend 无法更新客户端。

员工使用记录与监控共享镜像数据，但员工页仅查询 v2 已核实参与归属。即使补传成功，历史 v1 记录仍会被原有查询排除。模型账单又是独立消费流水，没有相应任务正文或严格会话归属时，不能凭账单构造输入输出。

## 2. 修复目标与边界

1. 修正客户端监控请求，使四种写操作满足现有生产 CSRF 策略，保持 JWT、企业隔离、有效员工授权和现有管理员正文审计。
2. 现有 outbox 在当前登录用户/企业范围内恢复，并保持任务/run/sequence 幂等；历史补传保留实际业务时间。
3. 员工页继续展示已核实 v2 参与记录，并兼容明确属于当前订阅的旧单员工对话。历史兼容记录始终标为“旧客户端记录 / 归属未核实”，不能升级协议或伪造 participation。
4. 多员工编排或无法安全关联的旧任务仍只在客户端监控展示，员工页明确说明覆盖范围，不能误导为完全没有使用。
5. 本轮只修改代码、文档及进行本地验证；不发布客户端、不改生产配置、不部署、不运行真实客户端触发历史上传、不修改生产数据库。不新增依赖，不需要数据库迁移，不提交或推送 Git。

## 3. 上传链路修复

### 3.1 请求来源

在 ClientMonitorApi 的统一请求方法中同时设置 Origin 和 Referer。优先使用配置的 SEP_WEB_ORIGIN，按 URL.origin 规范化，兼容 Web/API 不同域名；测试或独立构造可显式提供 webOrigin，否则使用项目配置。Referer 为来源 origin + `/`。Authorization 的来源和 token 刷新逻辑保持原有约束。

不得将 `/client/tasks` 整段加入 CSRF 白名单，不能去掉生产来源校验，也不能把用户自定义 API 域名直接当成默认可信 Web 来源。

### 3.2 错误与恢复

403 错误允许识别服务端有限的已知安全错误，例如缺少来源、来源不允许、没有员工授权；不持久化任意响应正文、令牌或模型输入输出。保留状态码和现有 outbox 重试信息。401 仅按原逻辑刷新一次。修复后由现有当前 scope 恢复机制继续处理积压，不改变其他账户的历史。

历史运行记录增加 queuedAt，来源为本地已保存 run 创建时间；缺少时允许任务首次运行的创建时间，无法证明时不构造业务时间。已有未上传 create payload 如缺少 queuedAt，只按匹配的本地 run 安全补齐，不重写已上传任务、不生成新 run、不把 v1 改为 v2。明确区分业务时间和接收时间。

## 4. 服务端历史兼容契约

### 4.1 来源与列表

共享来源枚举新增 `client-legacy`。`source=client` 表示客户端记录集合，包含已核实 v2 和符合下述限制的 v1；`source=client-legacy` 可单独筛选历史兼容记录。详情地址保持现有格式：

`GET /subscriptions/:id/usage-records/client-legacy/:recordId`

只有同时满足以下条件的镜像可作为历史兼容记录：

- enterpriseId、subscriptionId 匹配当前授权范围；普通用户只匹配自身 userId，管理员可查看本企业成员；
- protocolVersion < 2，taskType 为 conversation；
- 整个镜像没有 run/participation 记录，避免与精确 v2 数据重叠或错误混合；
- 详情仅读取镜像当前 clientRunId 的未关联 participation 事件，返回输入输出事件；不得跨 run、跨订阅拼正文。

旧 arrangement 不进入员工使用列表。兼容来源不是 v2 证据，不承诺节点归属或任务级费用。

### 4.2 时间与分页

历史列表 usedAt 优先镜像 startedAt，其次当前 run 输入事件 occurredAt，其次 queuedAt，最终 createdAt；对应 timeBasis 分别为 `legacy-started`、`legacy-input`、`legacy-queued`、`legacy-received`。最后一种仅代表同步接收时间，页面明确标注，不能当真实执行时间。旧协议没有保存时间来源字段，既有 startedAt/queuedAt 也可能由服务端补齐，全部旧记录时间须提示来源未核实，详情解释这一限制；不能以时间相近等启发式猜测来源。历史日期过滤采用这个 usedAt 的 [from,to) 范围；既有 v2 运行区间/事件范围和 Web 时间逻辑保持。

三类来源统一 UNION ALL 后排序、分页、计数；保持业务时区 UTC+8。管理员成员选项加入符合条件的旧记录成员。消费汇总仍是账单指标，不受来源过滤影响，不用于虚构任务费用或正文。

coverage 保留 legacyClientTaskCount（当前订阅与用户范围内全部时间的历史任务总数），增加 readableLegacyClientTaskCount（符合员工页兼容读取规则的数量）。两个数都是覆盖说明而非当前日期筛选数量。旧多员工编排等差额提示去客户端监控查看。

### 4.3 详情结构与权限

新增独立 SubscriptionLegacyClientUsageDetail：source/recordId/task，单个 run 的 clientRunId、status、queuedAt、startedAt、completedAt、usedAt、timeBasis，及 events。events 的 participationId 为 null，可包含 occurredAt 缺失的旧事件，前端复用分片组装逻辑并标注接收时间、缺片。

coverage.attribution 固定为 `legacy-root-subscription-unverified`，currentRunOnly 为 true，taskCost 为 unknown。在同一 RepeatableRead 事务内检查可读条件并获取事件；复用管理员正文审计，审计失败不返回正文。详情和列表必须保持一致的可读边界。

## 5. Web 展示

- 来源列分别显示“客户端任务”“旧客户端记录”；历史行补充“归属未核实”。来源筛选“客户端”包含两类，增加“旧客户端记录”单独选项。
- 覆盖说明分别列出历史总数与员工页可读数，并说明其他历史记录在监控页查看；空列表提示“暂无可展示的使用记录”。账单不等于正文。
- 历史详情显示未核实提示、仅当前运行批次、业务时间或接收时间、输入/输出及其分片完整性，并保留带 subscriptionId/taskId 的监控链接。
- 带员工筛选的监控详情先读取已核实参与；只有 404 时尝试同订阅的历史兼容详情，401/403/503 等不切换。历史兼容也为 404 时说明无法按单个员工读取，并提供清除员工范围的完整任务入口；不自动获取完整正文。完整任务入口仍执行既有监控权限和正文审计。
- 不给旧历史伪造参与节点、真实归属或任务消费；已核实 v2 的参与选择、正文范围、运行批次选择保持原有行为。

## 7. 验收用例

- 四个监控写操作均携带配置的 Web 来源；生产 guard 有来源放行、无来源/不允许来源仍拒绝。API 与 Web 域名不一致也正确。
- 当前账户历史任务保留 runId/sequence；重复恢复不重复创建；未上传历史能补真实 queuedAt；已上传/无对应 run 的记录不被擅自改写；退出或换账户停止旧 scope 恢复。
- v1 单员工 conversation 可在客户端监控和员工详情看到输入输出，显示未核实；v1 arrangement、v2/mixed 镜像不能进入旧兼容详情。
- 普通用户不能读其他用户或企业的旧正文；管理员只能读本企业；失效授权按既有策略拒绝；正文审计失败不泄露正文。
- 详情读取仅当前 run 和 participationId=null 的输入输出；不泄露其他 run、参与节点或订阅事件。
- 日期范围、统一分页排序、客户端集合/旧来源筛选正确；createdAt 回退有接收时间提示；分片缺失不隐瞒。
- 既有 v2 精确参与与 Web 严格账单证明、消费汇总、监控使用正文功能无回归。

## 8. 发布与现场验收（本轮不执行）

先部署共享契约兼容的 backend/web，再安装含来源修复和恢复逻辑的新客户端。使用明确构建时间/提交标识判断包是否更新，不能只看仍可能相同的 0.1.2 版本号。客户端发布遵循仓库已有发布流程，不擅自修改其版本/更新工作。

由授权用户在本人账号下登录新客户端，观察恢复队列。记录修复前后本用户 taskId/mirrorId、上传成功或安全错误摘要，以及服务端对应镜像数和员工详情。10 条快照不等于所有本地历史总数，不能承诺总量精确为 10，也不能把原来其他用户的 3 条当成这 10 条中的 3 条。

历史任务日期可能早于默认最近 7 天；验收先用全部时间或实际历史范围。单员工旧对话进入兼容记录，多员工旧编排只在监控展示；新任务应有 protocolVersion=2、run、participation、所属事件。核验管理员看到本企业所有成员、普通用户仅本人，并确认没有跨企业正文。

回滚：客户端可回退代码版本但来源缺失问题会重新出现；backend/web 同步回退兼容契约版本。修复不迁移数据库、不把 v1 转 v2，不删除积压队列，已成功上传的数据不能通过应用回滚删除。
