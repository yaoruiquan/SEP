# 技能库发布版本与提交审核信息架构设计 v3

- 日期：2026-10-10。
- 状态：已实施并完成开发验收；尚未进行用户验收或真实数据库端到端验证。
- 范围：企业技能库列表及技能详情的信息架构、文案、预览与审核交互。
- 调研方式：用户截图、工作区源码、既有已确认业务规则，以及 GitHub 官方发布与审核文档；未进行用户访谈或可用性测试。
- 与 v2 的关系：保留《技能库客户端修改与 Web 审核启用改造方案-v2》冻结的业务规则，仅重新组织企业 Web 展示与操作。本文不恢复 Web 正文编辑、个人选版、企业向平台投稿或独立技能审核中心。

## 1. 设计结论

将技能详情拆成四个明确的工作视图：

**发布版本｜提交与审核｜使用统计｜迭代建议**

- 发布版本回答：现在运行哪个版本，有哪些可启用的历史发布版。
- 提交与审核回答：谁提交了什么，处理到哪一步，为什么通过或驳回，最终生成了哪个发布版。
- 使用统计回答：使用范围与调用情况。
- 迭代建议保留现有定位与权限，不在本次扩展。

审核记录属于提交详情。发布版本仅保留“来源提交”链接，不再承载待审提交、驳回记录及完整审核流水。

这里分开的是信息对象，不是业务步骤：**审核通过仍然在同一事务内生成企业版并自动启用**。

### 2.2 外部模式参考

GitHub 官方文档将两种对象分别定义：

- Pull request reviews：对提出的变更提供意见与审核决定，讨论和决定出现在该请求的时间线中。
- Releases：向使用者提供可分发的发布成果、发布说明与固定版本内容。

对 SEP 的设计推论：提交详情承载过程与审核，发布版本承载成果与启用。只借鉴对象边界，不引入 Git 分支、合并请求、多人审批或审批与启用解耦机制。

参考来源，2026-10-10 读取：

- [GitHub：Pull request reviews](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/reviewing-changes-in-pull-requests/about-pull-request-reviews)
- [GitHub：About releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases)

## 3. 命名与对象边界

| 当前 | 建议 | 边界 |
| --- | --- | --- |
| 版本 | 发布版本 | 仅正式、已通过的平台版与企业版 |
| 大家的改动／我的提交 | 提交与审核 | 页签名称两种角色一致，数据范围及操作权限不同 |
| 使用 | 使用统计 | 不改统计、执行明细的业务范围 |
| 改动待审核 | 待审核提交 | 明确这是已提交的待办，不是未保存的本地修改 |
| 审核通过 | 通过并启用 | 明确现有批准动作会发布并切换企业启用版本 |
| 预览并审核 | 审核 | 打开提交详情，先比较再决策 |
| 预览正文 | 查看详情 | 同时包含内容、来源、审核结果与发布去向 |
| 客户端提交 `<内部 version>` | 变更说明首行 | 来源作为次级字段，技术版本字符串仅放详情 |

选“提交与审核”而非“贡献”：这里是内部技能修改，不保证被采纳为贡献。

选“提交与审核”而非“审核记录”：还要承载待处理提交，不能只表达已完成流水。

选“提交与审核”而非“变更申请”：可直接对应客户端“提交”动作，不增加一套新术语。数据层仍可视为变更请求。

## 4. 详情页结构

### 4.1 公共页头

页头保留返回技能库、技能名称和描述，下面增加紧凑的当前启用摘要：

```text
多平台经营协同
统一淘宝／天猫、京东、拼多多等平台的日常经营任务。

当前启用  企业版 v1.0.0       启用时间  2026/10/10 13:22

发布版本    提交与审核 · 1    使用统计    迭代建议
```

- 当前启用摘要放在页签上方，切换到审核时仍能看见执行背景；版本页不再重复放一张相同摘要卡片。
- 若无显式默认且各相关订阅实际使用同一平台版，显示该有效平台版及“自动使用”，不写“暂无启用版本”。需要后端统一当前有效版本语义。
- 若没有统一企业默认，且相关订阅实际使用不同版本，显示“未设置统一启用版本”及按员工查看的入口；不能随意取第一条订阅的回落结果冒充全企业启用版本。
- 启用时间只在有可靠字段时显示；创建时间、审核时间不能冒充启用时间。
- 待审核数字由有权限的汇总数据提供，不能按当前页条目数计算。管理员是企业待审数，成员是本人待审数；为零时不显示角标。
- 使用 URL 保存页签与必要筛选，返回详情或收到深链接时恢复上下文。保留 `?tab=versions`、`?tab=changes` 的现有含义。

### 4.2 发布版本

采用紧凑、对齐的列表，不再把所有对象串成一条时间线。

```text
来源 [全部 ▾]

版本              更新说明        发布时间             状态         操作
企业版 v1.0.0     姚瑞泉测试2      2026/10/10 13:22     当前启用     查看详情
平台版 v1.0.0     初始版本         2026/10/08 11:31     可启用       查看详情  启用
```

展示规则：

- 发布集合严格为 `PLATFORM / PLATFORM_APPROVED` 或 `ENTERPRISE / ENTERPRISE_APPROVED`；已通过 PERSONAL 仍然是提交，不能混入。
- 当前启用版置顶，其余按发布时间倒序；来源标签区分平台和企业，不把两个 `v1.0.0` 当成同一版本。
- 主状态仅“当前启用／可启用”，不重复显示“企业已通过／平台已通过”。发布列表本身已经表达可用性。
- 查看详情展示版本内容、更新说明、发布时间、来源提交链接；来源提交链接必须按当前角色授权，不能泄露他人个人提交。
- 管理员可启用其他正式版本。确认框说明将切换企业当前启用版本，历史版本不会被删除；成员没有启用操作。
- 切回旧版也是启用现存版本，不重新创建版本、不改变原审核结果。
- 如展示切版历史，在当前启用摘要旁设次级“启用记录”入口，复用审计；不新增一级页签，也不称为审核记录。
- 对只有创建时间的历史数据，标“创建时间”；只有确定发布时点的记录才标“发布时间”。

### 4.3 提交与审核

管理员查看企业全部提交，成员仅查看本人提交；权限遵循现有服务端规则，不增加跨成员可见性。

```text
状态 [全部 ▾]                                  共 2 条

提交内容           提交人   提交时间             审核状态   发布结果       操作
姚瑞泉测试         刘凌     2026/10/10 13:16     待审核     —              审核
姚瑞泉测试2        刘凌     2026/10/10 13:19     已通过     企业版 v1.0.0  查看详情
```

- 筛选为全部、待审核、已通过、已驳回；初次直接打开该页签默认全部，待办入口默认待审核，避免已处理记录被误认为丢失。
- 待审核在前，同状态按提交时间倒序；采用服务端排序和分页，不能对当前页局部排序冒充全局排序。
- 提交主标题使用变更说明首个非空行，完整说明在详情中展示。没有说明则用“技能修改提交”，历史副本用“历史 Web 副本”。
- 长摘要 ID 不出现在主标题。详情中展示内部版本和提交 ID，提供复制；短 ID 仅用于辅助定位，不生成虚构流水号。
- 提交时间使用 `submittedAt`；历史副本没有提交时间则明确写“更新时间”，不伪造时间。
- 来源渠道、来源版本等放在次级信息或详情里，不重复挤满每个列表项。
- 已通过显示可点击的正式版本号，不显示 `publishedVersionId` 原始 ID；已通过不等于仍在启用。
- 驳回原因在详情完整显示，列表可显示简短摘要。普通驳回记录只读，后续修改从客户端形成新提交。
- 保留历史副本及审核快照，列表按根记录去重。未送审、通过但未发布等遗留情况明确标注，不强行归成待审核或已发布。
- 管理员自己的提交与其他成员一致，仍按现有审核权限处理；不新增禁止自审规则。

### 4.4 提交详情与审核

使用宽侧栏或宽弹层；桌面可左右对比，窄屏切换为上下对比。内容区和审核操作区有明确边界。

```text
姚瑞泉测试                                      待审核
提交人 刘凌 · 2026/10/10 13:16 · 客户端提交
来源版本：平台版 v1.0.0

内容差异       完整内容       处理记录

对比对象 [提交来源版本 ▾]
<来源内容与本次提交内容的对比>

                                      [驳回] [通过并启用]
```

内容差异：

- 默认与提交时的来源版本比较，保证回看时语义稳定；来源版本 ID 由提交真实 `parentVersionId` 决定，不用企业版的 parent 代替。
- 可切换“当前启用版本”，明确展示两端版本名和对比类型；当前启用版变化时刷新或提示，不继续把旧对比当作最新事实。
- 无来源或无权读取时显示“无可读取的来源版本”，仍允许查看完整提交内容，不把全部内容伪装成新增。
- 当前审核是完整内容替换，不标为“合并”。来源与当前启用版本不同，应提示“基于较早版本提交，请检查是否覆盖后续修改”。是否强制阻止过期基线审批属于后续业务决策，本次不擅改。

处理记录：

- 展示实际保存的提交、企业审核决定、审核人、时间、意见／驳回原因、生成企业版本的关联。
- 历史工作副本按审核快照展示各次真实决定，并标注对应修订；不将快照单独列为一次客户端提交。
- 不把平台内部审核流水带入企业提交详情；平台收录不改写企业审核状态。
- 与发布结果相关的启用记录可关联查看，但后续切版不修改该提交的审核结果。
- 不存在的历史事件或意见明确缺省，不依赖版本创建时间重建虚假审核记录。

操作：

- 点击“通过并启用”后，确认当前提交与企业切版后果；审核意见选填。
- 驳回原因必填；原记录保留，不影响当前企业启用版本。
- 处理中禁用重复提交；审核状态或可变副本修订变化时要求重新预览；冲突响应刷新最新状态。
- 通过成功后留在当前详情，状态变为已通过并显示企业版链接；公共当前启用摘要、发布版本及待审数量同步刷新。

## 5. 列表入口与状态设计

- 技能库待办名称统一为“待审核提交”，成员为“我的待审核提交”。点击进入对应技能的 `?tab=changes&status=pending`。
- 一般技能条目进入发布版本，不再根据角色随机进入不同职责页面。
- 原 `/skill-reviews` 继续跳转技能库，不恢复第二个审核中心。
- 提交链接与发布结果链接可精确定位对象；返回时保留页签、筛选与分页。
- 空状态：发布页“暂无发布版本”；审核页按筛选显示“暂无待审核提交／暂无提交记录”。有待审但未发布的技能不能被判断为空技能。
- 加载采用稳定列宽和骨架；失败保留已有信息并提供重试，不能把请求失败显示为零条。
- 桌面内容宽度可由当前约 896px 调整到约 1120px，优先让列宽和内容对比可读；沿用企业壳和现有主题，不重做全站配色。
- 窄屏列表改为行式摘要，提交说明可换行，状态与主操作保持可见；技术 ID 使用截断或换行，不能撑破布局。
- 页签使用规范 tab 语义与键盘切换，图标配可读名称；状态不能只靠颜色传达。

## 6. 实现边界与接口缺口

### 6.1 复用，不另建流程

- 客户端提交入口、幂等语义和审核写接口不变。
- 复用 `EnterpriseSkillReviewService` 的单条审核、事务、锁、工作副本修订校验与通知。
- 复用 `EnterpriseSkillDefaultService` 的启用与审计，不新增默认版本模型。
- 复用现有 PERSONAL、SkillVersionReview、SkillVersionAdoption 及历史快照数据；不为了页签更名建表或迁移。
- UI 的“发布版来源提交”关联来自 Adoption；不能误用用于平台复制的 `SkillVersion.sourceVersionId`。
- 为保留客户端兼容，优先扩展只读 DTO 或增加聚合查询；不得直接缩减旧 versions API 的记录范围而未核查调用方。

### 6.2 需要补齐的只读能力

| 能力 | 当前缺口 | 建议 |
| --- | --- | --- |
| 完整提交处理记录 | personal-diffs 只有最新结果摘要；timeline 只见本人 PERSONAL | 按提交 ID 聚合根记录及其审核快照的真实日志，复用企业权限校验 |
| 稳定来源对比 | `basedOn` 只有元数据，无来源正文 | 授权后读取来源正文；区别来源不可读与没有来源 |
| 发布结果显示 | 当前只有 `publishedVersionId` | 补充发布版本的 id、version、scope 与当前启用标记 |
| 发布版追溯提交 | 当前列表缺少可直接导航的企业采纳来源 | 读取 Adoption，并按访问权限返回可打开的提交关联 |
| 真实当前有效版本 | timeline 顶层默认和运行解析 fallback 可能不一致 | 与现有执行解析统一只读语义，区分显式启用与自动回落 |
| 当前启用与切版历史 | 写审计已有，详情读取未齐 | 读取同企业、同技能审计；只展示有可靠来源的操作者和时间 |
| 审核待办汇总与排序 | 本页数不能代表总待审数；当前分页不足以全局待审优先 | 服务端汇总、稳定排序及分页；汇总和列表采用同一去重与权限规则 |

完整处理记录和来源对比需要服务端契约支持。本轮已实现提交详情、审核快照日志聚合、来源授权、发布关联、有效版本与待审汇总；启用审计历史为可选入口，本轮未新增读取接口或展示。

## 7. 验收标准

1. 用户截图中的两个客户端提交移入“提交与审核”；“发布版本”只留下企业版和平台版，原始记录不删除。
2. 主标题不再出现 `0.0.0-personal.<长摘要>`；完整技术信息仍可在详情读取。
3. 审核人、意见、驳回原因归对应提交详情；发布版本通过来源链接追溯，不重复承载整份审核流水。
4. 已通过提交与其企业版能相互定位；回切旧版后，该提交仍显示已通过，但不再错误显示当前启用。
5. 批准按钮清楚标“通过并启用”，成功后真实发布并切版；驳回保持当前启用版本不变。
6. 管理员查看企业提交，成员只查看自己的提交；任何对象深链接均经过服务端授权，角色切换不残留越权缓存。
