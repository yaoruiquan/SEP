# 客户端监控状态同步与筛选体验优化开发方案 v1

日期：2026-10-10（Asia/Shanghai）。适用仓库：`SEP`、`/Users/yao/LLM/sep-client`。

文档状态：已进入本地实施与验证，当前结果见 [客户端监控优化实施记录-2026-10-10.md](客户端监控优化实施记录-2026-10-10.md)。本文保留方案编写时的事实与验收要求；实施不包含部署、生产补传或生产数据修改。本方案承接 2026-10-09 的缺失记录修复，重点解决“记录可见以后，状态是否可信、输出是否完整、筛选是否好用”。

## 1. 目标与范围

用户最新截图显示：全部历史 33 条、进行中 19 条、待处理 0 条；一条 `hi` 记录显示排队中、0%、开始时间未知、心跳延迟，详情只有一个 `user_input` 事件。

本次交付应达到：

1. Web 显示客户端已成功上报的真实运行状态，保留暂停与中断的区别；缺少状态证据时明确说明。
2. 暂停、中断等状态请求不会因时间字段冲突卡住同步队列。
3. 本地仍保存的输入与回复能幂等补齐，已有旧 outbox 也能修复；没有恢复证据的内容明确标记。
4. 常用筛选一次操作即可生效，取消分类与状态交叉导致的隐藏交集。
5. 任务状态、心跳情况、内容完整性分别表达，避免将“能看到任务”理解为“已经完整同步”。
6. 客户端监控与员工使用记录保持同一内容与时间口径，保持既有企业、用户、订阅权限。

沿用现有产品范围：展示用户输入和员工回复文本，保留失败、暂停、中断时已经生成的部分回复并标注。工具参数、工具原始结果、模型思考过程、任意本地文件及附件上传不纳入本次。已有结果链接可以原样呈现，不因此增加附件采集能力。

## 2. 证据与结论边界

### 2.1 已确认的实现问题

| 问题 | 当前行为与影响 | 代码入口 |
| --- | --- | --- |
| 两层状态筛选互相限制 | `view=active` 与 `statuses=COMPLETED` 取交集，得到空列表 | `backend/src/modules/client/client.service.ts`：`taskMirrorReadWhere()` |
| 筛选提交步骤多 | 搜索、下拉和复选框先改 draft，再点“筛选”才生效 | `web/src/features/task/components/client-task-monitor.tsx` |
| 未知状态契约不一致 | Web 提供 `UNKNOWN`，后端查询和写入枚举均不接受它 | `backend/src/shared/client-task.dto.ts`、监控组件 |
| 暂停状态请求会被拒绝 | 客户端 `taskFinished()` 对 PAUSED 也传非空 `completedAt`；后端禁止非终态带完成时间 | 客户端 `client-monitor-service.ts`、后端 `updateTaskMirror()` |
| 单任务队列可能被持续阻塞 | 失败操作保留在队首，后续操作不能直接发送；错误状态指纹在入队时已经记录 | 客户端 `processPending()`、`addStatus()` |
| 已有 outbox 不补漏失正文 | `restoreHistory()` 只有没有监控 record 时才加入恢复出的 messages | 客户端 `client-monitor-service.ts` |
| 无 run 时只恢复输入 | 快照降级分支只取 task.prompt，不继续处理可归属的消息输出 | 客户端 `client-monitor-history-service.ts` |
| 初始值易被当成真实状态 | 新镜像默认 QUEUED、progress=0；后续更新失败时默认值持续展示 | `backend/prisma/schema.prisma`、`createTaskMirror()` |
| 筛选选项未覆盖旧员工记录 | 员工选项来自 participation，只有 v1 根订阅的任务可能可见但不可按员工选中 | `getTaskMirrorFilterOptions()` |
| 时间和数量口径不清晰 | 顶部“共 N 条”是当前结果；缺失 queuedAt 时服务端采用接收时刻 | 监控组件、`createTaskMirror()` |

补充说明：Web 已有模型输出展示和长文本组装能力；未确认员工归属的事件仍会展示正文。不能把“历史归属未确认”当作隐藏输出的原因。

2026-10-09 排查报告中的“生产只有 3 条”属于当时的历史快照，不能继续作为当前生产数量。以用户最新的 33 条截图作为本次核查线索，实施时重新获取带时间的基线。

## 3. 产品行为决策

本方案采用以下建议默认值，可据此安排开发；不把尚未核查的生产事实当作产品决策。

| 项目 | 建议行为 |
| --- | --- |
| 默认视图 | 全部状态、全部时间；有员工入口约束时始终限定该员工 |
| 常用筛选 | 任务标题搜索、硅基员工、任务状态 |
| 高级筛选 | 发起成员、任务类型、时间范围、自定义排序 |
| 生效方式 | 下拉即时生效；搜索约 300ms 防抖；自定义日期有效后应用 |
| 状态语义 | 暂停与中断分开；已取消采用真实 run outcome，不被本地 PAUSED 快照覆盖 |
| 回复展示 | 完整回复正常展示；中断或失败的部分回复可读，并提示结果可能不完整 |
| 缺失内容 | 根据证据提示“尚未生成”“同步未完成”“历史内容不可恢复”或“原因未确认” |
| 排序 | 默认最新业务活动优先，不能把心跳或历史接收时间当成真实执行时间 |
| 远程控制 | 继续只读监控，不增加 Web 重试执行、暂停、取消客户端任务 |

页面不以“已完成”推断输出已经同步，也不以“没有输出”推断任务未执行。客户端不在线时，云端无法知道当前 outbox，Web 应保留“最后收到”的语义。

## 4. 状态与时间契约调整（P0）

### 4.1 统一跨端状态

| 客户端证据 | 云端状态 | Web 标签 | 分类口径 |
| --- | --- | --- | --- |
| 已入队的 pending | QUEUED | 排队中 | 进行中 |
| 正在执行 | RUNNING | 执行中 | 进行中 |
| 等待人工审批 | WAITING_APPROVAL | 等待审批 | 待处理 |
| 用户暂停 / run outcome=stopped | PAUSED | 已暂停 | 待处理 |
| 客户端中断 / run outcome=interrupted | INTERRUPTED（新增） | 已中断 | 待处理 |
| 执行完成 | COMPLETED | 已完成 | 已完成 |
| 执行失败 | FAILED | 失败 | 失败 |
| run outcome=cancelled | CANCELLED | 已取消 | 已取消 |

`INTERRUPTED` 加入前后端 DTO、客户端契约、标签、查询计数及员工使用记录相关 SQL。数据库 status 当前为 String，增加该枚举值本身不需要 Prisma 迁移。旧 PAUSED 缺少停止原因时仍显示“已暂停”，不能批量猜成中断。

`UNKNOWN` 不作为本期可写业务状态或任务状态筛选项。缺少可信状态、未收到心跳、同步过旧分别用辅助信息表达。若数据库已存在其他未知状态值，应保留读取兜底，不伪装成已完成或排队中。

### 4.2 对齐时间语义并兼容旧队列

- `completedAt` 仅用于 COMPLETED、FAILED、CANCELLED，保留后端对非终态的现有校验。
- PAUSED、INTERRUPTED、WAITING_APPROVAL 的 status payload 不带非空 `completedAt`。暂停/中断的本次运行停止时间通过下述状态证据事件保存为 `runEndedAt`。
- 修复实时上报和历史恢复两个入口，并检查 participation 更新，防止同一个错误通过另一条路径进入。
- 发送已落盘的旧 status 操作前，针对上述已知错误进行一次受控规范化：保留 operation ID、run ID、顺序、状态及其他有效字段，移走非终态完成时间，补状态证据事件后原子保存，再重试。
- 对应状态指纹一并更新；区分“已排队”与“服务端已确认”，失败入队不能被解释为同步成功。
- 对缺少来源证明的其他 400/409 不自动改写或删除操作。已完成 run 的不一致终态保持冲突，进入核查，不能伪造新 run 绕过。
- 历史 queuedAt/startedAt 缺失时保留“时间未知”或“接收时间”说明。不能使用今天的补传时刻冒充原执行时间。

### 4.3 用现有事件保存状态来源

新增受共享 Zod 契约约束的 `monitor_state` 事件。沿用事件表和已有 `message` 字段存储短 JSON，限定 schema/version、字段、长度和合法时间，不接收任意对象；该类型在详情中按专用信息展示，不直接展示 JSON。

载荷限定：`version`、`reportedStatus`、`source=live|local-run|snapshot`、`observedAt`、可选 `runEndedAt`、可选明确上报的 `progress`。使用事件自身的 clientRunId/participation 绑定归属。该事件只证明客户端上报的来源，不能单独修改任务状态、解除终态保护或证明输出完整。

新客户端按同一队列先发送 status，再发送对应证据事件；读取端只采用同 run 且 reportedStatus 与当前状态一致的最新证据，旧证据不能为后续状态背书。证据缺失时读取端保守显示“最后上报状态，来源未核实”。没有证据的默认 QUEUED 不承诺真实排队。历史已有状态成功上报时允许补证据，但只能来自匹配的本地 run/快照。

心跳延迟保留为独立提示，不把任务改成 UNKNOWN/FAILED。不在没有明确进度来源时展示默认 0%；显示“进度未上报”或省略进度，COMPLETED 可按明确规则显示 100%。

## 5. 输入输出恢复与幂等补齐（P0）

### 5.1 恢复来源及归属

1. 优先读取现有 ConversationMessage，保留消息 ID、role、clientRunId、subscriptionId、真实时间。
2. 对确实没有 canonical 回复的 run，读取同 run 的已有 timeline，恢复可确认的 text_delta 或编排节点结果。
3. timeline 恢复的文本只能标记为“恢复片段/完整性未核实”，除非有明确结束与完整性证据；不能仅因拼接成功就认定完整。
4. 没有 TaskRunRecord 时，仍检查消息存储。有明确 task/run/subscription/owner 绑定的消息可按原 run ID 恢复；不能把所有孤立消息塞进 `history-${taskId}`。
5. 只剩 task.prompt、没有可归属输出时，保留快照输入并返回原因。没有证明的员工参与继续是旧协议，不能补成 v2。
6. 部分轮次可恢复、部分不可恢复时分别显示；不能用“某 run 有一个输出”判断所有轮次内容已齐。

### 5.2 已有队列也执行差异补偿

将 `restoreHistory()` 从“没有 record 才补正文”调整为“对每个可证明的 run/message 核对缺口”。保留原 outbox 的 operation ID、sequence、run ID、重试信息及已发送记录，只追加缺失操作，不清空再生成。

补偿前比对三类内容：本地 canonical 消息、现有 pending 内容、云端已接收内容。需要云端核实时只读取当前用户拥有的对应 mirror；沿用详情权限，不读取企业其他成员的正文做自动修复。

幂等规则：

- 新内容使用稳定 messageId：优先源消息 ID；没有 ID 时使用稳定来源记录键，必要时对脱敏正文做摘要作为补充。同正文的两轮真实回复仍是两条消息，不能只按正文去重。
- 所有新正文均携带 `content:v1:<messageId>:<index>:<total>`，包括单片正文；协议 messageId 使用不含冒号的稳定编码，并保留源 ID 映射，兼容现有解析规则。保持现有分片长度、脱敏顺序、空白保留和跨 run 隔离。
- 在任务级串行写入中，为新增片段分配 sequence 并原子保存映射与 pending；重试复用已经分配的 sequence，不重新生成随机 messageId。
- 旧无稳定 ID 的事件先按同 run、归属、类型、时间和组装正文进行有重数的匹配；歧义时记为“待核查”，不盲目重复上传。必要的归一化只处理已证实的旧格式差异。
- 如果旧正文只是前缀或被截断，单独识别为替代候选。新完整内容经确认接收后，用受校验的替代关系隐藏旧展示，保留历史事件；不能靠“更长”直接覆盖另一条真实回复。
- 本地补偿索引同时记录已入队和已确认状态，进程在响应后、落盘前崩溃时仍通过原 sequence 重放保持云端幂等。
- 旧 run 正文可按原 run 归档，不重选镜像当前 run，不覆盖当前任务进度或状态。

### 5.3 内容覆盖证据

新增 `content_manifest` 事件，使用受校验的短 JSON 描述逻辑消息：`version`、`messageId`、`type`、片数、来源、完整性、可选被替代消息标识。载荷必须在已有单事件上限内；每条消息一个 manifest，避免任务级大清单。

manifest 使用与正文相同的 run/participation 归属，排在对应正文片段之后；本地确认后不重复生成。服务端与 Web 依据实际收到的片段校验 manifest，不能只信任“完整”标志。canonical 消息存在仅证明正文已持久化；只有消息完成标记或可关联的输出结束证据支持时才声明完整，失败/中断的最终状态本身不能证明正文完整。已有完整旧消息无须重复上传正文，可在明确匹配后补对应覆盖证据。对无 messageId 的旧正文，manifest 必须携带受长度限制的已匹配事件 sequence 引用；无法唯一绑定或超过单事件上限时留待核查，不能挂到另一条同文消息。替代关系同样使用可唯一定位的消息/事件引用。

运行结束且经过恢复核查后，可追加 `content_recovery` 事件，限定原因：`not-generated`、`source-missing`、`ambiguous`。事件包含核查时刻和来源范围；新证据到达后可更新结论，不能作为永久拒绝补齐的标记。`not-generated` 仅在明确执行证据支持时使用。

建议读取语义：

| 证据 | 页面提示 |
| --- | --- |
| 有输出，manifest 与实际片段一致且来源完整 | 已收到完整回复 |
| 有输出但无完整性证据，或运行中断 | 已收到回复，完整性未核实 / 部分回复 |
| 已知片段缺失 | 回复同步未完成，显示收到片数 |
| 本地明确未生成输出 | 尚未生成回复 |
| 恢复检查确认源内容不存在 | 历史回复无法恢复 |
| 无输出，也没有恢复结论 | 暂未收到回复，原因未确认 |

正文覆盖与员工归属覆盖分别表达。输出完整不代表 v1 员工参与已经核实，任务完成也不代表所有内容已接收。

## 6. Web 筛选与详情优化（P1）

### 6.1 筛选区

取消现有“进行中 / 待处理 / 全部历史”作为额外隐含查询条件，使用一个状态筛选控件。控件默认“全部状态”，允许按 8 个真实状态选择；需要快捷分类时，仅转换为同一个 statuses 值，不再叠加另一份 view。

```text
客户端任务监控                         刷新
当前结果 19 条 · 当前权限范围共 33 条

[搜索任务标题…]  [硅基员工：全部]  [任务状态：全部]  [高级筛选]
已选：已中断 ×  发起成员：刘凌 ×                   清空筛选

任务列表
```

高级区默认折叠，收纳发起成员、任务类型、时间范围和排序。时间提供今天、近 7 天、近 30 天、自定义；初始不设时间限制。明确使用 UTC+8，日期范围采用左闭右开区间，不把“时间范围”标签写成任务自身的开始/结束时间。

搜索提示改为“搜索任务标题”；本期不扩展正文全文搜索。任务类型显示中文名，保留未知类型兜底。

切换筛选重置页码，保留其他条件；条件写入 URL 以支持刷新和返回，认证信息不写入 URL。已有 taskId/subscriptionId 深链保持可用。清空用户筛选不能解除来自员工页的 subscriptionId 固定范围，指定任务详情与列表条件的关系要明确。

### 6.2 后端查询与选项

- 新 Web 使用现有 `view=history` 加 statuses，实现单一状态条件；保留旧调用方显式 view/statuses 的兼容行为，不能无告知更改其交集语义。
- `filter-options` 增加可选 `counts.byStatus`；保留旧 counts 字段。按除状态之外的已应用条件统计，与相同权限范围的列表一致。
- “当前权限范围共 N 条”由独立、同权限的无用户筛选计数提供；缺少该计数时只显示当前结果，不能用状态分组数量拼造总数。
- 员工候选补充授权范围内 v1 根订阅，标记“旧记录归属未核实”；不能伪造成 participation。
- 每个候选维度忽略自身当前选择、保留其他生效条件，避免选中一个员工后无法切换；固定员工入口范围仍保留。
- 增加可选 `activityAt_desc` 排序：来源优先级为可证明的业务事件时间、startedAt、queuedAt，最后才用接收时间；同时返回时间来源。以数据库聚合排序再分页，不能在当前页内排序冒充全量结果。
- 对旧时间来源未核实的数据继续给出说明；在真实 PostgreSQL 上验证聚合分页、稳定排序与权限条件，避免列表 N+1 详情读取。

### 6.3 任务行与详情

任务行优先展示：标题、硅基员工或旧归属提示、发起人、业务时间、任务状态、必要的同步/心跳提示。客户端版本、技术 taskType、run ID、诊断时间放到展开详情；缺少 activity 不用“当前活动：未同步”反复占一行。

详情先展示“用户输入 → 员工回复”，按 run 与可证明的消息/轮次顺序排列；无可靠轮次关系时按时间排列，不强配问答。旧归属提示压缩为一条可展开说明，不放在正文之前形成大段空白。

始终保留回复区域：没有输出也展示有依据的空态。长文本保持可读与缺片提示；“技术事件”默认折叠，新增 metadata 事件转为用户可理解的说明，不展示协议 JSON。文本呈现保持安全，不为格式优化开启不受控 HTML。

## 7. API、存储与权限边界

本期推荐复用 `ClientTaskMirrorEvent` 保存状态来源与内容覆盖证据，扩展 status 枚举、可选查询参数和只读响应，不新增同步任务表或数据库列。

实施要求：

1. 共享 DTO 对新增事件类型做专用校验，并明确记录写入兼容策略。旧客户端普通事件继续可写；不得依赖未知字段会被保留。
2. 新 metadata 事件继续遵循 `(mirrorId, clientRunId, sequence)` 幂等键；不能改变已有事件身份。
3. 客户端 outbox 增加可选的消息映射、确认记录、修复版本。读取旧 record 不丢 pending；新客户端 schema 必须接受新状态，防止 parseRecord 过滤操作。
4. 员工详情专用接口同步返回该员工可见的覆盖摘要；不能为显示完整性转调全任务正文，泄露其他员工节点。
5. 普通用户只读本人，管理员只读本企业；保留正文审计、订阅授权、Origin/Referer 和 JWT 校验。
6. metadata 与业务正文同级授权，日志只记录 ID、分类、计数、时间及 HTTP 状态，不输出正文或任意错误响应。
7. 若实现验证后确需新增持久化字段，单独写明原因及迁移范围，按 `pnpm db:migrate` → `pnpm db:generate` 生成，不手改历史迁移。本方案默认路径不需要迁移。

## 8. 生产基线与历史修复步骤

### 8.1 实施前只读核查

选取截图的 `hi`、一条客户端确认有回复的完成任务、一条暂停任务、一条中断任务和一条编排任务。记录实际客户端路径/构建标识、账号 scope、云端部署版本；客户端显示的 0.1.1 不能单独证明包内实现。

按 clientTaskId/clientRunId 对照：本地 task、run outcome、消息数量及角色、timeline 是否可恢复、outbox 队首类型/错误码、云端 status/protocolVersion/events 类型及数量。优先只读元数据；正文逐字核验只针对当前用户授权的样本。

输出分类计数：真实排队、状态补传失败、正文未入队、上传失败、源正文不存在、归属歧义。未核查项保留 unknown，不把截图中的 19 条统称为假排队。

### 8.2 客户端补偿

先对当前登录 scope 生成 dry-run 差异：可规范化操作数、可补消息/片数、歧义数、不可恢复数。dry-run 不执行任务、不发送写请求、不扫描任意目录。

发布验证后的客户端在同 scope 执行补偿，保留原镜像 ID、run ID 和历史事件。补偿不得跨账号、重新执行模型、重放工具或修改本地业务结果。生产补传属于实际数据变更，本轮方案编写不包含执行授权。

已有云端错误终态触发不可变保护时，记录冲突并提出针对单条记录的处理建议；不批量改数据库、删除任务或重建历史。老包继续上传导致异常时优先暂停修复 rollout，不能让补偿反复覆盖。

### 8.3 对账口径

记录检查时刻与当前权限范围，比较同一组 task/run/message 的前后差异。33 是截图时的基线线索，不能要求持续有新任务的系统最终仍固定 33 条。

对账成功包括：镜像身份不变、状态与可证明本地结果一致、可恢复正文一致、重复补偿不新增重复消息、无法恢复内容原因可见。单纯“云端记录数量增加”不算通过。

## 10. 测试与验收标准

| 场景 | 必须满足 |
| --- | --- |
| 暂停/中断 | 后端接受有效状态，completedAt 为空，停止时间可读，后续队列继续发送 |
| 旧失败 pending | 同一操作安全规范化并成功重放；其他未知错误不被悄悄丢弃 |
| 终态保护 | 当前 run 已完成后不被旧 RUNNING 或不同终态覆盖；旧 run 事件不更新当前状态 |
| 已有 outbox 缺输出 | 本地有完整回复时补齐；连续两次恢复及重启恢复不重复显示 |
| 无 run、仍有消息 | 有明确归属的消息按原 run 恢复；归属不明时不拼接、不伪造 v2 |
| 长文本/相同回复 | 缺片可见、空白保留；不同轮次相同正文均保留，同一消息重试不重复 |
| 截断旧正文 | 有证明时以完整内容替代展示，历史事件保留；歧义时不自动覆盖 |
| 部分/无输出 | 已完成无输出不伪装完整；中断片段明确提示；源内容丢失与原因未知区分 |
| 跨端契约 | 用真实 ClientMonitorApi 的序列化结果经过真实 DTO/服务，覆盖 400/409/429、断网、响应后落盘前崩溃 |
| 单一状态筛选 | 选“已完成”直接命中完成任务；没有 active 的隐藏交集；无 UNKNOWN 非法请求 |
| 范围与候选 | v1 员工可筛选；重置/刷新/深链不解除员工固定范围；非管理员不能读取他人 |
| 数量与分页 | 结果数、权限范围总数、状态数口径可解释；跨页稳定排序，无漏项与重复项 |
| 性能与界面 | 列表不逐条请求详情；桌面与移动可直接看到任务，回复空态不缺席，无原始 metadata JSON |

验证顺序：先针对性回归，再三端 typecheck、改动文件 ESLint 与构建；涉及 runtime 并发再跑客户端 invariants，层间改动跑 boundaries。新增聚合查询需在隔离 PostgreSQL 验证真实 SQL；mock 测试不能替代它。

可使用现有命令入口：

```bash

pnpm --dir backend test -- --runInBand client-task-mirror.spec.ts subscription-usage.service.spec.ts
pnpm --dir backend typecheck
pnpm --dir web test -- src/features/task/components/client-task-monitor.test.tsx src/features/task/client-task-content.test.ts src/features/task/use-client-task-mirrors.test.tsx src/features/employee/employee-usage-records.spec.tsx
pnpm --dir web exec tsc --noEmit --incremental false
pnpm build

# sep-client：在该仓库执行
npm run test:tasks
npm run typecheck
npm run check:boundaries
npm run build
```

浏览器验收先使用隔离 fixture，再以真实客户端执行一个正常完成、一个暂停/中断任务；记录实际请求、截图和样本身份。没有实际客户端与生产对账证据时，只能表述本地验证通过。

## 11. 发布与回退

顺序：支持新枚举/事件/查询的 backend → 兼容新旧数据的 Web → 新客户端小范围安装 → 样本对账 → 历史补偿扩大范围。先确认来源配置、权限及实际运行构建，不能只部署 Web 就宣称客户端修复生效。

后端新增字段以可选形式返回，旧事件格式继续读取；新 metadata 事件默认由旧 Web 当作普通技术事件降级处理。新客户端发布前必须验证后端已支持 INTERRUPTED 和新增契约。

回退优先停止新补偿并回退页面。新客户端已经写入新状态/事件后，后端不能直接降级到拒绝新契约的版本；应保留兼容接收或提供向前修复。客户端也不能直接退回会过滤新状态 pending 的旧包，需先验证 outbox 可读性。历史已补事件保留，不通过删除数据完成回退。
