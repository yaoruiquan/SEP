# 电商视频员工详细开发文档

日期：2026-10-19

## 1. 文档定位

本文定义 SEP 与 Electron 后续接入电商视频员工的开发边界、协议扩展、mock 闭环和真实验收顺序。

视频应复用图片已经验证的媒体主链路，但不能直接复制图片字段或把视频模型伪装成图片模型。当前代码中的 `MediaProfile`、`MediaCapabilities` 和 `MediaGatewayParameters` 仍以图片为中心，视频必须先扩展共享 schema、fixtures、Web 配置和客户端协议，再开放真实执行。

当前状态：

- 真实视频首个模型已确定为 `minimax-h3`，本地已通过 sub2api / A6 文生、图生及原任务保存恢复；生产尚未部署视频 V2，不能直接将 mock 开关视为生产真实执行授权。
- 对话附件可以上传视频，但当前上游上下文只注入文件名说明，不代表员工能够观看或编辑视频。
- 图片与视频分开验收，视频真实验收使用独立连接、隔离本地身份和钱包，不改变生产图片配置。
- 不新增 SEP 云端视频 worker；客户端主进程负责任务跟踪、查询、下载和本地保存。

V0 基础链路和第二批隔离联调已落地：共享视频 v1 schema、两端一致的脱敏 fixture、SEP `/gateway/v1/media/video` mock 路由、数据库持久回执、客户端视频 job/asset 持久化及 HTTP adapter 已实现。已通过实际环回 HTTP、隔离 PostgreSQL 和 Electron mock 验收，包含 Pi 审批、IPC/页面、预览导出与退出恢复。

V1 已补 Web 视频 Profile 导入/配置校验/启用、企业授权、独立 `videoProtocolVersion=1` 协商和正式员工执行链路的显式 mock 组装。跨仓 HTTP 验证使用实际 ClientService、配置服务、视频网关和客户端 authorizer/宿主，身份及数据库仍为隔离测试替身；Web 浏览器与 Electron 验收同样使用合成身份。不等同于生产账号或真实模型验收。详情见 [V1 配置授权与运行时进度](../progress/2026-10-19-电商视频员工V1配置授权与运行时进度.md)。

依据：[电商图片与视频员工两端开发方案](2026-10-12-电商图片与视频员工两端开发方案.md)、[媒体接口协作合同 v1](../对接/2026-10-12-电商媒体接口协作合同-v1.md)。

## 2. 产品目标与首期边界

### 2.1 首期目标

首期只做一条可验收的视频能力：

```text
用户选择一张已确认的本地商品图片
  -> Pi 根据视频 Skill 生成分镜/动作说明
  -> 用户确认费用和视频规格
  -> 受控图生视频工具提交一次异步任务
  -> 客户端主进程查询原任务
  -> 下载视频、封面和元数据
  -> 本地原子保存、预览、导出
  -> 退出重启后按原 receipt 恢复，不重复生成或扣费
```

首期建议先做图生视频，因为输入商品图已经有图片资产、hash 和权限模型，可以验证图片到视频的交接；文生视频作为同一合同下的第二种 operation，待第一条真实模型链路稳定后加入。

### 2.2 首期不做

- 不做多镜头自动广告片、自动剪辑、自动配音和自动发布。
- 不承诺商品在视频中像素级不变。
- 不允许 Skill 自行指定供应商 URL、API key、费用或任意 vendor payload。
- 不把视频任务迁移到 SEP 后台定时 worker。
- 不在客户端 renderer 直接访问网络、文件系统或上游 key。
- 不在没有真实模型能力、价格和失败收费规则时启用生产视频工具。

## 3. 与图片方案的关系

### 3.1 可以复用的部分

| 能力 | 视频复用方式 |
| --- | --- |
| Skill 审核与批准版本 | 继续使用现有审核、批准、安装和版本 hash |
| runtime 协商 | 增加视频媒体能力，不污染聊天模型列表 |
| 企业授权 | 独立视频 Profile、默认 Profile、操作和预算上限 |
| employment token | 复用成员、部门、订阅和企业授权校验 |
| quote | 绑定 Profile、configVersion、输入 hash、视频规格和报价有效期 |
| receipt | 绑定 clientRequestId、上游 taskId、回执状态和账务状态 |
| 幂等 | `(enterpriseId, clientRequestId)` 唯一；响应丢失时查原回执 |
| 客户端任务 | 主进程持久化 job、asset、receipt 和状态 |
| 本地交付 | 临时文件、SHA256、fsync、原子 rename、重启恢复 |
| 计费核对 | 以 sub2api 原请求实际用量和 SEP 账本为权威 |

### 3.2 不能直接复制的部分

| 图片假设 | 视频必须改成 |
| --- | --- |
| `kind: image` | 增加视频 Profile 合同，不修改图片 Profile 的语义 |
| `generate/edit` 两种操作 | 至少区分 `text-to-video`、`image-to-video`；视频编辑另行定义 |
| 同步返回 PNG 或短轮询 | 默认异步提交，保存上游 `taskId` 并退避查询 |
| `size/count` | duration、resolution、aspectRatio、fps、audio、outputFormat 等严格参数 |
| 图片尺寸和字节大小 | 视频时长、帧率、分辨率、码率、文件大小和封面信息 |
| 按张报价 | 可能按秒、分辨率、模型、音频或任务档位报价，必须以实际接口为准 |
| PNG 下载 | MP4/WebM 等实际格式，支持大文件、超时和必要的范围读取 |
| 图片结果短 TTL | 视频 URL、任务结果和可刷新能力必须按实际模型记录 |

## 4. 上游模型确认门槛

开发真实视频前，必须从当前保存的 sub2api 连接和目标分组获得以下事实，不能从模型名称推断：

1. 实际视频模型 ID 和可用分组。
2. 创建任务的请求协议和认证方式。
3. 图生视频所需输入：二进制、临时引用或上游素材 ID。
4. 文生视频是否支持；如果支持，提示词和负面提示词字段。
5. 查询任务的路径、状态枚举和 `taskId` 规则。
6. 取消是否真实支持，取消后是否收费。
7. 输出 URL、文件格式、封面、有效期和刷新方式。
8. 允许的时长、比例、分辨率、帧率、音频和并发。
9. 报价接口、实际扣费接口、失败收费和超时收费规则。
10. 上游任务在客户端退出后是否继续，是否可在重启后查询。

任何一项无法核实时，只能进入 mock 或显示“未适配”，不能把视频 Profile 标为可执行。

## 5. 视频 Profile 设计

### 5.1 Profile 基础字段

视频 Profile 应与图片 Profile 独立存储，至少包含：

```text
profileId
kind: video
displayName
modelId
configVersion
enabled
verified
executionMode: async-query
operations: text-to-video | image-to-video
```

当前图片 `MediaOperationSchema` 只有 `generate/edit`。视频合同应新增版本化的 operation schema，不能让客户端用 `generate` 再从自由参数猜出是文生视频还是图生视频。

### 5.2 视频能力字段

建议的严格能力描述：

```json
{
  "supportsTextToVideo": false,
  "supportsImageToVideo": true,
  "supportsVideoToVideo": false,
  "supportsAudio": false,
  "durationsSeconds": [5, 10],
  "aspectRatios": ["1:1", "16:9", "9:16"],
  "resolutions": ["720p", "1080p"],
  "frameRates": [24],
  "maxInputBytes": 10485760,
  "maxReferenceCount": 1,
  "outputFormats": ["video/mp4"],
  "supportsTaskQuery": true,
  "supportsCancel": false,
  "resultRetentionSeconds": 86400
}
```

实际字段必须服从真实模型；不支持的能力不要用默认值填充。尤其不能因 UI 有“音频”选项就认为上游支持音频。

### 5.3 企业策略

企业视频策略独立于图片策略，至少包括：

```text
enabledProfileIds
defaultProfileId
allowedOperations
maxDurationSeconds
allowedAspectRatios
maxResolution
maxConcurrentJobs
periodBudget
```

企业只能收紧平台 Profile 能力。图片 Profile 被授权，不代表视频 Profile 自动授权；聊天模型白名单也不影响视频权限。

## 6. SEP 后端接口设计

视频沿用 `/gateway/v1/media` 受控网关，不新建独立视频服务。请求 DTO 按 `kind` 和 `operation` 严格分支校验。

### 6.1 配置接口

在现有媒体管理接口上增加视频能力，但保持图片接口兼容：

```text
GET  /api/admin/media/video/profiles
POST /api/admin/media/video/models/discover
POST /api/admin/media/video/profiles
POST /api/admin/media/video/profiles/:profileId/verify
PATCH /api/admin/media/video/profiles/:profileId

GET  /api/enterprise/media-config/video
PUT  /api/enterprise/media-config/video
GET  /api/enterprise/media-config/video/available-profiles
```

页面分图片和视频区域，以上为已落地的视频独立接口，旧图片接口不变。V1 候选发现仅返回显式启用的本地 mock 候选，不查询真实上游目录或报价。配置校验不执行视频生成；真实模型可以保存为未启用草稿，但尚不能通过校验或启用。候选发现不自动创建 Profile。

### 6.2 运行时接口

```text
GET /api/client/subscriptions/:subscriptionId/runtime?mediaProtocolVersion=1&skillArtifactProtocolVersion=1&videoProtocolVersion=1
```

视频采用独立 `videoProtocolVersion=1`，不升级或复用图片媒体协议。只有明确协商 v1 才返回 `runtime.video`；未协商或未知版本保持旧响应。客户端忽略损坏、未知版本或含私有字段的视频片段，不因此中断旧聊天，也不回退到图片工具。

runtime 中的视频 Profile 不包含上游地址、key、内部分组或可执行 vendor 参数，只下发能力和安全限制。

### 6.3 媒体网关接口

```text
POST /api/gateway/v1/media/video/references
POST /api/gateway/v1/media/video/quotes
POST /api/gateway/v1/media/video/requests
GET  /api/gateway/v1/media/video/requests/by-client-id/:requestId
GET  /api/gateway/v1/media/video/requests/:receiptId
GET  /api/gateway/v1/media/video/requests/:receiptId/outputs/:outputId/content
POST /api/gateway/v1/media/video/requests/:receiptId/cancel
```

约束：

- 参考图上传必须绑定企业、成员、订阅、Profile 和短期 TTL。
- quote 必须绑定参考图 hash、视频规格和输入语义 hash。
- request 只允许按原 quote 提交一次。
- 第一次提交写入 `SUBMITTING` 后才调用上游；写入不确定时返回 `SUBMISSION_UNKNOWN`，不能自动重提。
- query 由客户端驱动，不增加 SEP 定时 worker。
- cancel 只有上游实际支持时才转发；不支持时返回 `CANCEL_UNSUPPORTED`。
- content 只能按 `receiptId/outputId` 下载，不接受模型返回的任意 URL。
- 服务端限制响应大小、重定向、域名、超时和内网地址。

## 7. 视频请求与回执模型

### 7.1 请求示意

```json
{
  "kind": "video",
  "operation": "image-to-video",
  "clientRequestId": "video_request_001",
  "profileId": "product-video-standard",
  "configVersion": "cfg_video_001",
  "quoteId": "quote_video_001",
  "referenceIds": ["reference_image_001"],
  "creativeBrief": "商品保持外形和包装文字不变，镜头缓慢推进，背景有自然光变化",
  "parameters": {
    "durationSeconds": 5,
    "aspectRatio": "9:16",
    "resolution": "720p",
    "frameRate": 24,
    "audio": false,
    "outputFormat": "video/mp4"
  }
}
```

服务端拒绝未定义字段、超出 Profile 能力、超出企业限制、参考图数量不符和没有有效 quote 的请求。

### 7.2 回执状态

生成状态和本地跟踪状态分开保存：

```text
SUBMITTING
  -> QUEUED
  -> RUNNING
  -> SAVING
  -> SUCCEEDED

SUBMITTING -> SUBMISSION_UNKNOWN
QUEUED/RUNNING -> FAILED
QUEUED/RUNNING -> CANCELLED（仅真实支持取消）
SUCCEEDED -> RESULT_EXPIRED（上游结果失效且无法刷新）
```

本地跟踪状态：

```text
ACTIVE / PAUSED / INTERRUPTED / AUTH_REQUIRED / SAVE_FAILED
```

视频输出元数据至少包含：

```text
outputId
kind: video
mimeType
byteLength
sha256
durationSeconds
width
height
frameRate
format
thumbnail metadata
expiresAt
```

如果上游只返回临时 URL，URL 只能保存在受保护的服务端回执或短期缓存中，不能进入 Skill、Pi prompt、普通日志或客户端长期配置。

## 8. 计费设计

视频报价不能复用图片的按张模型。报价必须至少绑定：

```text
modelId
profileId
configVersion
operation
durationSeconds
resolution
frameRate
audio
reference input hash
quote expiration
pricing authority
```

推荐状态：

```text
NOT_QUOTED
QUOTED
NOT_RESERVED
RESERVED
SETTLED
RECONCILING
FAILED_NO_CHARGE
```

规则：

- 价格不可核验时不允许提交。
- 预占金额按冻结汇率转为平台账务金额，禁止客户端浮点计算。
- 上游实际账单按原 request 对齐，不按查询次数收费。
- 查询、下载、保存和恢复不新增媒体费用。
- 任务状态不明或上游已收费但结果未交付时保持 `RECONCILING`。
- 是否取消收费、失败收费和超时收费必须以真实上游合同为准，不能由 UI 文案决定。

## 9. Electron 客户端设计

### 9.1 分层

继续保持：

```text
renderer
  -> controller / preload
  -> media service
  -> local data + runtime scheduler
  -> SEP media HTTP client
```

renderer 只拿安全投影和 `localAssetId`，不能拿任意本地路径、上游 URL 或 key。主进程负责：

- 保存媒体 job 和 asset manifest。
- 任务查询退避和 `Retry-After`。
- 认证刷新。
- 大文件临时下载、hash、大小和文件头校验。
- 原子 rename、fsync 和保存状态更新。
- 退出/重启后的原任务恢复。
- 预览封面和视频范围读取。

### 9.2 本地字段

`LocalVideoJob` 应包含：

```text
jobId
taskId
runId
subscriptionId
skillVersion/hash
profileId/configVersion
clientRequestId/requestHash
referenceAssetIds
quoteId/receiptId
upstreamTaskId
upstreamStatus
localTrackingStatus
pollAfter
saveStatus
errorCode
createdAt/updatedAt
```

`LocalVideoAsset` 应包含：

```text
localAssetId
jobId
relativePath
mimeType
byteLength
sha256
durationSeconds
width/height/frameRate
thumbnailPath
saveStatus
missingReason
```

### 9.3 视频安全交付

- 下载写入 `.part`，验证后才改名。
- 预览只允许读取任务作用域内的文件。
- 不能接受模型传入的 `file://`、任意绝对路径或自由 URL。
- 视频播放器优先使用受限 IPC/custom protocol。
- 支持范围读取时必须校验范围边界、文件归属和响应长度。
- 封面和视频 hash 分开记录。
- 文件被移动或删除时提示缺失，不自动重新生成。

## 10. Pi 与 Skill 约束

Skill 只负责流程和质量规则：

1. 询问商品、平台、目标比例、时长和不可改变特征。
2. 先生成分镜/动作计划，再请求用户确认。
3. 明确提示视频会把必要图片和 prompt 传到受控上游。
4. 调用宿主 `video_generate` 或 `video_from_image` 工具。
5. 根据输出元数据和用户要求进行人工检查。

Skill 不负责：

- 选择未经授权的模型。
- 计算价格。
- 读取 API key。
- 访问任意本地路径。
- 直接调用 curl、shell、供应商 URL。
- 修改 receipt、billingStatus 或 requestId。

## 11. 开发阶段

### V0：共享合同与 mock

SEP：

- 新增视频 Profile、能力和企业策略 schema。
- 新增视频 fixtures，至少覆盖同步拒绝、异步排队、成功、失败、部分输出、未知提交、结果过期和不可取消。
- 扩展 quote、request、receipt 和 output DTO。
- 保证图片 v1 行为不变。

客户端：

- 解析视频 runtime。
- 新增本地 video job/asset 持久化。
- 接入异步查询、退出恢复、下载 hash 和视频预览 mock。

通过条件：不调用真实模型；两端使用同一份脱敏 fixtures；图片回归全部通过。

当前实现入口：

```text
SEP:
  backend/src/shared/media-video.dto.ts
  backend/src/shared/fixtures/media-video-v1.json
  backend/src/modules/media-gateway/media-video-gateway.controller.ts
  backend/src/modules/media-gateway/media-video-gateway.service.ts
  backend/src/modules/media-gateway/media-video-gateway.store.ts
  backend/src/modules/media-gateway/media-video-gateway.client-integration.spec.ts
  /api/gateway/v1/media/video/*

sep-client:
  src/shared/video-media.ts
  src/shared/fixtures/media-video-v1.json
  electron/data/mock-video-media-gateway.ts
  electron/data/sep-video-media-gateway.ts
  electron/data/video-store.ts
  electron/data/video-files.ts
  electron/domain/video-media.ts
  electron/service/video-service.ts
  scripts/test-video-mock-http.ts
```

本批 mock 输出改为离线生成的可播放 H.264 MP4：5 秒、720×1280、24fps、无音频，7295 字节。两端 fixture 文件完全一致，SHA256 为 `ba3671acef928d1735491c8cb53995edc860923ba70504f8f6cb525977c98a6e`。它只验证视频交付与恢复，不是模型生成的商品视频。

第一批持久化与验证基线（第二批进展见下）：

- SEP 复用既有 `MediaGatewayReference`、`MediaGatewayQuote`、`MediaGatewayRequest` 表，通过 `static-video-v1` discriminator 区分视频；未修改 Prisma schema 或执行迁移。图片和视频共享企业级 `clientRequestId` 唯一约束，碰撞时拒绝冒用。
- 数据库仅保存 hash、冻结配置、参考元数据和回执，不保存提示词、媒体字节或供应商 URL。提交语义含参考图 hash；不同内容重用请求 ID 返回 409；轮询用 revision CAS；撤权后查询、取消和下载均拒绝。
- 客户端提交前落盘冻结请求；未知提交只查询原 `clientRequestId`；按原回执恢复；下载验证大小、SHA256 和容器标记，采用 fsync、原子 rename 和 commit 证据恢复。当前未实现通用视频解码及元数据探测，不把容器标记校验等同于完整解码。
- 本地 mock gateway 可显式注入失败、部分成功、未知提交、结果过期、同步拒绝和损坏下载。SEP HTTP mock 当前执行固定成功路径，错误状态另有合同 fixture 与防护测试，尚无全部失败场景的 HTTP 控制入口。
- 第一批客户端 `VideoService` 由宿主显式推进单次查询，未接后台退避调度器和 UI；第二批已在隔离 mock 宿主补齐，不注册到正式员工执行链路。

### V1：Web 配置和权限（mock 已实现）

## 12. 测试与验收清单

### 12.1 后端

- shared Zod schema 严格拒绝图片参数混入视频。
- Profile、企业策略和 runtime 权限隔离。
- quote 语义 hash 包含时长、分辨率、帧率、音频和输入 hash。
- 同一企业同一 `clientRequestId` 只提交一次。
- 不同语义重用 requestId 返回幂等冲突。
- 提交写入不确定时进入 `SUBMISSION_UNKNOWN`，不自动重提。
- 旧配置查询仍能读取原 receipt，新配置不迁移旧任务。
- 下载禁止任意 URL、内网地址、无限大小和不受控重定向。
- 失败、未知和对账状态不错误扣费或释放资金。

### 12.2 Electron

- 异步查询退避、限流和认证刷新。
- 退出重启后使用原 receipt/taskId，不新建请求。
- 断网、查询超时和服务端 503 不触发重复提交。
- 大文件保存失败只重试下载。
- 部分输出可以单独交付和恢复。
- 视频和封面 hash、时长、尺寸、格式都能核验。
- renderer 无法访问任意磁盘路径和供应商 URL。

### 12.3 真实验收

真实视频闭环完成的最低证据：

```text

profile-video.json
quote-video.json
request-video.json
receipt-video.json
upstream-task.json
upstream-usage.json
```

并且必须证明：

1. 实际模型 ID 与 Profile/runtime/请求一致。
2. 上游 taskId 与 SEP receipt 一一对应。
3. 生成提交只有一次。
4. 下载保存和退出恢复不重复生成、不重复扣费。
5. 视频文件、封面和元数据都通过校验。
6. 结果过期、任务失败和费用不明状态有明确处理。

## 13. 尚需产品确认的事项

视频进入真实开发前，需要确认或由实际接口验证：

- 首个真实视频模型和允许的 sub2api 分组。
- 首期只做图生视频，还是同时开放文生视频。
- 首期最大时长、分辨率、比例、帧率和并发。
- 是否启用音频。
- 取消、失败、超时和审核拦截的收费规则。
- 结果 URL 有效期和是否支持刷新。
- 企业预算是按任务、秒数还是周期额度限制。

在这些事实确定前，视频只推进 V0 mock 和 V1 配置，不启用生产视频执行。
