# 电商图片与视频员工怎么做：SEP 落地调研

> 调研日期：2026-10-12。
> 阅读对象：产品负责人、运营人员、开发人员。先讲清楚做法，再给开发落地清单。
> 本文把需求中的“生食品”暂按“生视频”理解，因为同时提到了图片和视频上游 API。如果确实指食品类商品，见第 6 节。
> 这是调研与建议，不是已完成功能说明。本次没有修改业务代码，也没有发起收费生成或操作生产系统。
> 2026-10-12 边界修订：用户确认 SEP Web 只发布员工/Skill，员工执行、媒体跟踪和素材保存由客户端负责；彻底退出客户端后不做云端托管。原云端执行建议已修正。最新两端合同与开发清单见 `docs/development/2026-10-12-电商图片与视频员工两端开发方案.md`。

## 1. 先说结论

**建议继续用 Skill 沉淀电商经验，但不要只靠 Skill 实现整个图片、视频员工。**

最适合 SEP 的组合是：

**数字员工 + 电商 Skill + 受控的图片/视频工具 + 后台任务 + 素材交付。**

可以用一个简单比喻理解：

| 部分 | 类比 | 在产品里做什么 |
| --- | --- | --- |
| 数字员工 | 接单的设计师或视频制作师 | 理解需求、向用户解释、组织工作 |
| Skill | 工作手册 | 规定怎么做主图、场景图、分镜，怎么检查商品是否变样 |
| 图片/视频工具 | 制作设备 | 真正调用你已有的上游 API |
| 后台任务 | 工单系统 | 排队、查进度、恢复中断、防止重复生成 |
| 素材交付 | 成品库 | 保存图片和视频，提供预览、下载、版本记录 |

**你已经有上游模型，不需要训练模型，也不需要为每个员工搭一套独立模型服务。** 第一版重点应该是把现有 API 接成可靠工具，再用 Skill 把工具组织成电商工作流程。

我的产品建议：先做两个员工，底层共用客户端媒体工具与 SEP 受控网关。

1. **电商商品视觉设计师**：基于真实商品图制作白底整理图、场景图、活动视觉。
2. **电商短视频制作师**：基于商品图或已确认的画面制作短视频素材。

不要一开始就承诺“任何商品、一键整套详情页、一键完整带货视频、自动上架”。先把“商品不变样、结果拿得到、重复提交不重复收费”做好。

## 2. 到底哪些东西放 Skill，哪些写代码？

### 2.1 Skill 负责“怎么把活干好”

电商 Skill 应该写这些：

- 用户没说清楚时，需要补充哪些信息。
- 商品参考图、风格参考图、Logo，各自怎么使用。
- 不同素材的创作步骤：主图、场景图、促销海报、视频分镜。
- 不允许改变的东西：商品颜色、瓶身形状、包装、Logo、配件数量。
- 品牌风格、构图偏好、禁用表达。
- 先出方案还是直接生成，什么时候需要用户确认。
- 产出后检查什么，最多修改几轮。

Agent Skills 官方规范将 Skill 定义为包含 `SKILL.md` 的目录，也可以携带脚本、参考资料和模板。因此，Skill 不只是提示词；但它是否能执行脚本、调用工具，取决于运行它的系统是否提供这些能力。[S1]

**在 SEP 里，不能把“上传了 Skill ZIP”理解为“员工已经能自动调用生图 API”。**

### 2.2 客户端工具与后端网关共同负责可靠执行

这些必须由代码强制，不能只靠 Skill 文本约束；其中任务执行/恢复/本地保存归客户端，接入秘密/授权/硬额度/账务归 SEP 后端：

- API 认证、请求参数转换、模型能力校验。
- 判断用户有没有权限使用这个员工、素材和模型。
- 限定图片数量、视频时长、并发数、费用上限。
- 客户端保存任务 ID、查询状态、处理超时；首期不新增云端生成回调工作流。
- 客户端下载上游成品，保存到本地授权工作区。
- 防止重复创建上游任务、重复结算。
- 记录用户、企业、Skill 版本、模型和实际费用。

**企业可以修改“创作手册”，不应该因此就能修改系统的收费规则、API 地址或权限。**

### 2.3 三种做法的选择

| 做法 | 适合什么 | 问题 | 对 SEP 的建议 |
| --- | --- | --- | --- |
| 只有一份 Skill 提示词 | 生成文案、图片提示词、视频脚本 | 没有实际图片/视频生成、保存和结算能力 | 不满足本需求 |
| Skill 脚本自行调用 API | 受控内部试验、已有成熟隔离执行环境 | 密钥、租户隔离、重试与计费容易散落到脚本里 | 可以试验，不作为默认生产路径 |
| Skill + 平台受控工具 | 面向企业用户的数字员工 | 需要补媒体任务和交付链路 | 推荐 |

这里不是说“Skill 不能调用 API”，而是说：**平台收费能力应该由平台集中管理，Skill 调用这项能力。**

## 3. 你现在的 SEP 已经有什么，还缺什么？

以下根据本次工作区代码静态检查得出。表结构、注释或管理页面里出现一种能力，不等于执行链路已经支持它。**下表描述 SEP 已有的旧 Web/云端执行代码，不是此次客户端员工的推荐实现基础。** 最新客户端核实结果和缺口见开发方案第 3 节。

| 环节 | 当前实际情况 | 对本需求的影响 |
| --- | --- | --- |
| 员工绑定能力 | 已有；绑定能力会变成模型可选择的工具 | 可以复用员工入口和绑定机制 |
| Skill 版本 | 已有版本管理；执行时可解析企业/订阅生效正文 | 可以复用，不必另建电商专用版本系统 |
| 能力执行 | `CapabilityService.execute()` 目前要求 `agentConfig`，再交给适配器 | 不是任意 SKILL/AI_APP 都能直接执行 |
| 适配器工厂 | 实际只实现 Coze、OpenCode 分支 | 尚无 SEP 原生图片/视频执行分支 |
| OpenCode | 外部 jobs 服务；提交文本、轮询、读取第一个输出文件为文本 | 不能直接当完整媒体生产链路使用 |
| 结果协议 | `AdapterExecutionResult.output` 是文本；聊天工具结果也主要保存文本 | 缺结构化任务 ID、图片/视频资产引用 |
| 后台任务 | 已有 BullMQ、任务记录、事件与恢复机制 | 可复用技术设施，但当前步骤执行仍围绕文本对话 |
| 文件存储 | 已有本地/OSS 驱动、签名链接 | 可复用存储门面，不必重建存储平台 |
| 图片附件 | 可以上传、展示，当前轮图片能作为多模态输入 | 需要另外把有归属的图片资产传入生成工具 |
| 视频附件 | 可以上传；当前对话上下文只注入文件名说明 | 上传视频不等于员工已经能分析视频内容 |
| 前端交付 | 任务成品主要是 Markdown；聊天助手分支未展示生成附件 | 需要生成任务状态、图片结果和视频播放器 |
| 计费 | 已有对话 token 计费与钱包设施 | 不等于已支持媒体任务按张/秒/次计费 |

代码依据见附录 A。[C1-C10]

**所以，本次需求不是“多上传几个 Skill”就能完成，也不需要重做整个员工系统。需要补的是媒体能力从调用到交付的闭环。**

旧链路两个容易误判的地方（不要求为本需求扩展这些执行器）：

1. `AI_APP` 在 schema 中存在，但当前执行入口没有根据它的 API 配置直接请求第三方。因此，不能把上游 URL 填进 AI_APP 就认为接通了。
2. 现有任务队列的 job ID 包含时间戳，不能单靠它保证同一次业务请求只生成一次。新媒体任务必须独立设计业务幂等。[C1][C4]

## 4. 上游 API 应该怎么接？

### 4.1 保持现有边界：SEP 通过 sub2api 调模型

项目约束明确要求模型调用经 sub2api。推荐路径：

```text
用户
  -> 客户端电商员工/Pi + Skill
  -> 客户端受控媒体工具/本地后台任务
  -> SEP 媒体网关（授权、回执、按请求转发）
  -> sub2api
  -> 你已有的图片/视频上游
```

客户端负责组织和持续跟踪；SEP 后端只提供受控的模型通道、请求回执与账务，不跑员工流程，不定时查询生成、不自动保存成品，也不再搭独立模型网关。

**你的上游能直接调用，不代表现在的 sub2api 已经支持它的全部协议。** 接入前先核实图片编辑、异步提交、状态查询、结果下载这几条链路。

我查看了公开 sub2api 源码快照 `3a6fd1c9db07203ca308aaba69e502bc1f35b307`：它包含图片生成/编辑、异步图片任务和视频相关路由；图片处理与分组平台有关，视频创建/查询分支明确与 Grok、Composite 分组有关。这证明它并非只有聊天接口，**但不能推导出任意视频上游都能直接透传**。[S7]

你的部署版本、分组和上游模型名称尚未提供，本次没有验证实际服务。若协议缺失，先在现有 sub2api 接入该上游，再接 SEP；不让 Skill 偷绕过中转。改变这一边界需要明确的架构决策。

### 4.2 为什么不能都套一个“聊天 API”？

官方 API 资料体现了至少几种不同模式：

| 模式 | 例子与证据 | SEP 该怎么处理 |
| --- | --- | --- |
| 图片生成/编辑 | OpenAI 官方 Cookbook 演示图片输入、编辑和 mask；示例用 Base64 返回图像 [S2] | 支持二进制、Base64 或 URL 结果的归一化 |
| 创建任务后查询 | Runway 返回任务 ID，之后查询任务；万相图生视频也是异步任务 [S3][S5] | 客户端持久化任务关联，主进程后台轮询，网关按请求查询 |
| 商品专用工作流 | Runway Product Ad 将商品参考图、创作方向、分镜和生成包装为一个流程 [S6] | 借鉴产品流程，不假定你的上游也有同款接口 |
| 临时下载链接 | Runway 成品链接会失效；万相也明确要求及时保存结果 [S4][S5] | 下载到客户端本地授权目录，不把临时链接当永久资产 |

这些资料用于证明接入模式，不是要求你购买或切换这些模型。具体模型、参数、价格，以你现有上游的实际文档和合同为准。

### 4.3 接入前做一张能力表

每个上游模型都登记下面的信息，而不是只存一个模型名：

| 项目 | 要核实的内容 |
| --- | --- |
| 任务类型 | 文生图、参考图生图、局部编辑、图生视频、文生视频 |
| 商品参考 | 支持几张图？是否支持多角度、mask、首尾帧？ |
| 输出 | 支持哪些比例、分辨率、视频时长、文件格式？ |
| 调用模式 | 同步、异步；查询/回调是否支持？ |
| 可靠性 | 幂等键、超时、限流、任务保留期、取消能力 |
| 费用 | 按张、按秒、按次或其他；失败/审核拒绝是否收费？ |
| 访问 | 参考图要公网 URL、上传 ID、文件流还是 Base64？ |
| 权益 | 商用范围、输入素材处理方式、输出水印/元信息 |

对用户显示“标准图片、高清图片、商品短视频”等能力选项；具体允许的模型/规格由独立媒体 profile 和企业策略决定，客户端选择，网关重复校验。媒体配置不混用会话模型入口/白名单。第一版每类先接一个已验证模型，不急着做自动择优。

## 5. 两个员工实际怎么干活？

### 5.1 电商商品视觉设计师

用户可以这样说：

> “这是我们保温杯的实拍图。帮我做 3 张厨房场景图，瓶身和 Logo 不要变，整体偏清爽。”

推荐流程：

```text
读取真实商品图和商品信息
  -> 确认用途、比例、数量与不能改变的商品特征
  -> 给出简短创作方案和预计费用
  -> 按已授权的数量/预算生成
  -> 检查商品是否变形、Logo 是否错误、规格是否合适
  -> 展示成品，标明需要人工检查的地方
  -> 用户选图或要求局部修改
```

第一版建议包含：

- 基于真实商品图的场景图。
- 白底整理、背景替换，优先保留原商品主体。
- 活动视觉的无字底图，必要时后处理叠加确定的文字和 Logo。
- 围绕同一商品做少量风格变体，单张可以独立重做。

**白底主图和创意场景图要分开。** 前者重商品真实性，后者允许背景创作。对于必须严格还原的商品主体，优先“真实商品前景 + 新背景 + 合成”，不要默认整张重新生成。

如果没有抠图/合成工具，第一版就不承诺“商品像素级保持不变”。即使使用编辑或 mask，也不能直接把结果当作绝对不变；OpenAI 官方示例同样提醒 mask 区域可能受编辑影响。[S2]

### 5.2 电商短视频制作师

用户可以这样说：

> “用刚才选中的商品图，做一条竖版展示短片，镜头慢慢推进，别改变产品。”

推荐先走这条路径：

```text
已确认的商品画面
  -> 简短脚本/镜头方案
  -> 用户确认费用与画面方向
  -> 图生视频
  -> 保存、检查、预览
```

它比直接让文字提示词决定商品外观更容易控制输入。Runway 的商品广告流程也把真实参考图放在核心位置，并建议提供清晰、多角度的商品图。[S6][S8] 这不保证你的上游能达到同等效果，仍需实测。

第一版把交付范围叫清楚：

- **商品视频素材**：一条或少量短镜头，能够播放和下载。
- **完整电商广告**：还包括镜头拼接、字幕、配音、音乐、片尾等。

有视频生成 API，不等于已经有完整广告制作能力。如果上游本身提供完整成片工作流，可以在同一媒体任务层接入；否则把剪辑、字幕和音频列入后续阶段，不新增不必要的首期范围。

### 5.3 什么时候让用户确认？

不必每一步都问用户，但收费动作必须有可追溯授权：

- 用户已明确数量、用途，且在授权预算内：可以直接执行。
- 视频、批量任务、高清升级，或将超出预算：先展示费用与方案。
- 修改只影响背景或构图：在已授权修改额度内执行。
- 重做会再次收费：明确告知，不把它包装成免费重试。

这套授权是客户端审批与后端硬额度共同落实的产品规则，不能只写在 Skill 中。

## 6. 电商最关键的不是“好看”，而是“还是你的商品”

建议每次任务固定记录两类信息：

**不变项**：SKU、颜色、商品轮廓、材质特征、包装文字、Logo、配件数量。

**可变项**：背景、光线、布景、镜头运动、留白、创意氛围。

需要特别处理的情况：

| 风险 | 推荐做法 |
| --- | --- |
| Logo 或包装文字被改写 | 优先使用真实商品主体；必要时用原始 Logo 后处理；人工确认 |
| 文案中的价格、规格出错 | 来自用户确认的信息，用确定性排版叠加，不交给模型自由编造 |
| 一个系列的图像不像同一品牌 | 固定参考图、风格说明和模板版本，保存上次选择 |
| 视频中商品逐帧变样 | 限制复杂旋转和遮挡；提取关键帧辅助检查；人工观看 |
| 平台规格不符合要求 | 按具体平台、素材位置、类目维护模板，不写死“全平台通用” |
| 把广告效果当实物效果 | 区分实拍整理与创意素材，不宣称生成结果天然可上架 |

生成后可以用尺寸校验、OCR、多模态模型辅助检查，但**自动检查通过不等于保证完全合规或商品完全一致**。检查失败应标记问题和允许有上限的重做，不无限循环生成。

如果你说的确实是“食品类商品”，建议在共用媒体工具上增加一个食品 Skill，而不是另造食品模型接口：

- 锁定包装、净含量、份量和可见配料。
- 不擅自补充认证标识、营养数值或功效宣传。
- 对“实物份量”和“创意摆盘”分别处理，防止把想象画面当成真实交付。
- 对包装信息做人工复核；具体宣传、标签和发布要求另做目标地区/平台核验。

## 7. 后台生成任务必须独立于聊天连接

**切换页面或结束本轮聊天不丢任务；彻底退出客户端/关机后停止本地跟踪，重新打开先查询原任务。** 上游可能继续生成/收费，成品链接可能过期，不保证长时间关闭后还能取回。

Runway 和万相的文档都说明视频生成通过任务查询获取结果。[S3][S5] 因此，建议图片和视频统一进客户端本地媒体任务。SEP 不新增轮询 worker；客户端经网关查原任务。

```text
聊天调用生成工具
  -> 客户端校验本地输入，向 SEP 校验权限/报价/预算
  -> 持久化本地任务意图，经 SEP 建立幂等回执并提交
  -> 客户端保存回执关联，主进程经网关查询原任务
  -> 客户端下载、校验并原子保存成品
  -> 更新本地状态，SEP 按真实用量去重结算
```

推荐状态至少能区分：

```text
QUEUED -> SUBMITTING -> RUNNING -> SAVING -> SUCCEEDED
                  \-> SUBMISSION_UNKNOWN
其他结果：FAILED / CANCELLED
```

其中 `SAVING` 表示上游已经生成，但客户端还没存好，不能向用户宣称已交付。生成状态和本地跟踪状态分开，详见开发方案。

`SUBMISSION_UNKNOWN` 很重要：请求超时不代表上游没接单。此时不能立刻重新创建，否则可能生成两次、收两次钱。

| 情况 | 正确处理 |
| --- | --- |
| 已拿到 taskId，查询接口超时 | 继续查询原任务，不重新生成 |
| 提交超时，是否接单不明 | 使用上游幂等键/请求 ID 查找；无法确认时等待对账或人工处理 |
| 上游完成，下载或存储失败 | 重试下载/存储，保留原任务，不重新生成 |
| 用户切换页面，主进程仍在 | 本地后台继续 |
| 用户彻底退出客户端 | 停止本地跟踪；重启查询原任务，提示上游结果有效期风险 |
| 用户取消，上游不支持取消 | 停止后续本地步骤，但说明上游可能继续，费用按规则处理 |
| 已成功但用户不满意 | 创建有父任务记录的新版本，不当成网络重试 |

客户端 renderer 的 IPC 通知不是任务唯一记录；以本地持久化和网关原回执查询为恢复依据。监控镜像不接管任务执行，不破坏已有聊天和监控合同。

## 8. 素材保存与展示怎么做？

### 8.1 成品一定要保存到客户端本地

不要只在聊天中返回上游图片/视频 URL。Runway 文档说明输出链接会在 24-48 小时内失效，并建议保存到自己的存储；万相文档说明成品视频 URL 有效期为 24 小时。[S4][S5]

推荐流程：

1. 客户端从归属校验过的输出接口下载文件；网关必要时按请求流式转发，不建立云端成品库。
2. 校验 MIME、文件头、大小、尺寸/时长。
3. 在客户端授权目录原子落盘。
4. 记录稳定的 `localAssetId`、任务内相对路径、规格和 hash。
5. 通过受限 IPC/素材协议预览、播放和导出，不开放任意本地路径读取。

不要把 Base64 大图、视频内容或临时签名链接当成唯一交付记录，也不要把上游链接直接交给模型当“永久结果”。

输入图也同样注意：客户端 `localhost`/本地路径不能供云端模型下载。工具从批准的本地资产读取字节，经网关按协议上传、编码或提供短期可访问参考；临时参考传输不是云端成品托管。[S3]

### 8.2 第一版不需要大型素材管理系统

先在客户端现有员工聊天和任务详情中增加：

- 排队/生成/保存/失败状态，不能只有一句“正在生成”。
- 图片预览、大图查看、选择和下载。
- 视频播放器、封面和下载。
- 生成数量、已完成数量、失败数量和费用。
- “基于这张修改”和“用这张生成视频”。
- 原图/新版本关联，明确这次改了哪里。

把生成成品与用户输入区分来源，在客户端补结构化媒体成果；SEP Web 不为本需求新建制作/交付界面。旧 Web 展示代码 [C8] 不代表客户端已经有同样能力。

批量任务应能部分成功：3 张里 2 张成功，先交付这 2 张，只对失败项决定后续动作，不整组重新生成。

## 9. 费用怎么管，才不会越用越乱？

要分开三个东西：

1. **员工订阅费**：用户能不能使用这个岗位。
2. **创作对话费用**：需求分析、提示词和脚本产生的模型费用。
3. **媒体生成费用**：图片、视频、处理和存储等费用。

推荐由 SEP 统一展示预计价格，并记录独立媒体用量。不要把媒体用量强行伪装成普通文本 token。

```text
生成前：检查余额 + 占用本次预算
生成中：任务与预算记录绑定
结束后：按实际规则结算，释放未用额度
状态不明：保留待对账状态，不重复扣费或贸然退款
```

当前钱包的算力专款划入/划回不等于已经实现“每个媒体任务的预算冻结”。落地时应复用现有账本与事务模式，补任务级占用、释放、结算，不另建一套互相不对账的钱包。[C9]

需要固定的规则：

- 数量、画质、时长变更后重新报价。
- 一个任务只产生一次对应的结算，重复查询、响应重放和恢复不能重复收费；首期不依赖云端回调。
- 创意重做是新生成，网络重试不是新创意订单。
- 失败是否收用户费，是平台产品规则；上游是否收平台费，是另一件事。
- 不能笼统写“失败免费”：例如 Runway 官方说明审核拦截的生成也消耗费用。[S9]
- 后端强制总预算和最大修改次数，不能让员工无限重做。

收益评估要看“每张被用户采用的图 / 每条被采用的视频”的成本，不只是单次 API 标价。具体费用当前未知，本文不编造单价或利润率。

## 10. 安全和权限的最低要求

这不是额外功能，而是面向多企业用户上线的前提：

- 每次提交、查询、下载，都校验企业、成员和员工授权；不可只靠难猜的 ID。
- 本地参考素材用宿主校验的 localAssetId，经受控传输转为网关参考 ID，模型不能任意指定别人的文件。
- API 密钥只保存在后端受控配置，不进入 Skill 正文、前端或聊天记录。
- 只允许平台批准的模型、用途和参数，服务端重复校验，不相信模型输出。
- 用户填写的网址、回调地址和模型返回的下载地址都需要访问约束，防止访问内网资源；下载要限制大小、跳转和超时。
- 首期客户端经网关查询，不新增云端回调推进员工流程。
- 支持源图/成品的保留与删除策略；第三方是否保留输入需要核对上游条款。
- 人物、品牌、音乐等素材的使用授权在产品流程中收集；不能把“模型生成”当作授权证明。

第一版建议只运行平台审核的流程，不开放企业 Skill 任意 shell、网络地址或文件系统访问。

## 11. 第一版具体做什么？

### 第 0 步：先证明上游链路能跑通

拿你提供的 API 文档和脱敏示例，完成能力表；通过实际 sub2api 验证：

- 一次参考图生图或编辑。
- 一次图生视频及状态查询。
- 一次失败/超时的状态处理。
- 结果下载并写入客户端授权目录。
- 可取得怎样的费用和用量数据。

这一步需要模型名、请求格式、计费规则和测试授权。本次没有这些具体信息，未发起验证调用。

### 第 1 步：完成图片员工的最小闭环

- 新增客户端媒体工具/本地任务记录、SEP 独立媒体配置和受控请求回执，接一个图片模型。
- 上传商品图 -> 生成少量场景图 -> 保存 -> 预览/下载。
- 绑定一个电商视觉 Skill，能锁定商品特征和品牌风格。
- 支持单图重做、任务刷新恢复、费用上限和执行记录。

这一阶段不承诺像素级锁定商品、自动排完整详情页或自动上架。

### 第 2 步：用同一套底层接视频员工

- 接一个视频模型，支持图生视频。
- 补异步状态、查询重试、提交不明与下载失败恢复。
- 支持播放器、封面、下载和费用展示。
- 将用户选中的图片以本地资产 ID 交给宿主视频工具，经授权传输，而不是复制任意 URL。

这一阶段先交付短镜头素材。时长和分辨率以已验证模型的允许值为准。

### 第 3 步：按真实需求增强

- 同一 SKU 的批量模板、品牌预设、多比例输出。
- 图文合成、确定性字幕、剪辑与配音。
- 多镜头成片、商品素材库、选图历史。
- 企业工作流与目标电商平台的发布前检查。

不在首期新增 Agent 框架、不训练模型、不重建网关、不部署大型工作流平台。沿用客户端 Pi/本地持久化与 SEP NestJS/Prisma/网关；不使用 SEP BullMQ 执行本次员工。是否需要图片/视频处理依赖到具体需求确认后再决定。

## 12. 上线前怎么判断“这两个员工真的能干活”？

先用你们真实商品做小规模基准，不用几张好看的演示图替代验收。

建议起点：选至少 20 个有代表性的 SKU，包含包装文字、透明材质、反光、不同形状等难点；分别测图片和视频任务。这个数量是初步测试建议，不是统计可靠性的保证。

记录所有尝试，包括失败、审核拒绝和用户没选中的结果：

| 指标 | 怎么看 |
| --- | --- |
| 商品还原 | 外形、颜色、包装、Logo、数量有没有改变 |
| 用户采用率 | 生成多少张/条，用户最终选用了多少 |
| 实际交付率 | 不只上游成功，还要存储成功、用户能打开 |
| 等待时间 | 端到端耗时，观察中位数和较慢任务 |
| 被采用的成品成本 | 包含失败和重做，不能只看成功调用单价 |
| 恢复能力 | 切换页面、重启客户端、断网后能否查询原任务；过期是否明确提示 |
| 财务一致性 | 重复提交、查询和恢复，是否重复生成或重复结算 |

开发验收至少覆盖：

1. 重复点击、重复工具调用，只创建同一业务任务；同一幂等键配不同输入应拒绝。
2. 已提交但接口超时，不盲目再次生成。
3. 客户端重启后，沿用原 jobId/requestId/receiptId 查询，不创建新生成。
4. 下载失败只重试保存，不再次生成。
5. 结果链接过期时，只在上游支持刷新且授权有效时重新获取；无法找回则明确显示结果已过期。
6. 企业 A 不能查、用、下载企业 B 的素材和任务。
7. 部分成功、审核拒绝、余额不足，都有明确状态与账务结果。
8. 图片商品细节、视频关键帧经人工验收，不只看 API 的成功状态。

## 13. 最后的建议

**员工卖的是电商工作成果，Skill 管的是电商方法，模型 API 提供的是制作能力。三者不是互相替代。**

对你当前的情况，我建议：

> 保留 SEP 的员工和 Skill 体系，在客户端补媒体工具、持久任务与本地素材交付；SEP 补独立媒体模型配置、授权网关、回执与账务。先做商品场景图，再做基于确认图片的短视频。所有模型请求仍经 sub2api；退出客户端不做云端托管。

下一步最需要的不是更多提示词，而是你现有图片/视频 API 的接口文档：模型名、参考图传法、异步任务格式、费用、失败收费规则。拿到它们后，才能把本方案落到准确接口，而不是猜参数。

## 附录 B：修订后的两端开发边界

用户已确认“客户端负责到底”。原先的 SEP 后端 processor、固定云端流程和云端成品表方案不再采用。完整合同、字段示意、文件边界与验收清单见 [两端开发方案](../development/2026-10-12-电商图片与视频员工两端开发方案.md)。以下为待开发设计，不是现有功能。

### B.1 SEP 只提供控制面与受控网关

- Web：员工/Skill 上架审核、独立图片/视频模型配置、企业媒体权限和额度；不新增制作工作台。
- 后端：批准版本分发、runtime 能力清单、参数/归属/费用校验、sub2api 请求转发。
- `MediaRequestReceipt`：最小持久回执，关联归属、稳定 requestId、请求 hash、配置版本、上游任务和账务；客户端请求时才查询上游。
- 不新增媒体轮询 worker、不跑 Pi、不推进分镜、不自动下载成品；临时参考图传输不等于云端成品库。

### B.2 客户端提供执行面与素材交付

- 在现有 Pi SDK 扩展入口注册受控媒体工具；不走 SEP 的 `CapabilityService.execute()` 或 OpenCode 适配器。
- 消费批准 runtime，安装自包含 Skill 或完整批准包，锁定任务实际使用的版本/hash。
- `LocalMediaJob` 持久化提交意图、原 requestId/receiptId、生成与本地跟踪状态；主进程负责退避查询与恢复。
- `LocalMediaAsset` 管理输入/成品的批准路径、规格、hash、来源与版本关联；renderer 经受限 IPC 预览/导出。
- 保持客户端现有分层，不让 Skill 自行运行供应商脚本，不因最高权限模式绕过硬预算。

### B.3 重启与成品合同

- 收到 jobId 表示受理，不表示已交付；依赖成品的步骤必须等待本地保存成功。
- 彻底退出/关机后停止本地跟踪，上游可能继续生成和收费；SEP 不接管。
- 重启先查原回执/任务；提交不明不自动重发，下载失败只重试保存。
- 结果 URL 不是永久资产。只有上游支持刷新且权限允许时才能找回，过期不可恢复则明确提示。
- 批量任务分别记录子项；成功项不因其他项失败被重新生成。
