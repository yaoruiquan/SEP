## 5. 任务 4：正文、思考与工具转换

SEP 不按 content/reasoning/tool_calls 过滤返回字段。中转对输入 tools 和历史消息进行结构转换：标准工具定义变为 Responses tools，assistant 工具变为 function_call，tool 结果以 tool_call_id 关联为 function_call_output。**这只是部署实现，不能替代本次 26 项 schema 和调用 ID 的实际逐项对照**，因为入口与上游 body 没有保存。

发现两项值得处理的兼容行为：

1. **历史思考写入普通历史正文。** `chatcompletions_to_responses.go:160` 将历史 `assistant.reasoning_content` 包成 `<thinking>…</thinking>`，再与 assistant 正文合并。离线验证可确定性复现。它能解释这类标签可能被平台引入历史输入，但没有本次历史输入，不能断言请求 9 返回标签就是这一步导致。响应转换本身按 reasoning delta 映射 reasoning_content，不凭标签自动拆正文。
2. **终态快照没有流式补齐。** `responses_to_chatcompletions.go:147–174` 只处理受支持的 delta/added 事件，忽略 output_item.done、output_text.done、function_call_arguments.done 等用于完整快照的事件；终态处理 `:299` 不从 `response.output` 恢复缺失内容，工具判定依赖此前的 `SawToolCall`。如果上游没有对应增量，完整终态中的正文/工具会遗漏。

本轮用生产提交的原始转换包构造合成事件，结果如下：

| 合成输入 | 实际输出 | 结论 |
| --- | --- | --- |
| incomplete / max_output_tokens / output=8704 | length，usage=8704 | 不能把相同用量直接映射为 stop |
| reasoning delta + completed，无正文/工具 | reasoning_content + stop，usage=8704 | 协议正常完成不保证业务交付 |
| incomplete 外层与 completed 内层冲突 | 无成功 finish | 严格校验有效 |
| 标准 function_call added + 参数 delta + completed | tool_calls，工具增量保留 | 标准工具路径有效 |
| 只有 completed 快照内含完整 function_call | stop，工具增量 0 | 流式快照补齐缺口已复现 |
| 只有 completed 快照内含完整正文 | stop，正文为空 | 流式快照补齐缺口已复现 |
| 同一个完整工具快照直接转非流式 Chat 响应 | tool_calls，工具数 1 | 转换入口不同可产生内容差异 |

这是**合成协议复现，不是原业务复现或历史原始流回放**。是否允许供应商只发这些快照、还是供应商漏发必需增量，需要接入协议与实际流确认。即便需要兼容修复，也应根据完整工具内容恢复，不能把所有 stop 强制改为 tool_calls。
