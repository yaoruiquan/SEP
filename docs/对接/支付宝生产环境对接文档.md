## 1. 代码改动详情

### 1.1 `alipay.provider.ts` — PKCS8 私钥格式

`alipay-sdk` 3.x 默认用 `-----BEGIN RSA PRIVATE KEY-----` 头包裹私钥，但 Alipay 开放平台生成的私钥是 PKCS#8 格式（`-----BEGIN PRIVATE KEY-----`）。在 Node 20 较严格的 OpenSSL 上直接签会失败。

**修复**：在 SDK 初始化选项中增加 `keyType: 'PKCS8'`。

```typescript
// alipay.provider.ts:36-46
this.sdk = new AlipaySdk({
  appId: config.appId,
  privateKey: config.privateKey,
  alipayPublicKey: config.alipayPublicKey,
  gateway: config.gateway || 'https://openapi.alipay.com/gateway.do',
  charset: 'utf-8',
  signType: 'RSA2',
  keyType: 'PKCS8',   // ← 关键修复
});
```

同时处理了 `alipay-sdk` 的 ESM/CJS 兼容导出：

```typescript
const AlipaySdkModule = require('alipay-sdk');
const AlipaySdk = AlipaySdkModule.AlipaySdk
  || AlipaySdkModule.default
  || AlipaySdkModule;
```

### 1.2 `payment.service.ts` — 回调前初始化 SDK

**问题**：`handleAlipayNotify` 直接调用 `this.alipayProvider.verifyNotify(postData)`，但 `this.sdk` 在容器重启后为 `null`（SDK 只在首次支付请求时懒初始化）。支付宝异步回调到达时，`verifyNotify` 抛异常 → 500 → 支付宝收到非 200 → 持续重试失败。

**修复**：在 `handleAlipayNotify` 开头增加 `await this.initializeAlipay()` 的 try/catch 保护：

```typescript
// payment.service.ts:162-170
async handleAlipayNotify(postData: Record<string, any>) {
  try {
    await this.initializeAlipay();
  } catch (error) {
    this.logger.error('支付宝 SDK 初始化失败，无法校验通知', error);
    return { success: false, message: '支付宝配置初始化失败' };
  }
  // 然后才 verifyNotify...
}
```

### 1.3 `backend/.gitignore` — 修复源码被误伤

原来写的是 `storage/`（非锚定），匹配了 `backend/src/modules/upload/storage/` 下的 5 个 TypeScript 源码文件。`git clone` 后缺少这些源文件 → `nest build` 失败（14 个 webpack 错误）。

**修复**：改为 `/storage/`（仅匹配 `backend/` 顶层），并将 5 个源文件重新提交。

```diff
- storage/
+ /storage/
```

被误伤的 5 个文件：
- `backend/src/modules/upload/storage/local-storage.driver.ts`
- `backend/src/modules/upload/storage/local-storage.driver.spec.ts`
- `backend/src/modules/upload/storage/oss-storage.driver.ts`
- `backend/src/modules/upload/storage/storage.service.ts`
- `backend/src/modules/upload/storage/storage.types.ts`

### 1.4 `docker-compose.yml` — 生产环境变量

新增 4 个环境变量到 `sep-backend` 服务：

```yaml
- API_BASE_URL=https://longdaoSEP.cn/api
- WEB_BASE_URL=https://longdaoSEP.cn
- FRONTEND_URL=https://longdaoSEP.cn
- ALIPAY_SANDBOX_MODE=false
```

**关键点**：`API_BASE_URL` 必须包含 `/api` 前缀，因为 Next.js 的 rewrite 规则是 `/api/:path*` → `${API_ORIGIN}/:path*`（已剥离 `/api`），而 NestJS 没有全局路由前缀。通知 URL 最终为 `https://longdaoSEP.cn/api/payment/alipay/notify`。

## 3. 遇到的问题与解决

### 3.1 构建失败：`storage/` gitignore 误伤源码

**现象**：`nest build` 出现 14 个 webpack 错误，`Can't resolve './local-storage.driver'` 等。

**根因**：`backend/.gitignore` 的 `storage/` 规则匹配了 `backend/src/modules/upload/storage/`，5 个源码文件被 git 忽略。

**解决**：改为 `/storage/`（锚定顶层），重新提交 5 个源文件，并手动 scp 到服务器临时修复。

### 3.2 回调 500：SDK 未初始化

**现象**：`POST /payment/alipay/notify` 返回 500（空 body 请求）。

**根因**：`handleAlipayNotify` 在调用 `verifyNotify` 前没有确保 `initializeAlipay()` 已执行，容器重启后 `this.sdk` 为 null。

**解决**：在 `handleAlipayNotify` 开头增加 `await this.initializeAlipay()` 的 try/catch 保护。

### 3.3 构建失败被 pipe 掩盖

**现象**：`docker compose build ... | tail -30` 结合 `set -e`（无 `pipefail`），构建失败被 `tail` 的 exit 0 掩盖，`up -d` 用旧镜像启动。

**解决**：使用 `set -eo pipefail` 或直接全量输出（不 pipe 到 tail）。

### 3.4 服务器 git 与 CI/CD 的冲突

**状态**：服务器 `/opt/sep/app` 有未提交的改动（与本地 2 个 commit 内容一致）。CI/CD（`.github/workflows/deploy.yml`）在 push 后触发 `git pull`，会因服务器有未提交改动而失败。

**影响**：当前 CI/CD 的 `git pull` 实际上是一个安全网——它阻止了 CI/CD 在服务器未同步时强行覆盖。如果需要让 CI/CD 正常部署，需先将服务器同步到 origin/main。

### 3.5 `sep-deploy.sh deploy-web` 使用 `docker restart`

`deploy/production/sep-deploy.sh` 的 `deploy-web` 命令用 `docker restart sep-web`（重启旧容器），而非 `docker compose up -d`（重建并启动新镜像）。这导致 web 前端更新时不会应用新 Docker 镜像。此 bug 尚未修复。
