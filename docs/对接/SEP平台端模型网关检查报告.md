# SEP 平台端模型网关检查报告

日期：2026-10-12

检查范围：平台网关、代理链路、模型调用限制与协议兼容性。

源码位置：`D:\github\SEP-main`。本报告根据本地源码、部署模板及隔离验证整理；线上部署版本与实际配置尚未确认。未修改代码、未重启应用、未调用线上模型。

## 一、结论

优先处理：固定 30 秒总时长超时、流中断静默关闭、SSE 转发破坏部分合法事件边界。这些问题可能导致 HTTP 200 后仍出现 `Stream ended without finish_reason`。429 限流是独立问题，仅调整访问次数不能解决所有断流风险。

## 二、高优先级问题

### 1. 固定 30 秒总时长超时

- 证据：`backend/src/modules/gateway/gateway.service.ts:132` 使用 `AbortSignal.timeout(30000)`，该信号也影响响应体读取。
- 影响：持续有数据返回，达到总时长仍会取消。长报告、慢模型和大型工具参数容易中断，重试可能再次失败。
- 建议：分开设置连接/首包、空闲及总时长限制；收到数据时重置空闲计时；总时长合理配置，不直接取消所有保护。
- 验收：持续输出超过 30 秒能正常完成；真正停流时按约定超时并记录原因。

### 2. 流中断后静默关闭

- 证据：`backend/src/modules/gateway/gateway.controller.ts:110` 附近捕获读取异常后直接结束响应，未记录具体异常。
- 影响：HTTP 200 不代表响应完整，客户端难以区分超时、上游断连和代理失败。
- 建议：记录请求 ID、上游关联 ID、模型、首包耗时、总耗时、最后数据时间和结束原因。响应头发送前返回结构化 HTTP 错误；发送后按双方约定返回客户端可识别的流错误，不再修改状态码。
- 要求：不能把单独 `[DONE]` 或连接关闭当作完整成功，不能伪造 `finish_reason`。日志不得泄露令牌、API Key 或敏感对话。
- 验收：人为中断上游后可通过请求 ID 定位原因，不完整响应不会被包装为成功。

### 3. SSE 转发破坏事件边界

- 证据：`backend/src/modules/gateway/gateway.controller.ts:87-108` 按行拆分，只特殊处理 `data: `，忽略空行并重建输出。
- 影响：合法的 `data:` 无空格格式可能丢失事件分隔符；多行 data 存在被拆成不同事件的风险。
- 建议：优先原样透传，usage 统计独立解析；必须重建时使用完整 SSE 解析器，处理无空格字段、多行 data、LF/CRLF、注释及 UTF-8 跨块。正确完成解码器收尾，不将截断尾部强行补成成功事件。
- 验收：上述格式、中文跨块和不同网络分块测试通过，结束事件不丢失。

## 三、其他限制与风险

### 4. 多层限流与 Retry-After 不一致

- 证据：`backend/src/modules/security/security.module.ts` 配置 default 100、auth 10、chat 60 次/分钟；测试环境不同。`backend/src/common/middleware/basic-rate-limit.middleware.ts` 还包含 120 次/分钟限制。
- 证据：网关没有保留上游 Retry-After；`backend/src/common/filters/http-exception.filter.ts:22` 缺少该头时补固定 60 秒。
- 待确认：实际启用桶、路由覆盖/跳过规则、真实 IP、上游 RPM/TPM。不能仅凭桶名称认定 auth 桶只限制登录接口。
- 建议：明确各层作用域，区分用户、企业、订阅、模型和 IP；核对可信代理，避免共用代理 IP 限流；规范化真实等待时间，区分限流、余额与权限错误。
- 验收：限制来源和恢复时间明确，等待后成功，正常串行调用不被误判。

### 5. JSON 请求体默认 2MB

- 证据：`backend/src/main.ts:44` 默认上限 `2mb`，由 `REQUEST_JSON_LIMIT` 配置。
- 影响：历史消息、工具定义和大型工具结果可能先触发 HTTP 限制，与模型 token 上限不同。
- 建议：统一各层大小政策，合理配置；验证超限返回明确 413 与可识别错误，避免不透明的 500；向客户端提供限制，不静默删除历史。
- 验收：边界请求符合约定，超限明确失败，不静默裁剪。

### 6. 整条代理链配置需核对

- 证据：`deploy/production/Caddyfile.snippet` 将非 WebSocket 请求送到 Next.js；`web/next.config.mjs` 再把 `/api/*` 转发到 Nest。
- 说明：Caddy 模板设置 `flush_interval -1`，压缩匹配不包含 SSE，没有证据直接归因于 Caddy 压缩。
- 待确认：实际 Caddy → Next.js → Nest → sub2api → 模型链路，以及各层首包、空闲、总时长和缓冲限制。
- 建议：逐层核对版本和配置，不能只提高 Nest 超时。评估网关直接转发后端是否合适，保留鉴权与安全边界。
- 验收：实际公网入口长流正常，各层断连原因可定位。

### 7. 模型能力和协议兼容性需统一契约

- 待确认：客户端模型 ID 的真实映射、上下文与最大输出、工具/多模态/推理字段、结束信息与 usage 支持。
- 证据：`backend/src/modules/conversation/conversation-stream.service.ts:313-321` 已针对部分 sub2api 的 `tools + stream_options` 返回 400 做兼容处理，需要对当前上游复测，不能推定所有模型一致。
- 建议：提供模型能力元数据，按实际能力校验；建立字段兼容矩阵，不未经测试全部透传或删除；usage 缺失明确标识并核对记账；订阅、余额、权限和模型不可用使用稳定错误码。
- 验收：在用模型均有能力配置；工具请求无不明 400；结束信息完整，用量缺失可追踪。

### 8. 下游断连取消和写入背压不足

- 证据：网关没有明确处理 `res.write()` 返回 false 的背压，也未将下游关闭与上游取消关联。
- 影响：慢客户端可能造成缓冲积压，断开后上游仍可能继续生成和消耗资源。
- 建议：写入受阻时等待恢复或使用支持背压的管道；下游关闭及时取消上游；各结束路径释放 reader 等资源，避免重复结束响应。
- 验收：慢速读取资源受控，中途断开后上游及时取消，无未处理异常。
