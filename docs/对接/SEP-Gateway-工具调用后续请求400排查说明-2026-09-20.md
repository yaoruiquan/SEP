- **提交日期**：2026-09-20
- **问题模块**：SEP Gateway / Pi 对话模型调用 / Function Calling
- **客户端版本**：sep-client 当前联调版本
- **模型**：`deepseek-v4.1-flash`
- **关联任务**：`d80fb03c-fdb0-4d19-80d5-7569b4d62207`
- **关联运行记录**：`735a05cf-f8ce-48ff-ade0-9f3b79b778a6`
- **订阅 ID**：`cmu3wbhhv0004r19ziwonu40e`

> **平台核查更新**：已确认网关 Schema 会删除工具调用关联字段，并复现错误格式导致的 SDK `no body` 提示。本地修复及验收说明见第 8 节；尚未部署或完成真实上游联调。

## 1. 问题现象

用户向员工发送“查看工作目录中有什么文件”之类的请求后，客户端日志显示：

```text
provider response received { status: 200 }
provider tool calls assembled {
  toolCalls: [ { toolId: '...', toolName: 'ls' } ]
}
```

随后客户端本地执行 `ls` 成功，并取得了工作目录结果。但任务最终失败：

```text
ERROR pi-task-worker run failed {
  taskId: 'd80fb03c-fdb0-4d19-80d5-7569b4d62207',
  runId: '735a05cf-f8ce-48ff-ade0-9f3b79b778a6',
  subscriptionId: 'cmu3wbhhv0004r19ziwonu40e',
  modelId: 'deepseek-v4.1-flash',
  stage: 'agent-result',
  error: 'Error: 400 status code (no body)'
}

ERROR conversation-executor conversation run failed {
  taskId: 'd80fb03c-fdb0-4d19-80d5-7569b4d62207',
  runId: '735a05cf-f8ce-48ff-ade0-9f3b79b778a6',
  subscriptionId: 'cmu3wbhhv0004r19ziwonu40e',
  modelId: 'deepseek-v4.1-flash',
  control: 'none',
  stage: 'run',
  error: 'Error: 400 status code (no body)'
}
```

这里的 `conversation-executor` 错误是上层转发，不代表发生了第二个独立错误。

## 2. 客户端确认的执行流程

本次调用不是第一次请求就失败，而是典型的两阶段工具调用流程：

```text
请求 1：用户消息 + tools 定义
    ↓
SEP Gateway 返回 200
    ↓
模型返回工具调用：ls
    ↓
客户端本地执行 ls
    ↓
ls 执行成功并产生目录结果
    ↓
请求 2：assistant 工具调用 + tool 执行结果
    ↓
SEP Gateway 返回 400（无响应正文）
```

因此：

- `status: 200` 说明第一次模型请求成功；
- `toolName: 'ls'` 说明模型正确返回了 `ls` 工具调用；
- 客户端随后执行 `ls`，工具本身不是失败原因；
- 最终的 `400` 很可能发生在客户端把工具结果回传给模型后的下一次模型请求；
- `control: 'none'` 说明不是用户点击终止造成的；
- 该错误也不是客户端无法连接 SEP，因为客户端收到了 SEP 返回的 HTTP 400。

## 3. 客户端第二次请求发送的消息结构

客户端会保留模型的工具调用消息，并把工具执行结果作为下一条 `tool` 消息发送。抽象后的请求结构如下：

```json
{
  "model": "deepseek-v4.1-flash",
  "messages": [
    {
      "role": "user",
      "content": "查看工作目录中有什么文件"
    },
    {
      "role": "assistant",
      "content": "",
      "tool_calls": [
        {
          "id": "call_xxx",
          "type": "function",
          "function": {
            "name": "ls",
            "arguments": "{}"
          }
        }
      ]
    },
    {
      "role": "tool",
      "tool_call_id": "call_xxx",
      "content": "<ls 工具返回的目录结果>"
    }
  ],
  "stream": true,
  "tools": [
    "<当前会话注册的工具定义>"
  ]
}
```

说明：

1. `call_xxx` 是示例值，实际值由模型响应生成；
2. `tool_call_id` 与上一条 `assistant.tool_calls[].id` 必须完全一致；
3. `content` 是客户端执行 `ls` 后得到的文本结果；
4. 客户端保留了 `assistant.tool_calls` 和 `tool.tool_call_id`，没有把工具结果丢弃；
5. 这是 OpenAI Chat Completions 风格的常见工具调用上下文结构。

## 4. 请 SEP 平台重点检查的内容

请在 SEP Gateway 服务端根据同一 `x-request-id` 或网关请求日志定位返回 400 的请求，并重点检查以下内容。

### 4.1 确认 400 对应的是第几次请求

请确认失败请求是否包含以下消息：

```text
role=assistant，并且存在 tool_calls
role=tool，并且存在 tool_call_id 和 content
```

如果失败请求的消息数量比初始请求多，并且包含 `role: "tool"`，则可以确认问题发生在工具结果回传阶段。

建议服务端记录以下非敏感摘要：

```text
requestId / x-request-id
model
messageCount
每条 message 的 role
assistant.tool_calls 的工具名和 id
tool.tool_call_id
tool.content 是否存在及长度
是否存在 tools
stream
返回状态码
返回错误码和错误消息
```

不要在生产日志中记录完整 token、授权头、工作目录敏感内容或完整工具参数。

### 4.2 检查 `tool_call_id` 关联校验

请确认网关是否要求：

```text
messages[i].role == "tool"
messages[i].tool_call_id
```

必须匹配前一条 assistant 消息中的：

```text
messages[i - 1].tool_calls[j].id
```

本例中应满足：

```text
assistant.tool_calls[0].id === tool.tool_call_id
```

如果 SEP Gateway 使用了其他字段名，例如要求 `tool_call_id` 改为 `call_id`，或者要求额外的 `name` 字段，请提供明确的协议定义。

### 4.3 检查工具结果消息是否被网关支持

请确认 `deepseek-v4.1-flash` 是否支持以下消息角色和字段：

```json
{
  "role": "tool",
  "tool_call_id": "call_xxx",
  "content": "..."
}
```

如果该模型接入层不支持 `role: "tool"`，需要明确要求客户端使用 SEP Gateway 支持的兼容格式，或者由网关在转发前完成格式转换。

### 4.4 检查工具定义格式

请确认第一次请求与第二次请求中的 `tools` 定义是否都符合该模型适配器的要求，特别是：

- `tools` 是否要求完整对象数组，而不是字符串数组；
- 工具类型是否必须为 `function`；
- function 是否必须包含 `name`、`description`、`parameters`；
- `parameters` 是否必须为合法 JSON Schema；
- 是否允许 `additionalProperties`；
- 是否允许空对象参数 `{}`；
- `ls` 的 `path` 是否可以省略；
- `tool_choice` 是否必须显式设置为 `auto` 或必须省略。

### 4.5 检查流式请求兼容性

客户端请求使用流式响应：

```json
{
  "stream": true
}
```

请确认：

- `deepseek-v4.1-flash` 是否支持流式工具调用；
- 工具调用参数是否会在 SSE 多个 chunk 中分片返回；
- 网关是否正确合并 `tool_calls[].function.arguments`；
- 工具结果回传后的下一次请求是否仍允许 `stream: true`；
- 如果请求失败，是否能返回可读的 JSON 错误正文。

### 4.6 检查模型 ID 和模型能力配置

请确认以下模型 ID 在当前环境中已注册并允许调用：

```text
deepseek-v4.1-flash
```

同时确认该模型配置的能力是否包含：

```text
function calling / tool calling
streaming
多轮 messages
role=tool
```

如果模型名称实际应为其他值，或者模型只支持普通文本对话，请返回明确的错误信息，而不是空响应正文。

## 5. 建议 SEP Gateway 返回的错误格式

当前服务端仅返回 HTTP 400，没有错误正文，导致客户端无法判断具体字段。建议所有 4xx/5xx 响应统一返回 JSON，例如：

```json
{
  "error": {
    "code": "INVALID_TOOL_MESSAGE",
    "message": "tool_call_id does not match any assistant tool call",
    "param": "messages[2].tool_call_id",
    "requestId": "<gateway-request-id>"
  }
}
```

可考虑使用以下错误码：

| 错误码 | 含义 |
|---|---|
| `MODEL_NOT_FOUND` | 模型 ID 未注册或不可用 |
| `MODEL_TOOL_CALL_UNSUPPORTED` | 当前模型不支持工具调用 |
| `INVALID_TOOL_DEFINITION` | tools 定义不符合模型要求 |
| `INVALID_TOOL_MESSAGE` | tool 消息结构或关联 ID 不合法 |
| `INVALID_MESSAGE_SEQUENCE` | assistant/tool 消息顺序不合法 |
| `INVALID_PARAMETER` | 请求参数不合法 |
| `STREAMING_NOT_SUPPORTED` | 当前模型或路由不支持流式响应 |

HTTP 400 响应建议至少包含：

```text
错误码
可读错误消息
出错字段路径
网关 requestId
```

## 6. 客户端侧当前结论

客户端已经通过本地 Pi SDK 和 mock gateway 验证：

1. `ls` 工具可以被模型调用；
2. `ls` 可以正常执行并产生结果；
3. 工具结果会被加入下一轮模型上下文；
4. 下一轮上下文包含 assistant 工具调用和 tool 结果；

6. 当前错误发生在收到工具结果之后的模型请求阶段更为可能；
7. 仅凭 `400 status code (no body)` 无法确定网关拒绝的具体字段。

请 SEP 平台根据本说明检查返回 400 的具体请求体和服务端校验日志，并反馈：

- 400 对应的请求序号；
- 被拒绝的字段；
- 当前模型是否支持工具调用；
- 当前网关接受的工具消息协议；
- 是否需要客户端调整 `tools`、`tool_choice`、`role: tool` 或 `tool_call_id` 格式。

## 8. 平台代码核查与修复结论（2026-09-20）

> 本节基于当前 SEP 工作区代码与本地回归测试。未访问生产日志、未调用真实 sub2api 模型、未部署；因此能确认代码缺陷，但不能把本次线上任务的具体失败分支当成已核实事实。前文“无响应正文”是客户端错误字符串的表象，并不等于 HTTP 正文确实为空。

### 8.1 已确认根因：请求校验破坏了工具调用上下文

链路为：

```text
POST /api/gateway/v1/chat/completions
  → ZodValidationPipe(ChatCompletionRequestSchema)
  → GatewayController
  → sub2api /chat/completions
```

原 `backend/src/shared/index.ts` 的消息 Schema 仅声明 `role`、`content: z.string()` 和 `name`。`ZodValidationPipe` 返回解析后的 `result.data`，未声明的字段会被剥离。

因此文档第 3 节的第二轮请求在转发前会变成：

```json
[
  { "role": "user", "content": "查看工作目录中有什么文件" },
  { "role": "assistant", "content": "" },
  { "role": "tool", "content": "<目录结果>" }
]
```

- `assistant.tool_calls` 被删除。
- `tool.tool_call_id` 被删除。
- 客户端即使提交 `assistant.reasoning_content`，也会被删除。
- 顶层 `tool_choice`、`parallel_tool_calls`、`stream_options` 等未声明参数同样丢失。
- 如果使用第 7 节的 `assistant.content: null`，则在网关校验阶段直接返回 400，尚未请求 sub2api。

这解释了首轮可成功、工具结果回传后失败的模式：首轮不需要历史工具调用关联字段，第二轮却依赖这些字段。**不能通过让客户端把 `tool_call_id` 改成 `call_id`、重复执行 `ls` 或单纯关闭 SSE 解决这一缺陷。**

已先写回归测试验证旧实现：9 个用例中 7 个失败，直接显示字段被删除、null/省略 content 被拒绝；随后才修改 Schema。

### 8.2 已确认的诊断障碍：`no body` 可能只是错误格式不兼容

原全局异常过滤器输出：

```json
{ "statusCode": 400, "message": "请求参数校验失败", "requestId": "..." }
```

本地安装的 OpenAI SDK 在 `APIError.generate()` 中读取的是响应的 `error` 属性。对上面这个**非空 JSON**调用同样的错误构造逻辑，会复现 `400 status code (no body)`。

因此客户端这条日志不足以证明服务端发出了空正文。原过滤器还丢弃了 Zod pipe 产生的 `errors`，掩盖了具体字段路径。客户端实际 SDK 版本仍需客户端团队确认，但本地测试已经证实此格式存在兼容性问题。

另一个已确认的问题是：原 controller 把所有上游非 2xx 一律包装成 `BadRequestException`，上游 429/5xx 也会被客户端看到为 400。

### 8.3 本次工作区修复

| 文件 | 修复内容 |
|---|---|
| `backend/src/shared/index.ts` | 显式声明并校验工具调用、关联 ID、推理字段及相关请求选项；工具调用 assistant 支持空字符串、null 或省略 content；tool 结果必须有 tool_call_id；继续剥离无关字段，不全量开放 passthrough |
| `backend/src/modules/gateway/gateway.service.ts` | 将上游请求转发移入 service，仍只经 sub2api；保留上游 HTTP 状态和标准 error 的 message/type/code/param；连接失败返回 502；空/非 JSON 错误给可读兜底，不回显原始代理页面 |
| `backend/src/modules/gateway/gateway.controller.ts` | 调用 service 转发，保持 SSE 数据透传和既有记账路径；补充 Swagger 响应说明 |
| `backend/src/common/filters/http-exception.filter.ts` | 仅 gateway 路由新增 OpenAI 兼容 error；保留外层既有字段；包含 requestId、校验字段路径及 INVALID_PARAMETER 错误码；普通业务接口错误格式不变 |
