# 模型流式中断与监控 403 排查

日期：2026-10-10。范围：生产只读日志/部署代码检查、本地合成复现和既有定向测试；未修改业务实现、生产配置或生产数据，未部署或重启。

## 结论与证据边界

1. **流式问题优先处理：已复现 SEP 后端在请求开始约 30 秒后取消上游响应体，即使此前已经收到 HTTP 200 和文字。** Controller 随后吞掉读流异常并结束 SSE，客户端缺少 `finish_reason`，报 `Stream ended without finish_reason`。生产存在多个 SEP 约 30 秒结束、同 request ID 的 sub2api 持续 58–77 秒的对应记录，是这条机制的强证据。
2. **另有 Web 代理超时风险：** 当前 `/api/*` 经过 Next external rewrite；部署的 Next 代理默认 `proxyTimeout=30000`。其底层 `ClientRequest.setTimeout()` 是连接空闲超时，不能与后端 `AbortSignal.timeout(30000)` 的全请求计时混为一谈。生产 Web 有 `Failed to proxy` / `socket hang up` / `ECONNRESET`，但现有记录不足以把每条代理错误精确绑定到目标任务。
3. **监控 403 单独归因：** 该窗口的任务创建请求缺少 `Origin`/`Referer`。实际生产全局 `CsrfGuard` 的无副作用重放返回 `403 / Missing Origin or Referer header`，与日志元数据和响应长度一致；不是任务创建接口要求管理员的证据。
4. **不认定本次仍由 429 引起：** 检查窗口内入口记录为网关 63 次 200、5 次 500，监控 10 次 403，没有网关 429。此统计仅涵盖该入口/窗口，不代表所有上游和其他时间没有限流。

目标 `taskId=b8725ddc-1f56-4f0d-8cce-b6932ef50a0d`、`runId=0ee087b5-cbc0-4c55-b65f-f4a8ed574131` 未与历史网关/监控请求一一绑定。未取得目标运行客户端日志、订阅 ID 或历史 SSE 尾帧，因此不能声称已证明该任务全部异常的唯一根因，也不能推断缺失帧在每次请求中的精确位置。HTTP 200 和上游完成日志均不证明客户端收到正常结束帧。

### 已复现的网关行为

| 检查点 | 位置 | 结果 |
| --- | --- | --- |
| 上游请求计时 | `backend/src/modules/gateway/gateway.service.ts:163` | `AbortSignal.timeout(30000)` 在返回 headers 后继续作用于 body 读取；不是仅首包超时 |
| SSE 读流异常 | `gateway.controller.ts:114` | `catch` 不记录异常、不区分超时/取消/上游断连，直接 `res.end()` |

| EOF 残留 | `gateway.controller.ts:93` | 未换行的尾部 buffer 未处理；此例上游本身已是不完整 SSE，不能据此补造成功帧 |

### 客户端判定、日志、重试与状态

- 安装的 `pi-ai` 为 0.83.0。`dist/api/openai-completions.js:326` 仅非空 `choice.finish_reason` 设置完成状态；`:436` 缺失时抛 `Stream ended without finish_reason`。合成“文字 + usage + `[DONE]`”仍产生 error；单纯有文字、用量、200 或 DONE 都不能替代结束原因。
- `pi-coding-agent-adapter.ts:308` 已有 `provider response received`，记录 status 和经过 redaction 的 headers，没有 SSE body/尾帧。该日志为 debug；`electron/common/logger.ts:47` 在 production 默认 info，可能根本没有输出。默认 sink 是 console，未发现启动代码默认配置持久化文件 sink。
- `pi-coding-agent-adapter.ts:234` / `:244` 传递 `auto_retry_start/end` 的 attempt、delay、error。`:504` 开启 session 自动重试、最多 3 次，provider 层 maxRetries 为 0；`pi-task-worker.ts:175` 还有本轮预算保护。实际目标 run 的重试次数尚无日志证据，不能从平台重复请求直接断言次数。
- SDK 的 signal abort 与“正常 EOF 但缺少 finish_reason”是不同错误分支。`pi-task-worker.ts:220` 后的运行流程把终态错误上抛；取消/中断再由 runtime 的控制状态分类，不应全部标记为上游限流。
- `electron/domain/arrangement-execution.ts:87` 将失败节点设为 `failed`，依赖后续节点设为 `blocked`，编排设为 `waiting-user`；`:105` 的节点重试仅将目标失败节点恢复 `ready` 并释放其依赖。既有定向测试证明不会重跑已完成节点；未读取目标任务持久化状态，不能宣称其实际状态已恢复。

## 链路二：监控接口 403

### 产生层和拒绝规则

- 历史入口记录：`POST /api/client/tasks` 有 Authorization、没有 Origin/Referer，返回应用 JSON、180 bytes、36 字符 response request ID。
- 后端完成日志在对应时间返回 403、处理耗时约 2–16 ms，确认请求进入 Nest；不是只凭入口状态码推测业务拒绝。
- `backend/src/modules/security/security.module.ts:38` 全局注册 `CsrfGuard`。`guards/csrf.guard.ts:79` 的生产路径对缺少 Origin/Referer 抛 `Missing Origin or Referer header`。网关 Bearer 路由与部分客户端认证路由有精确豁免，任务监控写路由没有。
- 提取生产 bundle 中实际 guard，在其生产/origin 配置下做纯内存重放：相同方法、路径、Bearer 存在且缺 Origin/Referer，得到相同 403 原因，实际异常响应封装长度也是 180 bytes。未发送生产 POST、未使用真实 token、未查询或写入数据库进行该重放。
- **历史 response body 未取得。** 归因来自缺头事实、实际部署分支、确定性重放、后端日志和响应长度的共同证据；长度本身不唯一，不能单独作为拒绝原因判据。

示例 request ID：`78864361-a727-4924-8db6-b94b525dbb63`（19:20:18.267）、`f2aa10ac-09cb-465e-866d-d018a496e092`（19:32:34.030）；全部 10 条在 `production-summary.json`。

### 登录和订阅权限

- `client.controller.ts:283` 的任务创建使用 `JwtAuthGuard`，没有管理员 guard。`client.service.ts:811` 的创建业务也不要求管理员；`:906` 管理员规则用于企业范围任务读取，不能套到创建上。
- `client.service.ts:877` 的订阅准入仍要求当前企业一致、ACTIVE、未过期以及有效成员/部门授权；不应为解决 CSRF 放宽这些条件。
- 对模型用量窗口关联用户和三条订阅做了只读 DB 事务核验：用户仅一个企业 membership，三条订阅在窗口起点均通过任务准入条件。**未将该身份/订阅绑定每个失败 POST**，所以不能宣称每条监控请求的 accessToken 和 subscriptionId 均已核验。
- 本机客户端的 `electron/common/platform/client-monitor-api.ts:117` 使用 accessToken，`electron/bootstrap/build-backend.ts:111` 注入 `authSession.getValidAccessToken(forceRefresh)`，不是把 refreshToken 当 Bearer。adapter 仅在首次 401 时刷新重发一次，403 不进入刷新分支。实际运行版本与生产请求 body 未取得时，仍不能证明线上带入了正确登录 token 或订阅 ID。

### 当前客户端与历史缺头请求存在差异

- 当前本机源码 **以及本地 HEAD** 的 `client-monitor-api.ts:121` 已统一为 create/status/events/heartbeat 发送归一化 Web `Origin` 及 `Referer`。这些来源头不是本轮添加，也不是只存在于当前未提交改动。因此不能提出“在当前源码再加一次头”作为已定位修复；必须核对事发安装包构建版本、实际注入配置、是否走不同 adapter，以及传输中的丢头环节。
- `electron/runtime/task-runtime.ts:741`、`:763`、`:777` 的上报为 `void ... .catch(...)`，不等待网络完成，不因监控 rejection 取消模型。本地 mock 测试确认全部监控 Promise 持续 pending 时，本地执行仍能完成；未对历史目标run做同样证明。
- `electron/data/client-monitor-store.ts:145` 的 pending 是持久化监控 outbox，不是任务重执行。成功确认才移除操作；`client-monitor-service.ts:581`、`:599` 在 create 尚无 mirrorId 时阻止后续非create操作发送。
- `client-monitor-service.ts:644` 的单轮即时 retry 排除403；但失败操作仍保留、默认冷却30秒（`:620`），默认每30秒恢复队列（`:190`、`:251`），没有永久排除403。因此后续重复POST可能是补发pending，不能直接当作模型自动重试。测试验证即时403不重试、pending恢复与隔离；**未专门验证推进冷却时间后的403再次补发**。
- 客户端仓库已有多处未提交修改，本轮仅只读检查和运行既有测试，没有改动或回滚其中任何文件。上述代码/测试结论适用于当前工作区，实际发布运行版本仍需单独核对。

## 修复顺序与验收建议（本轮未实施）

1. **先修模型链路的时间预算：** 将首包/连接、流空闲、总时长预算分别配置；消除后端 30 秒全响应硬截止，并协调 Next 代理的空闲超时与入口/上游预算。不是仅把一处常量改大，也不是无限延长全部连接。
2. **完善 SSE 转发和终止分类：** 保留合法事件边界，兼容 `data:`/`data: ` 与跨 chunk 分隔；记录 upstream/downstream 是否看到 finish/DONE、耗时、字节数、abort reason。EOF、读流异常、客户端断开与总/空闲超时分别分类。不能补造 `finish_reason=stop` 或 DONE 将中断伪装为成功；已发 headers 后也不能再改 HTTP 状态为 JSON 错误。
3. **补目标 run 的脱敏关联日志：** 在请求、响应头、自动重试、终止事件绑定 taskId/runId/subscriptionId/model/requestId；只保存事件结构、结束原因和允许的 headers，不记录 prompt、文本增量、token 或全部请求 body。SDK headers hook 的本地计数 requestId 不等于平台 response request ID。
4. **独立核对监控 CSRF 合同和发布版本：** 当前源码及HEAD已有来源头，不重复添加；先定位实际发布版本/配置与生产缺头请求的差异，确认 create/status/events/heartbeat 一致携带已经允许的 Origin/Referer。若需原生 Bearer 路由豁免应单独安全评审；不关闭全局 CSRF，不误改管理员角色或订阅归属规则。
5. **验收长流与失败恢复：** 连续流超过 30 秒、首包慢、流中空闲、上游断连、显式取消、文字+usage+DONE但无finish，以及缺Origin的403/允许Origin的普通成员有效订阅创建。验证节点可单独重试，监控403不触发模型取消；区分模型自动重试与pending队列再次发送。
