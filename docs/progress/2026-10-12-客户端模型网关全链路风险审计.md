## 2. 阶段与限制矩阵

| 阶段 | 当前限制或处理 | 可能失败及风险 |
| --- | --- | --- |
| DNS/TLS/公网连接 | 生产站点 TLS 1.2/1.3；此轮未做故障注入 | DNS、握手、连接重置、离线；需保留网络错误与平台错误区别 |
| Caddy 入口 | 生产站点文件 `request_body max_size 100MB`，`flush_interval -1`；SSE 不在压缩匹配列表 | 站点文件没有请求频率/并发规则；全局/CDN规则未核实 |
| Web rewrite | `/api/:path*` -> backend；本地草稿代理空闲预算 180000ms | 不是 180 秒总时限；完整取消传播未联调，不能只靠配置测试认定有效 |
| 入站 body | backend 默认 JSON/urlencoded 2mb，生产相关环境变量未设置；本地 Next 默认克隆体上限 10MiB | 上下层上限不同，长上下文/工具结果可触发 413 或截断；2mb 是字节上限，不是 token 上限 |
| CSRF | 标准模型路径仅凭 Bearer 格式豁免，之后仍验证 JWT | 尾斜杠路径没有相同豁免，原生请求可被错误拒绝为 403 |
| employment JWT | 验签、type、身份字段、exp；签发默认有效期 15 分钟，可由设置覆盖 | 401；未关联会话/设备撤销，封禁后旧 token 可继续有效 |
| 身份限流 | 生产实测 `60` 次 / `60000ms`；Redis 固定窗口，从该键第一次放行起算 | 429；键是企业+成员+订阅，不是 IP、单任务、单模型或全局 |
| Redis 故障 | fail closed | 503 `PLATFORM_RATE_LIMIT_UNAVAILABLE`，不是 429，也不是额度不足 |
| DTO | JWT 与身份计数后执行 Zod；消息/工具/输出上限约束不足 | 400 也可能消耗窗口；某些畸形请求却通过并转发上游 |
| 订阅与 grant | 每次查 ACTIVE、企业归属、endDate、成员/部门 grant 与 grant 到期 | 403；成员移除与订阅过期未发现确定绕过 |
| 模型策略 | 平台 enabled 模型与企业 allowedChatModels 相交 | 未执行部门/强制默认策略，未排除 isStale，可能选择禁止或已失效模型 |
| 余额 | 调用前检查可用余额；调用后按实际 usage 扣费 | 403；无成本预留，无并发/token预算，已发生成本可能转为欠费 |
| sub2api 建连/响应 | 应用所有模型调用走统一 sub2api 配置 | API key、路由、模型映射、共享上游 RPM/TPM/并发/额度均可失败，当前未读取其精确阈值 |
| 生产上游时限 | HEAD stream/non-stream 均 `AbortSignal.timeout(30000)` | 截止覆盖 body 消费，持续输出也会被中断；不是仅首包 30 秒 |
| 草稿流预算 | 响应头 120s、无字节 120s、总时长 600s；非流式仍 30s | 未部署；慢下游背压可能被误报为上游 idle timeout |
| SSE 输出/结束 | HEAD 逐行重写、无背压、读流异常正常 end；草稿原字节 pipeline、背压、异常 destroy | 草稿仍未校验响应内容类型；普通 EOF 缺结束信息仅 warn |
| 客户端模型 HTTP | SDK 缺省配置 300000ms | 不是任务总时限；与后端各类预算含义不同，应分别验证 header/body/idle 行为 |
| Agent 多轮与重试 | 会话层最多 3 次重试，2/4/8s；provider 重试关闭；跨轮还有累计保护 | 每个模型续轮单独消耗平台额度；重试未读取 Retry-After，失败文本可能与新尝试拼接 |
| usage/记账 | 有 usage 才 setImmediate 记账，失败只记录日志 | usage缺失、断流、退出、DB错误可漏账；幂等键未绑定认证身份 |
| 发布/回滚 | 默认6次检查，间隔10s，之后再等15s停止旧容器 | 固定等待不等于排空；长流仍可能被停止容器截断，回滚候选也同样存在风险 |

### 限流计数的精确口径

源码：`backend/src/modules/gateway/gateway-rate-limit.service.ts:45`、`gateway-rate-limit.guard.ts:15`。

- Redis key 为 `SHA256(JSON.stringify([enterpriseId, memberId, subscriptionId]))`。同一成员同一订阅的不同客户端、任务、模型、工具续轮与重试共用额度。
- 更换模型、刷新 token 不另开桶；更换成员或订阅另开桶。没有附加企业总量、用户跨订阅总量、并发数或 TPM 限制。
- 放行请求计数；超过阈值的拒绝不递增、不延长窗口。返回 `Retry-After`、`X-RateLimit-Limit/Remaining/Reset`，error 包含 rule、dimension、count、resetAt。
- 有效 JWT 后先计数，再做 DTO/业务校验，因此已认证的错误 DTO、授权/余额失败和上游失败也占用该次放行额度。
- 无效 JWT 在身份计数前拒绝。模型接口已豁免基础 IP middleware 和全部全局 Nest throttler，不能再把普通 REST 的 10/100 次桶当作该接口当前规则。
- 其他路由的全局桶默认为 default=100、auth=10、chat=60，每个窗口60秒；未跳过的桶可能同时生效，具体路由须逐一检查。基础敏感路径 middleware 为120次/60秒，使用进程内IP键。
- 桌面登录另有账号12次失败/900秒、IP30次失败/300秒风控；阻断状态为401。上述非网关数值是源码默认值，未读取其生产配置。

## 3. 优先 Findings

### F01 [P1] 客户端删除 usage 请求和实际输出上限

位置：客户端 `electron/pi/sdk/pi-coding-agent-adapter.ts:183`、`:463`；本地 SDK `pi-ai/dist/api/openai-completions.js:1163`。

适配器声明 maxTokens=4096，但当前 provider/URL 下 SDK生成 `max_completion_tokens`，归一化只保留 `max_tokens`，同时删除 `stream_options.include_usage`。本轮直接运行归一化确认：输入带4096与include_usage，输出两者都没有；客户端现有测试也明确断言删除stream_options。

结果：4096不是实际出站上限；若上游遵循未请求usage即不返回的协议行为，模型正常执行却无法计费。上游是否仍主动返回usage需实测，不能声称所有当前调用都已漏账。

修复：显式映射输出上限并按模型能力校验，保留受支持的stream_options；平台不能仅依赖客户端主动申请usage，应有强制请求/上游对账方案。同步修改把usage视为provider-only字段的旧测试。

### F02 [P1] 客户端可控 ID 可使独立模型执行被误认为同一笔计费

位置：`gateway.controller.ts:117`、`compute-credit.service.ts:298`、`backend/prisma/schema.prisma:1913`。

session/message取自请求headers；缺消息ID时还可使用客户端request ID。全局唯一幂等键仅为 `sessionId:messageId`，命中已有账单不核验企业、用户、订阅或内容。网关并未对模型执行本身去重。

风险：已认证调用方可反复使用同一ID继续执行但只扣一次；跨租户同键或冒号组合碰撞也可能跳过计费。官方客户端当前没有发送这些计费headers，因此这不是已证实的自然碰撞事故，但不影响服务端信任边界缺陷。

修复：服务端创建执行ID，账单绑定认证身份与执行；若支持业务重试幂等，应同时去重执行、校验内容指纹与作用域。不能简单让整项任务的所有工具续轮共用一个messageId。

### F03 [P1] usage缺失和后台记账失败没有可靠补偿

位置：`gateway.controller.ts:182`、`:205`、`gateway.service.ts:255`。

仅观察到usage才记账；setImmediate不是持久任务；DB错误只日志后返回，发布/崩溃可丢失尚未执行的工作。客户端取消/断流可能丢尾部usage，已有上游成本不等于零。

修复：建立持久执行状态与用量待结算记录，幂等重试及sub2api对账；监控缺usage、记账失败、待结算积压。估算不能冒充实测usage，补账应保留来源和对账结果。

### F04 [P1] 封禁、退出及设备/会话撤销不能撤销旧 employment token

位置：`client.service.ts:654`、`client-employment.guard.ts:33`、`gateway.service.ts:69`。

JWT没有sid、设备ID或撤销版本；guard只校验签名/字段/时间，service不查用户封禁或session撤销。订阅、grant、余额仍有效时，旧令牌可调用至exp，缺省最长剩余15分钟，实际TTL受设置控制。成员移除与grant取消是另一条校验链，不能混为所有授权均不检查。

修复：绑定已验证会话或撤销版本，检查用户状态；增加退出、封禁、撤销设备后旧令牌立即不可用的测试。

### F05 [P1] 生产流式30秒截止和异常正常结束

位置：HEAD `gateway.service.ts` 的 `AbortSignal.timeout(30000)`，HEAD controller的reader循环/catch。

生产仍运行HEAD：持续生成超过30秒可能中断；catch调用res.end，使HTTP看起来正常结束；逐行重写不完整覆盖SSE格式，res.write不处理背压，客户端断连未取消上游。

本地草稿已处理预算拆分、原字节透传、背压和断连取消，但尚未上线且仍有F10问题。不能以“本地测试通过”宣称生产风险已经消除。

### F06 [P1] 无效认证流量不受模型身份限流约束

位置：`basic-rate-limit.middleware.ts:11`、`gateway.controller.ts:44`、`client-employment.guard.ts:23`。

模型POST跳过基础和全局桶，伪造/过期token在Redis计数前拒绝；解析JSON和JWT验签仍消耗资源。生产站点Caddy文件未见速率规则；未核实全局/CDN是否补充防护，不能断言整个公网毫无限流。

修复：增加独立、宽阈值的入口连接/体积/无效认证防护；正确处理可信代理链。不能恢复把所有已认证用户合并到代理IP的模型业务计数。

### F07 [P2] 429重试不等待服务端恢复时间

位置：客户端 `pi-coding-agent-adapter.ts:503`；SDK `agent-session.js:2130`、`provider-retry.js:86`。

会话层2/4/8秒重试不读取Retry-After；provider层解析器因重试预算0不会执行。因此平台返回60秒窗口剩余时间时，三次重试可能全部提前失败。SDK是否重试还取决于错误正文分类。

修复：单一重试所有者，读取秒数/HTTP日期/结构化retryAfterSeconds，加jitter、等待上限与可取消等待；按error.source区分平台和上游。401/403/400不能统一套用429重试。

### F08 [P2] 模型策略和模型可用性与Web标准路径不一致

位置：`gateway.service.ts:117`、`client.service.ts:704`；对照 `enterprise-model-config.service.ts:201`、`model.service.ts:175`。

网关只读取企业白名单，未执行部门限制、禁止切换/强制默认策略；查询enabled模型未排除isStale。管理端禁止或上游已经失效的模型仍可能在客户端被选择并转发。

修复：复用现有有效模型策略解析与可用性校验，在列表展示和执行时保持一致；明确空白名单语义。

### F09 [P2] DTO与资源预算不足，RPM不等于成本/并发控制

位置：`shared/index.ts:1835`、`gateway.service.ts:107`、`gateway-rate-limit.service.ts:45`。

messages可为空，tools使用z.any，max_tokens只有正整数而无模型上限；不查上下文/输出/工具能力。余额只做调用前可用性检查，不预留成本；多个并发都可通过，最终差额进入unpaid。欠费可能是业务设计，但当前无额外并发/token/企业聚合预算，暴露需明确接受或收紧。

修复：消息/工具结构与模型能力校验、上下文和输出预算；按实测吞吐设计成员/企业并发与token预算，增加预留和释放。不要把12次工具调用直接等同12次模型请求，应统计实际续轮。

### F10 [P2] 草稿仍有流结束/类型/背压超时缺口

位置：`gateway.controller.ts:125`、`:169`、`gateway-stream.ts:84`、`:122`。

- 上游200 JSON/HTML没有Content-Type校验，被强制标记SSE，客户端可能报协议错误而非收到明确上游异常。
- 普通EOF缺finish/DONE仅warn，HTTP已经正常结束。当前Pi SDK无finish_reason会报错，因此不能宣称它必定静默成功；有finish_reason但缺DONE则可成功，usage可能仍缺失。
- idle timer在下游背压暂停pull时仍运行，可把慢客户端误报为上游无数据。代理内存复现已确认该计时分支，未做生产慢网压测。

修复：发送SSE头前校验类型；按兼容协议明确完成判据，不伪造finish/DONE；区分上游读等待和下游写等待预算，并验证取消跨Caddy/Next的传播。

### F11 [P2] 刷新队列可能阻塞，认证hook异常可能被SDK吞掉

位置：客户端 `platform-api.ts:366`、`:381`、`refresh-token-rotation.ts:30`、`pi-coding-agent-adapter.ts:390`；SDK `extensions/runner.js:818`。

access刷新没有显式业务timeout/signal；共用队列等待前序promise时不可取消。认证依赖headers hook，hook异常被SDK捕获后仍可继续返回headers，provider配置又是placeholder凭证。此路径不是认证绕过，平台仍验JWT，但可把刷新失败变成无意义401并丢原始错误。

修复：刷新有界且排队可取消，保留refresh rotation串行语义；有效雇佣token作为模型发出前的硬前提，不依赖会吞异常的hook保障。

### F12 [P2] 重试输出和截断完成态不准确

位置：客户端 `task-runtime.ts:672`、`:724`、`run-events.ts:83`、`conversation-executor.ts:352`、`pi-coding-agent-adapter.ts:56`。

text_delta按run累加，auto_retry_start没有清除失败attempt文本；可重试断流后成功会留下失败片段+新回复。SDK把length作为正常done，客户端只判error/aborted失败，可能把达到输出上限的截断回复当作完整方案。

修复：输出按attempt/message维护，只提交有效结果；显式表达length、取消、协议缺finish与网络错误，不与业务成功混用。

### F13 [P2，长流上线前阻断] 固定发布等待不是活动流排空

位置：`deploy/production/sep-deploy.sh:427`、`:528`、`:535`。

默认观察等待约50秒再等15秒后stop旧容器，没有活动流计数；回滚失败候选直接stop。HEAD模型流自身30秒截止使正常切换时长流暴露受限，但草稿放宽到600秒后此问题变得直接可见。

修复：停止接新请求后按活动流排空，有界最长等待、取消原因和可靠记账；发布和回滚都覆盖，不能只提高sleep常量后称“零中断”。

### F14 [P2] 错误体和非流式响应缺大小/协议约束，观测不完整

位置：`gateway.service.ts:192`、`:200`、`gateway.controller.ts:200`、`main.ts:47`。

上游错误直接response.json完整缓冲，非流式也无响应体大小上限；草稿流总预算变长扩大资源暴露。非流式解析异常位于fetch异常捕获之外，可能变成笼统500；usage数值未做与流式相同验证。非429上游HTTP错误缺包含上下游request ID的日志，HTTP日志又未携带request ID。

修复：有界读取、校验内容类型/结构/usage数值，明确超时与协议错误；所有失败阶段记录安全的身份/模型/request ID/上游ID，不记录token或完整提示词。

### F15 [P2] 尾斜杠CSRF兼容不一致

位置：`security/guards/csrf.guard.ts:59`；对照基础middleware的可选尾斜杠正则。

生产模式下标准无Origin Bearer路径通过，但相同端点加尾斜杠返回403。审计代理已做本地生产模式断言，并非生产发请求验证。

修复：在路由接受范围内规范化路径，保持精确端点豁免；不放宽整个gateway或client前缀。

## 4. 对原429事故可以及不可以下的结论

- 原窗口：2026-10-10 17:48:27-17:49:30 UTC+8；任务 `65151dec-56d7-41b1-8b39-76f1def6fc13`，选定 `deepseek-v4.1-flash`。
- 四次request ID：`1ebb43e4-5cd4-4901-b2f4-4c10533dba85`、`3381a3d4-347c-4423-8059-43924a989c97`、`934105d5-ce4c-4a68-bac0-c96dfcd50710`、`0afe29f5-63ec-4ae8-9bd4-506fd3b3d680`。
- 当前代码可区分平台429（source=platform，规则/计数/重置）与上游429（source=upstream，上游ID/可用的Retry-After）。ThrottlerException文本不能单独定位服务。
- 已确定客户端的2/4/8秒策略不足以保证等待窗口恢复，但尚不能据此断言原四次全部来自同一规则。
- 第一个节点12次工具调用不等于五节点并发，也不等于12次模型请求；需按request ID及续轮日志重建实际请求数。
- 历史归因仍需入口/平台/sub2api的四条关联日志、当时命中规则与计数、窗口和共享上游额度。当前生产60/60秒配置不是历史阈值证据。

## 5. 修复顺序与验收

1. 优先补计费完整性：保留/强制usage、输出上限、执行ID与账单作用域、持久补偿；同时修token撤销和入口无效认证防护。
2. 完成流式草稿的内容类型、EOF、背压计时与取消链验收，再协调发布排空；不得直接把现有草稿视为全部通过review。
3. 客户端按Retry-After统一重试，刷新等待有界，输出按attempt回滚；模型选择复用部门/企业/可用性策略。
4. 按真实Agent续轮与成本数据设置并发、TPM、企业聚合预算及预留，不以“一项任务一次请求”估算。
