## 二、产品重新定位

### 2.1 核心概念

**碳基员工（Digital Employee）**：
- 平台售卖的"岗位包"（例如"电商运营专员"）
- 由平台运营方创建和上架
- 包含多个硅基能力

**硅基能力（Silicon Capability）**：
- 第三方开发者上传的 AI 能力
- 4 种类型：Agent / RPA / Skill / AI 应用
- 可被多个碳基员工复用

**关系**：
```
企业/个人用户
  → 订阅碳基员工（电商运营专员）
    → 碳基员工包含硅基能力（竞品分析、文案生成、商品上架...）
      → 用户通过对话使用碳基员工
        → 碳基员工自动调度硅基能力完成任务
```

### 2.2 与 SEP v1.0 的区别

| 维度 | SEP v1.0 | 新平台（硅基人才） |
|------|---------|------------------|
| 产品定位 | 数字员工租用 + API 调用 | AI 能力订阅平台 |
| 核心商品 | 数字员工（能力容器） | 碳基员工（岗位包） |
| 能力形态 | Capability（固定 I/O schema） | 硅基能力（Agent/RPA/Skill/AI 应用） |
| 交互方式 | 手动选能力、填参数、调用 | ChatGPT 风格对话，Agent 自动编排 |
| 技术底座 | Gateway + ModelRelayClient | OpenCode + SKILL.md / 第三方 API |

## 三、架构设计（已确认）

### 3.1 三层架构

```
用户交互层（ChatGPT 风格对话窗口）
       ↓
碳基员工层（Agent 编排、tool calling）
       ↓
硅基能力抽象层（统一接口 Capability.execute()）
       ↓
底层实现（OpenCode / Coze API / RPA / AI 应用）
```

### 3.2 硅基能力实现路径

**路径 A：第三方集成**
- Agent（Coze/Dify/N8N）
- AI 应用
- 实现：调用外部 API

**路径 B：自研 Agent**
- Agent（OpenCode）
- Skill（SKILL.md）
- 实现：OpenCode Runtime + SEP ModelRelayClient
- 优势：MIT 开源、商用无风险、模型自主可控

**核心设计**：
- ✅ 一个碳基员工可以混合绑定多种路径的硅基能力
- ✅ 例如：OpenCode Agent（竞品分析）+ Coze Agent（选品）+ Skill（文案）

### 3.3 数据模型设计原则

**A. 能力配置存储**：
- 采用分表 + metadata JSON 混合方案
- `Capability` 表存共同字段
- `AgentConfig` / `RPAConfig` / `SkillConfig` / `AIAppConfig` 分表存类型特定字段
- `metadata` JSON 兜底未来扩展
- 优势：类型安全 + 灵活扩展 + 长期维护友好

**B. 字段规范**：
- 主键统一用 `cuid()`，不用自增 ID
- 第一阶段不设计多租户（B/C 端直接关联 User）

### 3.4 前端交互设计

**A. 碳基员工选择**：
- 对话窗口顶部下拉框，随时切换碳基员工

**B. 会话管理**：
- 一个碳基员工可新建多个会话
- 会话列表在左侧边栏

**C. 能力调用展示**：
- 可折叠模式（默认简洁，可展开查看详情）

**D. 会话持久化**：
- 会话存数据库，刷新不丢失
- 支持多轮对话、中途追问

## 七、关键教训

### 7.1 架构决策要趁早

- SEP v1.0 花了大量时间修补错误架构
- 应该在发现根本性问题时立刻重构，不要打补丁
- "架构假设错误"不是代码 bug，无法靠修改几行代码解决

### 7.2 产品定位要清晰

- "数字员工租用" vs "AI 能力订阅平台" 看似相似，实则不同
- 前者是"租用 API"，后者是"租用 Agent"
- 产品定位决定技术架构

### 7.3 需求讨论要充分

- 今天花了大量时间讨论需求（碳基 vs 硅基、架构设计、交互流程）
- 需求清楚后，技术方案自然清晰
