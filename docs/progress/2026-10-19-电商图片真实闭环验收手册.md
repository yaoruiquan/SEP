# 电商图片真实闭环验收手册

日期：2026-10-19

## 1. 文档目的

本文用于验收电商图片员工从 Web 配置到 Electron 本地交付的真实闭环：

```text
Web 保存 sub2api 连接
  -> 发现实际模型与报价
  -> 创建/导入图片 Profile
  -> 只读报价校验
  -> 显式启用
  -> 企业授权与默认 Profile
  -> Electron runtime 选择实际 Profile
  -> Pi 组织请求并取得人工费用批准
  -> 真实生成或参考图编辑
  -> 本地保存、退出重启、显式恢复
  -> 核对上游账单、SEP 回执和本地资产
```

本文是验收手册，不把配置页面可见、模型目录可见或隔离夹具的真实回执接管，写成完整生产闭环。

## 2. 当前状态与验收边界

### 2.1 已有证据

- 图片 Profile、企业媒体策略、runtime 协商和真实媒体网关已经实现。
- mock 场景已覆盖生成、参考图、报价、幂等、查询、取消、下载、撤权、过期、损坏下载和部分保存。
- 隔离夹具已经完成真实 `gpt-image-2` 生成、参考图编辑、上游账单核对、Electron 保存和重启恢复。
- 生产真实图片开关、图片连接、`gpt-image-2-prod` 和一个企业授权曾经启用并通过报价及参考图上传预检。

### 2.2 不能直接视为完成的事项

- 隔离环境接管已有真实回执不等于生产自然订阅员工的 Pi 发起闭环。
- 模型目录和报价成功不等于该 Profile 的真实生成和编辑成功。
- 新部署版本必须重新确认活动镜像和页面是否包含多模型发现、导入、验证、启用能力。
- 旧任务的固定 `gpt-image-2` 成功不证明新增模型没有静默回退。
- 恢复成功必须证明没有重新 POST、没有重新扣费，不能只证明界面重新显示图片。

## 3. 验收前置检查

### 3.1 部署检查

记录以下信息，不输出密钥、JWT 或完整连接配置：

| 项目 | 预期 |
| --- | --- |
| 活动颜色 | blue 或 green，与发布记录一致 |
| 活动源码/镜像 SHA | 与本次发布提交一致 |
| `/api/health/ready` | HTTP 200，依赖项正常，Gateway 为 ready |
| `MEDIA_GATEWAY_REAL_ENABLED` | 目标企业真实验收期间为 `true` |
| 旧环境 | 已按蓝绿流程排空，仍可回滚 |
| 数据库迁移 | 无待应用迁移 |

若 readiness、活动 SHA 或媒体开关不一致，停止真实生成，只做只读检查。

### 3.2 生产安全边界

- 只使用指定测试企业、指定测试成员和已批准的电商图片 Skill。
- 每个模型最多先验证一次 generate 和一次 edit，避免重复产生费用。
- 真实请求前必须看到报价、有效期、资金来源和费用批准界面。
- 不修改共享 sub2api 分组价格，不把 key 写入文档、日志、客户端或 Git。
- 不把未知价格当作零元；报价 unavailable 时不得提交。
- 只调用 `/gateway/v1/media/real` 真实接口；mock 和 real 的证据目录分开。

## 4. Web 配置验收

### 4.1 连接和模型发现

通过管理页面完成，不在前端回显密钥。对应后端入口为：

```text
GET  /api/admin/media/connection
PUT  /api/admin/media/connection
POST /api/admin/media/models/discover
GET  /api/admin/media/profiles
```

验收要求：

1. 保存地址后只显示已配置状态，不显示原 key。
2. 模型目录来自当前保存的 sub2api 连接。
3. 记录每个候选模型的 `modelId`、是否兼容、原因和检查时间。
4. 只有实际适配的模型允许创建可执行 Profile；不可兼容模型必须显示未适配，不能按名称猜能力。
5. 切换连接后，旧 Profile 的验证状态必须撤销或进入待重新验证状态。

### 4.2 创建、校验和启用 Profile

对应入口为：

```text
POST  /api/admin/media/profiles
POST  /api/admin/media/profiles/:profileId/verify
PATCH /api/admin/media/profiles/:profileId
```

每个待验收 Profile 至少记录：

```text
profileId
modelId
configVersion
operations: generate/edit
executionMode
supportsReferenceImage
sizes
maxOutputs
verified
enabled
```

校验只允许调用模型目录和只读报价，不得因为打开管理页面而执行生成。只有同时满足 `enabled=true` 和 `verified=true` 的 Profile 才能进入生产 runtime。

### 4.3 企业授权

对应入口为：

```text
GET /api/enterprise/media-config
PUT /api/enterprise/media-config
GET /api/enterprise/media-config/available-profiles
```

企业配置必须满足：

- 只从平台已验证且已启用的 Profile 中选择。
- 明确允许的操作：`generate`、`edit`。
- 明确默认 Profile。
- 企业上限只能收紧平台上限。
- 企业媒体配置不写入聊天模型白名单，不改变聊天默认模型。
- 未授权企业的 runtime 不出现图片工具。

## 5. 客户端 runtime 验收

使用真实有效订阅获取：

```text
GET /api/client/subscriptions/:subscriptionId/runtime?mediaProtocolVersion=1&skillArtifactProtocolVersion=1
```

核对：

| 字段 | 验收要求 |
| --- | --- |
| `runtime.media.protocolVersion` | 为 1 |
| `executionAvailable` | 目标企业为 true；其他企业不因客户端参数变为 true |
| `profiles[].profileId` | 与 Web 企业授权一致 |
| `profiles[].configVersion` | 与 Web 当前版本一致 |
| `profiles[].modelId` | 能追溯到实际选择的模型，不能只看显示名称 |
| `profiles[].operations` | 与平台 Profile 和企业策略一致 |
| `defaultProfileId` | 为企业配置的默认 Profile |
| `tools` | 包含实际支持的图片工具 |
| key/baseUrl | 不出现在 runtime |

客户端必须使用 runtime 下发的 Profile，不允许写死 `gpt-image-2`，也不允许在 Profile 不可用时静默回退到另一个模型。

## 6. 真实生成验收

### 6.1 生成流程

1. 在 Electron 选择一个真实有效订阅员工。
2. 确认批准 Skill 已安装，任务锁定 Skill 版本和 hash。
3. 用明确商品描述发起一次图片生成请求。
4. Pi 只能通过宿主图片工具发起请求，不能使用 curl、shell 或模型输出 URL。
5. 费用审批显示实际报价、币种、资金来源和本次规格。
6. 服务端再次校验 profile、configVersion、企业授权、quote 和预算。
7. 提交后记录 `clientRequestId`、`quoteId`、`receiptId`、`profileId`、`configVersion` 和实际 `modelId`。
8. 下载后验证 MIME、文件大小、文件头、SHA256 和图片尺寸。

生成验收证据至少包含：

```text
runtime.json
quote-generate.json
request-generate.json
receipt-generate.json
upstream-usage-generate.json
local-asset-generate.json
```

### 6.2 参考图编辑流程

1. 选择本地已保存图片，显示图片 hash 和授权范围。
2. 通过受控 reference 上传，不把本地路径交给模型或服务端。
3. 取得绑定 reference hash、Profile、configVersion 和规格的报价。
4. 费用批准后只提交一次 edit。
5. 核对回执的 `operation=edit`、参考图 hash、实际模型和账务记录。
6. 保存编辑结果并核验 SHA256；恢复时不能重新上传后重新提交生成。

## 7. 保存、断线和恢复验收

### 7.1 必测场景

| 场景 | 预期 |
| --- | --- |
| 下载中断 | 本地状态为 interrupted/save-failed，不伪造成功 |
| 部分输出已保存 | 成功项保留，失败项单独重试下载，不重生成 |
| 正常退出重启 | 先读取原 job/receipt，再查询和下载 |
| 响应丢失 | 用原 `clientRequestId` 找回回执，不重新 POST |
| 授权撤销 | 新查询/下载按权限拒绝；原本地文件不被删除 |
| 结果已过期 | 显示 result expired，不自动新建收费请求 |
| 文件已存在且 hash 一致 | 标记 verified-existing，不覆盖、不收费 |
| 文件损坏 | 删除或隔离损坏临时文件，只重试下载 |

### 7.2 通过条件

恢复前后以下字段必须保持不变：

```text
jobId
clientRequestId
receiptId
profileId
configVersion
requestHash
outputId
```

恢复阶段模型 POST 数量必须为零；可以有原回执 GET 和结果 content GET。恢复后本地文件 hash、预览 hash 和导出 hash 必须一致。

## 8. 计费核对

逐请求建立对照表：

| 字段 | 来源 | 要求 |
| --- | --- | --- |
| `modelId` | runtime/请求/上游记录 | 三处一致 |
| `profileId` | runtime/quote/receipt | 一致 |
| `configVersion` | runtime/quote/receipt | 一致 |
| `quoteId` | SEP quote/request | 一次绑定 |
| 上游实际 USD | sub2api usage | 按原请求核对 |
| SEP 结算 CNY | 钱包/账本 | 与冻结汇率和实际金额一致 |
| 消费记录 | SEP ledger/usage | 每次真实执行一条，不重复 |
| 恢复阶段 | 请求和账本 | 不新增 POST、不新增扣费 |

未知、超预占、上游已收费但结果未交付等情况必须保留 `RECONCILING`，不能擅自补扣或退款。

## 9. 最终通过标准

只有以下条件全部满足，才可写“图片真实闭环完成”：

1. 活动部署版本、媒体开关和 readiness 均正确。
2. Web 实际发现并启用了目标模型，企业完成授权。
3. Electron runtime 下发的模型与请求实际使用模型一致。
4. 真实 Pi 生成和参考图编辑各成功一次。
5. 两次请求均经过费用批准和服务端报价校验。
6. 结果成功保存、退出重启后显式恢复成功。
7. 恢复阶段没有重复提交或重复扣费。
8. sub2api 实际用量、SEP 回执、SEP 账本和本地资产能够按 requestId 对齐。
9. 证据中没有 API key、JWT、完整提示词或不必要的商品原图泄露。

## 10. 未通过时的处理

- 模型回退：立即停止该 Profile，记录实际模型和预期模型，禁止继续收费验收。
- 报价不一致：停止提交，保留 quote 和上游价格证据，不手工改金额继续跑。
- 回执丢失：按原 requestId 查询；不能通过“再生成一次”判断第一次失败。
- 保存失败：只重试下载和保存，不重新报价、不重新生成。
- 部署版本不一致：停止生产验收，先确认活动 SHA 和蓝绿切流结果。

本手册完成后，另行更新本目录下的验收记录，记录实际模型、Profile、configVersion、请求 hash、结果 hash、账务金额和未解决风险。
