# 客户端模型网关连续 429 排查

## 结论

任务：智能行李箱产品策划案，`65151dec-56d7-41b1-8b39-76f1def6fc13`。
模型：`deepseek-v4.1-flash`。日期：2026-10-10；本文时间除证据 JSON 外均为北京时间 UTC+8。

四个 Request ID 全部命中 **SEP 后端全局 ThrottlerGuard 的 auth 规则**，不是 Caddy 入口限流，也不是 sub2api 或模型上游返回的 429。

直接原因：模型执行接口没有排除登录防刷规则，实际同时执行 `default`、`auth`、`chat`，其中 `auth` 仅允许 60 秒内 10 次请求。第 11 次命中触发从超限时刻开始的独立 60 秒阻断，2、4、8 秒重试仍处于阻断期。

同时存在两项配置问题：当前代理链路下 `req.ip` 会落到 Web 代理地址，不包含成员、企业或订阅身份；通用异常过滤器把标准 `Retry-After` 固定补成 60 秒，没有采用 `Retry-After-Auth` 中的真实剩余时间。

本次只读检查线上和本地复现，没有修改应用代码、生产配置或重启服务；只新增本报告和脱敏证据文件。

## 规则与计数维度

| 层/规则 | 阈值 | 计数键 | 是否命中本次故障 |
| --- | --- | --- | --- |
| basicRateLimitMiddleware | 120 次/60 秒 | 原始 req.ip + `/api/gateway/v1` 路径前缀 | 否 |
| Throttler default | 100 次/60 秒 | controller + handler + default + 归一化 req.ip | 否 |
| Throttler auth | 10 次/60 秒 | controller + handler + auth + 归一化 req.ip | **是** |
| Throttler chat | 60 次/60 秒 | controller + handler + chat + 归一化 req.ip | 否；auth 抛异常后不会执行 |

具体实现：

- `backend/src/modules/security/security.module.ts:14` 注册三条命名规则，`:35` 全局安装 guard。规则名称不会自动把 auth 限定到登录接口。
- `backend/src/modules/gateway/gateway.controller.ts:25` 没有排除 auth 规则；`:39` Swagger 将 429 仅描述为上游限流，与实际行为不符。
- `backend/src/common/middleware/basic-rate-limit.middleware.ts:7` 包含 gateway，`:11` 构造前缀/IP 键。
- Throttler 使用 `SHA256(controller-handler-rule-tracker)`；tracker 为归一化 IP，普通 IPv6 默认按 /64 聚合。
- 三条命名规则在相同 TTL 下依次执行 default、auth、chat。不同 handler 的 Throttler 计数隔离，因此普通的其他 REST handler 不消耗该模型 handler 的桶；同一网关 handler 的不同用户、企业、订阅、模型和任务则未隔离。
- 两层均为进程内存计数，不是 Redis 共享计数。它们按 HTTP 请求频率计数，不按 token、工具调用数或任务数计数，也没有并发流占用/释放机制。

### 当时计数

同一公网 IP 的请求序列中：

- 17:48:33.578 至 17:49:14.620 开始了 10 次成功模型 POST，逐次消耗 auth 额度；最后一次成功响应的 `X-RateLimit-Limit-Auth=10`、`X-RateLimit-Remaining-Auth=0`。
- 17:49:18.9 的下一次请求从 10 增到 11，超过阈值并触发阻断。此前 17:47:44 的成功调用已经在触发时过期，不需要假设其他客户端流量才能解释本次超限。
- 第二、第三次拒绝时 auth 自身不增加计数；按请求到期计时器重建仍为 11。最后一次拒绝时最早的一次成功调用已满 60 秒，重建计数约为 10，但独立 block 尚未到期，仍然拒绝。
- 上述计数是成功响应头和实际 storage 语义重建，**不是历史内存快照**。现有日志缺少成员/任务维度，不能把每个成功请求独立归属到任务 ID；该时间段未观察到其他公网 IP 的 gateway 请求。

12 次工具调用不等于 12 次模型请求。可确认的是该序列的 10 次成功模型 POST 和后续超限，不是五个节点同时运行造成的并发。

### 恢复时间

首次拒绝约 17:49:18.9，默认 blockDuration 等于 TTL，即 60 秒。**本次 auth 阻断预计在 2026-10-10 17:50:19 左右解除**，阻断到期后的下一次请求清零该规则计数并从 1 重新开始。

原请求到期不提前解除阻断；阻断期请求也不延长 auth 的阻断。但它们仍可能增加前置 default 和 basic 的计数，大量重试可能另行触发其他规则。

这是本次阻断的计算截止时间，不代表任务后来实际恢复，也不代表当前已修复；原配置下下一轮连续调用仍可再次复现。

## 代理合并风险

线上实际链路为：客户端 -> Caddy -> `sep-green-web:3000` -> Next.js `/api` rewrite -> `sep-green-backend:3001`。

- Caddy SEP 站点配置确认 `/api` 也走 Web；只有 `/ws` 直接转后端。
- `web/next.config.mjs:21` 将 `/api/:path*` 转发到 backend。
- `backend/src/main.ts` 与生产编译产物均未设置 `trust proxy`，Express 默认不信任转发头，`req.ip` 来自直接 socket peer。
- 实际 Docker 地址：Web `172.18.0.8`，backend `172.18.0.6`，Caddy `172.18.0.5`。依当前链路重建，Throttler tracker 是归一化后的 Web IP `172.18.0.8`，不是 Caddy 日志中的公网客户端 IP。

历史日志没有记录 backend 的 `req.ip`，因此上述值来自运行配置与网络拓扑重建，不是当时请求 IP 快照。该设计会把经同一个 Web 代理的不同用户网关请求合并；不过本次已有的连续请求本身足以触发 10 次阈值，不能声称已发现其他用户抢占额度。

## 客户端等待与错误分类

`backend/src/common/filters/http-exception.filter.ts:22` 对没有标准等待头的所有 429 固定补 `Retry-After: 60`。库给命名规则返回的是 `Retry-After-auth`，导致同一响应同时有真实剩余值和固定 60 秒。第四次响应真实剩余 45 秒，但标准头仍为 60 秒。

guard 产生的错误经当前网关 filter 转换后，`error.type=invalid_request_error`、`error.code=null`，不能稳定区分平台频率限制、并发限制或上游限制。`backend/src/modules/gateway/gateway.service.ts` 另外没有保留上游的 Retry-After；这不是本次原因，但需要避免将上游重试时间替换成固定值。

本次没有并发限制槽位，因此不涉及断连、异常或取消未释放并发计数。授权/余额不足在 gateway service 中使用 403，与本次 auth 429 不同。

## 修复建议

1. 网关明确排除 auth 规则，保留有意设计的频率保护；不要通过全局提高登录接口阈值修复模型接口。模型额度需按实际多轮调用负载评估，不能按一任务一次请求设置。
2. 选择稳定的模型网关计数主体，例如验证后的企业/成员/订阅，明确是否跨模型共享；需保证先验证身份再使用 claims 构造键。若保留 IP 防滥用层，按实际代理拓扑配置可信代理，不无条件信任任意 X-Forwarded-For。
3. 标准 Retry-After 使用命中规则实际剩余时间；补充平台频率限制/并发限制/额度不足/上游限制的稳定错误码，保留上游等待信息。
4. 记录 Request ID、规则、键的脱敏摘要、主体 ID、阈值、计数及 block/reset 截止时间；上游转发继续携带关联 ID。不记录 token、完整对话或工具结果。
5. 补真实 guard/storage 回归测试：多轮请求、跨成员隔离、代理 IP、超限、阻断重试、到期恢复、上游 429 头保留。

本次未实施上述应用修复，未经授权未作生产变更；`/enterprise/skill-versions` 和客户端 `task:retry` 不在本次排查范围。
