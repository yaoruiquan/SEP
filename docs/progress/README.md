# 开发进度（Progress）

记录每天/每阶段的开发进展。**主要读者是开发者自己**——既要能快速回忆当时的决策和坑，也要有一段能直接转给老板的通俗汇报。

## 写作原则

- **技术部分写深**：涉及决策就写清「怎么做的 + 为什么这么做」，可以具体到文件、字段、方法名、错误信息。参考 `docs/status/development-status.md` 第七节的深度。
- **通俗部分写浅**：给老板的那段用大白话，技术名词顺带一句人话解释。
- **分层，不混写**：老板看第 1 块，开发者看 2/3/4 块。
- **只记有价值的**：决策、坑、新方法、关键改动。日常的增删改查不用记。

## 固定结构（每篇按此写）

1. **写给老板（通俗版）**
   大白话解释今天做了什么、现在能用到什么程度。不堆技术名词。

2. **遇到的问题和解决办法**
   每条写清：现象 → 根因 → 解决。根因和解决要写到技术层面（哪个文件、哪个字段、什么机制），方便日后回溯同类问题。

3. **技术决策与实现要点**
   当天做的架构/实现选择，写清方案和理由。可具体到关键代码位置和数据结构。这是给未来的自己看的「为什么当初这么写」。

4. **开发方法上的改进**
   流程、工具、协作方式上的新做法（例如建索引、文档编号、验收闭环）。沉淀下来供以后复用。

5. **今日改动概览**
   一张表，按模块列改了哪些文件、改了什么。粒度到文件 + 一句话说明。

6. **下一步**
   下阶段要做的事，标出优先级或原因。

> 允许按当天实际情况增删小节，但 1/2/3 三块尽量保留。

## 文件命名

- 按日期：`YYYY-MM-DD.md`（如 `2026-07-24.md`）
- 同一天多篇专题：`YYYY-MM-DD-主题.md`（如 `2026-07-24-e2e-fixes.md`）
- 阶段性报告：`layer-N-completion-report.md` 或自定义有意义的名字
