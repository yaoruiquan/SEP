## 一、写给老板（通俗版）

今天把「用多少付多少」的计费链路从 0 做到基本可用：

- **实现**：对话结束后自动记录这次花了多少 token、折合多少人民币，并从用户账户余额里扣减，用户能在"用量统计"页看到明细。
- **测试发现大坑**：跑端到端测试时发现，AI 每次回复后系统拿到的"输出 token 数"始终是 0，导致计费被整段跳过——相当于用户白嫖，平台一分钱收不到。
- **修复**：上游不返回 token 数时，改用"回复文字长度 ÷ 4"来估算，先保证不漏计费；同时修掉两个让后端编译不过的错误。
- **结果**：代码编译通过，后端日志已出现正常的计费记录，用量统计页面数据也更新了。还差**一轮完整验收**来最终确认。

一句话：计费能跑起来了，但"输出 token 为 0"是上游 AI 代理的问题，我们目前用估算兜底，后续要么让上游修，要么做对账修正。

## 二、遇到的问题和解决办法

### 2.1 outputTokens 始终为 0，计费全部被跳过（P0，核心阻断）
- **现象**：三轮对话后端日志均为 `[Billing Check] ... outputTokens:0` → `[Billing] Skipped recording - missing usage data`，`compute_transactions` 表零条 CONSUME 记录，用量页四项统计全为 0。
- **根因**：sub2api（上游 AI 代理）返回的 usage 对象里 `outputTokens` 恒为 0，而代码要求 `inputTokens > 0 && outputTokens > 0` 才记账，于是静默漏计费。
- **解决**：当 `outputTokens=0` 但存在实际回复内容时，用 `Math.ceil(accumulatedText.length / 4)` 估算输出 token；输入侧同理。保留 `warn` 日志标记"本条为估算值"，便于后续审计。估算后仍为 0 才降级为 `error`（说明对话本身异常）。
- **风险**：中文 1 token ≈ 1.5–2 字符，用 4 字符通用值会**低估** 5–10 倍 → 短期少收费。属可接受方向（少收优于多收投诉），但需后续对账修正。

### 2.2 calculateCost() 返回值使用错误（P1，编译失败 + NaN）
- **现象**：`TS2322: Type 'number' is not assignable to type '{ costUSD; costCNY }'`；修复初期还报 `PrismaClientValidationError: amount: NaN`。
- **根因**：`calculateCost()` 返回 `{ costUSD, costCNY }` 对象，但调用处只用 `const costUSD = calculateCost(...)` 接收，再 `* 7.2` 算 CNY，得到 undefined→NaN。
- **解决**：调用处改为解构 `const { costUSD, costCNY } = calculateCost(...)`；同时把 `calculateCost` 返回类型显式声明为对象，未知模型返回 `{ costUSD: 0, costCNY: 0 }` 而非崩溃。

### 2.3 多余括号导致作用域崩溃（P1，编译失败）
- **现象**：`TS2304: Cannot find name 'userId' / 'inputTokens' / ...` 一连串变量找不到。
- **根因**：计费分支多了一个 `} else { ... }`，整个类括号不对称（brace count = -1），作用域全乱。
- **解决**：删除多余分支，恢复括号计数为 0，编译通过。

### 2.4 流式助手回复在页面重复显示（P1，残留）
- **现象**：每轮 AI 回复在聊天窗口出现两次。
- **根因**：流完成后已持久化的 ASSISTANT 消息与实时流式预览同时渲染（`pendingUser`/live 状态未清）。
- **状态**：此前已在 `chat-window.tsx` 做过清理，本轮测试发现仍有残留，**待复测确认**。

## 三、技术决策与实现要点

| 决策 | 选择 | 原因 |
|------|------|------|
| Token 缺失策略 | Fallback 估算，而非静默跳过 | 跳过 = 用户免费，直接损失收入 |
| 估算公式 | 1 token ≈ 4 chars | GPT 系经验值；对中文偏保守（少收费），可接受 |
| 日志分级 | 估算 `warn` / 成功 `log` / 全零 `error` | 计费是资金敏感操作，需逐笔可审计 |
| `calculateCost` 返回类型 | `{ costUSD, costCNY }` 对象 | 调用方无需自己换算汇率，接口清晰 |
| 价格表位置 | 硬编码在 `shared/index.ts` | MVP 阶段够用，中期迁移到数据库 |

**价格表不一致（待统一）**：测试指南写 `gemini-3.5-flash-high` 为 0.05/0.15（USD/1M），当前实现是 0.15/0.60，相差约 4 倍。修复计费后需统一"产品价格 / 实现价格表 / 测试指南"三处来源，再做真实金额核验。

## 四、开发方法上的改进

- **测试先行暴露隐性假设**：靠 E2E 真机测试而非人工推断，才发现"上游 API 不返回 usage"这一隐性依赖——单看代码 review 很难发现。
- **缺陷分级响应**：P0（核心路径不通）立即停工修复；P1（编译失败）同批处理；P2（文档/配置偏差）进 backlog。
- **日志即审计**：资金敏感路径用 warn/log/error 三级日志，确保每次计费/估算行为可回溯。
- **文档债显性化**：测试指南与实际演示环境（账号密码、余额、健康检查路径、管理员对话入口）多处不符，已在测试报告逐条列出，作为下一步待办。
